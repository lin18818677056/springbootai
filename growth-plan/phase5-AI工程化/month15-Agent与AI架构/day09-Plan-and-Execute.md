# Day 09 · Plan-and-Execute：先拆清单再干活

> **今日目标**：学第二种复杂任务模式——Plan-and-Execute（先出计划清单，再逐项执行，最后汇总）；用"生成客服周报"案例跑通三段式；和 ReAct 做同任务对比，产出三种模式选型表。
> **时长**：理论 1h / 实操 2h / 输出 0.5h
> **今日产出**：PlannerAgent.java + 两模式对比记录 + 选型表一张
> **对照教程**：`ai-learning/05-Agent与MCP协议.md` 第 3 节

## 1. 知识地图（先讲人话）

```
复杂任务两种干法（教材对比表的大白话版）：

ReAct（走一步看一步）：
  像探路：不知道路多长，走一步看路牌决定下一步
  适合：未知路径的探索型任务（排障/查数/多跳检索）
  风险：容易绕路（轮次多=延迟高），方向跑偏要靠观察纠正

Plan-and-Execute（计划-执行）：
  像装修：开工前先出施工清单（拆墙→水电→瓦工→…），逐项验收
  适合：步骤可预期的结构化任务（周报/账单汇总/固定流程）
  三段式：
    ① 规划：模型一次性输出计划清单（JSON 数组，每项一个子任务）
    ② 执行：逐项跑（每项可能是一次工具调用/一次检索）
    ③ 汇总：所有子结果拼给模型，产出最终交付物

同个例子看差别：
  "给我生成上周客服周报"
  ReAct：想了想→查工单量→看了眼→再查高频问题→咦还缺差评→补查→汇总
    （每步现场决定，灵活但轮次不可预期）
  Plan-Execute：
    ① 一次性出计划：["查上周工单量统计","查高频问题Top5",
                    "查差评关键词Top10","汇总成周报"]
    ② 逐项执行（每项都是已知操作，可并行可断点续跑）
    ③ 汇总成文
    （路径确定，轮次可预估=延迟和成本可预估）

工程视角的取舍（面试要答出的深度）：
  Plan-Execute 的"计划"也是模型出的——计划可能不合理！
  所以：计划要人工/规则审核一道（子任务白名单+数量上限），
  执行中遇到子任务失败，可以局部重试或回炉重新规划。
  ——它不是"更高级"，是"更可预期"：可预期=可预算=可排期。
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Plan-and-Execute | 计划-执行 | 先出任务清单再逐项干（装修模式） |
| Task Decomposition | 任务拆解 | 把大目标拆成子任务清单（规划段的产出） |
| Deterministic Path | 确定性路径 | 步骤可预期（=延迟成本可预估） |
| Plan Review | 计划审核 | 出的计划先过规则/人工审查（防离谱计划） |
| Subtask | 子任务 | 清单里的一项（执行段的基本单位） |
| Reflection | 反思 | 执行失败后复盘再重试（进阶模式，day26 演练预埋） |

## 3. 动手实操：PlannerAgent 三段式

### 3.1 规划段（计划也是约定格式输出）

```
System Prompt 约定：
  你是周报助手。先输出计划清单，一行一个子任务，格式：
  PLAN: ["子任务1", "子任务2", ...]
  子任务只能是以下操作之一（白名单！）：
    queryTicketStats(日期范围) / queryTopQuestions(日期范围,数量)
    queryBadReviews(日期范围,数量)
规则侧审核：清单长度 ≤5 项 + 每项工具在白名单内（模型计划也可信不过）
```

### 3.2 执行与汇总（关键 30 行）

```java
// PlannerAgent.java —— 三段式
List<String> plan = parsePlan(llm.chat(planPrompt, goal));   // ① 规划
plan.forEach(p -> auditLog.record("plan-item", p));          //    审核留痕
List<String> results = new ArrayList<>();
for (String task : plan) {                                   // ② 执行
    results.add(tools.invokeTask(task));                     //    每项过三道闸
}
String report = llm.chat(summarizePrompt,                    // ③ 汇总
    "任务清单: " + plan + "\n各结果:\n" + String.join("\n", results));
```

## 4. 面试连接

**Q：ReAct 和 Plan-and-Execute 怎么选？（模式选型必问）**
> 一句话判断：路径可预期用 Plan-and-Execute，路径未知用 ReAct。我们项目里两个都有真实案例。周报生成是典型的 Plan-and-Execute：查工单量、查高频问题、查差评、汇总，四步固定，先用白名单约束让模型出计划清单，规则侧审核清单合法性和长度，再逐项执行、最后汇总——好处是轮次固定，延迟和成本都可预估，还能断点续跑。多跳公司查询就必须 ReAct：第二跳的查询词取决于第一跳的结果，计划根本没法预先写。实践中还有个混合用法：Plan-and-Execute 的执行段，每个复杂子任务内部其实是个小 ReAct。两个坑都要防：ReAct 的坑是轮次失控，必须有迭代上限和 Token 预算；Plan-Execute 的坑是计划离谱——计划也是模型出的，会编出不存在的步骤，所以清单要过白名单和长度审核。最后还是那句架构师原则：这俩都解决不了才考虑 Multi-Agent，大多数场景单 Agent 加好工具就够了。
