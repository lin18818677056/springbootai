## 1. 知识地图（先讲人话）

```
单工具闭环全图（今天的装配现场）：

  用户："我的订单 S20260912003 到哪了？"
    ↓
  ① 模型（带工具菜单）→ 输出意图 {"tool":"queryOrder","args":{...}}
    ↓
  ② IntentParser 解析（day03）→ 结构化意图
    ↓
  ③【闸一】参数校验：orderNo 匹配 ^S\d{12}$ ？不匹配 → 拒执行
    ↓
  ④【闸二】权限校验：这单是当前登录用户的吗？不是 → 拒执行
    ↓                        （身份只认 CurrentUser.id()，不信模型！）
  ⑤【闸三】审计日志：谁/何时/调什么/入参 → 先记账再执行
    ↓
  ⑥ 真执行：查订单库 → 返回物流信息
    ↓
  ⑦ 结果拼回上下文 → 模型组织成人话 → 回答用户

一个容易被忽略的点——工具失败怎么办？
  错误信息是"给模型看的输入"，不是"给人看的报错"：
  ❌ 抛个 NullPointerException → 模型懵了，开始胡说
  ✅ 返回结构化错误：{"error":"ORDER_NOT_FOUND","msg":"订单号不存在，
     请确认后重试"} → 模型能向用户转述"没查到这个单号，您核对下？"
  类比：实习生打申请被驳回，驳回意见写得清楚，他才知道怎么改。

三道闸和 M14 的血缘（老纪律换了个门牌）：
  闸一 ≈ M14 入库链路的参数校验（垃圾进垃圾出）
  闸二 ≈ M14 权限检索前过滤（身份只认登录态）+ M6 网关鉴权
  闸三 ≈ M14 call_log 台账（降级有痕→调用有痕）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Parameter Validation | 参数校验 | 模型给的参数当不可信输入验（格式+存在性） |
| Ownership Check | 归属校验 | 资源是不是当前用户的（越权第一道墙） |
| Audit Log | 审计日志 | 每次工具调用留痕（谁/何时/调什么/入参/结果） |
| Structured Error | 结构化错误 | 能被模型理解并转述的失败信息（不是堆栈） |
| Closed Loop | 闭环 | 意图→校验→执行→回填→回答，一圈走通 |
| IDOR | 越权访问漏洞 | 拿别人的单号查别人数据（闸二防的就是它） |

## 3. 动手实操：真工具三道闸

### 3.1 OrderTools.java（核心 50 行）

```java
// agent/tool/OrderTools.java —— 三道闸版工具
@Component
public class OrderTools {
    private static final Pattern ORDER_NO = Pattern.compile("^S\\d{12}$");

    /** 工具描述同时写进给模型的菜单：参数格式要在这里说清 */
    public static final String DESC =
        "按订单号查询物流。orderNo: S开头+12位数字，如 S20260912003";

    public ToolResult queryOrder(String orderNo) {
        // 闸一：参数校验（格式不对根本不进数据库）
        if (orderNo == null || !ORDER_NO.matcher(orderNo).matches())
            return ToolResult.fail("INVALID_PARAM",
                "订单号格式错误，应为 S 开头+12位数字，收到: " + orderNo);
        // 闸二：归属校验（身份只认登录态，绝不信任模型转述的"我是谁"）
        Order order = orderMapper.findByNo(orderNo);
        if (order == null)
            return ToolResult.fail("ORDER_NOT_FOUND", "订单不存在，请核对单号");
        if (!order.getUserId().equals(CurrentUser.id()))
            return ToolResult.fail("FORBIDDEN", "无权查看该订单");   // 防越权(IDOR)
        // 闸三：审计（先记账后返回，M14 call_log 同款）
        auditLog.record("queryOrder", CurrentUser.id(), orderNo);
        return ToolResult.ok(order.getLogisticsInfo());
    }
}
```

### 3.2 三个对抗实验（每个都是一次真实攻击的模拟）

```powershell
# ① 幻觉参数：问"帮我查一下订单"（没给单号）
#    预期：模型编一个 or 模型追问用户 → 记录行为
#    若模型编单号 → 闸一拦下（INVALID_PARAM 回给模型→它转述请用户补单号）
# ② 越权探测：登录用户 A，问"B 的订单 S202609120999 到哪了"
#    预期：闸二 FORBIDDEN → 模型转述"无权查看"
#    □ 检查：审计日志里这次探测有记录（攻击留痕）
# ③ 不存在单号：S000000000000
#    预期：ORDER_NOT_FOUND → 模型转述"没查到，请核对"
#    □ 关键观察：模型不再编造物流信息（结构化错误喂回去的功劳）
```

## 4. 面试连接

**Q：工具调用的安全怎么做？讲讲你的三道闸？（安全必问，本月核心题）**
> 我把每次工具执行都过三道闸。第一道参数校验：模型产出的参数一律当不可信输入，比如订单号先用正则验格式，格式不对根本不碰数据库，并且把错误以结构化方式返回给模型——注意错误信息是给模型看的输入，要写成它能理解并转述的话，比如"订单号格式错误，应为 S 开头加 12 位数字"，这样模型会礼貌地请用户补单号，而不是对着堆栈胡说。第二道归属校验：查到的订单必须属于当前登录用户，身份只从登录态取，绝不信任模型自述的"我是谁"——这防的是越权访问，我们做过红蓝演练，让用户 A 问 B 的单号，系统返回无权查看，审计日志里留了这次探测记录。第三道审计：每次工具调用先记账再执行，谁、何时、调了什么、入参是什么，全量留痕——出问题能回放，攻击能发现。一句话总结：把模型当实习生，它填的单子，格式、权限、台账三关都过了才准办。
