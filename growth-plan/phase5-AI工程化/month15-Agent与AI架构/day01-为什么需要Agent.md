## 1. 知识地图（先讲人话）

```
先复盘 M14 交棒时的那道思考题：
  "检索明明把对的资料放进上下文了，模型为什么还是答错？"

今天三种翻车现场（都是项目四真实可复现的）：

现场① 懒得用（资料在嘴边，它扯旧账）：
  上下文里明明有《2026 退款政策：7 天》，模型张口：
  "根据我的了解，退货周期一般为 30 天……"（训练时的旧知识）
  → M14 的 Grounding Prompt 是第一道防线，但它防不住所有场合
    （用户绕一句"你就说大概几天嘛"，模型就容易滑回旧知识）

现场② 这事不该查资料（知识库答不了"办事"问题）：
  用户："我的订单 S20260912003 到哪了？"
  → 知识库里只有政策文档，没有他的订单！RAG 只能：
     a. 检索不到 → 拒答（用户体验差：这问题明明该能答）
     b. 硬答 → 编造物流单号（事故）
  → 这不是"知识问题"，是"办事问题"——该去调订单系统接口。
  类比：你问前台"我的快递到没到"，她翻遍《员工手册》也答不了，
       但她要是有权限登录快递系统查一下，10 秒搞定。

现场③ 一步不够（多跳问题）：
  "A 公司法人控股的另一家公司主营业务是什么？"
  → 一次检索拿到的资料里没有答案的"下半段"——
    得先查 A 的法人是谁，再拿法人名去查他控股的公司。
  → 明天见到的 Agent 循环（走一步看一步）就是解药，day10 专攻。

结论（本月的出发点）：
  RAG = 给模型一本《公司手册》——只能答"书里有没有"
  Agent = 给模型一个工具箱+系统账号——能"查了再查、查完再办"
  但 Agent 不是升级版 RAG，是另一种武器——
  武器越强，走火风险越大（死循环/越权/烧钱），所以本月一半篇幅讲防御。
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Agent | 智能体 | LLM+工具+循环+记忆=会办事的系统（模型当大脑，代码当手脚） |
| Tool Use | 工具使用 | 给模型一份"能办的事的菜单"，它点菜，你炒菜 |
| Grounding | 有据生成 | M14 三板斧：答案必须挂在资料上（Agent 时代的底线而非全部） |
| Capability Boundary | 能力边界 | RAG 管"书里有没有"，Agent 管"系统能不能办" |
| Agentic RAG | Agent 化检索 | 让模型自己决定"要不要检索、检索什么"（M14 是固定两步，这是动态的） |

### 3.3 Agent 决策卡（今天最重要的一页纸）

```
《RAG vs 工具 vs Agent 决策卡》：
  问题类型                     | 解法        | 本项目例子
  书里有标准答案               | RAG 检索    | 退款政策怎么规定
  需要系统里的实时数据         | 单工具调用  | 查订单物流 queryOrder
  一步查不出来，要先 A 后 B    | Agent 循环  | 多跳公司关系查询
  要办操作（退款/改地址）      | 工具+人工确认 | 办退款（Human-in-the-loop）
  闲聊/情绪发泄                | 别检索别工具 | 直连闲聊话术（M14 day25 路由）

架构师第一课（背下来）：
  能用固定流水线（RAG 两步）解决的，别上循环；
  能用一个工具解决的，别上多工具；
  能单 Agent 解决的，别上 Multi-Agent。
  Agent 的每一分"智能"，都是用延迟、成本、调试难度换的。
```

## 4. 面试连接

**Q：RAG 和 Agent 是什么关系？有了 RAG 为什么还要 Agent？（开场必问）**
> 我在项目里是这么划界的：RAG 解决"知识从哪来"，是固定两步流水线——先检索后生成，路径写死；Agent 解决"事情怎么办"，是动态循环——模型自己决定下一步是检索、调工具还是直接回答。举我们工单系统的例子：用户问退款政策，RAG 检索政策文档就够；用户问"我的订单到哪了"，知识库里根本没有他的订单，RAG 只能拒答，正确做法是调订单系统的查询接口——这是工具；用户问一个多跳问题，得先查 A 再拿结果查 B，这就需要 Agent 循环走一步看一步。所以 Agent 不是 RAG 的升级版，是更大的框：RAG 可以是 Agent 循环里的一个工具。但我也会强调反向的工程判断——我们大部分流量是标准政策问答，固定 RAG 流水线延迟低、成本可控、行为可测，我特意没把它们 Agent 化。知道什么时候不用 Agent，比会用 Agent 更能体现架构判断。
