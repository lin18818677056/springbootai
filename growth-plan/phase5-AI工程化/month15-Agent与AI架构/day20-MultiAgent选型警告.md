# Day 20 · Multi-Agent 选型警告：不是银弹

> **今日目标**：正面消化教材的架构师警告——"Multi-Agent 不是银弹，每加一个 Agent，延迟/成本/调试难度都乘上去"；掌握灵魂拷问"单 Agent+更好的工具设计能不能解决？"；产出四问决策卡，给 W3 收官。
> **时长**：反面案例 1h / 成本对比实验 1.5h / 输出 0.5h
> **今日产出**：四问决策卡 + 单/双 Agent 成本对比数据 + W3 心法三句
> **对照教程**：`ai-learning/05-Agent与MCP协议.md` 第 3 节架构师警告

## 1. 知识地图（先讲人话）

```
教材原话（架构师警告，一字不差）：
  "Multi-Agent 不是银弹——每加一个 Agent，延迟/成本/调试难度
   都乘上去。先问：单 Agent + 更好的工具设计能不能解决？
   大多数场景答案是能。"

乘法有多狠（昨天实验数据的延续推演）：
  Agent 数 ×2 →
    延迟：子 Agent 各自多轮循环，串行时总时长近似翻倍
    成本：每轮都是完整 Prompt 调用（子 Agent 的 System Prompt
          还特别长——专业 Prompt 不便宜）
    调试：单 Agent 出错看一条思考链；双 Agent 出错要看
          "主拆得对不对→子干得对不对→合得好不好"三层
    ——所以昨天说"明天专门讲什么情况坚决不拆"

反面案例库（都是真实容易犯的）：
  ✗ 把"查订单+查政策"拆两个 Agent
    → 单 Agent 挂俩工具就完事（拆分理由不成立）
  ✗ 为了"显得架构高级"上三 Agent
    → 面试官追问一句"为什么两个工具不行"就露馅
  ✗ 子 Agent 之间互相调用形成网状
    → 调用时序图画出来像毛线团，出问题没人知道查谁
  ✓ 拆的正当理由（值得拆的三种情况）：
    ① 专业知识确实互斥（退款规则 vs 排障手法，Prompt 各需一大篇）
    ② 上下文确实互扰（两摊长历史挤一个窗口互相带偏）
    ③ 任务天然可并行且耗时（并行省回乘法亏的延迟）

《拆不拆·四问决策卡》（今天最重要的一页纸）：
  ① 单 Agent+更好的工具设计（day05 描述优化/动态挂载）真的不够吗？
  ② 拆出去的子任务，专业知识/Prompt 是否真的互斥？
  ③ 上下文是否真的互相干扰到影响质量？（不是"感觉会"）
  ④ 延迟与成本的乘法，预算扛得住吗？（拿数字说话）
  ——四问有三个"否"→ 不拆（默认不拆，举证责任在"拆"的一方）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Silver Bullet | 银弹 | 一招鲜吃遍天的幻想（架构界不存在） |
| Orchestration Overhead | 编排开销 | 多 Agent 带来的乘法成本（延迟/钱/调试） |
| Premature Decomposition | 过早拆分 | 没证明需要就拆（架构界的 premature optimization） |
| Tool-first Design | 工具优先 | 先把工具做好，再考虑加 Agent |
| Burden of Proof | 举证责任 | "要拆"的一方拿证据，默认不拆 |
| Trade-off Ledger | 取舍台账 | 每次架构决策的成本收益记录（老朋友） |

```powershell
# 记录三行：
#   方案 | 平均总延迟 | 平均 token | 出错定位平均耗时（故意埋一个错）
#   A    | __s        | __        | __min
#   B    | __s(≈A×__) | __(≈A×__) | __min(看三层日志)
#   C    | __s        | __        | __min
# □ 预期发现：方案C（单 Agent+路由动态挂载）很可能拿到 B 的质量
#   还保住 A 的成本——这就是"更好的工具设计"的胜利
```

### 3.3 四问决策卡实战（拿三个候选场景过卡）

```
场景① 客服三诉求混合（退款+物流+发票）
  → 过卡：工具设计可解（路由+挂载）？能 → 不拆，C 方案
场景② 代码生成+单测+评审流水线
  → 过卡：三角色 Prompt 互斥且都长/上下文互扰明显/可流水
     → 三问"是" → 拆（但要主从结构不许网状）
场景③ "更聪明的回答"（没有明确分工，就是想变聪明）
  → 四问全否 → 换更大的模型或优化 Prompt，别拆
□ 把三个场景的过卡结论写进决策卡背面（以后照抄）
```

## 4. 面试连接

**Q：你什么时候会上 Multi-Agent？（架构师判断题，答好就是加分题）**
> 默认答案是不上——举证责任在要拆的一方。教材那句话我当座右铭：每加一个 Agent，延迟、成本、调试难度都是乘法不是加法，我们实测过，双 Agent 方案对比单 Agent，延迟和 token 都接近翻倍，更疼的是调试——单 Agent 出错看一条思考链，双 Agent 要查主拆得对不对、子干得对不对、合得好不好，三层日志。我们的灵魂拷问是：单 Agent 加更好的工具设计能不能解决？大多数场景真能解决——同样是"退款加物流"混合诉求，我们试过三个方案：单 Agent 四工具、双 Agent、单 Agent 加意图路由动态挂载，第三种拿到了接近双 Agent 的正确率，成本却和单 Agent 持平，这就是工具设计的胜利。真正值得拆的要过四问决策卡：工具设计真的到头了吗、专业知识是否真的互斥、上下文是否真的互扰、乘法成本预算扛不扛得住，四问里三问是否就坚决不拆。我们项目里唯一过卡的是代码生成、单测、评审这类流水线——三个角色 Prompt 又长又互斥，而且天然串行分工；同时立了规矩：只许主从结构，不许子 Agent 之间网状互调，否则调试时序图画出来就是毛线团。一句话总结：Multi-Agent 是重武器，重武器的纪律是——证明需要才上膛。
