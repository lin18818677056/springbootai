# Day 05 · 工具描述与参数设计：写给模型看的说明书

> **今日目标**：吃透 Function Calling 五条军规；用对照实验证明"description 写得含糊 = 工具选错"——工具描述是提示词工程的一部分，不是代码注释；学会参数设计的三个细节和"动态挂载"控数量。
> **时长**：军规精读 1h / 对照实验 1.5h / 输出 0.5h
> **今日产出**：五条军规卡 + 好坏描述对照实验记录 + 参数设计清单
> **对照教程**：`ai-learning/05-Agent与MCP协议.md` 第 2 节

## 1. 知识地图（先讲人话）

```
一个反直觉的事实：工具描述不是写给人看的注释，是写给模型看的
"使用说明书+使用场景"——模型选择工具，唯一依据就是这份描述。

类比：给新员工的任务分派单。
  ❌ 坏分派单："处理订单相关事宜"
     → 新员工不知道啥时候该用它、要带什么信息，乱派单
  ✅ 好分派单："按订单号查询物流状态。仅当用户提供 S 开头
     订单号时使用。orderNo: S+12位数字，如 S20260912003"
     → 何时用（场景）+ 怎么用（格式）+ 例子，全齐

《Function Calling 五条军规》（教材原文，本月圣经）：
  ① description 写给模型看：何时该调+参数格式，含糊=选错
     （今天的对照实验就是证明这条）
  ② 模型产出的参数一律当不可信输入：格式校验+存在性校验
     +权限校验（day04 三道闸已落地前两条）
  ③ 工具数量 ≤10 个为宜：多了模型选择就糊
     → 解法：动态挂载——按意图分组挂子菜单（见下）
  ④ 工具失败信息要"可被模型理解"：返回结构化错误说明，
     模型能向用户转述或重试（day04 结构化错误已落地）
  ⑤ 敏感操作（退款/删除）必须 Human-in-the-loop 人工确认
     （day13 专攻，先把军规立起来）

动态挂载（军规③ 的解法，M13 老朋友出场）：
  工具 20 个装不下也选不准 → 按业务域分组：
    订单域（查物流/查订单/改地址）| 政策域（RAG 检索）
    售后域（退款申请/换货申请）
  M13 意图分类器先判域 → 只把该域的工具菜单给模型
  → 每次模型只见 3~5 个工具，选择准确率回血
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Tool Description | 工具描述 | 模型的"使用说明书"：何时用+怎么用+例子 |
| Five Rules | 五条军规 | Function Calling 工程五纪律（本月圣经） |
| Dynamic Mounting | 动态挂载 | 按意图只挂相关工具子菜单（军规③解法） |
| Enum Parameter | 枚举参数 | 参数限定几个合法值（如 status: pending/shipped） |
| Self-explanatory | 自解释命名 | 参数名见名知义（orderNo 而不是 p1） |
| Negative Constraint | 负向约束 | 描述里写清"什么时候不要用"（防误触发） |

## 3. 动手实操：好坏描述对照实验

### 3.1 实验设计（同一份考卷，两种描述各跑一遍）

```
考卷 10 题（day06 会扩成 20 题正式版）：
  6 题该调 queryOrder（含订单号）+ 4 题不该调（闲聊/政策/投诉）

描述 A（坏）：
  "查询订单"
描述 B（好）：
  "按订单号查询物流状态。仅当用户消息中包含 S 开头的订单号时调用；
   用户没提供订单号时请先追问。orderNo: S+12位数字，如 S20260912003"
  （注意三要素：何时用+负向约束+参数格式与例子）
```

### 3.2 跑实验并记录

```powershell
# 描述 A 跑 10 题 → 记录：误触发 __ 次（闲聊也调了）/漏调 __ 次/参数错 __ 次
# 描述 B 跑 10 题 → 同样三格
# 预期：A 的误触发明显多（"我的订单怎么还没到"没有单号它也调）
# 结论一句：改描述（不写一行代码）就能修 bug——提示词工程的证据
```

### 3.3 参数设计清单（每个工具过一遍）

```
□ required 划对：必须有值才能调的才设 required（单号是，备注不是）
□ 枚举限定：状态类参数用 enum（model 想编 "已发货(大概)" 都没门）
□ 自解释命名：orderNo/userId/status（不是 p1/p2/p3——模型也看名字猜义）
□ 例子进描述：给一个真实格式的例子（模型模仿能力 > 理解能力）
□ 数值给边界：金额类标 min/max（防退款金额填负数——day13 会真实验证）
```

## 4. 面试连接

**Q：模型总选错工具/乱调工具，你怎么排查？（工程调优题，五条军规的舞台）**
> 我按五条军规的顺序排查，大部分问题在前两条就解决了。第一步看描述：工具描述是写给模型的使用说明书，要三要素齐全——什么时候该用、什么时候不该用（负向约束）、参数格式带例子。我做过对照实验：同一份十题考卷，描述从"查询订单"四个字改成带场景约束和参数例子的完整版，误触发直接从六次降到一次，一行代码没改，纯提示词工程。第二步看数量：工具一多模型选择就糊，我们的纪律是不超过十个，超了就按业务域分组，用 M13 的意图分类器先判域，每次只把相关子菜单挂给模型——比如售后类问题只挂退款换货那三四个工具。第三步看失败信息：工具报错要写成模型能理解的结构化错误，它才能向用户转述或者自行重试。最后兜底才是代码侧校验：参数格式正则、归属权限、敏感操作人工确认。这个顺序的本质是：先修"模型看得见的信息"，再修"代码守得住的底线"。
