> **今日目标**：三档并发压测项目五（Agent 版和 RAG 版压测的三点不同）；算清单任务成本账（轮次×单轮）；精算预算熔断的 TOKEN_BUDGET 该定多少；容量结论落盘。

> **今日产出**：压测记录表 + 单任务成本模板 + 预算配置依据 + 容量结论

## 1. 知识地图（先讲人话）

```
Agent 压测和 RAG 压测的三点不同（继承两个月的压测血统）：

① 延迟从"固定两步"变"N 轮循环"：
  RAG：检索+生成=延迟基本可预估
  Agent：2 轮任务和 5 轮任务延迟差 2.5 倍——
    报 P95 必须分桶报（按轮次分桶：1 轮 P95 / 3 轮 P95 / 5 轮 P95）
    混在一起报=自欺欺人（少数多跳题拖高全部数字）

② TTFT（首字延迟）只被第一轮决定：
  用户体感"开始出字"=第一轮模型响应出来之后
  后续轮次是"憋大招"（中间轮不流式给用户）→
  优化方向：第一轮快（路由轻+菜单短）比总轮次少更救体感

③ 成本账多了"轮次"这个乘数：
  单会话成本 = Σ(每轮 token) ≈ 轮次 × 单轮 token
  而单轮 token 又含"越滚越大的历史"（第 N 轮要背前 N-1 轮）
  → 成本随轮次超线性涨（平方级趋势，day10 就预告过）

预算精算（day11 留的 TOKEN_BUDGET 问题今天回答）：
  实测口径：单轮平均 __T（含历史膨胀）× MAX_ITER(5) × 1.5 安全系数
  = TOKEN_BUDGET —— 预算=上限轮次的真实花销×1.5，
    太小正常任务被误杀，太大熔断形同虚设
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Round-aware Load Test | 轮次感知压测 | 按轮次分桶报延迟（混报自欺欺人） |
| TTFT (First Token) | 首字延迟 | 用户体感起点=第一轮响应时间 |
| Cost per Session | 单会话成本 | 轮次×单轮 token（超线性） |
| Context Inflation | 上下文膨胀 | 历史越滚越大，单轮越来越贵 |
| Safety Factor | 安全系数 | 预算=实测×1.5（防误杀又防虚设） |
| Capacity Line | 容量线 | 本部署安全并发（天花板×0.7 老规矩） |

## 4. 面试连接

**Q：Agent 服务的压测和成本怎么算？和普通 LLM 应用有什么不同？（压测三代目）**
> 我们压测 LLM 应用是三代演进过来的：普通调用一代，RAG 分段压测二代，到 Agent 这代最大的新变量是轮次。三点不同。第一，延迟必须按轮次分桶报：两轮任务和五轮任务差两倍多，混在一起报 P95 是自欺欺人，少数多跳题会把整体数字全拖高——我们的报表是 1 轮、3 轮、5 轮各报各的。第二，体感指标看 TTFT，而 Agent 的首字只被第一轮决定，后面轮次用户看到的是停顿——所以优化第一轮（路由做轻、工具菜单挂少）比省总轮次更救体感。第三，成本多了轮次乘数，而且上下文膨胀让单轮越来越贵——第 N 轮要背着前 N-1 轮的历史，成本随轮次超线性涨，我们实测五轮多跳的 token 是两轮任务的好几倍。压测结论落两个数字：容量线还是天花板乘零点七定限流的老配方，但 Agent 比纯 RAG 更早到顶，因为单会话要占更多次模型调用；预算熔断的 TOKEN_BUDGET 用实测口径精算——单轮均值乘轮次上限乘一点五安全系数，太小误杀正常任务，太大熔断形同虚设，两个边界我们都用实验验证过。总结一句：Agent 的账本比 RAG 多一个维度，轮次，压测按轮分桶、成本按轮累计、预算按轮精算，这个维度管住了，Agent 才从演示品变成可运营的服务。
