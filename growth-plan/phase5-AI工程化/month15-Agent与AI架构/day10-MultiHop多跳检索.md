> **今日目标**：兑现 M14 交接卡思考题②——多跳问题一次检索不够；用 ReAct 循环落地两跳检索（先查 A 拿钥匙，再用钥匙查 B）；给循环装上"跳数上限"；多跳考卷入库评测。
> **时长**：场景分析 1h / 实操 2h / 输出 0.5h
> **今日产出**：两跳检索闭环记录 + 跳数与预算防线 + 多跳考卷 5 题

## 1. 知识地图（先讲人话）

```
M14 留下的那道题：
  "A 公司法人控股的 B 公司主营业务是什么？"
  一次检索为什么不行？——资料是分开存的：
    文档甲：《A 公司工商信息》（里面有法人张三）
    文档乙：《张三关联企业列表》（里面有 B 公司）
    文档丙：《B 公司简介》（里面有主营业务）
  一跳的查询词最多命中其中一份——答案的"链条"断在中间。

多跳的本质：上一跳的输出是下一跳的输入（钥匙链）：
  跳1：查"A 公司 法人" → 得到"张三"          （拿到了第一把钥匙）
  跳2：查"张三 控股公司" → 得到"B 公司"       （第二把钥匙）
  跳3：查"B 公司 主营业务" → 得到答案         （开门）
  ——每跳的查询词要从上一跳结果里"提取"出来，
    这正是 ReAct 的主场：走一步看一步，查询词动态生成。

工程三防线（多跳的刹车和护栏）：
  ① 跳数上限：MAX_HOPS=3（问题最多拆几跳心里要有数，超了=拆解失败）
  ② 预算熔断：累计 token 超预算即停（多跳是 token 大户，
    每跳都是"完整上下文+新查询"，成本随跳数平方级涨）
  ③ 卡壳检测：连续两跳检索结果和上跳相同/为空 → 判定死胡同，
    主动放弃转人工（诚实说"这个我查不出来"好过编）

和应用侧硬编码流水线的对比（为什么不用代码写死三跳？）：
  硬编码：if 问公司关系 then 三步固定查——快且省，但只服务这一种问法
  Agent：  任何"链条式"问题都能自己拆——通用但贵
  折中真话：高频问法硬编码（快），长尾问法走 Agent（通用）——
    这就是 M14 day25 路由思想的再次上场（高频走快路，长尾走活路）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Multi-hop | 多跳 | 答案要查好几次、接力才能拼出来（钥匙链） |
| Query Decomposition | 查询拆解 | 把大问题拆成接力的小查询 |
| Intermediate Result | 中间结果 | 上一跳查到的"钥匙"（法人名/公司名） |
| MAX_HOPS | 跳数上限 | 多跳版的迭代刹车 |
| Dead End | 死胡同 | 查了两跳没进展（卡壳检测的对象） |
| Chain Question | 链式问题 | 答案分散在多份文档、靠引用串起来的问题 |

## 3. 动手实操：两跳检索闭环

### 3.1 知识准备（造一个链条库）

```powershell
# 往 M14 知识库灌三份小文档（链条造好才玩得起来）：
#   company-a.txt：A 公司工商信息……法定代表人：张三
#   zhangsan.txt：张三对外投资……控股 B 公司（持股 60%）
#   company-b.txt：B 公司简介……主营业务：跨境电商仓储
# 验证一跳检索：直接问整题 → 只命中一份文档 → 拼不出答案（复现断链）
```

### 3.2 ReAct 版多跳（工具菜单加一个 kbSearch）

```powershell
# 给 ReActAgent 的工具菜单加：kbSearch(keyword)——M14 的检索器包成工具
# 问："A 公司法人控股的公司主营业务是什么？"（故意不给 B 公司名）
# 预期 ReAct 链路（记录每跳的 THINK/ACT/观察）：
#   跳1 THINK:"先查 A 公司的法人" ACT:kbSearch("A公司 法人")
#       → 观察:"法定代表人：张三"
#   跳2 THINK:"查张三控股的公司" ACT:kbSearch("张三 控股")
#       → 观察:"控股 B 公司（持股 60%）"
#   跳3 THINK:"查 B 公司主营" ACT:kbSearch("B公司 主营业务")
#       → 观察:"跨境电商仓储" → ACT:ANSWER（带三段引用！）
# □ 引用检查：答案的 citations 应覆盖三份文档（M14 引用纪律在 Agent 里依然有效）
```

### 3.3 三防线验证 + 多跳考卷

```powershell
# 防线① 跳数上限：把 MAX_HOPS 设 2 重跑 → 第 3 跳被拦 → 诚实转人工
#   （拦得对吗？该题确实要 3 跳——所以上限设定要"够用+兜底"，
#    生产上可按问题类型动态定：公司类 3 跳，订单类 2 跳）
# 防线② 预算：把 token 预算砍半重跑 → 中途熔断 → 留痕完整
# 防线③ 死胡同：问"张三的初恋女友的公司"（库里没有）
#   预期：连续空结果 → 卡壳检测触发 → 拒答话术（不硬编！）
# 考卷：5 道多跳题入工具考卷（type=multi-hop），
#   指标：答案正确率 + 平均跳数 + 死胡同正确拒答率
```

## 4. 面试连接

**Q：多跳问题（要查好几次才能答）你的系统怎么支持？（本月压轴技术题）**
> 这是我从 RAG 升级到 Agent 的真实动因。知识是分片存的，链条式问题的答案散在多份文档里，一跳检索只能拿到链条的一环。我的方案是把检索器包成一个工具，交给 ReAct 循环：第一跳查"A 公司法人"得到张三，这个中间结果回填上下文，第二跳的查询词就从它生成——查"张三控股的公司"得到 B 公司，第三跳查主营业务，最后汇总作答，引用覆盖三份文档，M14 的引用校验在 Agent 里原样生效。多跳的工程难点不在跳，在刹车：我装了三道防线——跳数上限，按问题类型动态设定，公司关系类三跳、订单类两跳，超了说明拆解失败，诚实转人工；Token 预算熔断，因为每跳都携带完整上下文，成本随跳数平方级涨；卡壳检测，连续两跳没新信息判死胡同，主动拒答不硬编。最后补一个架构判断：高频的链条问法其实可以硬编码成固定流水线，快且省；Agent 多跳留给长尾问法——高频走快路、长尾走活路，还是路由那套思想。
