# Day 18 · MCP 架构与传输：Host / Client / Server

> **今日目标**：看清 MCP 三角架构的角色分工与数据流；对比 stdio 与 HTTP 两种传输的适用场景；理解会话生命周期与能力协商；补齐教学版与 Spring AI 正路的能力差距清单。
> **时长**：架构精读 1h / 传输实验 1.5h / 输出 0.5h
> **今日产出**：三角架构图 + 双传输对比表 + 生命周期时序记录
> **对照教程**：`ai-learning/05-Agent与MCP协议.md` 第 4 节

## 1. 知识地图（先讲人话）

```
MCP 三角架构（三个角色，别和"我们应用的分层"搞混）：

  ┌────────────────────────────────┐
  │ MCP Host（宿主：你的 AI 应用/IDE）│  ← 用户在这里说话
  │  ┌──────────────┐              │
  │  │ MCP Client   │              │  ← 宿主内部的"标准插口"（可多个）
  │  └──────┬───────┘              │
  └─────────┼──────────────────────┘
            │ JSON-RPC（stdio 或 HTTP）
  ┌─────────▼──────────────┐
  │ MCP Server（工具提供方） │  ← 我们 day17 写的 KbMcpServer
  │  Tools/Resources/Prompts│
  └────────────────────────┘

记忆钩子：
  Host = 电视机（用户面对的整机）
  Client = 电视机上的 HDMI 口（标准接口，可以有多个）
  Server = 机顶盒/游戏机（提供内容的外设，插上就能用）
  一个 Host 可以同时插多个 Server（知识库一台+Git 一台+日历一台）

两种传输（day17 用了 stdio，今天补全视野）：
  ① stdio：Server 是宿主的子进程，stdin/stdout 对话
     优点：零网络配置、天然隔离（子进程崩了不拖累宿主）
     适合：本地工具（文件系统/本地命令）——Claude Desktop 的主流姿势
  ② HTTP（Streamable HTTP）：Server 是远程服务
     优点：多客户端共享一个 Server、可独立扩缩容、可集中鉴权
     适合：团队级共享工具（我们 kbSearch 给全公司宿主用 → HTTP）
     鉴权：OAuth 走标准流程（教学版环境变量传 token 的升级正路）

会话生命周期（协议的"礼数"）：
  initialize（握手：互报版本+能力协商）→ 正常操作（tools/resources/prompts）
  → notifications（单向通知，如工具清单变更）→ shutdown
  能力协商 = 握手时互相声明"我会什么"（Server 说：我有 tools 和
  resources；Client 说：我支持 sampling）——不支持的特性别用

教学版 → 正路的差距清单（诚实盘点，Spring AI 补齐项）：
  □ 多会话并发（教学版单线程单会话）
  □ 标准错误码与重试语义（教学版只有 -32601/-32602）
  □ 通知机制（工具热更新时宿主能收到推送）
  □ HTTP 传输+OAuth 鉴权（教学版仅 stdio）
  □ 注解式开发：@McpTool 一挂，协议层全自动
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Host | 宿主 | 面向用户的 AI 应用整机（电视机） |
| Client | 客户端 | 宿主内的标准插口，一宿主可多 Client（HDMI 口） |
| Server | 服务端 | 工具提供方外设（机顶盒） |
| stdio | 标准IO传输 | 子进程管道对话（本地标配，天然隔离） |
| Streamable HTTP | 流式HTTP传输 | 远程共享服务（团队级标配） |
| Capability Negotiation | 能力协商 | 握手互报"我会什么"（防用错特性） |
| Session Lifecycle | 会话生命周期 | 握手→操作→通知→关闭（协议礼数） |

### 3.2 两种传输各跑一次（体感差异）

```powershell
# stdio（昨天的姿势）：宿主起子进程
#   记录：进程启动耗时 __ms | 一次调用往返 __ms | 子进程崩溃宿主无恙 ✓
# HTTP 教学版：给 KbMcpServer 包一层 HTTP 皮（Spring 一天后缀）
#   记录：无需进程管理 | 支持并发多客户端 ✓ | 鉴权要自己做（引出 OAuth 话题）

#   并发      | 一宿主独占   | 多宿主共享
#   鉴权      | 本地信任     | OAuth 标准
#   适用      | 个人本地工具 | 团队共享工具
```

## 4. 面试连接

**Q：讲讲 MCP 的架构角色和传输方式？你们选哪种？（架构细节题）**
> 三个角色：Host 是面向用户的 AI 应用本体，比如我们的工单系统或者一个 IDE 助手；Client 是 Host 内部的协议插口，一个宿主可以挂多个 Client，对应多个工具来源；Server 是工具提供方，通过 Tools、Resources、Prompts 三类能力对外服务。我的记忆钩子是电视机：Host 是电视，Client 是 HDMI 口，Server 是机顶盒，插上就能用，一台电视可以接好几个外设。传输两种：stdio 是 Server 作为宿主的子进程走标准输入输出，零网络配置、天然进程隔离，适合个人本地工具；Streamable HTTP 是 Server 作为独立远程服务，多客户端共享、独立扩缩容、鉴权走 OAuth，适合团队级共享——我们的 kbSearch 要给全公司宿主用，正路是 HTTP 加 OAuth。会话上有个容易被忽略的细节：握手时要做能力协商，双方互报支持哪些特性，像我们演练时故意调用 Server 未声明的能力，握手期就被拒了——错配提前暴露好过运行期翻车。最后诚实交代实践路径：教学版我手写了 stdio 单会话版看穿协议，生产落地直接用 Spring AI 的 MCP starter——多会话、标准错误码、通知机制、注解式开发都是它托管，手写那遍的价值是出问题时知道往哪层查。
