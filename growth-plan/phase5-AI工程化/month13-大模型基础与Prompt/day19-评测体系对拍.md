## 1. 知识地图（先讲人话：评测就是 AI 界的对拍）

```
对拍方法论的五次演进（跨月主线，面试压轴素材）：
  M8  分布式对账：重复请求不重复记账（对账思想诞生）
  M10 数仓对拍：ODS→DWD→DWS→ADS 层层对账（分层的信任链）
  M11 双引擎对拍：Hive 账=Spark 账（换引擎不换口径）
  M12 实离对拍：实时账≈离线账（新鲜是近似，精确靠兜底）
  M13 模型评测：模型输出 vs 人工标注真相（概率系统的信任链）
  —— 共同哲学：不信任单点，信任交叉验证；数字会骗人，制度不会

评测体系的四个组件（对应实离对拍 SOP 的结构——同构！）：
  ① 真相源：评测集（带人工标注标准答案的考卷）
     ←→ 实离对拍里的"离线账"
  ② 跑分：全链路对评测集执行，产出分数
     ←→ "差异率计算"
  ③ 判定：分数阈值三档
     ←→ "≤1% 归档 / 1~5% 预警 / >5% 告警"
     评测版：正确率 ≥90% 可上线 / 80~90% 预警（修复后复测）/<80% 禁止上线
  ④ 归因：失败样本逐条归因（缺示例/指令冲突/模型能力/标注争议）
     ←→ "嫌疑人清单"
[兑现 M12 思考题②完整版] temperature 的随机性 vs 实离差异是同一类问题：
  概率系统的输出都不保证逐次一致 → 都不靠"祈祷这次对"，都靠制度化验证——
  实时账每天对拍一次，模型输出每次改动评测一次。
  区别只在节奏：数据链路对拍是"日清"，模型评测是"变更触发"。

盲评（Blind Review）——防"自己给自己打分"的偏心：
  打分时只看"输入+输出"，不看是 v1.1 还是 v1.2 产生的
  （人对自己刚改的东西会手下留情——代码 review 同款心理，制度防它）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Golden Set | 黄金评测集 | 带标准答案的"真相源考卷" |
| Blind Review | 盲评 | 不知道出自哪版再打分（防偏心） |
| Regression Test | 回归测试 | 每次改动重跑全量评测（防改好这处坏那处） |
| Score Threshold | 分数阈值 | 三档判定线（可上线/预警/禁止） |
| Error Attribution | 错误归因 | 每个错都有出处（和差异率每 0.1% 有出处同款纪律） |
| LLM-as-Judge | 模型当裁判 | 用强模型给弱模型打分（辅助手段，下卡说明坑） |

## 3. 动手实操：扩考卷+正式跑分+立 SOP

### 3.1 步骤①：评测集 20→50 条（v2）

```
扩容原则（考卷也要有代表性）：
  □ 每类工单 ≥12 条（refund/logistics/consult）
  □ 模糊/边界件 ≥8 条（分类器最疼的地方要考足）
  □ 注入攻击样本 4 条（安全考题常态化）
  □ 高风险样本 6 条（审核流水线的考题）
  □ 新增 8 条"多轮场景"考题（day17 记忆管理的：跨轮引用编号）
  □ 来源继续真实化：客服记录/评论改写，每条标注：标准答案+标注理由
git tag: eval-v2（考卷版本化管理——改 Prompt 前后必须同一份考卷！）
```

### 3.2 步骤②：全链路正式跑分

```
跑分（固定 temperature=0 + seed，评测可复现——day05 配置卡的评测行）：
  分类正确率 = __%（目标 ≥90%）
  优先级正确率 = __%
  need_human 判准率 = __%（该转人工的转了没有）
  注入防御 = __/4
  审核风险分级准确率 = __%
  多轮关键信息记忆 = __/8
三档判定：整体 ___ → 可上线 / 预警 / 禁止上线
失败样本全量归因表（每条错都有出处——同款纪律）
```

### 3.3 步骤③：《AI 评测 SOP v1》（贴墙，生产直接抄）

```
1. 时机：任何变更触发——改 Prompt / 换示例 / 调参数 / 换模型 / 升级版本
2. 纪律：跑分前锁定评测集版本（考卷变了分数没有可比性）
3. 执行：固定 temperature=0+seed，全量跑，分数入台账（曲线化）
4. 判定：≥90% 过 / 80~90% 预警修复复测 / <80% 禁止上线
5. 盲评：人工核对环节打分者不知道样本出自哪个版本
6. 归因：失败样本四分类归因（缺示例/指令冲突/模型能力/标注争议），
   归因结果决定修哪里——不是哪个错都值得修 Prompt
7. 留痕：分数曲线+归因表随版本存档（回看"这次改动值不值"）
LLM-as-Judge 的坑（用模型当裁判时要记得）：
  裁判模型自己也有偏差（偏爱长答案/偏爱自己的风格）——
  只做初筛辅助，关键分数必须人工盲评（裁判也要被监督）
```

## 4. 面试连接

**Q：怎么系统性保证 AI 应用的输出质量？（本月压轴题，对拍方法论收官）**
> 我的方法论是把"数据对拍"的思想完整平移到模型输出上。真相源：建 50 条黄金评测集，人工标注标准答案，含边界件、注入攻击、高风险、多轮记忆各类考题，考卷版本化管理。跑分：任何变更（Prompt/参数/模型）必须全量回归，固定温度加种子保证可复现。判定：分数三档——九成以上可上线、八到九成预警修复、八成以下禁止上线。归因：每个失败样本四分类——缺示例、指令冲突、模型能力、标注争议，归因决定修哪里，不是所有错都值得改 Prompt。制度上盲评防偏心、留痕防抵赖。这套东西的源头是我做数据链路的方法论：M8 分布式对账、M10 分层对拍、M11 双引擎对拍、M12 实离对拍，到 M13 是第五次上场——共同哲学就一句：概率系统的输出不能靠感觉验收，要靠制度化的交叉验证。另一个体会：评测集不是一次性工程，失败样本持续回流补充——就像对拍发现的差异会反哺数据质量，评测发现的错例会反哺考卷。
