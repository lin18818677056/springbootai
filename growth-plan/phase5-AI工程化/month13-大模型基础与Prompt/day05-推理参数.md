# Day 05 · 推理参数：调 API 时你在拧哪个旋钮

> **今日目标**：把 temperature/top_p/max_tokens/stop 这几个最常用的推理参数搞透——每个参数对应"文字接龙"的哪个环节、工程场景怎么配；建立"参数跟着场景走"的配置纪律。
> **时长**：概念 0.5h / 实操 2h / 输出 0.5h
> **今日产出**：参数对照实验记录 + 《推理参数配置卡》
> **对照教程**：`ai-learning/01-大模型基础原理.md` 第 4 节

## 1. 知识地图（先讲人话）

```
回到 day01 的接龙现场，参数就是控制接龙过程的四个旋钮：

  旋钮① temperature 温度（抽签手抖程度）
    模型脑内：北京 89% | 上海 3% | 南京 1% ...
    temperature=0：永远选"北京"（贪心，稳定但呆板）
    temperature=1.0：基本按原概率抽（多样，偶尔出人意料）
    temperature=1.5+：把概率"抹平"，小概率词也有机会（发散，容易胡言乱语）
    场景配置：知识库问答/代码生成/分类抽取 0~0.3（要稳）
             创意文案/头脑风暴 0.7+（要活）

  旋钮② top_p 核采样（只从头部候选人里抽）
    换个角度限制随机：只在"累计概率达 p 的词"里抽
    —— 和 temperature 二选一调，另一个保持默认（同时调=旋钮打架，排查噩梦）

  旋钮③ max_tokens 生成上限（话说多长必须闭嘴）
    控成本+防失控输出（比如让它写 50 字简介，不设限可能写 2000 字）
    注意：设太小会把 JSON 截断成废铁（day10 的坑，先记住）

  旋钮④ stop 停止序列（看到这个词立刻刹车）
    结构化提取场景神器：让它输出到 "END" 就停
    —— 和 max_tokens 互补：stop 是"内容驱动刹车"，max_tokens 是"里程驱动刹车"

其他不常拧但要知道的：
  n：一次生成几个候选（打分选优场景用，费钱）
  seed：随机种子（固定后近似可复现——评测场景固定它，day19）
  frequency_penalty / presence_penalty：重复惩罚（防车轱辘话，微调即可）

一句话纪律：参数是"生成过程"的控制，不是"对错"的控制
  —— 输出不对先查 Prompt（day11+），别上来就拧旋钮
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| temperature | 温度 | 抽签手抖程度：0 贪心稳定，越高越随机 |
| top_p | 核采样 | 只从累计概率达 p 的头部词里抽 |
| max_tokens | 生成上限 | 硬性字数天花板（控成本/防失控） |
| stop | 停止序列 | 看到指定内容立刻刹车 |
| seed | 随机种子 | 固定抽样起点（评测复现场景） |
| Greedy Decoding | 贪心解码 | 每步都选最大概率（temperature=0 的效果） |

## 3. 动手实操：参数对照实验（有模型才有体感）

### 3.1 实验①：temperature 三档对比

```powershell
# Ollama 里用 /set parameter 或 API 里传参数，同一问题各问 3 次
>>> /set parameter temperature 0
>>> 给"高效Java开发"写一句广告语   （×3 → 观察稳定性）
>>> /set parameter temperature 1.2
>>> 给"高效Java开发"写一句广告语   （×3 → 观察多样性/失控）
# 记录：0 档三句几乎一样；1.2 档三句发散（偶尔惊艳偶尔翻车）
# 结论：创意场景的"翻车率"就是发散的代价
```

### 3.2 实验②：max_tokens 截断 JSON（预演 day10 的坑）

```
Prompt：输出一个 JSON：{"name":"...","intro":"一句话简介"}
max_tokens 设 20 重跑 → 观察 JSON 被腰斩（引号不闭合，程序解析直接报错）
教训卡：结构化输出的 max_tokens 要按"最长合理输出"设，不是越小越省
（省钱省出 bug 的经典案例——和容量规划"别顶满"一个道理）
```

### 3.3 实验③：stop 刹车演示

```
Prompt：从 1 数到 10，用顿号分隔，输出完数字后立即结束，不要任何解释
配合 stop=["11"] 或让模型输出 <END> 再用 stop 截断
观察：干净利落 vs 没有 stop 时的"补充说明"废话
结论：stop 是"内容驱动刹车"，比在 Prompt 里求模型"别多说"更可靠
```

```
《推理参数配置卡》（贴墙）：
  场景            temperature  top_p   max_tokens      stop
  知识库问答      0~0.3        默认     按答案上限×1.5   —
  代码生成        0~0.2        默认     按代码块上限     ```
  分类/信息抽取   0~0.1        默认     小（几十）       JSON结束符
  创意文案        0.7~1.0      默认     宽松             —
  评测复现        0 + 固定seed  默认     固定             固定
  纪律：top_p 与 temperature 只调一个；输出不对先查 Prompt 再查参数
```

## 4. 面试连接

**Q：temperature 是什么？生产上怎么配？（高频实操题）**
> temperature 控制采样的随机度：模型输出的是概率分布，temperature=0 时永远选最大概率词（贪心解码，稳定但呆板），调高则把分布"抹平"、小概率词更容易被抽中（多样但可能翻车）。生产配置跟着场景走：知识库问答、代码生成、分类抽取这类"要稳"的场景 0~0.3；创意文案、头脑风暴这类"要活"的场景 0.7 以上。两个纪律：一是 temperature 和 top_p 只调一个、另一个保持默认，两个都动等于旋钮打架，出问题没法归因；二是评测场景固定 temperature=0 加 seed 保证可复现——参数是控制生成过程的，不是控制对错的，输出不对先查 Prompt 和知识输入，最后才动参数。

**Q：max_tokens 设置不当会出什么问题？（踩坑题，答出细节=做过）**
> 两个方向的坑。设太大：成本失控加输出失控，让它写一句话简介可能写出一千字。设太小更隐蔽：JSON 被从中间腰斩——引号不闭合、括号不配对，下游程序解析直接抛异常，而且这种 bug 是"偶现"的，因为截断位置取决于这次生成到哪。我实验里 max_tokens=20 时 JSON 必废。正确做法：结构化输出场景的 max_tokens 按"最长合理输出"设，留 50% 余量；更稳的方案是让模型输出带明确结束标记并用 stop 截断，或解析时做 JSON 修复兜底。本质和容量规划一个道理——"省出 bug"比"花冤枉钱"更贵。
