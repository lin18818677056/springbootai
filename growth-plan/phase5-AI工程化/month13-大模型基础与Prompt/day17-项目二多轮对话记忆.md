# Day 17 · 项目二：多轮对话记忆（上下文管理实战）

> **今日目标**：给工单系统加"对话回复"能力——实现 day02 埋的"上下文管理策略"：滑动窗口+超限摘要压缩；用实验验证记忆策略对成本和连贯性的影响。
> **时长**：实现 2.5h / 实验 1h / 输出 0.5h
> **今日产出**：记忆管理器 v1 + 滑动窗口 vs 摘要的对照数据 + 模板⑦入库
> **对照**：M12 day02 的同构表（上下文窗口 vs Flink 状态）今天代码级兑现

## 1. 实现设计（先讲人话：记忆怎么管）

```
问题重演（day02 的滚雪球）：
  多轮对话每轮都重发全部历史 → 第 10 轮时输入爆炸（成本+延迟+窗口三重压力）

两种记忆策略（今天都实现，对比着看）：

策略① 滑动窗口（简单粗暴）：
  只保留最近 N 轮，更早的直接丢
  优点：实现 5 行代码；缺点：早期约定丢失（"我工号 9527"在第 2 轮说的就没了）
  —— Flink 类比：状态设 TTL，到期就忘

策略② 滑动窗口+摘要压缩（工程标准姿势）：
  ┌─────────────────────────────────────┐
  │ system 提示词                        │ ← 永远在
  │ [历史摘要] "用户此前咨询订单退款进度，│ ← 早期对话压缩成一段
  │  工号9527，已提供单号，情绪一般"      │
  │ [最近 N 轮完整对话]                  │ ← 近期原文保留
  │ [当前用户输入]                       │
  └─────────────────────────────────────┘
  触发条件：总 token > 阈值（如 2000）→ 把最老的 M 轮交给模型压缩成摘要，
  摘要替换原文（摘要本身也用 AI 生成——模板②摘要模板的实战）
  —— Flink 类比：RocksDB 增量——把"老数据"压实，热数据留原样

关键工程点：
  ① 关键信息保护：工号/订单号这类"必须记往"的信息，压缩时明确要求保留
     （摘要 Prompt 里写"保留所有数字编号类信息"——TTL 里的"不可忘清单"）
  ② 摘要异步做：用户等回复时不等摘要——先滑窗保命，摘要后台补
  ③ 每轮 token 记账：窗口占用曲线要能画出来（day20 的素材）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Sliding Window | 滑动窗口 | 只留最近 N 轮（简单粗暴版记忆） |
| Summarization | 摘要压缩 | 老对话压成一段"备忘录"塞回窗口 |
| Memory Threshold | 记忆阈值 | 触发压缩的 token 水位线（如 2000） |
| Protected Fields | 保护字段 | 压缩时必须保留的关键信息（工号/单号） |
| Async Summarize | 异步摘要 | 用户不等摘要生成（先滑窗，后台压） |
| Context Utilization | 上下文利用率 | 窗口占用曲线——越平缓说明策略越稳 |

## 3. 动手实操：造记忆管理器+对照实验

### 3.1 步骤①：实现两种策略（伪代码骨架）

```
class MemoryManager:
  history = []            # [(role, content)]
  summary = ""            # 摘要备忘录

  def add(role, content):
      history.append(...)
      if est_tokens(summary + history) > 2000:   # 超水位线
          old = history[:5]; history = history[5:]   # 滑走最老 5 轮
          summary = llm_summarize(summary, old)      # 异步/同步压缩
          # 摘要 Prompt：把以下对话并入备忘录，保留所有数字编号，
          #             输出 ≤200 字摘要：{旧摘要} + {old}

  def build_messages(user_input):
      msgs = [{"role":"system","content": 系统提示 + "\n[历史摘要]" + summary}]
      msgs += history
      msgs += [{"role":"user","content": user_input}]
      return msgs
```

### 3.2 步骤②：15 轮长对话对照实验

```
设计一段 15 轮对话脚本（第 2 轮埋关键信息："我的工号是 9527"，
第 14 轮提问："我的工号多少？"——考验记忆策略）

三组跑同一对话：
  A 组：无管理（全量历史重发）→ 第 14 轮答对 __
       总输入 token 累计 = ____（滚雪球实锤，画占用曲线）
  B 组：纯滑动窗口（保留 5 轮）→ 第 14 轮答对 __（预期：答不上，9527 早被滑走）
       总输入 token = ____（最低，但失忆）
  C 组：滑窗+摘要（保护数字）→ 第 14 轮答对 __（预期：答对，摘要有 9527）
       总输入 token = ____（居中——花钱买记忆，但远低于 A）
结论写台账：C 组是"记忆/成本"的平衡点；A 组 token 增长曲线贴进笔记
```

## 4. 面试连接

**Q：多轮对话的记忆怎么管理？（AI 应用高频设计题，本项目核心）**
> 这本质是"有限记忆"问题，我在 Flink 状态管理里处理过同构问题——都要回答记什么、忘什么、怎么省。我的方案是滑动窗口加摘要压缩的混合策略：最近 N 轮保留原文（热数据），更早的对话超过 token 水位线时用模型压缩成摘要塞回 system（冷数据压实），摘要 Prompt 里明确要求保留数字编号类信息——工号、订单号是"不可忘清单"。三组对照实验的数据支撑决策：全量历史滚雪球成本最高、纯滑窗最便宜但直接失忆（第 2 轮说的工号第 14 轮就问不出来了）、滑窗加摘要在成本和记忆之间拿到平衡。两个工程细节：摘要是异步生成的，不让用户等；每轮 token 落库，窗口占用曲线持续监控——水位线思想在上下文管理里的直接复用。
