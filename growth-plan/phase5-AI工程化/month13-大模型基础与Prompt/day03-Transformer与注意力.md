# Day 03 · Transformer 与注意力：不用懂数学，但要懂代价

> **今日目标**：用"带着问题翻书划重点"讲清注意力机制；理解一条对工程师最值钱的结论——**注意力计算量随上下文长度平方增长**，这就是"Prompt 越长越贵又越慢"的底层原因。
> **时长**：概念 1h / 实操 1h / 输出 0.5h
> **今日产出**：注意力的比喻讲解（费曼法录音）+ Prompt 长度与延迟的关系记录
> **对照教程**：`ai-learning/01-大模型基础原理.md` 第 2 节

## 1. 知识地图（先讲人话）

```
Self-Attention（自注意力）= 带着问题全书划重点：
  读到这句话时——"它"指什么？
  "用户提交了订单，系统冻结了库存，随后【它】被取消了"
  → 模型处理"它"这个 token 时，会给句中所有词算一遍"关联度"：
     订单 0.7 | 库存 0.2 | 冻结 0.05 | ...
  → 按"关联度"加权融合信息 → "它"就带上了"订单"的语义
  —— 每个词都这么干一遍（"自"注意力=自己和自己句子里的词互相打分）

三个工程必知的点（不推导数学，只记后果）：
  ① 并行：整句所有词同时算（对比 RNN 逐词串行）
     → 这是千亿参数能训得动的算力前提（历史课，听懂即可）
  ② 平方代价：每个词要和所有词打分
     → 长度翻倍，计算量×4（不是×2！）
     → 【本月最重要的工程结论】Prompt 越长：越贵（token 费）+ 越慢（平方计算）
       —— day02 的"上下文预算表"从"省钱"升级为"保延迟"
  ③ KV Cache：生成时已算过的"打分结果"缓存起来，只算新词
     → 所以生成过程第一个字最慢（要处理全部输入），后面越写越快
     → 这就是 TTFT（首 Token 延迟）的由来：输入越长 TTFT 越大

给 Java 工程师的锚点类比：
  attention 的"加权融合" ≈ 加权平均：分数高的话语权大
  KV Cache ≈ 计算过的结果缓存（ day 之于 M4 Redis 缓存，思想同源）
  平方代价 ≈ M1 学过的 O(n²) 算法——n 一大就灾难，必须控制 n
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Transformer | 变换器 | 当前主流模型架构（名字来自"变形金刚"，2017 论文） |
| Self-Attention | 自注意力 | 句内每个词和所有词互相打关联分，按分加权融合 |
| Attention Score | 注意力分数 | 词与词的关联度（0~1 的权重，越相关越高） |
| O(n²) Complexity | 平方复杂度 | 长度翻倍计算量×4——长上下文贵慢的根源 |
| KV Cache | 键值缓存 | 已算过的注意力结果缓存；首字慢后字快的原因 |
| TTFT | 首 Token 延迟 | 等第一个字的时间；交互应用要求 <2 秒 |
| RNN | 循环神经网络 | 老架构：逐词串行处理，已被 Transformer 淘汰 |

### 3.2 工程决策落地（把平方代价变成纪律）

```
《Prompt 长度纪律》（贴墙，day25 架构时引用）：
  ① 系统提示词 ≤ 500 token：能一句话说清的不写三句
  ② 检索资料按需注入：只贴相关段落，别整本文档塞进去（RAG 的切片动机！）
  ③ 历史对话管理：滑动窗口+摘要（day17）
  ④ 监控 TTFT：>2s 就该检查 Prompt 是不是塞太满
  —— 发现没有：①②③全是"控制 n"，因为代价是 O(n²)
     （M1 算法课：看到 O(n²) 先想"能不能不这么做"）
```

## 4. 面试连接

**Q：讲讲注意力机制？为什么长文本处理成本高？（原理+代价题）**
> 用比喻讲：注意力就是"带着问题全书划重点"——模型处理每个词时，给句中所有词算一遍关联度分数，然后按分数加权融合信息，让"它"这类代词能正确关联到指代的对象。工程上真正要记的是代价结构：注意力是每个词和所有词两两打分，计算量随长度平方增长——上下文翻倍，计算量翻四倍；再加上生成阶段用 KV Cache，已算过的缓存住，导致首 Token 延迟随输入长度明显上升。所以我在做 AI 应用时有条硬纪律：系统提示词精简、检索资料按需注入、历史对话滑动窗口加摘要——全是控制输入长度，因为平方代价下 Prompt 不是免费的，每一千个 token 都在同时烧钱和烧延迟。

**Q：KV Cache 是什么？为什么大模型第一个字出来特别慢？（追问）**
> 生成是自回归的：每生成一个新词，都要和前面全部内容做注意力。KV Cache 把已生成部分的打分中间结果缓存起来，新词来了只算新增部分——这就是为什么第一个字最慢（要完整处理你的输入 Prompt，TTFT 由此而来），后面越写越快。工程含义两个：交互式应用要盯 TTFT 而不是总时长（用户对"多久开始出字"最敏感）；输入侧能砍则砍，砍输入直接降 TTFT。这和我在缓存设计里"预计算+增量更新"是同一个思想家族。
