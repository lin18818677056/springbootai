# Day 22 · 模型选型五维：架构师的选型画法

> **今日目标**：掌握架构师视角的模型选型——能力/成本/延迟/合规/生态五维评估；亲手给工单系统做一次完整选型（候选 3 个模型走全流程）；理解"榜单只做初筛，业务评测集才是一票"。
> **时长**：概念 1h / 选型实操 2.5h / 输出 0.5h
> **今日产出**：工单系统选型报告（五维对比表）+ 《选型流程模板》
> **对照教程**：`ai-learning/01-大模型基础原理.md` 第 5 节

## 1. 知识地图（先讲人话）

```
选模型不是"选最强的"，是"选最合适的"——和 M9 技术选型同一哲学：

五维评估法（每维都有可操作的检查动作）：
  维① 能力：它能干好你的活吗？
    权威榜单（SuperCLUE/LMSYS 竞技场）只做初筛——榜单是"高考总分"，
    你的业务是"专业分"；一票决定权在自建评测集（day19 的 50 条）
    动作：候选模型全部跑一遍评测集，分数对比
  维② 成本：用得起吗？
    动作：单价 × 预估调用量（day02 成本公式）→ 月账单；加上评测/重试 10% 冗余
    注意：单价×3 的模型未必贵——省下的重试和兜底成本要算总账
  维③ 延迟：用户等得了吗？
    看 TTFT（交互场景 <2s）和生成速度（tokens/s）
    动作：评测集实际跑一轮，记录 P50/P95 延迟（平均数会骗人，P95 不会）
  维④ 合规：法律和行业让不让用？
    数据出境红线（用户数据发给境外 API？）/ 备案要求（政企必须国产备案模型）/
    私有化许可（要不要本地部署——day26 架构的输入）
    —— 这维经常一票否决：再强不能用也是零分
  维⑤ 生态：协议兼容性/工具链/社区
    OpenAI 兼容程度（day08）、结构化输出/function calling 支持（day10/15 伏笔）：
    换模型的成本=兼容协议的覆盖面

选型流程模板（六步，直接抄）：
  ① 列 3~5 个候选（按合规先淘汰一批）
  ② 同一套 Prompt+评测集跑分（能力分）
  ③ 记录 P50/P95 延迟（延迟分）
  ④ 按预估调用量算月账单（成本分）
  ⑤ 出五维对比表 → 加权决策（权重按业务定：客服场景延迟>成本>能力微弱领先）
  ⑥ 小流量灰度验证 → 全量
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Benchmark | 基准评测 | 公开榜单（初筛用，不是决定性） |
| Business Eval Set | 业务评测集 | 自己的考卷（一票决定权） |
| Data Residency | 数据驻留 | 用户数据存在哪/能出境吗（合规硬约束） |
| Weighted Decision | 加权决策 | 五维按业务权重打总分（客服≠科研） |
| Canary Release | 灰度发布 | 小流量验证再全量（M6 的老朋友） |
| Vendor Lock-in | 供应商锁定 | 生态依赖太深换不掉（兼容协议是解药） |

## 3. 动手实操：给工单系统走一遍完整选型

### 3.1 步骤①：列候选（模拟场景也能练流程）

```
候选池（按你实际可得性调整）：
  A. qwen2.5:7b（本地 Ollama，零成本，延迟取决于你的机器）
  B. qwen2.5:3b（本地更小更快，能力弱一档）
  C. deepseek-chat（API，能力强，按量付费）
  D. 某境外 API（合规淘汰示范：用户工单数据出境红线 → 直接出局）
  —— D 的存在是为了练"合规一票否决"的动作
```

### 3.2 步骤②~④：三个候选跑数据

```
能力分：评测集 50 条各自跑分（day19 流程原样复用）
  A（7b）= __% | B（3b）= __% | C（API）= __%
延迟分：P50 / P95（本地用 Measure-Command，API 加网络 RTT）
成本分：按 500 工单/天 × 平均 3 次调用估算月账单
  A ≈ 电费 | B ≈ 更少电费 | C = token 单价 × 日调用量 × 30
```

### 3.3 步骤⑤~⑥：决策表+结论

```
五维对比表（示例格式，填实测数）：
  | 维度  | 权重 | A 7b本地 | B 3b本地 | C API |
  | 能力  | 35%  | __       | __       | __    |
  | 成本  | 25%  | __       | __       | __    |
  | 延迟  | 20%  | __       | __       | __    |
  | 合规  | 一票 | 可       | 可       | 可    |
  | 生态  | 20%  | __       | __       | __    |
  | 加权  |      | __       | __       | __    |
决策范例（真实感）：分类器场景 B（3b）分够用且延迟最低 → 路由主力；
  审核复核场景选 A 或 C（风险判断要能力）→ 这就是 day20 模型路由的选型依据！
  结论：不是"选一个"，是"按场景分配"——组合拳才是架构师答案
```

## 4. 面试连接

**Q：你们怎么做大模型选型的？（AI 架构高频题）**
> 五维评估加六步流程。五维：能力、成本、延迟、合规、生态。其中两条纪律最重要：一是榜单只做初筛——公开榜单像高考总分，业务场景要专业分，一票决定权在自建评测集，我们 50 条业务考卷每个候选都跑；二是合规件经常一票否决——用户数据出境红线、备案要求，不合规再强也是零分。流程是：列候选→评测集跑分→实测 P50/P95 延迟（平均数会骗人）→按调用量算月账单→加权决策→灰度放量。最后我的选型结论从来不是"选一个模型"，是"按场景分配"：工单分类这种结构化任务，小模型分数够用且延迟低，做路由主力；风险审核这种判断类任务才上更强的模型——这个组合拳直接决定了成本结构，比单选旗舰模型省一大截。选型报告五维表加实测数字留档，换模型时也用同一套流程重跑，选型就从拍脑袋变成了可重复的工程动作。
