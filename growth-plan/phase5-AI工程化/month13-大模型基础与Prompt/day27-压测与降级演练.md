# Day 27 · 压测与降级演练：给 AI 服务做体检

> **今日目标**：给工单系统做一次并发压测（搞懂 LLM 压测和传统接口压测的三大区别）；演练四条故障预案——模型超时/返回坏格式/预算熔断/并发打满，全部真触发一遍。
> **时长**：压测 1.5h / 演练 2h / 输出 0.5h
> **今日产出**：三档压测记录表 + 四条预案演练记录 + 《上线验收结论》
> **思想来源**：M6 稳定性思想的 AI 版平移

## 1. 知识地图（先讲人话）

```
先说最大的认知差：LLM 服务的压测 ≠ 传统接口压测。

传统接口：无状态、毫秒级返回，瓶颈通常是"线程池/连接池"，
          100 并发加机器就扛得住。
LLM 服务：一个字一个字往外蹦（生成式），瓶颈是"GPU/显存"——
          类比食堂：传统接口是自助餐机（同时打 100 份没问题），
          LLM 是现炒窗口（8 个师傅，第 9 个客人就得排队，
          排队的人越多，每个人等越久——TTFT 飙升）。

三大区别（面试必背）：
  ① 响应是流式长响应：一个请求占着算力几十秒（连接挂时间久）
  ② 体感指标是 TTFT：用户不管总时长多长，就等第一个字（day09）
  ③ 并发天花板=算力：加并发不减人均速度=队列堆积；本地 Ollama 更明显
     （你的显卡/内存就是那 8 个师傅）

今天的四条预案（全在 day18/20 埋过，今天真点火）：
  预案① 模型超时 → 超时熔断 → 降级备用模型 → 人工队列
  预案② 返回坏格式 → 防御链修复/重试（day10）
  预案③ 日预算烧穿 → 熔断只跑缓存+人工（day20）
  预案④ 并发打满 → 排队限流，宁可慢不可崩（day20 用户级限流）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Concurrency | 并发 | 同时在处理的请求数（食堂里同时点的客人） |
| Throughput | 吞吐 | 每秒处理完多少请求（每分钟出几份菜） |
| Queueing | 排队延迟 | 并发超了，请求在门口等的等待时间 |
| Timeout | 超时 | 等太久主动放弃，别把用户吊死（默认无超时=裸奔） |
| Circuit Breaker | 熔断 | 连续失败就"跳闸"，直接走降级，别去撞死掉的模型 |
| Capacity Planning | 容量规划 | 用压测数据反推：这个部署能扛几路并发 |

### 3.2 实验二：四条预案点火演练

```powershell
# 预案① 超时熔断（最关键的一条）
curl.exe -s --max-time 5 http://localhost:11434/v1/chat/completions -d @big.json
# big.json = max_tokens 拉到 2000 的"慢请求" → 5 秒必超时
# 应用侧伪代码：catch timeout → 重试 1 次（指数退避 1s）→ 仍失败 → 降级链
#   降级链（day18 版）：主模型 → 备用模型 → 人工队列，每级落 call_log

# 预案② 坏格式：把 temperature 拉满 + Prompt 删约束发 10 次，
#   统计 JSON 解析失败率 → 验证防御链（修复/重试≤2/兜底）接得住
```

## 4. 面试连接

**Q：LLM 服务的压测和容量规划怎么做？（AI 平台高频题）**
> 先说认知差：LLM 是生成式流式长响应，瓶颈在算力不在线程池——像现炒窗口，师傅就 8 个，第 9 个客人开始排队，而且排得越久每人等越久。所以我压测盯三个数：TTFT、吞吐、并发天花板，用三档并发实测——我们从 1 路到 4 路吞吐还能涨，到 8 路吞吐不升反降、首字延迟飙升，天花板就摸到了。容量规划反着推：目标并发乘以 P95 单耗，倒推出算力需求；或者算力定了，把限流线设在天花板的七成留余量。预案上我坚持"每条都真点火过"：模型超时走熔断加降级链最后人工队列；坏格式靠防御链修复重试兜底；预算烧穿熔断只跑缓存；并发打满靠排队限流宁可慢不可崩。最后上线验收有一张结论表，六项全过才放行——和传统服务的上线纪律一脉相承，只是指标换成了 TTFT 和算力视角。
