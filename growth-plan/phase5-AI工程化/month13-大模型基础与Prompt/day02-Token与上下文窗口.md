# Day 02 · Token 与上下文窗口：模型的"有限记忆"

> **今日目标**：搞懂 Token（计费和长度的最小单位）与上下文窗口（记忆容量的天花板）；兑现 M12 思考题①——上下文窗口和 Flink 的状态本质上是同一类问题：**有限的记忆，都要回答"记什么、忘什么"**。
> **时长**：概念 1h / 实操 1h / 输出 0.5h
> **今日产出**：Token 估算实验记录 + 《上下文预算表》+ 成本估算公式卡
> **对照教程**：`ai-learning/01-大模型基础原理.md` 第 1/4 节

## 1. 知识地图（先讲人话）

```
Token（词元）= 模型眼里的"字"：
  人类读字：你 → 好 → ， → 世 → 界
  模型读 token："你好" 可能是 1 个 token，"world" 可能是 1 个 token
  经验公式：1 个汉字 ≈ 1~2 token；1 个英文单词 ≈ 1~1.5 token
  —— 为什么关心：①按 token 计费 ②上下文窗口按 token 数 ③限速按 token/s

上下文窗口 Context Window = 模型一次能"看见"的全部内容：
  ┌───────────── 上下文窗口（如 8K/32K/128K token）─────────────┐
  │ 系统提示词 + 历史对话 + 检索到的资料 + 你的问题 + 模型的回答  │
  └──────────────────────────────────────────────────────────┘
  装不下的 → 模型彻底"看不见"（不是压缩，是消失）

[兑现 M12 思考题①] 上下文窗口 vs Flink 状态——同构对照表：
  ┌────────────┬──────────────────┬──────────────────────┐
  │            │ Flink 状态        │ 上下文窗口            │
  ├────────────┼──────────────────┼──────────────────────┤
  │ 本质       │ 有限的记忆        │ 有限的记忆            │
  │ 超了会怎样  │ OOM/快照变慢      │ 头部内容被截断遗忘     │
  │ 管理思路    │ TTL：问"可以忘吗" │ 滑动窗口/摘要：问"留什么"│
  │ 外挂方案    │ RocksDB 落盘      │ RAG 外部知识库（M14） │
  │ 调优纪律    │ 降基数/瘦身       │ 砍历史/压缩/精简提示词 │
  └────────────┴──────────────────┴──────────────────────┘
  一句话：Flink 用 TTL 管遗忘，大模型应用靠"上下文管理策略"管遗忘（day17 实战）

成本意识（工程师的第一课）：
  一次问答成本 = 输入 token × 输入单价 + 输出 token × 输出单价
  —— 输出单价通常是输入的 2~4 倍：让模型少废话 = 直接省钱
  —— 多轮对话成本会"滚雪球"：每轮都重发全部历史（第 10 轮时前 9 轮全在付费）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Token | 词元 | 模型的"字"，计费/限长/限速的最小单位 |
| Context Window | 上下文窗口 | 模型一次能看见的 token 上限（8K=8000 个左右） |
| Prompt Token | 输入词元 | 你发给它的内容（便宜） |
| Completion Token | 输出词元 | 它生成的内容（贵 2~4 倍） |
| TTFT (Time To First Token) | 首 Token 延迟 | 等第一个字出来的时间（交互体验分水岭 ≈2s） |
| Sliding Window | 滑动窗口 | 只留最近 N 轮历史的记忆策略（day17 实战） |
| Snowball Cost | 滚雪球成本 | 多轮对话历史每轮重发导致的成本膨胀 |

## 3. 动手实操

### 3.1 实验①：亲手数 Token（建立体感）

```
方法①（有 Ollama）：ollama run qwen2.5:7b --verbose 后问一句话，
  输出里的 eval count 就是生成 token 数——对照你的字数，验证 1 汉字≈1~2 token
方法②（有 API）：响应 JSON 的 usage.prompt_tokens / usage.completion_tokens
方法③（降级，纯手工）：找 3 段文字自己按公式估算，再对照真实值校准手感：
  "你好世界" → 估 4~8 token
  "Spring Boot autoconfiguration" → 估 6~10 token
  一段 500 字的中文需求描述 → 估 500~1000 token
《Token 手感表》：中文 1 字≈1.5 token（宁可高估，预算要留余量——和资源倒推一个思想）
```

### 3.2 实验②：算一笔真实的账（成本意识）

```
场景：智能客服，平均每次咨询 8 轮对话，每轮用户输入 50 字、回答 150 字，
     系统提示词 500 字，窗口 8K token 足够（先不算被截断）
粗算（1.5 token/汉字）：
  每轮输入：(500 系统提示 + 之前 7 轮全部历史 + 50 新输入) × 1.5
  —— 滚雪球实锤：第 8 轮时历史已有 (50+150)×7=1400 字 ≈ 2100 token
  全程粗估：累计输入 ≈ 1.2 万 token + 输出 ≈ 1800 token
  × 日咨询量 1000 次 × 单价（查你所用模型价目表）→ 这就是每月的模型账单
结论写进《上下文预算表》：
  □ 系统提示词控制在 ___ token 内
  □ 历史保留 ___ 轮 / 超出转摘要（day17 实现）
  □ 回答长度约束写进 Prompt（"不超过 150 字"）
```

### 3.3 实验③：亲眼看"遗忘"

```
有模型：第一轮告诉它"我的工号是 9527"，然后聊 30 轮别的，
  再问"我工号多少"——小窗口模型/长对话下会答不上来（被截断遗忘）
降级：拿一张 8K 窗口的纸模拟——第 31 轮时第一行已经写不下，被撕掉了
体会：模型不是"记性差"，是"窗口就这么大"——工程责任在你（应用侧管理）
```

## 4. 面试连接

**Q：什么是上下文窗口？超了会怎么样？（必考基础题）**
> 上下文窗口是大模型一次推理能处理的 token 总量上限，里面装着系统提示词、历史对话、检索资料、当前问题和回答——所有内容共享这个窗口。超了不是报错，而是头部内容被截断或忽略，模型"看不见了"，表现为答非所问或忘记早期约定。工程上三招管理：滑动窗口只保留最近 N 轮；摘要压缩把早期对话浓缩成一段；关键信息外置——存数据库或向量库按需注入（这就是 RAG 的入口）。我做的多轮对话项目用的就是"滑动窗口+超限摘要"的组合，把成本和窗口占用都控制住了。

**Q：怎么估算一个 AI 应用的模型成本？（成本意识题，P7 信号）**
> 三步估算法。第一步定单次成本：拆出输入和输出 token——输入=系统提示+历史+检索内容，输出=回答长度约束；用"1 汉字≈1.5 token"粗估，再拿 usage 实测校准。第二步抓乘数：日调用量、平均轮次；特别注意多轮对话的滚雪球效应——历史每轮重发，第 N 轮的输入是前面所有轮次之和，所以"砍历史/转摘要"是最大的省钱杠杆。第三步留余量做预算：峰值系数照搬我在秒杀项目里的 3 倍原则，再加上评测和重试的消耗（通常再 10%）。成本不是算完就完了——把"单次成本、日成本、可优化项"写成表格持续盯，token 消耗突然翻倍往往意味着 Prompt 失控或循环调用 bug。
