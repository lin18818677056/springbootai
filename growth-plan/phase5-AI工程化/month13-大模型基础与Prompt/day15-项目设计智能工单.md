# Day 15 · 项目设计：智能工单系统总设计

> **今日目标**：项目周开工——设计"智能工单系统"（W3 三天造三个零件：分类器/多轮记忆/审核流水线，day19 评测、day20 成本）；画架构图、定数据契约、备评测集。沿用 M11/M12 项目周节奏。
> **时长**：设计 2h / 备料 2h / 输出 0.5h
> **今日产出**：项目架构图 + 数据契约（Schema 定义）+ 评测集 v1（20 条起步）
> **配套**：practice-projects 项目四（RAG 知识库）的设计预演——工单系统的"知识问答"部分 M14 升级为 RAG

## 1. 项目设计（先讲人话：要造什么）

```
业务故事（虚构但真实感）：
  你是"某电商"的售后技术负责人。客服团队每天 500 张工单，
  人工分类+回复耗时 4 分钟/张。目标：AI 预处理，把人工介入压到 1 分钟/张。

系统总图（W3 逐块实现）：
  用户工单（文本）
      ↓
  ①【day16 分类器】结构化输出：类别+优先级+置信理由（few-shot 版模板④）
      ↓
  ②【day17 多轮对话】追加回复能力：
      简单咨询直接回复（多轮记忆：滑动窗口+摘要压缩）
      ↓
  ③【day18 审核流水线】高风险工单（退款金额/情绪激动）→
      二级审核 Prompt 复查 → 输出处理建议；超时/异常走降级（人工队列）
      ↓
  ④【day19 评测】50 条评测集全链路回归（对拍思想第五次上场）
  ⑤【day20 成本】token 预算、缓存、限流

架构决策（先想清楚再动手——M9 方法论）：
  决策① 单 Prompt 还是级联？→ 级联（分类/回复/审核职责分离，
     各自可独立优化评测——单一职责原则的 Prompt 版）
  决策② 同步还是异步？→ 分类异步（进队列），回复同步（用户在等）
  决策③ 模型输出权限？→ 只有"建议权"：分类结果/回复草稿/审核意见，
     最终动作（真退款）永远人工点确认（day13 红线的系统级落实）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Data Contract | 数据契约 | 各环节输入输出的 Schema 约定（先签合同再开工） |
| Cascade | 级联 | 多个 Prompt 按流水线串行（各管一段） |
| Pre-processing | 预处理 | AI 先跑一遍，人只看 AI 搞不定的 |
| Human Review Queue | 人工队列 | AI 处理不了/高风险的转人工（兜底队列） |
| Evaluation Set | 评测集 | 带标准答案的考卷（day19 主角） |
| Suggestion-only | 仅建议模式 | AI 出主意、人拍板（本项目的安全底线） |

## 3. 动手实操：签契约+备料

### 3.1 数据契约（三份 Schema，全项目遵守）

```
① 工单输入契约：
  { "ticket_id": "T20260928-001", "text": "工单原文", "user_level": "vip|normal" }
② 分类器输出契约（day16 实现）：
  { "category": "refund|logistics|consult|unknown",
    "priority": "high|medium|low",
    "reason": "≤30 字判断依据",          ← 可解释性：人审核时看得懂为什么
    "need_human": true|false }           ← 高风险标记，true 直送人工队列
③ 审核输出契约（day18 实现）：
  { "risk": "high|medium|low",
    "suggestion": "处理建议 ≤80 字",
    "violations": ["检测到的风险点"] }
```

### 3.2 评测集 v1（今天 20 条，day19 补到 50 条）

```
攒考卷（对拍思想的"真相源"）：
  □ 每类工单至少 4 条（refund/logistics/consult 各 4+模糊 2 条）
  □ 含 2 条注入攻击样本（day13 的攻击工单——安全测试也要入考卷）
  □ 含 2 条高风险样本（大额退款/辱骂客服——审核流水线的考题）
  □ 每条标注标准答案：category/priority/need_human/risk
  □ 来源要真实感：去客服聊天记录/电商评论里改写（脱敏），别自己瞎编得太顺
存 git：evaluation/tickets-v1.json（评测集也是代码，版本管理！）
```

## 4. 面试连接

**Q：设计一个 AI 预处理系统，你的思路是什么？（系统设计题，本周总纲）**
> 我的框架是"先定边界，再定链路，最后定契约"。边界上最重要的一条：AI 只有建议权没有执行权——分类、回复草稿、审核意见都是输出建议，真正涉及钱的动作必须人工确认，这是从第一天就定死的架构红线，而不是事后补丁。链路上选级联不选单 Prompt：分类器、对话回复、审核流水线职责分离，各自独立优化、独立评测，一个环节升级不会弄脏另一个环节——单一职责原则的 Prompt 版。契约上先签三份 Schema 再写 Prompt：输入、分类输出、审核输出，字段和枚举写死，可解释性字段（reason）和人工标记（need_human）是一等公民。质量保障用评测集对拍：50 条带标准答案的考卷，每次改 Prompt 跑一遍，分数说话。这套设计里没有一步是"AI 玄学"，全是传统工程方法论的平移。
