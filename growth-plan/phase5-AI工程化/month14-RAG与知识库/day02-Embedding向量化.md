# Day 02 · Embedding 向量化：把文字变成坐标

> **今日目标**：兑现 M13 交接卡思考题②——"意思相近"怎么索引；搞懂 Embedding（文字→坐标，坐标近=意思近）和余弦相似度；用 Ollama 的嵌入模型亲手算几组相似度。
> **时长**：概念 1h / 实操 2h / 输出 0.5h
> **今日产出**：嵌入实验记录（三组对比）+ 《Embedding 认知卡》
> **对照教程**：`ai-learning/04-RAG检索增强.md` 术语表 + 第 2 节

## 1. 知识地图（先讲人话）

```
昨天留的问题：MySQL 的 B+ 树能查"订单号=123"，但"和这句话意思相近
的段落"怎么查？相等匹配好办，语义匹配呢？

答案分两步：
第①步 把文字变成坐标（Embedding，嵌入/向量化）
  类比：给每句话在一张"意思地图"上安排一个住址。
  "怎么申请退款" 和 "退款流程是什么" 住在隔壁；
  "怎么申请退款" 和 "今天天气不错" 住在一个城东一个城西。
  技术上：一句话 → 一串数字（如 768 个小数），这串数字就是坐标（向量）。
  谁来转？嵌入模型（Embedding Model）——另一种小一号的模型，
  只管"理解意思"，不管"说话"（和聊天模型分工不同，一个月前容易搞混）。

第②步 在坐标上找"最近的邻居"（近邻检索）
  问题也变成坐标 → 找库里离它最近的 K 个坐标 → 就是"意思最相近的 K 段"。
  这就是向量库干的事（明天 day03 上手）。

"近"怎么量化？余弦相似度（Cosine Similarity）：
  别怕名字，人话版：比较两个箭头的方向。
  方向越一致 → 越相似 → 分数越接近 1
  完全垂直（不相关）→ ≈ 0
  方向相反（语义相反）→ ≈ -1
  （为什么不用距离？——方向比长度更能代表"意思"，长度只代表"说多少"）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Embedding | 嵌入/向量化 | 文字→数字坐标（意思的住址） |
| Embedding Model | 嵌入模型 | 负责"翻译成坐标"的模型（理解意思，不说话） |
| Vector | 向量 | 一串数字，就是坐标（768 维=768 个数） |
| Cosine Similarity | 余弦相似度 | 比箭头方向：1 最像，0 无关，-1 相反 |
| kNN (k-Nearest Neighbors) | K 近邻 | 找离问题最近的 K 个住址 |
| Dimension | 维度 | 坐标由几个数组成（nomic-embed-text 是 768 维） |
| ANN (Approximate NN) | 近似近邻 | 数据量大时"找个差不多的最近"换速度（索引加速） |

## 3. 动手实操：亲手算相似度

### 3.1 步骤①：装嵌入模型 + 拿到第一个向量

```powershell
ollama pull nomic-embed-text      # 274MB，CPU 都能跑（嵌入模型都小）

# 造请求体 embed.json（注意：嵌入走 /api/embeddings，不是聊天接口）
# { "model": "nomic-embed-text", "prompt": "怎么申请退款" }
curl.exe -s http://localhost:11434/api/embeddings -d @embed.json
# 预期：一大串小数（768 个），这就是"怎么申请退款"在意思地图上的住址
```

### 3.2 步骤②：三组对比实验（今天的核心）

```
用 PowerShell 或任意语言把向量取回来，写个 20 行的余弦公式（照抄即可）：

组① 语义相近（预期分数高，0.7+）：
  "怎么申请退款" vs "退款流程是什么"
组② 无关（预期 ≈ 0 附近）：
  "怎么申请退款" vs "今天午饭吃什么"
组③ 语义相反/否定（重点体感！）：
  "支持七天无理由退货" vs "不支持七天无理由退货"
  —— 分数依然很高（0.9 上下）！模型对否定词不敏感
  → 大白话：方向几乎一样，只是差一点点
  → 工程教训：涉及"能不能/可不可以"的问答，光靠向量检索会翻车，
    要靠检索后的生成环节（把原文喂给模型，让它读出"不"字）或关键词路兜底
```

### 3.3 步骤③：一个认知校准实验（专有名词）

```
"qwen2.5 的 max_tokens 参数怎么设" vs "大模型输出长度上限怎么配"
  —— 语义近，分数高？✓
"max_tokens 怎么设" vs "MCP 协议怎么接"
  —— 两个都是 AI 术语，但语义无关，分数应该不高
  → 但真实知识库检索里，专有名词恰恰要精确匹配（day09 BM25 的伏笔：
    向量对"这个词本身"不敏感，专有名词要关键词路来救）
```

### 3.4 《Embedding 认知卡》

```
□ 嵌入模型和聊天模型的分工：理解意思 vs 组织语言（两个都要，别混用接口）
□ 相似度是"方向"不是"字面"：同义不同字也能高、一字之差也可能翻车
□ 否定词/专有名词是向量的两大软肋 → 分别由生成环节/BM25 兜底
□ 维度只是"地址精度"，768 维够用；别迷信越大越好
```

## 4. 面试连接

**Q：Embedding 是什么？为什么语义检索要用它？（M14 高频第一题）**
> Embedding 就是把文字映射成高维空间里的坐标——可以理解成给每句话在"意思地图"上安排住址，意思近的句子坐标就挨得近，用余弦相似度衡量，本质是比两个向量的方向，方向越一致分数越接近 1。这样"意思相近"这个模糊需求就变成了"找最近邻"这个数学问题，向量库专门干这个。但它的软肋必须知道：一是否定词不敏感——"支持退货"和"不支持退货"的相似度能到 0.9，因为方向几乎一样，所以涉及可不可以的问题要靠把原文喂给生成模型去读，不能只信检索；二是专有名词不敏感，它认意思不认字面，所以生产检索都是向量加 BM25 关键词双路，互为兜底。嵌入模型和聊天模型是分工：嵌入管理解，聊天管表达，接口都不同。这两个软肋是我自己实验踩出来的，比背文档印象深刻。
