## 1. 知识地图（先讲人话）

```
故障点火的老规矩（M12 预案演练 / M13 四预案，这是第三季）：
  每条预案必须"真触发过"——写在文档里的降级叫愿望，
  点过火的降级才叫能力。

RAG 特有三预案（对比传统服务的新故障类型）：

预案① 向量库挂（检索侧瘫痪）：
  现象：PGVector 连不上/超时 → 检索全失败
  降级链：重试（1 次指数退避）→ 降级纯 LLM 模式（无检索直接答，
         答案前缀"以下回答未经知识库核实，仅供参考"）
         → LLM 也挂 → 拒答转人工
  为什么不直接拒答？——部分降级好过全瘫：诚实标注的"裸模型回答"
  仍能覆盖通用问题（"什么是发票"），只是丢了私有知识能力。

预案② 检索空（链路活着但没找到）：
  现象：相似度全线低于阈值（day06 的拒答场景，但要从"故障视角"再看）
  区分两种情况：
    a. 正常库外问题 → 拒答（这是特性不是故障）
    b. 异常批量检索空（命中率断崖）→ 说明检索侧坏了（索引损坏/
       切分变更翻车）→ 告警+降级纯 LLM 模式
  判断依据：拒答率的"突变"——单次拒答是特性，批量拒答是事故
  （day26 说的"拒答率是最灵敏信号"就是为这条预案服务的）

预案③ 知识过期（无声过期，最阴险）：
  现象：一切正常运行，答案在说旧话（day23 剧本）
  防御三道（今天验收）：
    a. 更新链路自动同步（day23 每夜任务）
    b. 答案带资料更新时间展示（day19 citation 的 updatedAt 字段——
       用户自己能看到"这条资料是 9 月 1 日的"）
    c. 周质量抽检 + 政策类答案 TTL 24h（day24 缓存纪律）
  演练方式：改文档不触发 sync → 问新旧交界问题 → 验证 b 防线
  能让用户看见资料时间 → 手动触发 sync → 验证分钟级生效
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Graceful Degradation | 优雅降级 | 瘸着走好过躺倒（带标注的裸 LLM 模式） |
| Partial Degradation | 部分降级 | 丢私有知识能力，保通用问答能力 |
| Refusal Spike | 拒答率突刺 | 单次拒答=特性，批量拒答=事故 |
| Annotated Fallback | 带标注降级 | 降级答案必须声明"未经核实" |
| Drill | 演练 | 真点火（预案的实弹考核） |
| Acceptance Checklist | 验收清单 | 全过才放行上线 |

## 3. 动手实操：三预案点火

### 3.1 预案① 演练：停掉 PGVector

```powershell
docker stop pgvector
# 问一个知识库内的问题（"退款多久到账"）
# 预期链路：
#   检索超时（day16 客户端 3s 连接超时触发）→ 重试 1 次
#   → 降级纯 LLM 模式 → 答案带"未经知识库核实"前缀 → SSE 正常收尾
# 验证点：
#   □ 用户看到降级标注（不是无声裸答）
#   □ call_log 记录 status=degraded（降级有台账）
#   □ 恢复 PGVector 后 10 秒内自动回到正常模式
docker start pgvector
```

### 3.2 预案② 演练：制造批量检索空

```powershell
# 手段：把检索阈值临时改到 0.99（基本永远检不到）模拟索引损坏
# 连发 10 问 → 观察：
#   □ 单问层面：拒答话术正常（特性）
#   □ 系统层面：拒答率 100% > 30% 红线 → 告警触发
#   □ 自动降级：连续 5 次拒答 → 自动切入纯 LLM 模式 + 告警通知
# 恢复阈值 → 拒答率回落 → 自动切回（或人工确认切回）
```

### 3.3 预案③ 演练：知识过期（无声）

```powershell
# 步骤：改 refund-faq.txt（改新政策）→ 不跑 sync → 问交界问题

#   □ 答案引用的 updatedAt 显示旧日期（用户可见的诚实）
```

## 4. 面试连接

**Q：RAG 服务的故障预案怎么设计？讲一个你演练过最隐蔽的故障？（压轴题）**
> 我的纪律是每条预案都真点火，写在文档里的降级叫愿望，点过火的才叫能力。RAG 比传统服务多了三类新故障，我们各演练过。向量库挂：检索侧全瘫，降级到纯 LLM 模式——答案带"未经知识库核实"前缀，诚实标注的降级好过全瘫，通用问题还能答，只是丢私有知识能力；call_log 记 degraded，恢复后自动回归。批量检索空：单次拒答是特性，批量拒答是事故——靠拒答率红线判别，连续拒答自动降级加告警，这正是拒答率是最灵敏信号的原因。最隐蔽的是知识过期：系统一切正常，答案在说旧话。我们演练时真挖出一个 bug：更新链路刷新了知识库，但缓存里还有 24 小时 TTL 的旧答案——修法是入库成功后主动清相关文档的缓存。这道预案的防线有三层：更新链路自动同步、答案展示资料更新时间让用户自己能看见、周质量抽检兜底。最后上线验收六项全过才放行。总结成一句话：RAG 的故障一半是技术故障，一半是"诚实的故障"——系统没坏但答案不对，预案设计的核心是让降级可见、可审计、可恢复。
