# Day 13 · 父子块与表格：检索精度与语境完整的两全法

> **今日目标**：解决 day04 埋的两难——块小检索准但语境断、块大语境全但检索糊；父子块（小块检索、大块喂模型）+ 表格特殊处理；这是 W2 的最后一块检索拼图。
> **时长**：概念 1h / 改造实操 2h / 输出 0.5h

## 1. 知识地图（先讲人话）

```
回顾 day04 的死结：
  块切小（100 字）→ 检索精准，但"退款 3~5 个工作日（切）原路返回"
  被切成两半，检索到哪半都答不全；
  块切大（整章）→ 语境完整，但相关段落被无关内容稀释，
  检索相似度被拉低，窗口还被塞满。

父子块 = 鱼和熊掌分开拿：
  入库时切两层：
    子块（child，~100 字）：负责"被检索"——小块语义集中，向量准
    父块（parent，~500 字）：负责"被阅读"——命中子块后，把它爹整块喂模型
  类比：图书馆的书签系统——
    书签（子块）插在关键句上，找的时候按书签找（准），
    但借阅时借走整章书（全）。没人借"半张书签"。

实现要点（工程三件事）：
  ① 只给子块做嵌入+建索引（省空间省算力——父块不用向量）
  ② 子块表带 parent_id 外键（命中子块 → 查父块内容）
  ③ 父块之间允许少量重叠（爹的边界也别切伤句子）

表格特殊处理（day04 遗留的第二件事）：
  问题：表格按行切=表头丢了（"运费谁出"检索到"首重 5 元"——
        谁的首重？什么业务的首重？——行脱离表头就是断章）
  处理：整表转 Markdown 成一个"表格父块"+ 每行带表头前缀生成
        "行级子块"（"运费：首重 5 元"——行级块自带语境）
  类比：撕日历不能只撕数字，得把"几月"带着一起撕
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Parent-Child Chunking | 父子块切分 | 子块检索、父块喂模型（书签与整章） |
| Small-to-Big | 小到大检索 | 父子块的统称思想（检索小、生成大） |
| parent_id | 父块外键 | 子块指向爹的指针（命中后取整块） |
| Header-aware Row | 带表头的行块 | 行级子块自带表头前缀（撕日历带着月份） |
| Context Window Budget | 窗口预算 | 父块更大 → Top3 父块要重新算 token 账 |
| Retrieval Granularity | 检索粒度 | 检索的最小单位（子块级） |

## 3. 动手实操：把知识库改造成父子块

### 3.1 表结构升级（PGVector 加一张表）

```sql
-- 子块表（带向量，检索用）
CREATE TABLE kb_children (
  id         bigserial PRIMARY KEY,
  parent_id  bigint NOT NULL,        -- 指向爹
  content    text NOT NULL,
  embedding  vector(768) NOT NULL
);
-- 父块表（不带向量，阅读用）
CREATE TABLE kb_parents (
  id       bigserial PRIMARY KEY,
  doc_id   text NOT NULL,
  title    text,                      -- 父块标题（引用溯源显示用）
  content  text NOT NULL              -- 完整大块（~500 字）
);
-- 查询两步走：
-- ① 子块检索：ORDER BY embedding <=> qv LIMIT 8
-- ② 取爹：SELECT p.* FROM kb_parents p
--         JOIN kb_children c ON c.parent_id = p.id
--         WHERE c.id IN (子块 Top8)  → 去重后进重排
```

### 3.3 认知三连

```
① 父子块和 Rerank 什么关系？→ 流水线上下游：
   子块检索海选 → 取爹扩充语境 → 重排精评爹块 → Top3 进窗口
   （顺序别乱：先取爹再重排——评的是"将要喂给模型的爹块"）
② 所有文档都值得父子块吗？→ FAQ 问答对（本身就是小块）不用；
   长文档手册/规范才值得（又是一次"按需选型，别过度工程"）
③ 父块多大合适？→ 500 字上下起步，上限看窗口预算：
   Top3 父块 + 模板 ≤ 4000 token（day02 预算表的老规矩）
```

## 4. 面试连接

**Q：块大小怎么定？检索准和答得全怎么兼顾？（切分进阶题）**
> 单一块大小注定顾此失彼：切小了检索精准但语境断——"退款三到五个工作日原路返回"被切在中间，检索到哪半都答不全；切大了语境全但相关段落被稀释，检索相似度下降还挤窗口。所以我上父子块：子块一百字左右做嵌入建索引负责被检索准，命中后按 parent_id 把五百字左右的父块整块喂给模型负责答得全——书签定位、借整章读。流水线顺序是子块检索海选、取爹扩充、重排精评爹块、Top3 进窗口，注意先取爹再重排，因为要评的是真正喂给模型的块。表格是另一个坑：按行切会把表头切丢，行脱离表头就是断章，我处理成整表一个父块，行级子块自带表头前缀。改造成本可控：只有子块要嵌入，父块纯文本省算力；窗口预算重算一遍，三个父块两千 token 左右依然便宜。效果上我们的跨段问题和表格题从答不全变成稳定答对。选型上补充一句：FAQ 问答对本身是小块，不值得上父子块——长文档手册才值得，按需选型，不过度工程。
