# Day 23 · 知识更新链路：让知识库不过期

> **今日目标**：兑现"没有更新机制的 RAG 一上线就过期"——增量更新全链路（文档改动→自动感知→增量重嵌入→旧块清理）；灰度切流保安全；M6 灰度思想的检索版。
> **时长**：设计 1.5h / 链路搭建 2.5h / 输出 0.5h
> **今日产出**：更新链路跑通（全流程演示）+ 《知识库运维手册》
> **对照教程**：`ai-learning/04-RAG检索增强.md` 第 4 节"知识更新链路"

## 1. 知识地图（先讲人话）

```
先看没有更新链路的下场（真实剧本）：
  9 月 1 日：退款政策改成"3~5 个工作日"，知识库灌了
  9 月 15 日：政策改成"实时到账"，运营改了 Word 文档——但没通知你
  9 月 15 日起：RAG 仍答"3~5 个工作日"——不是报错，是自信地说旧话
  —— 客服按它答 → 客诉 → 事故。知识库的过期是"无声的"，
  不像服务宕机有告警，它安静地毒害每个答案。

更新链路全图（三段式，像快件的"揽收-分拣-派送"）：
  ① 感知（揽收）：文档变了怎么知道？
     方案 a 定时轮询：每夜扫文档库目录的修改时间+指纹（简单可靠）
     方案 b 事件触发：文档系统 webhook/消息队列通知（实时，依赖多）
     本项目：先 a 后 b（先简单后复杂的老纪律）
  ② 增量更新（分拣）：day17 的地基直接复用——
     指纹对比：没变跳过 / 变了删旧插新（幂等三保险原样生效）
     只处理变了的文档=增量（全量重灌 1 万文档 vs 增量 3 篇的算力差）
  ③ 校验与切流（派送）：更新完不是就完了——
     自动跑 30 条回归（评测闸门最后过一遍）
     异常（召回掉了）→ 自动回滚到上一版本块表（版本化兜底）

灰度切流（M6 老朋友检索版）：
  大版本更新（切分策略变更/嵌入模型更换）→ 不能全量直接切：
  新旧两套块表（v2 影子表）→ 新表先接 10% 流量 → 四指标对比
  → 达标再 50% → 100%，旧表保留随时回退
  —— 和服务发版灰度一模一样，只是"版本"从代码变成了索引
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Incremental Update | 增量更新 | 只重灌变化的文档（不全文重扫） |
| Polling / Event-driven | 轮询/事件驱动 | 感知变更的两种方式（闹钟/门铃） |
| Shadow Index | 影子索引 | 新版本块表先暗处建好，验证后切流 |
| Canary Traffic | 灰度流量 | 新版本先接 10% 用户（M6 老朋友） |
| Index Versioning | 索引版本化 | 块表带版本号，回滚=切回旧表 |
| Silent Staleness | 无声过期 | 知识库最危险的坏法：不报错只答旧话 |

## 3. 动手实操：更新链路三段搭建

### 3.1 感知+增量（定时任务 30 行）

```java
// kb/schedule/KbSyncJob.java —— 每夜 2 点跑
@Scheduled(cron = "0 0 2 * * ?")
public void sync() {
    for (DocSource src : docSourceMapper.listAll()) {        // 遍历文档源
        String text = src.read();                             // 读最新内容
        String hash = sha256(text);
        DocMeta meta = metaMapper.findByDocId(src.docId());
        if (meta != null && hash.equals(meta.hash())) continue;  // 没变→跳过
        ingestService.ingest(src.docId(), text);              // 变了→day17 全流程
        syncLogMapper.record(src.docId(), meta == null ? "create" : "update");
    }
}
// 同步日志表 sync_log：doc_id/动作/耗时/结果——更新也有台账
```

### 3.3 影子索引与灰度（大版本变更的流程）

```
剧本：把嵌入模型从 nomic-embed-text 换成另一个（维度变了/效果待验证）
  ① 建 v2 影子表：全量文档按新模型重新嵌入入库（线上 v1 不动）
  ② 影子验证：30 条考卷对 v2 跑四指标（离线关卡）
  ③ 灰度切流：配置项 kb.index.version，先 10% 请求走 v2
     → 四指标+用户反馈对比 v1 → 达标逐级放量 50% → 100%
  ④ 回滚开关：v2 出问题，配置改回 v1（秒级，旧表一直在）
□ 《知识库运维手册》三节：日常同步（自动）/ 大版本变更（灰度 SOP）/
  应急回滚（配置切换）——运维同事拿到手就能值班
```

## 4. 面试连接

**Q：知识库的更新机制怎么设计？怎么保证更新不出事故？（day17 的续集+生产化收口）**
> 先说反面剧本立意：知识库最危险的坏法是无声过期——政策改成实时到账，它还自信地答三到五个工作日，不报错只毒害答案，比宕机难发现得多。所以更新链路三段式。感知段：定时轮询起家，每夜扫文档指纹，简单可靠；实时性要求高再上事件触发，先简单后复杂。增量段：day17 的幂等地基直接复用——内容指纹没变跳过、变了删旧插新、事务兜底，只处理变化文档，一万文档的库增量更新只有几篇的算力开销。校验段：每次更新自动跑三十条回归，异常自动回滚——更新的最后一步是体检不是写库成功。大版本变更走灰度：新模型重嵌入先建影子索引，离线考卷过一遍，再百分之十灰度放量逐级切流，旧表保留随时秒级回退——和服务发版灰度一模一样，只是版本从代码变成了索引。运维手册三节写清楚：日常自动、大版本走 SOP、应急改配置回滚。一句话：更新机制的完成度决定 RAG 是 demo 还是产品，无声过期是知识库的头号事故源。
