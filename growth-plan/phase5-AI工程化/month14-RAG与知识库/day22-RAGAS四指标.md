# Day 22 · RAGAS 四指标：给 RAG 做血常规

> **今日目标**：把评测从"自己拍的 HitRate/MRR"升级成业界标准四指标（RAGAS）——忠实度/答案相关性/上下文精确率/上下文召回；用四指标组合定位问题环节（排查决策树）。
> **时长**：概念 1.5h / 四指标实测 2h / 输出 0.5h
> **今日产出**：四指标实测报告 + 《四指标排查决策树》
> **对照教程**：`ai-learning/04-RAG检索增强.md` 第 5 节

## 1. 知识地图（先讲人话）

```
之前的尺子：HitRate/MRR（检索侧）+ 人肉判答案（生成侧）——够用但土。
RAGAS 四指标 = RAG 的血常规，四项各盯一个环节：

  ① Context Recall 上下文召回（盯检索的"全"）：
     该找到的资料都找到了吗？
     算法人话：把"标准答案"拆成要点，逐点问"检索块里能找到这个点吗"
  ② Context Precision 上下文精确率（盯检索的"准"+重排的功）：
     找回来的块里，有用的排前面了吗？
     算法人话：Top-K 里相关块的占比，且越靠前权重越高
  ③ Faithfulness 忠实度（盯生成的"实"）：
     答案是不是都出自资料？（防幻觉的核心指标，day06 三板斧的成绩单）
     算法人话：答案拆成断言，逐条能溯源到资料的比例
  ④ Answer Relevancy 答案相关性（盯生成的"题"）：
     答案答的是这个问题吗？（防答非所问）
     算法人话：拿答案反推"这可能是在问什么"，和原问题比相似度

及格线经验值（教程给的，先背后验）：
  忠实度 > 0.85 | 答案相关性 > 0.8 | 精确率 > 0.7 | 召回 > 0.8

谁来打分？——LLM-as-Judge（M13 day19 讲过它的坑）：
  每个指标本质是"逐条比对+判分"，用 LLM 当判卷老师
  三条防坑纪律（复习）：温度 0 / 判分标准写死在 Prompt / 抽样人肉复核
  今天不用装 RAGAS 框架——四指标各写一个判分 Prompt 手工实现
  （原理懂了，框架只是批量器）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| RAGAS | RAG 评估框架 | 业界标准的四指标评估体系 |
| Faithfulness | 忠实度 | 答案句句有出处吗（防幻觉） |
| Answer Relevancy | 答案相关性 | 答的是所问吗（防跑题） |
| Context Precision | 上下文精确率 | 找回的块有用且靠前吗（检索+重排） |
| Context Recall | 上下文召回 | 该找的都找到了吗（检索+切分） |
| LLM-as-Judge | 模型当判卷 | LLM 给 LLM 打分（要防坑，M13 已学） |
| Assertion | 断言 | 答案拆成的最小可验证句子 |

## 3. 动手实操：四指标手工实测

### 3.1 四个判分 Prompt（简化实现版）

```powershell
# 每个指标的 Judge Prompt 骨架（都输出 JSON，防御链照旧）：
# Faithfulness：
#   "资料：{chunks}。答案：{answer}。把答案拆成断言列表，
#    逐条标注 supported（资料能支撑）或 unsupported，输出 JSON：
#    {assertions:[{text,supported}]}。"
#   分数 = supported 数 / 总数
# Context Recall：
#   "标准答案要点：{golden_points}。检索块：{chunks}。
#    逐要点标注 found/not_found，输出 JSON。"
#   分数 = found 数 / 要点数
# （Precision/Answer Relevancy 同风格——四个 Prompt 模板入库：模板库⑩号）
```

### 3.3 《四指标排查决策树》（今天的精华产出）

```
上线后某天质量掉了，四指标一看便知哪里坏了：
  Recall 低 → 检索/切分坏了（新文档没切好？嵌入模型换了？）
            → 看 day08 检索评测细分题型
  Recall 正常 + Precision 低 → 重排失效/候选集被污染
  Recall+Precision 正常 + Faithfulness 低 → 生成侧坏了
            （Prompt 被改？模型换了？——先查最近的变更）
  四个都正常但用户投诉 → 考卷没覆盖该场景 → 坏例回流进评测集
□ 这棵树 = 教程第 7 节"数据看两头"的可执行版：
  先检索后生成，定位到环节再动手，不做无据调参
```

## 4. 面试连接

**Q：RAG 的质量怎么系统评估？线上效果掉了怎么排查？（本月大题）**
> 我用 RAGAS 四指标做体检，四项各盯一个环节：上下文召回看该找的资料找全没有，低了好在检索和切分；上下文精确率看找回来的块有用且靠前没有，它同时检验重排；忠实度看答案是否句句有出处，防幻觉的核心指标；答案相关性看答的是不是所问。经验及格线：忠实度零点八五、相关性零点八、精确率零点七、召回零点八。打分用 LLM-as-Judge，但要防坑——温度压零、判分标准写死、抽样人肉复核，我不用框架，四个判分 Prompt 手工实现，原理懂了框架只是批量器。这四项的价值在组合排查：线上质量掉了，召回低查检索切分；召回正常精确率低查重排；前两个正常忠实度低查生成侧，先审最近变更；四项都正常还有投诉，说明考卷没覆盖，坏例回流补评测集。这套排查树让"感觉变差了"变成可定位的工程问题——和传统服务的监控告警同构，只是指标从延迟错误率换成了这四项。
