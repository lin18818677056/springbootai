# Day 15 · 项目四总设计：实验件变工程件

> **今日目标**：项目四《工单知识库 RAG 问答》开工总设计——把 W1/W2 的实验件组装成 Java 工程；三个架构决策；评测集先行；五天里程碑排期。
> **时长**：设计 2h / 排期与契约 1.5h / 输出 0.5h
> **今日产出**：《项目四设计文档》+ 数据契约三份 Schema + 里程碑表
> **前情**：M13 day25 架构图的 RAG 插槽，今天正式接入

## 1. 知识地图（先讲人话）

```
项目四是什么：给 M13 的智能工单系统装上"知识问答"能力——
  客户问政策/流程类问题（"退款多久到账""碎屏险怎么理赔"），
  系统自动检索知识库、有据作答、带引用；
  检索不到 → 拒答转人工。

W1/W2 vs W3 的区别（实验件 → 工程件）：
  实验件：PowerShell 脚本 + 手动流程 + 单文档知识库（能跑就行）
  工程件：Spring Boot + 正式分层 + 幂等入库 + 流式接口 + 可降级
  —— 这一步的差异就是"demo 一天，生产三个月"（README 心法③）

三个架构决策（设计评审的自问自答）：

决策① 检索流水线：全盘复用 W2 成品（双路+RRF+重排+父子块）
  为什么不简化？——台账五行数据摆着：每个组件都有涨分证据，
  砍组件=丢分。也不加新组件？——没验证过的东西不进生产（克制）。
  唯一调整：Rerank 做成配置开关（秒开场景可跳过，day12 的决策延续）。

决策② 接入点：M13 审核流水线的"知识类"分支（决策树兑现）
  M13 day23 定了"知识类问题走 RAG"；day25 架构图预留插槽在编排层。
  接入动作：工单分类器输出 category=consult 且子类型=知识问答
  → 路由到 RAG 问答链路 → 答案+引用回填工单回复草稿。
  好处：闲聊/投诉类不打扰知识库（意图路由 day25 再精细化，
  本周先用 M13 现成的分类结果）。

决策③ 语言与形态：Spring Boot（工作区本尊）+ 正式分层
  controller → RagService（编排）→ Retriever（检索）/ Generator（生成）
  —— 把 M13 欠的账一起还：Java 客户端封装（明天 day16）、
     SSE 流式（day18）。
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Engineering Hardening | 工程化加固 | 实验件→生产件：分层/幂等/降级/可观测 |
| Layered Architecture | 分层架构 | 接口层/编排层/检索层/生成层各司其职 |
| Idempotent Ingestion | 幂等入库 | 同一文档重复导入不产生重复块（doc_id 幂等） |
| Contract-First | 契约先行 | 先定输入输出 Schema 再写实现（M9 老规矩） |
| Milestone | 里程碑 | 每天交付一个可验证的切片 |
| Reuse over Rebuild | 复用优先 | 验证过的组件直接用，不重造 |

## 3. 动手实操：设计文档三件套

### 3.1 数据契约（三份 Schema，先定再写）

```
契约① 问答请求 POST /api/kb/ask
  { "ticketId": "T2026-001",          // 关联工单（审计用）
    "question": "退款多久到账",
    "sessionId": "s-123",             // 多轮场景（改写要用历史）
    "stream": true }                  // 是否流式
契约② 同步响应
  { "answer": "退款将在 3~5 个工作日原路返回[1]。",
    "citations": [ { "no": 1, "docTitle": "退款政策",
                     "snippet": "退款将在...", "score": 0.92 } ],
    "refusal": false,                  // true=走了拒答
    "latencyMs": 2850,
    "retrieval": { "hitCount": 3, "rerankEnabled": true } }
契约③ SSE 流式帧（day18 细讲）
  event: citation  → 先发引用元数据
  event: delta     → 逐段正文（M13 day09 的 delta 拼接）
  event: done      → 结束帧（带 usage 记账）
```

## 4. 面试连接

**Q：从实验到生产，你们的 RAG 项目怎么演进的？（项目叙事总纲）**
> 分两个阶段。实验阶段一周半：无框架把切分、嵌入、检索、有据生成全链路手工跑通，故意先让朴素 RAG 三大病全部暴露，然后建二十四题检索评测集当尺子，按消融台账逐步上混合检索、RRF 融合、重排、父子块——命中率从七成提到九成上下，每个组件都有涨分证据。工程阶段一周：迁移到 Spring Boot 正式分层——接口层、RagService 编排、检索器、生成器各司其职；三个架构决策：检索流水线全盘复用验证过的组件不做未经验证的创新；接入点走工单分类器的知识问答分支，闲聊投诉不打扰知识库；契约先行，请求响应和流式帧三份 Schema 定好再写实现，评测集扩到三十条端到端考卷，每天收工跑回归。这个节奏对应我理解的工程化本质：先在实验环境把不确定性消灭掉，再用确定性的工程纪律封装它——demo 一天生产三个月，差的那两个月就是分层、幂等、降级、回归这些不起眼的活。
