# Day 11 · 查询改写：替用户把话说全

> **今日目标**：治病①的另一半——问题本身有毛病：多轮对话的指代（"它怎么退款"）、口语省略、错别字；学会查询改写（用 LLM 把"病句"补成"完整检索语句"）；想清楚它的延迟成本账。
> **时长**：概念 1h / 对照实验 2h / 输出 0.5h
> **今日产出**：改写实验记录 + 《改写决策卡》+ 优化台账第三行
> **对照教程**：`ai-learning/04-RAG检索增强.md` 第 4 节 Query Rewriting

## 1. 知识地图（先讲人话）

```
场景还原（多轮对话的检索灾难）：
  用户第 1 问：你们的碎屏险包含哪些机型？
  系统答了一堆机型列表。
  用户第 2 问：那它怎么理赔？
  —— "它"是谁？！独立看第 2 问，检索器一脸懵：
  "理赔"的块也许能碰上，但"碎屏险理赔"那块才是对的。
  单块知识库+单轮假设的检索，被口语化的真人对话一打就碎。

查询改写 = 在检索前加一道"话务员"：
  把用户的"病句"补全成"完整问题"再拿去检索：
  第 2 问 + 对话历史 → LLM 改写成 "碎屏险的理赔流程是什么" → 检索
  类比：客服接待——客人说"那个咋弄"，老客服会确认
  "您是说碎屏险的理赔吗？"——改写模型就是这个老客服。

三种改写手法（由轻到重）：
  ① 指代消解：把"它/这个/那个"替换成真实指代对象（多轮对话刚需）
  ② 查询扩展：补同义词（"退款"→"退款 退货 返还"），给 BM25 路送弹药
  ③ HyDE（假设文档）：让 LLM 先"编一个假答案"，拿假答案的向量去检索
     —— 原理：答案和文档的话术更像，问题和答案不像
     （听着玄乎，实测对"答案权威文档"类效果好；成本高，疑难杂症专用）

成本账（架构师的克制）：
  改写要多调一次 LLM：延迟 +1~2s、token 成本 +几百/次
  → 不是所有查询都值得改：直问型（"退款多久到账"）改了白改
  → 策略：先判型再改写（day25 意图路由的伏笔）；
    或只对"多轮第 2+ 问"和"短问题"触发改写
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Query Rewriting | 查询改写 | 检索前用 LLM 把病句补成完整问题 |
| Coreference Resolution | 指代消解 | "它"→"碎屏险"（补全主语） |
| Query Expansion | 查询扩展 | 补同义词扩弹药（退款/退货/返还） |
| HyDE | 假设文档嵌入 | 先编假答案，拿假答案去搜（以答找文） |
| Multi-turn Context | 多轮上下文 | 改写时要带上对话历史（不然"它"解不开） |
| Standalone Question | 独立问题 | 改写的目标产物：脱离上下文也能看懂的问题 |

## 3. 动手实操：改写前后对照实验

### 3.1 造多轮对话测试对（加入评测集）

```
往评测集追加 4 条"多轮型"（day08 尺子扩容，20→24 条）：
  轮次1：碎屏险包含哪些机型？
  轮次2：它怎么理赔？                 ← 标准块：理赔流程块
  轮次1：7天无理由退货有什么条件？
  轮次2：那运费谁承担？               ← 标准块：运费规则块
（评测口径：只对第 2 问打分；改写版把历史一起给改写器）
```

### 3.2 对照跑分（不改写 vs 改写）

```powershell
# A 组（不改写）：第 2 问原文直接走双路检索
# B 组（改写）：
#   改写 Prompt（简洁版）：
#   "根据对话历史，把最后一个问题改写成不含指代、独立完整的检索问题，
#    只输出改写后的问题本身。"
#   → 拿改写结果走双路检索
# 记录：4 条多轮题的 HitRate 变化 + 改写耗时（Measure-Command）
```

```
《改写实验记录》（填实测）：
  问题            | 不改写 Hit | 改写后 Hit | 改写结果
  它怎么理赔       |  ✗/△      |   ✓       | "碎屏险的理赔流程是什么"
  那运费谁承担     |  ✗        |   ✓       | "7天无理由退货的运费谁承担"

预期结论：多轮题命中率大幅提升；代价是每次问答多 1~2 秒
→ 把这行记进《优化台账》第三行（台账+1）
```

### 3.3 《改写决策卡》（什么时候值这个钱）

```
□ 多轮对话的第 2+ 问？→ 改（指代不消解=检索盲猜）
□ 单轮直问？→ 不改（直问没病，改了白付 1~2s）
□ 问题 < 8 个字的超短问？→ 改（大概率省略了主语）
□ 库外题/闲聊？→ 不改也不检索（day25 路由的事）
□ 生产优化：改写用小模型（3b 够）+ 改写结果可缓存（同问法复用）
```

## 4. 面试连接

**Q：多轮对话场景 RAG 检索不准，怎么治？（场景题，高频）**
> 先定位病因：多轮检索不准九成是查询本身有指代和省略——用户第二问说"它怎么理赔"，独立看是病句，检索器不知道"它"是碎屏险。我的方案是在检索前加查询改写：把对话历史和当前问题一起交给 LLM，改写成不含指代、独立完整的检索问题再走双路检索。我们实验过四组多轮考题，不改写命中率只有四成左右，改写后九成，代价是每次多一秒上下的改写延迟。所以工程上不是无脑全改：我做了改写决策卡——多轮第二问起才改、超短问改、单轮直问不改；改写用小模型就够，同问法结果缓存。另一个细节是改写 Prompt 只输出问题本身，别让模型顺带回答。这题往深了问还有 HyDE——先编假答案拿去检索，适合问答型文档，成本高我放在疑难场景按需启用。核心思想：检索器的输入质量决定检索质量，把"替用户把话说全"当成检索流水线的正式工序，而不是事后补救。
