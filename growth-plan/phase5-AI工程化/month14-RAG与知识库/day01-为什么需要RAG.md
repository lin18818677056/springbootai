# Day 01 · 为什么需要 RAG：三方案决策框架

> **今日目标**：兑现 M13 交接卡思考题①——"100 页文档全塞进上下文窗口 vs 只检索相关 3 段"的账算清楚；建立 RAG/微调/长上下文的三方案决策框架，以后遇到"让模型懂我们的资料"类需求 30 秒出方案。
> **时长**：概念 1h / 算账实操 2h / 输出 0.5h
> **今日产出**：全塞方案的成本账 + 《三方案决策卡》
> **对照教程**：`ai-learning/04-RAG检索增强.md` 第 1 节

## 1. 知识地图（先讲人话）

```
需求场景：让模型回答"我们公司退款政策是什么"——训练时没见过的私有知识。

三条路（类比三种带资料进考场的方式）：

路① 长上下文直塞 = 把整本书抄进答题卡
  可行吗？算三笔账就现原形：
  账一（窗口）：100 页 ≈ 5 万 token，qwen2.5:7b 窗口 32k → 根本塞不下
  账二（钱）：塞得下也要按 token 付费，每次问答都塞全书（M13 day02 滚雪球
             的极端版）；API 模型按输入 token 计费 → 账单起飞
  账三（效果）："中间遗忘"——长上下文中间部分的资料，模型经常视而不见
             （注意力稀释，M13 day03 平方代价的副作用）
  结论：文档总量小（<窗口的一半）且一次性任务才考虑
路② 微调 = 把书背进脑子
  M13 day23 讲过：微调管行为（格式/语气/话术），知识注入是大忌——
  贵（训练成本）、难更新（政策改了要重训）、无法溯源（答案从哪学的说不清）
路③ RAG = 开卷考试（先翻书再答题）
  查询时只检索相关 3 段塞进 Prompt：窗口小 ✓ 钱少 ✓ 能溯源 ✓
  知识更新=改文档重新入库（分钟级）✓
  —— 知识频繁更新/要溯源/私有数据/成本敏感，四条全占

决策金句（M13 day23 的完整版）：
  知识 → RAG（可更新、可溯源）
  行为 → 微调（格式语气）
  数据量小且一次性 → 长上下文直塞
  三者常组合：RAG 管知识 + 微调管输出风格，不冲突。
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| RAG (Retrieval-Augmented Generation) | 检索增强生成 | 先检索资料再生成答案（开卷考试） |
| Long Context | 长上下文 | 窗口能装很多字，但"装得下"≠"读得进" |
| Lost in the Middle | 中间遗忘 | 长上下文中间的资料容易被模型忽略 |
| Grounding | 有据生成 | 答案严格基于检索到的资料，不让模型自由发挥 |
| Citation | 引用溯源 | 答案标注"出自哪篇文档哪段"（可验证） |
| Knowledge Cutoff | 知识截止 | 模型训练数据的最后日期（day01 已学） |

## 3. 动手实操：把"全塞方案"的账算实

### 3.1 实验一：三笔账亲手算（M13 day02 预算表直接复用）

```
场景设定：客服知识库 100 页 PDF ≈ 150,000 汉字 ≈ 225,000 token
  （M13 day02 公式：1 汉字 ≈ 1.5 token）

账一 窗口账：
  qwen2.5:7b 上下文 32,768 token → 225k > 32k，塞不下（超 7 倍）
  就算换 128k 窗口的 API 模型也只够塞一遍
账二 成本账（假设某 API 输入价 ¥2/百万 token）：
  全塞：每次问答 225k token 输入 × ¥0.000002 = ¥0.45/次
    日 500 次问答 = ¥225/天 = ¥6750/月
  RAG：检索 3 段 ≈ 2000 token 输入 → ¥0.004/次 → 日 500 次 = ¥60/月
    —— 差 100 倍（这就是"高频调用"列全塞打叉的原因）
账三 效果账：下一节实测"中间遗忘"
```

### 3.2 实验二：亲眼看"中间遗忘"（今天最值钱的实验）

```powershell
# 造一个长 Prompt：开头/中间/结尾各藏一个不同暗号，问中间那个
# needle.json 的 messages.user 内容结构：
#   第一段：请记住暗号A是"苹果"。 （+ 8000 字无关填充文本）
#   中间段：请记住暗号B是"香蕉"。 （藏在正中间）
#   结尾段：现在回答：暗号B是什么？
curl.exe -s http://localhost:11434/v1/chat/completions -d @needle.json
# 把填充文本加长到 1 万/2 万/3 万字各试一次，记录暗号B答对没有
# 预期：越长，中间的暗号B越容易被答错或漏掉 → 亲眼看丢"Lost in the Middle"
```

```
降级路径（没有模型也没关系）：
  用 M13 day01 的人肉模拟法照样做——把三张纸条夹进一本 300 页书，
  让朋友只翻 30 秒找暗号B，体会"资料在但找不到"。
  诚实记录：这个实验体验的是同一件事（注意力有限），结论等价。
```

### 3.3 产出《三方案决策卡》

```
□ 问自己三连：
  ① 知识会变吗？→ 常变的走 RAG（更新=重新入库，分钟级）
  ② 要溯源吗？→ 要的走 RAG（微调的答案说不出出处）
  ③ 要改行为/格式吗？→ 要的才加微调（知识类问题别微调）
④ 文档 < 窗口一半且就问一次？→ 直塞最快（别过度工程）
→ 四连答完方案自动出炉，把卡片贴工位
```

## 4. 面试连接

**Q：为什么企业知识库都用 RAG 而不是微调或长上下文？（本月的开门题）**
> 三笔账算下来就清楚了。窗口账：百页文档几十万 token，多数模型根本塞不下，就算塞得下也有中间遗忘问题——我们实测过在长上下文正中间藏的暗号，填充越长越容易丢，注意力会稀释。成本账：全塞方案每次问答都付全书 token 钱，按日 500 次问答算月账单是 RAG 的一百倍——RAG 只检索相关几段，输入就两千 token 左右。更新账：政策改了，RAG 重新入库分钟级生效，微调要重训练还要防止灾难性遗忘，根本没法运营。所以决策框架是：知识频繁更新、要溯源、私有数据，走 RAG；输出格式语气这类行为定制才微调；文档小且一次性任务直接长上下文。三者不冲突，生产上常见组合是 RAG 管知识加微调管风格。一句话：RAG 是唯一同时满足"可更新、可溯源、成本可控"三个条件的方案——企业知识问答没有悬念。
