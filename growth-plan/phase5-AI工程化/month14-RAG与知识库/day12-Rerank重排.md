## 1. 知识地图（先讲人话）

```
先想一个问题：RRF 融合出的 Top5，顺序靠谱吗？
  RRF 只统计"两路都认可"——但"认可"只是名次信号：
  块D 在 BM25 单路第 1（词全对上了），但它可能只是"词撞上了"，
  和问题的真实相关度一般。RRF 管共识，不管真实相关度。

Rerank = 决赛前请专业评委逐个精评：
  海选（快而糙）：向量+BM25 双路并行，从全库捞出 Top20 —— 毫秒级
  决赛（慢而准）：Rerank 把"问题+每个候选块"配对细评，重排取 Top5 —— 慢但精
  类比选秀：海选靠评委扫一眼（快，难免看走眼），
  总决赛评委逐个看完表演打分（慢，但排次服众）。

为什么两级而不是全库精排？
  精排是"逐对细评"，全库几千块逐对评 = 几千次重排计算，延迟爆炸。
  两级的本质 = 计算资源的分层投放：
    海选广撒网（便宜操作覆盖 100%）→ 精排只评头部（贵操作只花在 Top20）
  （同构：MySQL 索引粗筛 + 业务逻辑细筛；Flink 窗口预聚合 + 下游精算）

Rerank 的两种实现（按成本从低到高）：
  ① 嵌入模型二次打分：问题向量 vs 每个候选块向量单独算余弦
     —— 等等，这和检索不是一回事吗？区别在"配对打分"的用法：
     检索是"先给全库建索引"，重排是"对这 20 个逐个精算"（无索引、更准的模型可用）
  ② LLM 打分：把"问题+候选块"给模型，让它输出相关度 0~10
     —— 最准但最贵（20 次调用），且延迟高
  ③ 专用 Rerank 模型（bge-reranker 类）：cross-encoder，
     问题+块拼一起过模型，相关度判别专精——生产首选，本机跑得动
  今天用 ②（最简，无新依赖）；生产方案记 ③ 的名字和定位即可
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Rerank | 重排 | 对候选精评重排序（治排名不准/噪声混入） |
| Coarse-to-fine | 粗排到精排 | 海选 20 → 精评 5（计算分层投放） |
| Cross-Encoder | 交叉编码器 | 问题+块拼一起过模型（精评的专用模型） |
| Bi-Encoder | 双编码器 | 问题/块分别编码再比方向（向量检索的架构） |
| Context Precision | 上下文精确率 | 窗口里"有用的块占比"（重排的直接收益） |
| Two-stage Retrieval | 两级检索 | 海选+决赛的流水线架构 |

## 4. 面试连接

**Q：检索结果排序不准/噪声多，怎么优化？（Rerank 标准题）**
> 上一级两级检索：海选快而糙，精评慢而准。海选是向量加 BM25 双路并行，从全库捞 Top20，RRF 按名次融合出 Top8——这一层毫秒级，负责"别漏"；精评是 Rerank 把问题加候选块逐对细评重排取 Top5——这一层负责"排对"。为什么必须两级：精评是逐对计算，全库几千块逐对评延迟爆炸，所以计算资源要分层投放，海选覆盖百分之百，精排只花在头部。重排器生产上用 cross-encoder 类专用模型，问题和块拼一起过模型，比双编码器准；我们实验阶段用 LLM 打分版验证收益：二十题评测集上 MRR 从零点五五提到零点七五左右，正确块基本都排到第一位，代价是多一秒多延迟——所以做成配置开关，客服场景开着，秒开场景降级跳过。粗排精排这个模式其实是老架构思想：MySQL 索引粗筛加业务细筛、Flink 预聚合加下游精算，同构的。窗口里的噪声块少了，生成的忠实度和答非所问率都跟着改善——检索侧的最后一块拼图。
