# Day 25 · 意图路由：不是所有问题都该检索

> **今日目标**：给 RAG 装上门卫——闲聊/投诉/库外问题不进检索链路（省钱+防检索噪声带偏答案）；复用 M13 分类器成果；路由前后对比实验。
> **时长**：设计 1h / 落地+实验 2.5h / 输出 0.5h
> **今日产出**：意图路由落地 + 前后对比报告 + 《路由决策表》
> **对照教程**：`ai-learning/04-RAG检索增强.md` 第 6 节"意图路由"

## 1. 知识地图（先讲人话）

```
一个反直觉的事实：RAG 最贵最糟的用法，是"所有问题都检索"。

三类问题混进来会发生什么：
  ① 闲聊（"你好""你是机器人吗"）：
     强行检索 → 检索回一堆不相关块（硬凑的最相似）→ 答非所问
     —— 白花 token 还拉低体验
  ② 投诉发泄（"我要投诉！你们是骗子！"）：
     强行检索 → 知识库答"退货政策如下..."——火上浇油
     —— 该走的是共情话术+转人工（M13 审核流水线的事）
  ③ 库外知识（"量子力学怎么理解"）：
     强行检索 → 硬凑块 → 有据约束下拒答（勉强及格）
     —— 但检索+生成的钱白花了，day06 的拒答判断本来在检索前就能做

意图路由 = RAG 链路最前面加一道门卫：
  问题进来 → 先判意图 → 知识问答才放行进 RAG；
  闲聊→轻量问候语；投诉→共情+转人工；库外→礼貌拒答（不检索）

门卫从哪来（三档，由轻到重）：
  ① 关键词/正则规则：毫秒级零成本，拦最明显的（"你好/投诉/退款"）
  ② 复用 M13 分类器：工单分类的 category 已经判过 consult/refund/...
     —— 项目四本来就从分类器分支接入（day15 决策②），天然路由！
     补一个子类型：知识问答 vs 政策咨询 vs 其他
  ③ 轻量意图模型/小模型判型：规则和分类器都拿不准的疑难件
  本项目落地：② 为主 ① 为辅（先复用已有资产，克制）

路由的隐性收益（比省钱更值钱）：
  检索库不被闲聊问题"试探"——安全性提升（有人用闲聊掩护注入，
  门卫直接把这类流量挡在检索外）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Intent Routing | 意图路由 | 先判来意再决定走哪条链路 |
| Gatekeeping | 门卫模式 | 检索链路的最前置过滤器 |
| Out-of-Domain (OOD) | 域外问题 | 知识库覆盖之外的问题（提前拒，省检索） |
| Fallback Intent | 兜底意图 | 判不准时的默认去向（转人工最安全） |
| Retrieval Pollution | 检索污染 | 不相关问题硬检索凑块带偏答案 |
| Intent Classifier | 意图分类器 | 判来意的模型/规则（M13 分类器的复用） |

## 3. 动手实操：路由落地+对比实验

### 3.1 路由器实现（规则+分类器两级）

```java
// kb/service/IntentRouter.java
public Route route(AskRequest req) {
    // 第 1 级：规则快筛（毫秒级，拦最明显的）
    if (GREETING.matcher(req.question()).find())     return Route.GREETING;
    if (COMPLAINT.matcher(req.question()).find())    return Route.COMPLAINT;
    // 第 2 级：M13 分类器结果复用（工单系统已判过的 category）
    TicketCategory c = categoryClient.of(req.ticketId());
    return switch (c) {
        case CONSULT -> Route.KB;        // 知识问答 → 放行 RAG
        case REFUND  -> Route.FLOW;      // 退款类 → 业务流程链路（M13）
        case UNKNOWN -> Route.HUMAN;     // 判不准 → 兜底转人工（fail-safe）
        default      -> Route.HUMAN;
    };
}
// RagService 开头调 route()：非 KB 路由直接回对应话术，不进检索
```

## 4. 面试连接

**Q：为什么 RAG 前要做意图路由？怎么实现？（架构收口题）**
> 因为不是所有问题都该检索，全量检索是 RAG 最贵最糟的用法。闲聊硬检索会凑回不相关块答非所问；投诉类硬检索会背政策火上浇油，该走的是共情加转人工；库外问题反正要拒答，何必先花检索的钱。路由实现用两级门卫：第一级关键词正则毫秒级拦最明显的问候和投诉；第二级复用工单分类器的结果——项目四本来就设计成从分类器知识类分支接入，路由是免费送的，只需补一个判不准走人工的兜底，fail-safe 原则照旧。我们做过一百条混合请求对比：路由后闲聊投诉体验从答非所问变成得体应答，非知识类延迟快九成，总 token 省了四成上下，知识类答对率还持平略升——因为检索库不再被垃圾问题试探，也顺带提升了安全性。有个隐性设计值得强调：路由的兜底永远是转人工而不是硬答——判不准的问题宁可人接。意图路由本质是流量治理：让每类流量走它该走的链路，这是网关思想在 AI 应用里的落地，和 M13 的模型路由一脉相承。
