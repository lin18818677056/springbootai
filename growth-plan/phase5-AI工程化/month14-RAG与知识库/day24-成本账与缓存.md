## 1. 知识地图（先讲人话）

```
先算账（教程的成本模板，拿过来填实数）：
  单次问答 = 输入 + 输出
    输入 = 系统模板 300T + 检索父块 3×500 字 ≈ 2250T + 问题 50T ≈ 2600T
    输出 ≈ 500T
    合计 ≈ 3100T/次
  本地 Ollama：≈ 电费（但吃你机器的算力和耐心）
  API 模型（¥2/百万T 输入、¥8/百万T 输出为例）：
    2600T×0.000002 + 500T×0.000008 = ¥0.0092/次
    日 5000 次 = ¥46/天 ≈ ¥1380/月 → 这就是 RAG 的价格标签

再省钱——观察客服场景的特点：80% 的问题是 20% 的高频问题
  （"退款多久到账""怎么开发票"每天被问几百遍，答案一模一样）
  → 每次都检索+生成一遍 = 重复劳动 = 白烧钱

Q→A 缓存（问答对缓存）：
  问题进来 → 先查缓存 → 命中直接返回答案（检索+生成全省）
  → 未命中才走全链路 → 答完写缓存
  类比：客服的 FAQ 快捷回复——常问问题直接发话术，不用现想。
  两个实现档位：
  ① 精确匹配缓存：问题原文（去空格/标点归一化）做 key
     —— 简单、零误伤，命中率取决于用户问法的一致性
  ② 语义缓存（进阶）：问题先嵌入，和缓存里的问题算相似度，
     超阈值（如 0.95）就算命中
     —— 命中率高，但有"答非所问"风险（0.95 的相似度也可能是
     不同问题！如"不支持退货的场景"vs"支持退货的场景"）——
     day02 否定词软肋的缓存版翻车。规则：语义缓存阈值 ≥0.97
     且答案带"仅供参考"注脚，或只对 FAQ 类问题启用。

三层杠杆 RAG 版（M13 day20 的清单平移）：
  杠杆① 缓存：Q→A 缓存（今天）
  杠杆② 精简：检索块 Top3→按需 2 块（day18 旋钮B）；模板瘦身
  杠杆③ 路由：高频简单问题→小模型；疑难→大模型（明天 day25 联动）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| QA Cache | 问答缓存 | 问题→答案直接缓存（命中免检索免生成） |
| Semantic Cache | 语义缓存 | 按意思匹配缓存（阈值高才有安全） |
| Cache Hit Rate | 缓存命中率 | 百次问答里多少次直接吃缓存 |
| Normalization | 归一化 | 问题去空格/统一标点后再做 key（提高精确命中率） |
| TTL | 存活时间 | 缓存多久过期（政策类答案必须设！防过期知识） |
| Cost per Query | 单次成本 | 一问一答的 token 账（¥0.009 级别） |

三个工程细节（都是坑换来的）：

## 4. 面试连接

**Q：RAG 的成本怎么优化？缓存有什么坑？（省钱题+踩坑题）**
> 先算账再省钱：单次问答约三千 token，API 价约九厘钱，日五千次月成本一千四——这是 RAG 的价格标签，汇报就靠这笔账。优化三层杠杆。第一层问答缓存：客服场景八成问题是两成高频问题，问题归一化后做 key 精确匹配，命中直接返回，检索生成全省——实测命中率六成上下，命中响应快两个数量级。缓存有三个必须防的坑：key 必须带权限维度，否则部门答案串门；拒答不缓存，转人工不该被缓存固化；TTL 按敏感度分级，政策类答案必须短 TTL，否则撞上无声过期——缓存了旧政策比不缓存更糟。语义缓存是进阶档，按问题相似度命中，但阈值必须压到零点九七以上，否则撞上否定词翻车——支持退货和不支持退货相似度零点九，语义缓存会把相反答案发给用户，这是事故级坑。第二三层杠杆：检索块按需缩减、高频简单问题路由小模型。原则不变：先精确匹配这种无风险的，命中不够再上语义缓存，每层都有监控和回退。
