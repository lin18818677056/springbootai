# Day 08 · 系统设计六步法

> **今日目标**：把系统设计题从"自由发挥"变成"按图施工"——掌握通用六步法，用入门题"短链接系统"完整走一遍，为三场演练（day09~11）装上骨架。
> **时长**：方法 1.5h / 热身演练 1.5h / 输出 0.5h
> **今日产出**：六步法卡片 + 短链接系统完整设计稿（含图）

## 1. 知识地图（先讲人话）

```
系统设计题的本质：不是考"你知道多少组件"，
  是考"你怎么做技术决策"——像装修房子：
  错误姿势：进门就画水电图（上来就画架构图的候选人）
    ——没问预算、没问住几口人、没问采光要求，
      画得再漂亮也是猜
  正确姿势：先问清楚（六步法）：
  ┌────────────────────────────────────────────┐
  │ ① 需求澄清（5min）：盖住宅还是商场？             │
  │    功能需求 3~5 条 + 非功能（QPS/延迟/一致性）    │
  │ ② 容量估算（5min）：多少人用？多大盘子？          │
  │    QPS/存储量/带宽——算出数量级                   │
  │ ③ API 设计（5min）：对外的"服务窗口"长什么样？     │
  │ ④ 数据模型（5min）：库表怎么设计？怎么分？         │
  │ ⑤ 架构图（15min）：边画边讲（最长时间，画图特训 day13）│
  │ ⑥ 权衡与演进（10min）：瓶颈在哪？10 倍流量怎么办？  │
  └────────────────────────────────────────────┘
  每一步都在"收集约束→缩小方案空间"，
  六步走完，答案是自己长出来的，不是背出来的。

评分视角（面试官的打分表）：
  P6：六步都走全，方案能落地
  P7：每步都有权衡（"我选 A 因为…代价是…备选是 B"）
      + ⑥ 主动推演瓶颈和演进——不等面试官追问
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Functional / Non-functional | 功能/非功能需求 | "做什么" vs "做到多好"（QPS/延迟/可用性）——新手只看前者 |
| Back-of-envelope | 毛算估算 | 数量级心算（不用精确到个位，1 亿≠100 万就行） |
| Read/Write Ratio | 读写比 | 决定存储选型的第一指标（读多→缓存+副本，写多→分片+异步） |
| Trade-off | 权衡 | 系统设计的通货——每个决策都要说"代价是什么"（day05 五步骨架） |
| Bottleneck | 瓶颈 | 第⑥步的主菜——"当前方案先挂在哪里"主动说，别等追问 |

## 3. 动手实操（热身：短链接系统）

### 3.1 演练一：六步法完整走一遍短链接

```
题目：设计一个短链接服务（如 t.cn/xxxx → 长链接）
限时 45 分钟，边讲边写，全程录音，按六步走：

① 需求澄清（5min，先问 4 个问题再动笔）：
  功能：长转短 + 301/302 跳转 + （可选）访问统计
  非功能：读写比？→ 追问假设：读 100:1（跳转远多于创建）
  规模假设：创建 1 万 QPS / 跳转 100 万 QPS
  约束：短码长度？是否要求不可猜测？
  （话术："我先确认几个关键假设——生产环境先问清楚
   再动手，和面试里先澄清再画图，是同一个习惯"）

② 容量估算（5min）：
  写入：1 万/s × 86400s ≈ 8.6 亿条/年
  存储：8.6 亿 × 100B ≈ 86GB/年 → 单库三年内不慌，
        但按增长分 4~16 个库留余量
  读：100 万 QPS → 单机扛不住（Redis 单机 10 万级）→
      必须缓存 + 多副本
  带宽：跳转响应 1KB × 100 万 ≈ 1GB/s（心算即可）

③ API 设计（5min）：
  POST /api/shorten  {longUrl} → {shortCode}
  GET  /{shortCode} → 302 Location: longUrl
  （讲清 301 vs 302 的权衡：301 浏览器缓存省服务器流量，
   但丢失统计能力——业务要统计就用 302，又一个权衡点）

④ 数据模型（5min）：
  表：id, short_code(唯一索引), long_url, created_at
  短码生成三方案对比：
  A 哈希截断（MurmurHash 取前 7 位）——冲突要处理
  B 自增 ID + Base62——无冲突但可被遍历
  C 发号器预生成号段——高写入下最优
  我选 C（秒杀号段模式 M6 的迁移），代价是发号器要高可用

⑤ 架构图（15min，边画边讲）：
  接入层（网关+限流）→ 应用层（无状态水平扩容）→
  缓存层（Redis 集群，读主力，命中率 95%+ 假设）→
  存储层（MySQL 分 4 库，按 short_code 哈希）
  写路径：发号器取号 → 写库 → 写缓存
  读路径：缓存优先 → 未命中回源 → （可选）异步统计埋点

⑥ 权衡与演进（10min，主动说瓶颈）：
  当前瓶颈 1：缓存未命中穿透 → 空值缓存+布隆过滤器
    （M4/M16 弹药直接引用）
  当前瓶颈 2：统计埋点打满写入 → Kafka 异步+批处理
    （M5 案例）
  10 倍流量推演：缓存集群扩容 + 多机房容灾
  诚实边界：不讨论 301 在 CDN 边缘的进阶玩法，
    生产中我会先 POC 再定（演进口）
```

### 3.2 演练二：六步法自检卡制作

```
把六步法做成手掌大的卡（面试白板前瞄一眼用）：
  ① 问清楚（功能 3~5 / 非功能 / 规模 / 约束）
  ② 毛算账（QPS/存储/带宽，数量级即可）
  ③ 定接口（写清请求响应 + 一个语义权衡点）
  ④ 建模型（表结构 + 分片键 + 生成方案三选一对比）
  ⑤ 画图（左→右：接入/应用/缓存/存储，边画边讲）
  ⑥ 亮权衡（主动说两个瓶颈 + 演进 + 备选方案）
每步一个"禁手"提示：
  ① 忌上来就画图 ② 忌精确到个位 ③ 忌只写 happy path
  ④ 忌没有分片键 ⑤ 忌画完不讲话 ⑥ 忌说"没有瓶颈"
```

### 3.3 演练三：错题重放

```
重听录音，标出三类问题（每类至少找 1 处）：
  A 类·跳步：哪一步没走直接跳到画图？（最常见是①②）
  B 类·哑画：画图时超过 20 秒没说话？
  C 类·无权衡：哪些决策是"直接报答案"没有对比？
  把 A/B/C 各改写一遍话术（只改那一句，不改全局）
  ——微改比重讲有效，明天 day09 演练立刻用上。
```

### 3.4 思考题

为什么六步法把"需求澄清"排在"容量估算"前面，明明估算也是澄清的一部分？（提示：顺序就是心理暗示——把"问"排在"做"前面，你就很难犯"上来就画图"的错。更深层：需求澄清是在和面试官建立"协作关系"（你是来和我一起定义问题的），容量估算是你在展示"独立分析力"。先用协作定对方向，再展示分析力——顺序反了，分析力越强跑偏越远。这和 M17 的"先复述再执行"（任务四件套）是同一件事。）

## 4. 面试连接

**Q：给你一道系统设计题，你一般怎么开始？（开场白，决定面试官第一印象）**
> 我会先花五分钟澄清需求，因为同一个题目在不同约束下答案完全不同。比如设计短链接，我会先确认四个问题：核心功能边界（要不要统计）、读写比例（跳转通常远多于创建）、规模数量级（万级还是百万级 QPS）、有没有特殊约束（短码是否要防遍历）。确认后我会毛算一轮容量——数量级对不对决定后面所有选型。然后才进入 API、数据模型、画图，最后我一定主动讲瓶颈和演进，因为方案没有瓶颈是不诚实的。（→这段话本身就是一次"六步法预告片"，面试官会顺着你的框架走）

**Q：系统设计题答到什么程度算好？（元问题，考自我认知）**
> 我认为有三个层级：初级是"组件齐全"——把 Redis、Kafka 都堆上；中级是"决策有据"——每个组件都知道为什么选它、代价是什么；高级是"方案有生命"——主动指出当前设计的瓶颈、给出触发条件和演进路径。我的目标定在中级到高级之间：比如我设计秒杀系统时，库存扣减从数据库乐观锁演进到 Redis 原子扣减再到热点分桶，每一步演进都有压测数据驱动（5000 并发零超卖）——这不是一次画对的设计，是设计+验证+迭代的循环。
