# Day 04 · 题库冲刺：JVM 与并发

> **今日目标**：五大题库冲刺第一站——JVM 与并发 20 题限时自测；每题按"方法论+我的案例"双段作答；薄弱题回归对应月度文档补课。
> **时长**：自测 1.5h / 补课 1.5h / 输出 0.5h
> **今日产出**：20 题作答记录（✓/○/×）+ 薄弱题回归清单 + 案例话术卡

## 1. 知识地图（先讲人话）

```
本计划的面试答题总公式（18 个月一贯）：
  答案 = 方法论（通用原理）+ 我的案例（具体证据）
  光背方法论 = 八股选手（面试官下一层追问就倒）
  光讲案例 = 没有体系（面试官觉得你只会歪打）
  两者绑定 = "懂原理且真做过"的信号

JVM 与并发 20 题的五类分布（按面试出现频率）：
  内存区域与对象（3 题）：对象创建/内存分配/逃逸分析
  GC（5 题）：分代/收集器/G1与ZGC/调优参数/GC 日志排查
  并发基础（4 题）：JMM/volatile/synchronized 锁升级/AQS
  线程池（4 题）：参数/执行流程/拒绝策略/动态调优
  实战排查（4 题）：CPU 飙高/内存泄漏/OOM 分类/元空间
  （实战排查类是 P7 和 P6 的分水岭——必须有真实排障故事）

答题模板（每题 60~90 秒）：
  ① 结论一句话（10 秒）
  ② 原理展开（30 秒，讲机制不讲名词堆砌）
  ③ 我的案例（20 秒："我在 XX 项目里遇到过…"）
  ④ 边界/演进（10 秒："这个方案的局限是…更优路径是…"）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| JMM | Java 内存模型 | 多线程读写共享变量的"交通规则"（可见性/有序性/原子性） |
| Stop The World | 停顿世界 | GC 时业务线程全停的那一下——延迟问题的头号嫌疑犯 |
| Safepoint | 安全点 | 线程停靠检查点——GC 日志里"没停多久但等了很久"的真凶 |
| Escape Analysis | 逃逸分析 | 对象没跑出方法就在栈上分配——"new 很便宜"的底气 |
| Lock Elision / Bias | 锁消除/偏向锁 | 无竞争时把锁的成本降为零的优化（JDK15 后偏向锁移除） |

## 4. 面试连接

**Q：线程池参数你怎么定？（高频题，双段示范）**
> 方法论：先按任务类型估起点——CPU 密集约 N+1，IO 密集约 2N；但公式只是起点，真实参数靠压测：我会先看 P99 目标反推并发数，再观察队列堆积和拒绝率微调，最后上线后按动态调参留后手。我的案例：AI 客服那次压测，把池子从 50 调到 500 反而 P99 翻倍——瓶颈在下游模型推理，不是线程不够；最后按"下游容量÷单线程吞吐"定到合理值。这件事后来变成我团队的调参四连问，压测返工从月均 4 次降到 1 次。

**Q：线上服务突然 Full GC 频繁，你怎么排查？**
> 五步：一、先看监控确认范围（什么时候开始、和发布/流量有没有相关性）；二、GC 日志看 Full GC 的回收效果——回收后老年代占用降不下去=对象泄漏，降得快=流量或缓存问题；三、jstat/jcmd 看代龄分布定位嫌疑区；四、必要时候 dump 一份（live 只活对象）用 MAT 看支配树找大对象来源；五、修复后回归观察 GC 频率。我实际遇到的案例是缓存未设 TTL 导致老年代缓慢堆积——所以后来我团队规范里缓存必配 TTL+容量上限。
