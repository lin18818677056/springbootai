# Day 10 · 演练 2：实时风控系统

> **今日目标**：第二场演练——"设计一个实时风控系统"，重点练"数据流类"题目（和昨天的"平台类"不同的题型）；继续双向评分，积累第二份复盘。
> **时长**：演练 45min / 复盘 1.5h / 输出 0.5h
> **今日产出**：风控系统设计稿 + 双向评分表 + 数据流题骨架卡

## 1. 知识地图（先讲人话）

```
系统设计题的三大题型（每类骨架不同，别一招走天下）：
  平台类（day09 限流）：四个面——规则/执行/数据/观测
  数据流类（今天风控）：五段流——采集→接入→计算→
    存储→服务，像"自来水厂"：
    ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐  ┌─────┐
    │水源  │→│进水口 │→│滤池  │→│清水池 │→│用户龙头│
    │埋点  │  │Kafka │  │Flink │  │存储   │  │决策API│
    └─────┘  └─────┘  └─────┘  └─────┘  └─────┘
  AI 类（day11 客服）：三线并行——效果线/安全线/成本线

为什么风控题值得练（选题逻辑）：
  ① 你真做过：M10~M12 实时数仓（Flink/Kafka/ClickHouse）
     就是这套管道——风控只是"滤池里装的滤芯"不同
  ② 它是"延迟敏感+准确性敏感"双高压题——
     能考出你对权衡的驾驭（快 vs 准 vs 省不可能全要）
  ③ 秒杀项目的防刷（M6）也能串进来——跨项目讲故事
     是 P7 信号（有体系，不是一个点）

风控题的灵魂三问（面试官真正在考的）：
  ① 延迟预算怎么分？（风控要在下单前给出判断，
    留给你的可能只有 50ms）
  ② 误杀和漏放怎么权衡？（拦错好人损失 GMV，
    放过坏人损失本金——两个都要量化）
  ③ 规则变了怎么生效？（规则热更新+灰度——
    M17 的"没有卡点的规范落不了地"同理）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| CEP | 复杂事件处理 | 在事件流里找"套路"（1 分钟内同卡 5 笔=可疑）——Flink 的杀手锏 |
| Watermark | 水位线 | "我等到这儿了，再晚的事件不算数"——乱序数据的迟到裁决者 |
| Exactly-Once | 精确一次 | 风控扣分不重复不遗漏——Flink 检查点机制背书 |
| Feature Store | 特征仓库 | 给模型喂的"体检指标"（近 1 小时下单次数）——在线要快离线要全 |
| Gray Release | 灰度发布 | 新规则先放 5% 流量试跑——风控自己的"试用期" |

## 3. 动手实操（45 分钟全真演练）

### 3.1 演练一：限时实战（录音）

```
题目："设计一个电商实时风控系统：识别黄牛刷单、
  撞库登录、优惠券薅羊毛，决策延迟 P99 < 200ms，
  日均 10 亿事件量。"

六步法走位（数据流版）：
  ① 需求澄清（5min）：
    三类风险的准确率要求不同：撞库要快准狠（直接拦），
    刷单要证据链（先标记后人工复核），薅羊毛要柔性
    （限流+验证码）——先分桶再设计，这一步就是加分项
    决策预算拆解：总 200ms = 采集 20 + 计算 80 + 特征
    查询 50 + 决策 30 + 冗余 20（拆预算=工程师味十足）
  ② 容量估算（5min）：
    10 亿/天 ≈ 1.2 万 QPS 均值，峰值按 5 倍算 6 万 QPS
    Kafka 分区：6 万 QPS ÷ 单分区 1 万 = 至少 8~16 分区
    Flink 并行度 = 分区数对齐
    特征存储：活跃用户 1 亿 × 特征 50 个 × 100B ≈ 500GB
    → Redis 集群 + 淘汰策略（热特征才放）
  ③ API（5min）：
    决策接口（同步，风控判决）+ 规则管理接口 + 复核工作台
    亮权衡：同步接口失败时"放行 or 拦截"？
    ——fail-open 但降级到事后追责（风控版 day09 的选择）
  ④ 数据模型（5min）：
    事件主题分区键：user_id（保证同人事件有序进同一分区）
    特征表设计：窗口特征（1min/1h/1d 三档）
    决策记录表：谁/什么时候/命中什么规则/动作——
      可解释性是风控的生命线（拦了要能说清为什么）
  ⑤ 架构图（15min）：
    埋点 SDK → Kafka → Flink（清洗+CEP+特征计算）
      → 特征库 Redis + 决策引擎（规则+模型双轨）
      → 动作执行（拦截/验证码/放行）
    旁路：ClickHouse 存明细（M12 案例）→ 离线复盘 +
      规则效果回测 → 新规则 → 灰度 5% → 全量
  ⑥ 权衡演进（10min）：
    瓶颈 1：特征查询 50ms 预算 → 热特征本地缓存+
      Redis 兜底（和 day09 限流同构！主动指出这一点）
    瓶颈 2：CEP 状态膨胀 → TTL + 状态分桶
    误杀率演进：规则引擎（可解释）和模型（高召回）
      双轨并行，模型只做"建议者"不做"终审者"
    10 倍流量：Kafka/Flink 水平扩，预算重拆
```

```
自评分表（同 day09 五项 + 数据流专属两项）：
  □ 风险分桶了（不同风险不同策略，不是一刀切）
  □ 延迟预算做了拆解（每一毫秒都有去处）
  □ 容量估算出了数量级（分区/并行度有推导）
  □ 决策可解释性讲了（拦人要说得清）
  □ 主动讲了 2 个瓶颈+演进
  □ （数据流专属）分区键/乱序/水位线至少提了两处
  □ （数据流专属）在线离线双链路都画了（特征口径一致性）
  总分 ≥20 = P7 信号；15~19 = P6 稳；<15 = 复盘加练

AI 面试官追问三轮：
  Q1"事件乱序了怎么办？窗口统计会不会错？"
    → 水位线+允许迟到+侧输出流兜底（M12 有实验背书）
  Q2"规则引擎和模型打架听谁的？"
    → 双轨定位：规则是法律（硬约束可解释），模型是

  Q3"风控误杀大客户怎么办？"
    → 白名单分级 + 申诉通道 + 误杀率进监控大盘
      （量化：拦错 1 个大客户损失多少 GMV，讲账）
```

### 3.4 思考题

风控的决策记录（谁/何时/命中什么规则/什么动作）为什么是"生命线"而不是"锦上添花"？（提示：三个角色都靠它活——用户申诉时要靠它自证"我不是黄牛"；运营调规则时要靠它回测"新规则放多少漏多少"；出事故时要靠它还原"当时为什么拦了这单"。没有决策记录的风控=黑箱执法，业务方第一个造反。面试里主动讲这块的候选人极少——多数人只讲"怎么拦"，不讲"拦完之后"。而"拦完之后"才是生产系统的开始。）

## 4. 面试连接

**Q：实时计算里怎么处理乱序和延迟数据？（高频，M12 实验背书）**
> 三层处理：水位线声明"事件时间推进到哪了"，之后到的算迟到；给窗口设"允许迟到时长"（比如 5 秒），迟到不严重的事件照常计入并更正结果；再晚的进侧输出流单独落表，事后补偿。参数是权衡出来的：水位线拉太紧漏数据，拉太松结果出得慢。我的案例：M12 实时数仓做过对比实验，水位线从 2 秒调到 10 秒，结果准确率从 99.2% 升到 99.9%，但大盘延迟多了 8 秒——我们业务允许 30 秒延迟，所以取了 10 秒。这段的结论是：所有"工程参数"都是业务约束的翻译，不是拍脑袋。

**Q：风控系统的准确率和召回率怎么平衡？（经典权衡题）**
> 先把账算出来再谈平衡：拦错一个正常用户的代价（体验损失+可能的客诉流失）和放过一个黄牛的代价（羊毛损失，可量化成钱）——两个数字一摆，阈值就不是拍脑袋了。我的实践是双轨制：规则引擎管"实锤"（设备指纹黑名单、频次超限，宁可严），模型管"嫌疑"（只给分数不直接拦，高危进验证码而不是直接拒绝）。上线后用误杀率和召回率双指标看板监控，任何规则调整先灰度 5% 流量回测一周。这个"先算账再定阈值+灰度回测"的思路，和我做 AI 评测（M14 考卷）是同一套方法论——效果要用数据对冲，不能凭感觉。
