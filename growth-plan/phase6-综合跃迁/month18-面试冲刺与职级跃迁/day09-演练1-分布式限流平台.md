## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Sliding Window | 滑动窗口 | 比固定窗口"缝细"的计数法——削掉边界突刺 |
| Token Bucket | 令牌桶 | 发牌员按固定速度发牌，有牌才能过——允许突发 |
| Distributed Rate Limit | 集群限流 | 多台机器共用一个"总闸"——Redis+Lua 原子扣减 |
| Hot Spot Key | 热 key | 全部请求抢同一个计数 key——限流平台自己的限流难题 |
| Config Push | 配置下发 | 规则改了怎么让所有节点秒级生效（M17 规范推广同理：没有卡点的规范落不了地） |

## 3. 动手实操（45 分钟全真演练）

### 3.1 演练一：限时实战（录音）

```
题目（写在纸上看不到答案的位置）：
  "设计一个分布式限流平台：支持多维度限流规则
   （接口/用户/IP）、规则动态生效、集群级精确限流，
   10 万 QPS 规模。"

六步法走位（对照 day08 卡片）：
  ① 需求澄清（5min）：
    功能：规则 CRUD/多维度/动态下发
    非功能：限流判定延迟预算（<5ms！限流自己不能成瓶颈）
    规模：10 万 QPS/平台要服务 N 个业务方
    约束：SDK 能不能侵入业务方？（关键约束！）
  ② 容量估算（5min）：
    判定 10 万 QPS → Redis 单机 10 万级 = 危险线
    → 分片计数 or 本地预扣（引出③⑤的核心权衡）
    平台自身可用性：99.99%（限流挂了=全站裸奔 or 全站拒绝，
      讲 fail-open vs fail-close 的选择！）
  ③ API（5min）：规则管理接口 + SDK 接入接口
    亮权衡：同步判定返回"拒绝"的语义（429 + Retry-After）
  ④ 数据模型（5min）：
    规则表 + 计数结构（Redis Hash：key=维度+窗口）
    分片键设计：按业务方哈希避免所有流量挤一个 key
  ⑤ 架构图（15min）：
    管理端 → 配置中心（规则版本号）→ 各节点 SDK 拉取
    执行层：本地令牌桶预扣（吸收 90% 判定）+
      Redis+Lua 精确校正（解决漂移）——两层限流
    观测面：限流事件异步上报（M5 MQ 案例）
  ⑥ 权衡演进（10min）：
    瓶颈 1：Redis 热 key → 分片+本地预扣（讲漂移容忍度）
    瓶颈 2：规则下发延迟 → 版本号轮询→推送演进
    fail-open（ Redis 挂了放行，保可用）vs fail-close
      （拒绝，保下游）——按业务分级选
    10 倍流量：判定全本地化，Redis 只做校正
```

```
  Q1"本地预扣和 Redis 校正，漂移了怎么办？"

  Q3"限流平台自己挂了怎么办？"
    → fail-open/close 分级 + 平台自身多副本 + SDK 兜底
      本地规则快照（配置中心最后版本）
```

### 3.4 思考题

限流平台自己的可用性设计（fail-open vs fail-close）为什么是这道题的"隐藏考点"？（提示：面试官通过它看你有没有"系统也会病"的敬畏心——设计保护别人的人，最容易被忽略的就是保护自己。fail-open 保可用但下游可能被打挂，fail-close 保下游但平台抖动就全站拒绝——这个选择没有标准答案，只有业务分级答案：核心交易选 fail-close（宁可拒绝不可超卖），边缘查询选 fail-open（宁可多扛不可白屏）。能讲出"分级"的候选人，才真理解限流。）

## 4. 面试连接

**Q：集群限流怎么实现？单机限流有什么坑？（必考题，双段示范）**
> 方法论：单机限流的问题是 N 台机器就是 N 倍额度，全局必然超卖；集群限流用 Redis+Lua 做原子"读-判-扣"，Lua 保证多步操作不被并发插队。但全集中式有两个代价：网络 RTT 加进判定路径（我的预算是 5ms，Redis P99 就 2ms，太挤）、热 key 把 Redis 打成瓶颈。所以我的方案是两层：本地令牌桶预扣吸收大部分判定，Redis 低频校正防漂移——用 5% 的精度损失换 90% 的延迟下降。我的案例：M6 网关改造时压测过全集中式，10 万 QPS 下 Redis CPU 80% 险些被打挂，切两层架构后 Redis CPU 降到 15%，判定 P99 稳定在 3ms 内。

**Q：限流算法那么多，你怎么选？（五步骨架示范）**
> 共同目标都是"控制速率保护下游"；差异在特性：固定窗口最简单但有边界突刺（两个窗口交界处可能放行 2 倍），滑动窗口平滑但计数成本高，令牌桶允许突发最贴真实流量，漏桶强制恒速适合保护脆弱下游。我的场景是开放 API 网关，调用方有突发需求，所以选令牌桶；对内部脆弱的下游适配层，我用漏桶。代价是令牌桶要调两个参数（速率+桶深），我靠压测定参不拍脑袋——M16 调参四连问就是这么来的。如果调用方从"突发"变成"恒速大客户"，我会切漏桶。
