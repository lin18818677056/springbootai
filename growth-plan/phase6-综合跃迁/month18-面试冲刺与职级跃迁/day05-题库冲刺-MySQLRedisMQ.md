# Day 05 · 题库冲刺：MySQL、Redis 与 MQ

> **今日目标**：题库第二站——MySQL/Redis/MQ 20 题限时自测；重点打磨"为什么这么设计"类权衡题；薄弱题回归补课。

> **今日产出**：20 题作答记录 + 薄弱题回归清单 + 权衡题话术卡

## 1. 知识地图（先讲人话）

```
三大件题目的命题规律（看清考什么）：
  MySQL 考"数据对不对+快不快"：索引原理/事务隔离/锁/调优
  Redis 考"快+一致性"：数据结构/持久化/缓存三兄弟/集群
  MQ 考"不丢不重+顺序"：可靠投递/幂等/顺序/堆积处理
  三者的公共考点：一致性权衡（强一致 vs 最终一致）
  ——这是分布式永恒主题，答案永远是"看场景"，
  但必须能讲出"我选的场景和代价"。

权衡题的万能骨架（高频题型："为什么用 A 不用 B"）：
  ① 先讲共同目标："两者都能解决 X 问题"
  ② 再讲差异维度："A 在 … 上强，B 在 … 上强"
  ③ 给我的场景和选择："我的场景是 …，所以选 A"
  ④ 交代代价："选 A 的代价是 …，我的缓解是 …"
  ⑤ 留演进口："如果场景变成 …，我会切到 B"
  （五步全有 = P7 信号；直接报答案 = P6 封顶）

高频陷阱题预警（本计划踩过的坑就是弹药）：
  "缓存和 DB 双写不一致怎么办？" → 别背"延迟双删"就完，
    讲你 M4 的方案对比和最终选型理由
  "消息丢失怎么办？" → 三段各聊一段（发/存/收），
    M5 的事务消息实验就是你的案例
  "Redis 为什么快？" → 别只说内存，讲单线程避锁+IO 多路复用
    +高效结构三层
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| MVCC | 多版本并发控制 | 读写不互相堵的"快照魔法"（Undo Log 版本链） |
| Cache Penetration/Breakdown/Avalanche | 缓存穿透/击穿/雪崩 | 查不存在的/热点过期/集体过期——三大高频故事源 |
| Idempotency | 幂等 | 同一操作执行多次结果不变——MQ 消费的保命符 |
| Half Message | 半消息 | RocketMQ 事务消息的"先挂起再确认"机制（简历写了就会被问） |
| Raft | 共识算法 | Redis Cluster/etcd 的选主基础——讲集群绕不开 |

### 3.2 演练二：权衡题五步骨架演练

```
抽 3 道权衡题用五步骨架完整作答（录音）：
  题 1"为什么用 RocketMQ 不用 Kafka？"
    我的场景答案：业务消息+事务消息需求（Kafka 无事务消息
    语义），代价是吞吐低于 Kafka，缓解是业务量没到瓶颈，
    演进口：日志/流式场景切 Kafka。
  题 2"为什么本地缓存+Redis 两级？"
    目标：抗热点 key；差异：本地快但不一致、Redis 一致但
    有网络；选择：秒杀库存读走本地+短 TTL；代价：短暂
    不一致窗口，缓解：库存扣减走 Redis 原子操作不走本地。
  题 3"为什么分库分表用 user_id 不用 order_id？"
    用户维度查询占 80%，按查询主维度分片；代价：订单维度
    跨片查询，缓解：异构一份按单号索引的表（canal 同步）。
自检：五步齐了吗？有没有直接跳到答案？
```

## 4. 面试连接

**Q：缓存和数据库的双写一致性，你怎么处理？（高频权衡题）**
> 我对比过四种主流方案：先更 DB 再删缓存（最常用，有小概率旧读）、延迟双删（缓解读并发回填）、订阅 binlog 异步删（解耦不侵业务）、分布式锁串行化（强一致但吞吐低）。我的场景是商品详情，允许秒级不一致，所以我选 binlog 订阅方案——业务代码零侵入，代价是删除有延迟，我用"更新时写一个短 TTL 的旧值标记"把窗口压到可接受。如果是对账类强一致场景我会直接上锁或干脆不用缓存——一致性和性能从来是交换，不是兼得。

**Q：怎么保证消息不被重复消费？**
> 我的原则是"至少一次投递+消费端幂等"，不去赌恰好一次。幂等三层做法：天然幂等的（set 类操作）直接用；不能天然幂等的用业务唯一键做去重表或状态机（订单状态流转天然防重）；批量场景用 Redis setnx 做短窗口去重兜底。我在秒杀项目里扣减库存就是状态机幂等：每个请求带唯一 ID，表里存在就直接返回上次结果——重复消息来了也不多扣。
