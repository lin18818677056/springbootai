# Day 25 · 全链路压测报告：整体到底快了多少

> **今日目标**：回答 W4 预习题——单点优化数字不能相加，整体提速必须全链路重测；产出项目六的正式压测报告（改造前后全对比 + 容量结论）。
> **时长**：压测 1.5h / 报告 1.5h / 输出 0.5h
> **今日产出**：《Agent 性能优化压测报告 v1》

## 1. 知识地图（先讲人话）

```
为什么单点数字不能相加？
  优化点①说"工具段省 180ms"、②说"留痕省 44ms"——
  相加 = 省 224ms？错！三个原因：
  ① 阿姆达尔定律：省的是占比不同的部分，上限受未优化部分约束
    （模型推理占 60~70%，我们最多在剩下 30~40% 里做文章）
  ② 相互影响：并行后两个工具同时打数据库，单工具的耗时
    可能比串行时更久（资源竞争）；GC 调优后整体抖动减少，
    也间接改善所有段落
  ③ 长尾不同于均值：P99 的改善曲线和平均值完全不同步
  结论：整体效果只有一条路——全链路重新压测对比。

报告五段式（写正式报告的骨架，也是面试讲项目的骨架）：
  ① 环境与方法（硬件/JVM 参数/压测工具/数据量——可复现性）
  ② 基线（改造前四档并发：吞吐/P50/P99）
  ③ 结果（改造后同口径对比 + 分桶细分）
  ④ 结论（提速多少、拐点移动、容量结论）
  ⑤ 遗留（未优化项与原因——诚实传统）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| E2E (End-to-End) | 端到端 | 从用户发请求到收到答案的全链路 |

### 3.2 分桶细分（M15 口径延续）

```
按会话轮次分桶（1 轮 / 2~4 轮 / 5+ 轮）各看 P50/P99：
  预期：5+ 轮桶改善最明显（多轮 = 工具调用次数多 = 并行红利放大；
  每轮留痕次数多 = 异步红利放大）——轮次越多优化越值钱
按问题类型分桶（单工具 / 双工具 / 含审批流程）：
  预期：双工具桶 -45% 左右；含审批桶改善小（审批是同步直写，
  高危路径故意没优化——安全优先）
```

## 4. 面试连接

**Q：你说优化了 40%，这个数字怎么来的？**
> 全链路压测对比：同机同口径四档并发，改造前后各测，取三次中位数，5 轮会话 P99 从 __ 降到 __。我不会用单点数字相加——工具段省的和留痕段省的有重叠（阿姆达尔），并行还会引入资源竞争的抵消，所以整体必须重测。报告里也写了遗留：模型推理占大头我们没法动，这是口径诚实。

**Q：容量怎么定的？**
> 压测找拐点（吞吐不再涨、P99 起飞的那档），生产安全并发 = 拐点 × 0.7 留余量。再结合日报持续观察——容量不是测一次定终身，回归卡点（day27）会防它悄悄变差。
