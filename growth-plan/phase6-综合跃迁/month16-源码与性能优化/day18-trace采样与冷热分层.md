> **今日目标**：给全量 trace 上采样策略（该全的绝不丢、可丢的按比例）；设计冷热三级存储；给出存储对比数字（目标：日增降 70%）。

## 1. 知识地图（先讲人话）

```
问题回顾（M15 交接卡②）：
  全量 trace 日增几十 MB，7 天几百 MB，查询越来越慢。
  但"全量"真的必要吗？——想清楚数据的价值密度：
  审批/退款 trace（出了事要翻账的）   → 一条都不能少
  出错的 trace（排查问题的金矿）     → 全存，排障刚需
  正常轮次 trace（99% 的日常）       → 存 10% 足够看趋势
  ——价值分级采样，不是拍脑袋砍。

采样策略（TraceSampler 三条规矩）：
  ① 白名单全存：isCritical()（审批/退款）+ 出错的 → 100%
  ② 普通轮次：10% 概率采样（哈希取模，稳定可复现：
     sessionId.hashCode() % 10 == 0 —— 同一会话要么全存要么全不存，
     保证"单个会话可回放"）
  ③ 降级联动：系统繁忙（队列水位高）时普通采样降到 1%
    ——跟 day13 的丢弃计数器联动（降级决策表思想延续）

冷热分层（三级仓库）：
  热（0~7 天）：PG 主表 agent_trace，明细全文，查询毫秒级
  温（8~30 天）：agent_trace_summary 摘要表
    （只留 question/轮次/耗时/工具名列表/错误码——千字节级）
  冷（31 天+）：JSON.gz 压缩归档到文件/对象存储
    （压缩率 ~85%，要翻旧账时解包看，接受分钟级）
  类比：银行流水——近 7 天手机秒查明细；近 30 天转总账看汇总；
  去年的去档案室调纸质卷宗。

配套动作：
  定时任务：每天凌晨把第 7 天的明细"瘦身"成摘要并归档原文
  查询路由：TraceQuery 按时间段自动路由到热/温/冷表
  ——用户查"上周的会话"无感（摘要也够看），要全文才解冷档
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Sampling | 采样 | 不是每条都记，按价值密度记 |
| Consistent Sampling | 一致性采样 | 同一会话要么全记要么全不记（可回放的前提） |
| Hot / Warm / Cold Tier | 热/温/冷分层 | 常用放快的、旧的放便宜的 |
| Data Lifecycle | 数据生命周期 | 数据的一生：产生→热存→摘要→归档→销毁 |
| Compaction | 压实/归档 | 把老的搬走压小，给热区腾地方 |

## 3. 动手实操

### 3.1 TraceSampler（落地代码，30 行内）

```java
public class TraceSampler {
    private final AtomicInteger queueWatermark = () -> 0;  // day13 队列水位注入

    public boolean shouldPersist(Trace t) {
        if (t.isCritical() || t.isError()) return true;          // 白名单全存
        int divisor = queueWatermark.get() > 5_000 ? 100 : 10;   // 降级联动
        return Math.floorMod(t.sessionId().hashCode(), divisor) == 0;  // 一致性采样
    }
}
// 接入点：AsyncTraceWriter.save() 开头先问采样器，
// 不该存的直接 return（连队列都不进——省内存才是真省）
```

## 4. 面试连接

**Q：日志/trace 数据量太大怎么办？**
> 三板斧按顺序：①源头采样（价值分级：高危+错误全存、普通一致性采样 10%，繁忙时降到 1%）；②生命周期分层（热 7 天明细、温 30 天摘要、冷档 gzip，压缩率 85%）；③写入端异步批量（day13 的记账员）。三招落地后日增降 70%+，查询 P99 反而更好（热区变小）。关键设计点是一致性采样保证"单个会话仍可回放"。

**Q：采样会不会漏掉关键问题？**
> 两个保险：错误和高危全存——排障需要的都在；留痕的"链路完整性"靠一致性采样（同一会话全存全不存）。再补一层业务兜底：审批/退款有独立审计表（day13 高危直写），trace 只是观测数据不是审计数据——职责分清就不怕。
