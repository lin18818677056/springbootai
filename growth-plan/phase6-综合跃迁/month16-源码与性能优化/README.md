# Month 16 · 源码与性能优化（M16）

> **本月一句话**：告别"感觉这里慢就改哪里"，学会用测量说话——先体检（基线/火焰图）再开方（优化），每个数字都有出处，每个优化都有前后对比。
> **主战场**：拿 M15 的 Agent 项目当"病人"——它有真实瓶颈（循环延迟、trace 同步写、存储膨胀），本月把它治好并留下全套病历。

## 1. 开场先讲人话：性能优化 = 看病

```
乱开药的程序员（反面教材）：
  "听说加缓存快" → 加缓存
  "听说池子调大好" → 池子从 10 调到 100
  "听说换了 GC 快" → 换 ZGC
  结果：更快了？更慢了？不知道——因为从头到尾没测过。

会看病的医生（本月套路）：
  ① 问诊定目标（哪里慢？多慢算慢？用户感知还是机器感知？）
  ② 化验测基线（火焰图/jstat/压测——病灶在哪、有多重）
  ③ 开方动手术（针对病灶下手，一次只改一个变量）
  ④ 复查做对比（改完再测一遍，数字说话，写进台账）

M15 交接卡（上月的病历）：
  ① Agent 每轮循环 = 拼 Prompt→调模型→解析→执行工具→回填，
    轮次多延迟线性涨，且留痕是同步写——主链路被磁盘拖累
    → 本月：并行工具调用 + 虚拟线程 + 流式中间帧 + 异步写入
  ② agent_session 全量 trace 日增几十 MB，7 天几百 MB
    → 本月：采样策略 + 冷热分层 + 查询优化
```

## 2. 核心心法三句（本月反复出现）

```
① 没有测量的优化 = 瞎吃药（JMH 死代码消除/预热不足会骗过你）
② 池子不是越大越好（线程/队列/缓存全是权衡，不是玄学加法）
③ 优化的终点是台账不是玄学（基线→瓶颈→改造→复测，四格缺一不可）
```

## 3. 四个硬指标（月底验收要对数字）

```
① Agent 循环 P99：基线 → 目标降 40%（并行工具调用贡献大头）
② trace 写入：同步写拖主链路 → 异步化后主链路增量 < 1ms
③ trace 存储：全量 → 采样+冷热分层后降 70%，查询 P99 不劣化
④ GC：Agent 服务 G1 调参后 P99 暂停 < 50ms（有 GC 日对比）
```

## 4. 八条验收标准（day30 逐条对账）

```
1. 能讲清"先测量后优化"，并举一个"白干优化"反例（JMH 预热/死代码）
2. 会用 JFR/Arthas 把 Agent 循环延迟归因到具体一步（毫秒级证据）
3. ThreadPoolExecutor execute 三步能白板写，说清参数何时生效何时失效
4. 虚拟线程改造并行工具调用：有前后对比数字，能讲 pinning 坑
5. trace 异步写入落地：有界队列+批量落盘+拒绝策略，讲清为什么不丢关键日志
6. trace 采样+冷热分层落地：给出存储对比数字与查询 P99
7. G1 调优一次实战：调参前后 GC 日对比，能讲为什么这么调
8. 性能台账至少 3 个优化点，每个都有"基线→瓶颈→改造→复测"四格证据
```

## 6. 环境准备（延续 M15，新增三样）

       （+ jmh-generator-annprocess），微基准统一放 src/jmh 下
新增② Arthas：curl -O https://arthas.aliyun.com/arthas-boot.jar（Windows 可直接 java -jar 启动）

       替代——功能等价（都是采样热点），面试口径照讲不虚。
