# Day 01 · 为什么优化总是白干

> **今日目标**：先答 M15 交接卡两道思考题（本月的第一件事）；认清三种"白干优化"；给 Agent 循环测出第一个基线——本月一切数字都从今天这条基线开始对比。
> **时长**：理论 1h / 实操 1.5h / 输出 0.5h
> **今日产出**：交接卡作答 + Agent 循环分段计时基线表

## 1. 知识地图（先讲人话）

```
M15 交接卡两道思考题（开工第一课，先答后翻）：

① Agent 循环为什么会越来越慢？每轮都在干什么？
   答：每轮 = 拼 Prompt → 调模型 → 解析 → 执行工具 → 回填历史。
   两个"偷时间"的地方：
   a) 工具是串行执行的——查订单 200ms + 查库存 200ms = 400ms，
     但这俩毫无依赖，本可以并行只要 200ms（差一倍的活）
   b) 留痕是同步写的——每轮干完活还要停下来把 trace 写进数据库，
     相当于服务员每上一道菜都先去记账房登记一趟
   解法（本月路线）：并行工具调用（day11）+ 异步写 trace（day13）

② trace 全量存储为什么撑不住？
   答：每轮 trace 存 think+act+observation 全文，一个 5 轮会话
   就几十 KB；1000 个会话/天 ≈ 日增几十 MB，7 天几百 MB，
   数据库表越来越大，查询越来越慢，备份越来越疼。
   解法：采样（不是每条都存全量）+ 冷热分层（近的存快的、
   远的存便宜的）→ day18 落地。

三种白干优化（对号入座，你中过几枪）：
  ① 没测就改：听说加缓存快，加了——加在哪了？快了多少？不知道
  ② 改了没复测：改完"感觉顺了"就上线（感觉是世界上最不可靠的监控）
  ③ 改错地方：80% 的请求走 A 路径，你优化了没人走的 B 路径

四步法（本月所有优化的固定动作）：
  定目标（多快算快？）→ 测基线（现在多快？）→ 改一处（一次只改
  一个变量）→ 复测对比（数字说话，写进台账）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Baseline | 基线 | 优化前的"原始成绩单"，没它你无法证明自己变快了 |
| Bottleneck | 瓶颈 | 排队最长的那一环——整个系统的速度由它决定 |
| Profile | 剖析 | 给程序做"CT 扫描"，看时间都花在哪个器官上 |
| Latency / Throughput | 延迟 / 吞吐 | 一个用户等多久 / 一秒能服务多少人（两者常打架） |
| Amdahl's Law | 阿姆达尔定律 | 你再怎么优化占 10% 的部分，整体最多快 11%——优化要挑大头 |

> **阿姆达尔定律必须懂**（一句话版）：整体提速上限 = 1 / (没优化的占比)。如果模型推理占 90% 时间，你把工具调用优化到 0，整体也只快 10%。这就是为什么本月要先用火焰图**找到大头再动手**。

## 3. 动手实操：给 Agent 循环测第一个基线

### 3.1 分段计时（最朴素的性能测量）

```java
public class LoopBaseline {
    record Seg(String name, long ms) {}

    public static void main(String[] args) throws Exception {
        // 模拟 M15 的 Agent 一轮：五步分别计时
        long t0 = System.nanoTime();
        String prompt = buildPrompt();                  // ① 拼 Prompt
        long t1 = System.nanoTime();
        String resp = callLLM(prompt);                  // ② 调模型（本地 Ollama）
        long t2 = System.nanoTime();
        var call = parseIntent(resp);                   // ③ 解析
        long t3 = System.nanoTime();
        String obs = callTool(call);                    // ④ 执行工具（查库/检索）
        long t4 = System.nanoTime();
        TraceWriter.saveSync(buildTrace(...));          // ⑤ 同步写留痕（M15 现状）
        long t5 = System.nanoTime();

        List.of(new Seg("拼Prompt", (t1-t0)/1_000_000),
                new Seg("调模型",  (t2-t1)/1_000_000),
                new Seg("解析",    (t3-t2)/1_000_000),
                new Seg("执行工具",(t4-t3)/1_000_000),
                new Seg("同步留痕",(t5-t4)/1_000_000))
             .forEach(s -> System.out.printf("%-8s %6d ms%n", s.name(), s.ms()));
        // 预期结论：调模型占大头（本地 7b 模型秒级），但工具 200~400ms
        // 和同步留痕几十 ms 是"我们能控制的部分"——优化对象就锁它们
    }
}
```

## 4. 面试连接

**Q：讲讲你的性能优化方法论？**
> 四步：定目标、测基线、单变量改造、复测对比。我会强调两头——动手前先测基线（不然不知道改哪），改完必须复测（不然不知道有没有用），中间用火焰图找大头而不是凭感觉。我拿 Agent 循环做过实战：测量发现工具串行和留痕同步写是可控大头，并行化后 P99 降了约 40%（day23 有数字）。

**Q：怎么判断一个优化值不值得做？**
> 两个问题：①它砍的时间占总时间多大比例（阿姆达尔定律，砍小头没意义）；②改造成本和维护风险多大。我踩过的坑是早期给没人走的代码路径加缓存——白干，后来养成习惯：先看流量分布再动手。
