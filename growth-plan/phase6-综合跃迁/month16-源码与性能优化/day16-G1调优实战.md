# Day 16 · G1 调优实战：给物业下停顿承诺

> **今日目标**：完成台账优化点④——给 Agent 服务调 G1 参数，把 GC P99 暂停压到 50ms 内；顺手解决 trace 大 JSON 的 Humongous 隐患。
> **时长**：理论 0.5h / 实操 2h / 输出 0.5h
> **今日产出**：调参前后 GC 对比报告 + 大对象治理记录

## 1. 知识地图（先讲人话）

```
GC 调优的正确姿势（先立规矩再动手）：
  ① 调优目标永远是"业务指标"不是"GC 指标"：
     "P99 暂停 <50ms" 的背后是"用户不感知卡顿"
  ② 大多数 GC 问题 = 分配速率问题 ≠ 收集器问题：
     少造垃圾 > 换收集器 > 调参数（优先级从高到低）
  ③ 一次只动一个参数，压测复测对比（老规矩）

三个最常用的 G1 参数（人话版）：
  -Xms = -Xmx（堆上下一样大）
    → 避免"扩容抖动"：出租屋面积不变，不用频繁搬家装修
  -XX:MaxGCPauseMillis=50（停顿目标，默认 200）
    → 给物业下承诺：检修单次最多 50 分钟。
    副作用：目标越小，单次扫的格子越少，扫的次数越多，
    总吞吐略降——延迟和吞吐的取舍（day02 的老朋友）
  -XX:G1HeapRegionSize（格子大小，默认自适应 1~32MB）
    → 格子的一半 = Humongous 门槛。想减少大对象进老年代，
     可以适当调大格子（比如 trace 大 JSON 常见 2MB → 格子 8MB）
    但格子太大也会降低并行度——权衡！

Humongous 大对象（今天的重点隐患）：
  对象 ≥ 格子一半 → 直接进老年代区（连续多格）
  我们的场景：trace 的 think 全文 JSON 可能几 MB —— 正中靶心！
  后果：老年代频繁被大对象污染 → Mixed GC 压力大 → 停顿恶化
  治理三板斧：
  ① 从源头减：trace 采样+摘要（day18 正好治这个）
  ② 存储格式减：JSON→压缩/截断 think 字段上限
  ③ 参数兜底：G1HeapRegionSize 调大让大对象"配得上正常格子"
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Allocation Rate | 分配速率 | 每秒造多少新对象——GC 压力的根源指标 |
| Mixed GC | 混合回收 | G1 的"小扫除+顺带扫部分老年代格子" |
| Humongous Allocation | 巨型分配 | 大对象直接进老年代的"特殊通道" |
| GC Pause | GC 暂停 | STW 时长——用户卡顿的直接来源 |
| Throughput vs Latency | 吞吐 vs 延迟 | 扫得彻底 vs 停得短暂，永恒取舍 |

### 3.4 思考题

-Xms 和 -Xmx 设成一样有什么代价？（提示：堆常驻内存，机器上其他进程可用内存变少；好处是无扩容抖动。服务器专属进程=设一样；混部小服务=留弹性。没有标准答案，只有场景匹配——这题考的是"知道取舍"）

## 4. 面试连接

**Q：GC 调优的思路？**
> 三层优先级：先减分配速率（少造垃圾，我们截断 trace 大字段后 Humongous 分配降了九成）；再调收集器行为（G1 的 MaxGCPauseMillis 定到 50ms，P99 停顿从 __ 降到 __）；最后才考虑换收集器。全程压测对比、一次一个变量——和性能优化的四步法是一套纪律。

**Q：MaxGCPauseMillis 调小有什么代价？**
> G1 会减少单次回收的 Region 数来兑现停顿承诺，代价是回收更频繁、总吞吐下降、并发标记可能跟不上分配速度。我会实测三档（200/50/20）找"甜点位"，我们的结论是 50——再小的话 YGC 次数上升吃掉了收益。能讲出这个权衡，说明调过而不是背过。
