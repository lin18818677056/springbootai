### 3.3 查询路由（30 行）

```java
public TraceView query(String sessionId, Instant time) {
    if (time.isAfter(Instant.now().minus(7, ChronoUnit.DAYS)))
        return hotRepo.findDetail(sessionId);            // 热：明细全文
    if (time.isAfter(Instant.now().minus(30, ChronoUnit.DAYS)))
        return warmRepo.findSummary(sessionId);          // 温：摘要
    return coldRepo.unarchive(sessionId);                // 冷：解档（分钟级）
}
// 用户无感的关键：TraceView 统一视图 + 明细/摘要共用字段对齐
```

### 3.4 思考题

为什么删除明细要分批（每批 5000）而不是一条 DELETE 全清？（提示：大事务 = 长锁 + undo 膨胀 + 主从延迟飙高；分批 + sleep 让复制链路喘气。这是"大表操作"的通用常识，面试数据治理场景常考）

## 4. 面试连接

**Q：你的 trace 存储治理最终效果？**
> 三层组合：写入端异步批量（day13）、价值分级采样（正常 10% 一致性采样、错误和高危全存）、三级生命周期（热 7 天/温 30 天摘要/冷 gzip 归档）。等比模拟 1 万会话实测：热区从全量 ___MB 降到 ___MB（约 -80%），近 7 天查询 P99 不劣化反降。关键设计是一致性采样保住"单会话可回放"，归档任务带水位线幂等。

**Q：数据治理时怎么保证搬家不出错？**
> 四道检查：数量对账（搬走数=摘要数=归档数）、幂等（水位线，重复跑零副作用）、分批删（5000 一批防长事务）、可观测（每次任务的行数和耗时都留日志）。思路和发版纪律一样：可回滚、可验证、可观测。
