# Day 02 · 性能指标与 P99：平均值是骗子

> **今日目标**：搞懂为什么大厂监控都看 P95/P99 不看平均值；学会自己算分位数；理解"长尾"才是用户流失的元凶。
> **时长**：理论 1h / 实操 1.5h / 输出 0.5h
> **今日产出**：分位数计算脚本 + Agent 基线数据的 P50/P95/P99 报告

## 1. 知识地图（先讲人话）

```
平均值骗人的经典例子：
  100 个请求：99 个 50ms，1 个 9500ms
  平均值 = (99×50 + 9500) / 100 = 144ms   ← 看起来"挺好"
  真相：每 100 个用户就有 1 个等了近 10 秒！
  如果这是下单接口，这个用户大概率流失——
  而且他身边可能还有 5 个人听他骂你。

分位数（Percentile）：把所有请求按耗时排队，站在不同位置看
  P50 = 排队站中间那个人的耗时（一半人比他快）
  P95 = 排队第 95% 位置的耗时（95% 的人比它快）
  P99 = 排队第 99% 位置的耗时（最慢的 1% 里的"门槛"）
  站得越靠后，越能暴露长尾问题。

为什么看 P99 而不是 P100（最大值）？
  最大值可能是意外（GC 停一下/网络抖一下/有人拿调试器连上了），
  单点波动没代表性；P99 稳定存在说明"真的有一批请求持续很慢"。
  大厂常见口径：看 P99 + 慢请求绝对数（1% 的量乘以日请求量，
  往往还是个惊人的数）。

长尾与用户体验（数字背下来，面试能用）：
  Google 曾报告：搜索延迟从 400ms 增到 900ms，流量降 20%
  Amazon：延迟每加 100ms，销售额约降 1%
  结论：伤害用户的是"最慢的那批请求"，不是平均值。

延迟和吞吐的关系（常见误区）：
  "加线程吞吐就高"——对，但队列排起来延迟也涨了；
  吞吐和延迟是一根管子的两端，优化要看你承诺的是哪个指标。
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Percentile | 分位数 | 全体排队，看第 N% 位置的耗时 |
| Tail Latency | 长尾延迟 | 最慢那一小撮请求——用户流失的真凶 |
| RT (Response Time) | 响应时间 | 通常讨论的就是延迟，别跟吞吐混着说 |
| Outlier | 离群点 | 慢得离谱的个别请求（先查意外再查规律） |
| Histogram | 直方图 | 按耗时区间数个数——比只存平均值诚实得多 |

## 3. 动手实操：自己算 P99

### 3.1 手写分位数统计（30 行，理解原理别只会调库）

```java
import java.util.*;

public class Percentile {
    /** 最朴素实现：排序取位置（数据量大时换 t-digest/HdrHistogram） */
    static long percentile(List<Long> latencies, double p) {
        List<Long> sorted = new ArrayList<>(latencies);
        Collections.sort(sorted);
        int idx = (int) Math.ceil(p / 100.0 * sorted.size()) - 1;
        return sorted.get(Math.max(0, Math.min(idx, sorted.size() - 1)));
    }

    public static void main(String[] args) {
        // 造数据：99 个 50ms + 1 个 9500ms（复现"平均值骗人"）
        List<Long> data = new ArrayList<>();
        for (int i = 0; i < 99; i++) data.add(50L);
        data.add(9500L);

        double avg = data.stream().mapToLong(Long::longValue).average().orElse(0);
        System.out.printf("平均   %8.1f ms  <- 骗子%n", avg);
        System.out.printf("P50    %8d ms%n", percentile(data, 50));
        System.out.printf("P95    %8d ms%n", percentile(data, 95));
        System.out.printf("P99    %8d ms  <- 真相%n", percentile(data, 99));
        // 预期输出：平均 144.1 / P50 50 / P95 50 / P99 9500
    }
}
```

## 4. 面试连接

**Q：为什么你们监控看 P99 不看平均值？**
> 因为平均值对长尾不敏感——99 个快请求能把 1 个超慢请求的痛苦完全抹平，但用户是按自己那次体验打分的。我们看 P99 定位系统性长尾，再看慢请求绝对数评估影响面。我在 Agent 项目里就是这么定位到留痕写入拖长尾的：均值看不出来，P99 一看全是它。

**Q：P99 很高但 P50 正常，说明什么？**
> 说明少数请求路径上有系统性问题，不是整体变慢。排查思路：按特征分桶（参数/用户/时间段/机器）找出慢的那一撮的共同点——可能是缓存未命中、走了一条冷代码路径、或者数据量大的特定请求。我实操过：按轮次数分桶后发现 5 轮以上的会话 P99 爆炸（M15 的轮次感知压测思路）。
