# Day 26 · 性能故障演习：给系统点一把火

> **今日目标**：延续 M12~M15 的点火纪律第五季——人为制造一次"GC 抖动+队列积压"复合故障，全流程计时排查；顺手在演习里挖一个真 bug。
> **时长**：演习 2h / 复盘 1h / 输出 0.5h
> **今日产出**：故障演习记录表 + 挖出的真 bug 修复记录

## 1. 知识地图（先讲人话）

```
为什么要主动点火（第五季了，思想不变）：
  故障不会提前打招呼。没演习过的排查流程 = 纸上谈兵；
  演习的价值：①把"四步排查法"练成肌肉记忆
            ②暴露预案里的破绽（今天的真 bug 就是这么挖的）
            ③计时——"发现→定位→修复"的真实耗时才是能力

今天的剧本（复合故障，更接近真实）：
  点火① GC 抖动：往服务里灌"大对象制造机"
    （模拟某个下游返回超大 JSON 被缓存的场景）
    → 预期症状：GC 频繁、Young P99 飙升、接口长尾
  点火② trace 积压：同时把数据库批量写入拖慢（加锁模拟）
    → 预期症状：队列水位上涨、dropped 计数出现、采样降级触发
  观察通道：日报性能行（day27 会做，今天先用 jstat + 日志）

排查剧本（练习四步法+计时）：
  发现（监控/jstat 告警）→ 定位（GC 日志看停顿分布；
  Arthas 看队列水位和 dropped）→ 归因（谁在造大对象？
  谁在拖写入？）→ 恢复（摘流量/限流/修复）→ 复盘（时间线）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Chaos Drill | 混沌演习 | 主动点火，验证系统与人的预案 |
| Time-to-Detect (TTD) | 发现耗时 | 故障发生到被发现的分钟数 |
| Time-to-Mitigate (TTM) | 缓解耗时 | 发现到止血的分钟数 |
| Root Cause | 根因 | 不是"GC 频繁"（症状），是"谁在造大对象"（原因） |
| Postmortem | 复盘 | 无指责、重改进的时间线复盘 |

## 3. 动手实操

### 3.1 点火与计时（全流程记录）

```powershell
# 灌大对象（点火①）：写个每秒打 10 次"5MB 字符串进老年代"的接口，
# 压测工具调它 + 同时正常跑 Agent 流量
# 拖慢写入（点火②）：给 agent_trace 表加一个长事务模拟写入慢

# 计时表（演习后立刻填）：
# T+0:00  开始点火
# T+__:__ 发现异常（依据：___ ——GC 日志？dropped 计数？接口报警？）
# T+__:__ 初步定位（jstat 看到什么 / Arthas 看到什么）
# T+__:__ 根因确认（谁在造对象 / 写入为什么慢）
# T+__:__ 恢复完成（摘流量？清缓存？解锁表？）
# 总 TTM = ___ 分钟（目标：定位 ≤15 分钟——第一次练别硬撑）
```

### 3.2 挖真 bug（演习的隐藏任务）

```
预埋真 bug（演习时不知道，复盘时揭晓）：
  TraceSampler 的 queueWatermark 注入漏了——降级阈值
  永远是 0，采样降级（10%→1%）从未触发过！
  表现：点火②时队列水位 8000+，dropped 飙升，
  但采样率纹丝不动——"降级联动"是个空转的保险丝。

复盘发现的路径：
  看 Arthas watch TraceSampler → divisor 恒为 10
  → 追注入点 → AsyncTraceWriter 构造时忘了传 queue 引用
  → 修复 + 补一个单测（水位>5000 时 divisor==100）
教训（这就是演习的意义）：
  "写了降级逻辑"≠"降级逻辑生效"——保险丝装了没接电，
  只有点火（真实故障）才能发现。对应 M15 演习挖会话活性
  bug 的同一课：预案要实弹验证。
```

### 3.3 修复后的回归验证

```powershell
# 修完 bug 重跑点火②：水位超阈值时采样应降到 1%
# 验证：watch divisor 变化 + 落库速率应下降 + dropped 归零
# ——修复必须回归验证（M15 五项回归的同一纪律）
```

### 3.4 思考题

为什么复盘强调"无指责"？如果这次挖 bug 的过程变成"谁忘传的参数"，会失去什么？（提示：指责让人隐瞒失误、修复变成甩锅；无指责让人抢着暴露问题——工程文化决定系统可靠性。面试管理面高频题）

## 4. 面试连接

**Q：讲一次你处理过的线上性能故障。**
> 按时间线讲：GC 抖动 + trace 写入积压同时发生，发现耗时 _ 分钟（dropped 计数器告警），定位用 jstat+GC 日志+Arthas 三样，根因是下游大 JSON 直接入堆+写入被长事务拖慢，恢复先限流再修复，TTM _ 分钟。复盘还挖出一个真 bug：采样降级的队列水位注入漏了，降级从未触发——修复后补了单测。这个故障教会我"保险丝要实弹验证"。

**Q：怎么设计一次故障演习？**
> 三要素：可控的点火点（模拟下游故障，不伤真数据）、明确观察通道（指标和日志预先布好）、计时评分（TTD/TTM）。演习后强制复盘挖系统问题（预案漏洞/监控盲区/代码 bug）。我在性能项目里做过"GC 抖动+队列积压"复合演习，最大的收获不是排练流程，而是挖出了降级空转的真 bug。
