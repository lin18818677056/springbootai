# Day 15 · GC 人话版：G1 是怎么"打扫卫生"的

> **今日目标**：用人话讲清分代回收和 G1 的核心设计；看懂 GC 日志；回答 day14 预习的问题（短命对象去哪了）。
> **时长**：理论 1.5h / 实操 1h / 输出 0.5h
> **今日产出**：Agent 服务 GC 日志阅读笔记 + 分区图手绘

## 1. 知识地图（先讲人话）

```
先答预习问题：AsyncTraceWriter 攒的 trace 字符串去哪了？
  → 绝大多数进了 Eden 区，活不过下一次"小扫除"（朝生夕死）。
  如果 Eden 满了 → 触发 Minor GC，没人引用的全部清走，
  幸存者搬到 Survivor——这就是"分代假设"在干活：
  大部分对象朝生夕死，少数长命的才值得慢慢伺候。

堆的小区结构（人话版）：
  Eden（新小区）：新对象都住这，人口流动最大
  Survivor S0/S1（周转房）：小扫除幸存者轮流住两个周转房
    （每躲过一次扫除"年龄"+1，攒够次数 15 搬家）
  Old（储藏室/养老院）：长命对象搬进来，打扫成本高
    → 老年代满了触发大扫除（很贵！要停全世界）

G1（Garbage First）的两大发明（JDK9+ 默认收集器）：
  ① 切格子（Region）：把大堆切成 ~2048 个等大的小格子
     （默认 1~32MB）。Eden/Survivor/Old 不再是连续大块，
     而是一格一格的"身份标签"——回收单元从"整个区"变成"格子"
  ② 停顿预测（Pause Prediction）：你承诺
     -XX:MaxGCPauseMillis=50（最多停 50ms），
     G1 就挑"垃圾最多、格子最少"的几格先扫——
     用最少的时间换最多的空间，Garbage First（垃圾优先）名字由此来

  类比：物业承诺"电梯检修最多停 50 分钟"→ 检修队不再整栋楼
  停摆大扫除，而是每次挑最乱的一两层楼快速清理。

三色标记（并发标记的人话版）：
  白=没扫到（候选垃圾）灰=自己扫到了但成员没扫完 黑=彻底扫完
  并发标记时用户线程还在改引用 → 漏标风险 →
  写屏障 + 卡表兜底：跨格子引用发生时"打点登记"（把引用方
  所在卡片标脏），重新标记阶段只查登记过的卡片——
  不用重新扫全堆。人话：搬家时新邻居关系登记在门卫处。
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Generational Hypothesis | 分代假设 | 大部分对象朝生夕死——所以按年龄分区伺候 |
| Minor / Major GC | 小扫除 / 大扫除 | 新生代回收（快）/ 老年代回收（贵） |
| Region | 区域 | G1 的格子，堆的最小回收单元 |
| Humongous | 巨型对象 | 超过半格的大对象，直接进老年代区（隐患！day16 讲） |
| Write Barrier / Card Table | 写屏障 / 卡表 | 跨区引用的"门卫登记簿" |
| Stop-The-World (STW) | 停全世界 | 回收时全体业务线程暂停（用户感知 = 卡顿） |

## 3. 动手实操

### 3.1 打开 GC 日志并看懂它

```powershell
# 启动 Agent 服务时加 GC 日志（JDK9+ 统一日志语法）
java -Xms1g -Xmx1g -Xlog:gc*:file=gc.log:time,uptime,level,tags -jar app.jar
# 压测 10 分钟后打开 gc.log，重点找两类行：
# [gc] GC(12) Pause Young (Normal) 256M->64M(1024M) 18.5ms
#      ↑第12次小扫除   ↑堆从256M清到64M    ↑停了18.5ms ← 核心指标！
# [gc] GC(3) Pause Full ... 450M->120M 350ms
#      ↑大扫除出现了！350ms 停顿 = 用户界面卡死一次 ← 坏消息
# 统计：小扫除次数/平均停顿/大扫除次数——这就是 GC 基线（台账优化点④）
```

### 3.2 观察分代搬家（验证人话版结构）

```powershell
jstat -gcutil <pid> 1000
# 列含义：E(Eden%) O(Old%) M(元空间%) YGC YGCT FGC FGCT GCT
# 预期模式：E 快速涨到 ~100 → 瞬间归零（小扫除）→ O 缓慢上涨
# O 上涨速度 ≈ 你的"长命对象"产量（trace 批量对象如果活太久就会堆这）
```

## 4. 面试连接

**Q：G1 和 CMS 的区别？为什么 JDK9 后默认 G1？**
> CMS 按代回收、标记清除（有碎片）、和业务抢 CPU；G1 把堆切成 Region，每次挑垃圾最多的格子优先回收，能按 MaxGCPauseMillis 目标做停顿预测，且整理式回收没碎片。一句话：CMS 是"定时全区大扫除"，G1 是"按承诺分楼栋快扫"。碎片可控+停顿可控+大堆友好，所以转正。

**Q：什么情况下对象直接进老年代？**
> 三条路：年龄到阈值（默认 15）；大对象（超过 Region 一半的 Humongous 直接进老年代区）；动态年龄判断（同龄对象超 Survivor 一半整体晋升）。大对象直接进老年代是我们 trace 场景的隐患——大 JSON 字符串会反复污染老年代，day16 调优的重点对象。
