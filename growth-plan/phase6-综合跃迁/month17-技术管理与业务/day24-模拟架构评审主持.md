# Day 24 · 模拟架构评审主持：物流工具方案评审

> **今日目标**：把 day15 的主持技术用在完整实战上——主持"物流工具"方案的架构评审（两个虚拟组员方案之争），全流程 45 分钟+决议邮件，录音并按评分卡打分。
> **时长**：备会 1h / 演练 1h / 复盘 0.5h
> **今日产出**：评审材料包 + 45 分钟主持录音 + 决议邮件 + 自评分卡

## 1. 知识地图（先讲人话）

```
今天是把 day15 的"主持技术"和 day19 的"选型方法"
组装成一次完整实战：

评审议题（提前一周就该定的，今天模拟）：
  物流查询工具（day08 的估算需求）怎么实现？
  方案 X（组员 A 提）：接第三方聚合 API（快递 100 类）——
    优点：一家接全搞定，快（估 3 天）
    风险：按次收费成本、第三方稳定性依赖
  方案 Y（组员 B 提）：对接各家快递官方 API——
    优点：无中间商，数据权威
    风险：每家申请+联调（估 10 天+），维护面广
  这是一组"完美的分歧"：两边都有理——
    正好练习"定标收敛"而不是"和稀泥"。

主持人今天的任务清单（对照 day15 流程卡）：
  会前：材料 24h 前发出（两方案对比 RFC）+预收意见
  会中：破题（今天定三事：方案选择/灰度策略/监控指标）
       →时间盒（X 讨论 15'/Y 讨论 15'）→收敛（定标+POC）
  会后：决议邮件 24h 内（决议/行动项/遗留分歧）
评分点（演练后自评）：
  ① 有没有变成"你评评谁对"（主持人不做裁判做引导）
  ② 收敛用的是什么（数据/定标 vs 拍板/和稀泥）
  ③ 遗留分歧处理了吗（记录+跟进机制）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| RFC Review | 方案评审 | 架构决策前的集体把关（day03 的 RFC 是输入） |
| Consensus | 共识 | 不是"都满意"，是"我不同意但我会执行"（disagree & commit） |
| Spike | 技术探针 | 为回答一个具体问题做的小实验（半天内），评审会常用收敛工具 |
| Action Item | 行动项 | 会后谁/何时/做什么——决议的落地形态 |
| Minutes | 会议纪要 | 决议+分歧+行动项三段式，24h 内发出 |

## 3. 动手实操（演练）

### 3.1 演练一：备会材料包

```
材料包四件（模拟"提前 24h 发出"）：
  ① RFC 一页纸：背景（物流咨询占比 15% 且增长）+
    两方案对比表（成本/工期/稳定性/维护面四维打分）
  ② 关键数据预置：
    当前物流咨询 3000 次/日；聚合 API 约 0.01 元/次
    = 月成本约 900 元；官方 API 免费但要 8 家逐一申请
  ③ 预收意见（你替 A/B 各写一条会前意见）：
    A："聚合 API 三天上线，业务等不起官方申请。"
    B："第三方挂了我们客服就瘫，这不是钱的问题。"
  ④ 议程：X 15' / Y 15' / 收敛 10' / 决议 5'
```

### 3.2 演练二：45 分钟评审主持（重头戏）

```
AI 扮演 A 和 B（人设照 day22，冲突剧本预设）：
  A 的立场句："业务等不起，先上聚合版快速验证。"
  B 的立场句："客服是门面，稳定性红线不能碰第三方。"
  剧本冲突升级点：A 说 B "老古董"，B 说 A "没吃过事故"——
    （你的救场时刻：day15 话术"两位说的其实是两件事"）

你的主持脚本锚点：
  [0-3'] 破题："今天定三事：方案/灰度/监控。先 X 后 Y 各 15 分钟。"
  [3-18'] X 陈述+质询：你追问 A："0.01 元/次在 10 万次/日时
    是多少钱？"（帮 A 看到规模的坑）+ "聚合商挂了的降级呢？"
  [18-33'] Y 陈述+质询：你追问 B："8 家申请的排期风险你算过吗？
    快递 API 审批延迟就是 day10 风险表第 1 条。"
  [33-43'] 收敛（今天的重点练习）：
    试定标："咱们其实都同意'稳定优先、速度其次'对吗？"（共同目标）
    → 试验收敛："三天做个 Spike：聚合 API 压测+降级演练，
      数据周三评审，好就聚合版灰度（保留官方 API 接口层），
      不好就官方路线，A 的'快'用灰度补。"
    → 双方点头（disagree & commit：B 接受灰度，A 接受接口层隔离）
  [43-45'] 复述决议+行动项：Spike 谁做/何时/数据标准
会后：决议邮件（模板照 day15）。
```

### 3.4 思考题

为什么主持人的最高纪律是"不做裁判做引导"？（提示：你一裁判，输的一方不再对结论负责——"那是主持人定的不是我"；引导出来的结论双方共同拥有（disagree & commit），执行时才不会消极怠工。裁判的权力快感是主持人最大的诱惑，也是最深的坑。）

## 4. 面试连接

**Q：讲一次你主持架构评审的经历。**
> 物流工具方案那次。两位同事分别提了聚合 API 和官方直连方案，各有道理僵持不下。我做的三件事：会前把对比表和数据预发给所有人，会上只谈分歧；质询阶段我不用自己的观点压人，而是追问帮双方看到盲区——问 A"10 万次日方聚合费用是多少"，问 B"8 家申请的排期风险算过吗"；最后用定标收敛——先确认共同目标"稳定优先速度其次"，再安排三天 Spike（聚合商压测+降级演练），数据出来定方案，同时要求接口层隔离保留切换余地。结论双方都认：B 接受了灰度，A 接受了隔离层。我的心得：主持人的价值不是辩赢谁，是让结论被所有人共同拥有。

**Q：评审会上双方吵到人身攻击怎么办？**
> 立刻拆解降温："两位说的其实是两件事——一个是速度，一个是稳定，都对，我们逐个过。"然后迅速把话题拉回数据：人身攻击的根因通常是"观点之争没有数据可依"，一旦进入 Spike/定标流程，情绪自然退场。会后我会分别私下各聊五分钟（对事不对人的规矩要单独安抚）。
