# Day 12 · 代码评审的教与审：抓错与育人两种目的

> **今日目标**：理解代码评审的两种目的（抓错 vs 育人）及各自的评审清单；学会"对事不对人"的评论话术；建立自己的评审分级标准（什么必须拦、什么随口提）。
> **时长**：理论 1h / 演练 1.5h / 输出 0.5h
> **今日产出**：双目的评审清单 + 评论话术对照表 + 一份模拟评审记录

## 1. 知识地图（先讲人话）

```
代码评审的两种目的（新手最容易混在一起）：
  审（gatekeeping 抓错）：守住质量底线——bug/安全/性能，
    该拦就拦，标准客观
  教（mentoring 育人）：让同事成长——写法/设计/习惯，
    多提多商量，标准主观
  混在一起的恶果：把风格偏好说成"必须改"→ 对方抵触；
    把真 bug 说成"建议"→ 上线出事。
  类比：审=交警（闯红灯必须罚），教=驾校教练（怎么打方向
    是商量着来）。

评论的三条规矩（对事不对人的技术化）：
  ① 指证据不指人：不说"你这里写得烂"，
    说"这里空指针风险，list 可能为 null（第 42 行）"
  ② 给理由给方案：不说"这样不好"，说"建议用 try-with-resources，
    因为文件句柄在异常时不会释放（附示例）"
  ③ 分级标注：[必须改]（bug/安全）/ [建议]（更优写法）/
    [随口]（纯偏好，标注"看你喜好"）——对方可以按级响应

评审清单（审的部分，逐项过）：
  正确性 > 安全（注入/越权/敏感信息）> 性能（N+1/大循环查库）
  > 并发（共享状态/锁）> 兼容（接口变更影响方）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| Code Review | 代码评审 | 提交前同事互相检查，一石二鸟：抓错+传帮带 |
| Blocking Comment | 阻塞性意见 | 必须改完才能合并的（对应 [必须改]） |
| Nit | 小瑕疵 | nitpick 的简称：纯偏好级意见（对应 [随口]） |
| LGTM | 我看行 | Looks Good To Me：评审通过的黑话 |
| Sunk Cost | 沉没成本 | "都写这么多了别推翻"——评审要防止的心理陷阱 |

## 3. 动手实操（演练）

### 3.1 演练一：评审一段真实代码（拿自己的）

```
把 M15 的 MiniAgent/IntentParser 翻出来，假装同事写的，过审：
  [必须改] 类：
    ① OrderTools 归属校验CurrentUser.id()——若被绕过？
       （check: 校验在服务层还是工具层，有没有旁路）
    ② 循环里 history 无限增长——内存风险+token 成本风险
       （check: 有没有截断/摘要策略）
  [建议] 类：
    ③ 魔法数字 MAX_ITER 提为配置
    ④ ToolResult 的错误码用枚举不用字符串
  [随口] 类：
    ⑤ 变量命名 round/iter 统一
  输出：评审记录（行号+问题+分级+建议方案），≥5 条。
```

### 3.2 演练二：评论话术对照表

```
| 反面（对人）            | 正面（对事）                              |
|------------------------|-------------------------------------------|
| "这写的什么玩意"        | "这段异常被吞了，出问题会没日志（L33）"      |
| "你怎么又忘了加锁"      | "这个 map 会被并发读写，建议加读写锁，       |
|                        |  参考 ConfigCache 的做法"                  |
| "不行，重构掉"          | "[建议] 这个 200 行方法建议拆成三个，        |
|                        |  每个只做一件事，评审也更好过"               |
| "我个人觉得…"          | "[随口] 命名风格看团队惯例，我倾向 xxx"      |
| "listen to me"         | （永远不需要——评审靠理由不靠权威）           |
话术公式：现象（行号+证据）+ 影响 + 建议方案（可参考的例子）。
```

### 3.3 演练三：AI 陪练"玻璃心同事"

```
让 AI 扮演被提了[必须改]就委屈的同事：
  同事："你是不是针对我？我上周才改过这块。"
  你（话术三步）：
  ① 共情+对事："不是针对人，这个空指针谁写都会踩——
    我自己上周也在这栽过"
  ② 给证据："你看这个调用链，user 可能为 null（我贴了复现代码）"
  ③ 给台阶："改完这单我带你过一遍这个模块的坑，下次一眼就能看到"
  录音复盘：有没有被情绪带偏成互相攻击？
```

### 3.4 思考题

为什么评审意见必须分级（[必须改]/[建议]/[随口]）？（提示：不分级=把选择权浪费在噪音上——对方要逐条猜"哪条是真问题"；分级后对方按级响应，[必须改]不吵、[随口]不争，评审速度和关系质量双赢。）

## 4. 面试连接

**Q：你怎么做代码评审？**
> 两个目的分开：审的部分守住底线，按"正确性>安全>性能>并发>兼容"清单过，这条线上该拦就拦；教的部分用商量语气，写法设计给建议附例子。所有评论分级标注[必须改]/[建议]/[随口]，并且话术永远"行号+证据+影响+方案"，不评价人。新人提交我还会多花十分钟讲"为什么"——评审是团队里成本最低的传帮带。

**Q：评审时和作者意见不合怎么办？**
> 先看分级：[必须改]级的用证据说话（复现代码/压测数据/历史事故案例），证据面前没得争；[建议]级的双方各有道理时，作者优先——代码是他的，他承担维护责任。原则是评审靠理由不靠职级，我在方案里写"我建议+因为+参考"，不写"我经验多听我的"。
