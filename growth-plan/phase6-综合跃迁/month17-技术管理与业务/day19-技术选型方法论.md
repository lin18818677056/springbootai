# Day 19 · 技术选型方法论：POC→定标→复盘闭环

> **今日目标**：掌握技术选型的完整方法论——需求定标先行、POC 验证、书面决策记录；学会用"决策记录（ADR）"让选型可追溯可推翻；识别"为技术而技术"和"为稳定而保守"两种选型陷阱。
> **时长**：理论 1h / 演练 1.5h / 输出 0.5h
> **今日产出**：一次完整模拟选型（定标表+POC 方案+ADR 文档）

## 1. 知识地图（先讲人话）

```
技术选型翻车的两个极端：
  追新派："用最新框架，简历好看"——上线三个月社区凉了，
    升级没人管，变成孤儿系统。
  保守派："用我们一直用的"——祖传框架连官方都停维护了，
    招个新人半年学不会。
  两个极端的共同病根：选型依据是"感觉"，不是"标准"。

科学选型四步：
  ① 定标（最重要且最容易被跳过）：先写下"这个场景什么最重要"——
    例：消息队列选型，我关心：吞吐/延迟/运维成本/团队熟悉度/
    社区活跃度。不先定标，选型=老板喜欢哪个选哪个
  ② 候选：列 2~4 个候选（一个也别太多——选型不是百科竞赛）
  ③ POC 验证：用真实场景的小样本验证定标项——
    不是跑官方 demo（demo 永远快），是自己造的刁钻场景
  ④ ADR 存档：把"当时怎么想的"写下来（决策记录），
    半年后复盘"当初的假设对不对"——这是团队经验的复利

ADR（Architecture Decision Record）长这样：
  背景：为什么要做这个选型
  决策：选了什么
  理由：定标怎么打的分、POC 数据
  后果：接受什么代价、什么情况下要重新评估
  （一段话五分钟写完，救未来的自己半年）
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| ADR | 架构决策记录 | 选型的"航海日志"：当时怎么想的，写下来防失忆 |
| POC | 概念验证 | 上真战场前的小规模实弹演习（用自己场景，别用官方 demo） |
| Weighted Score | 加权评分 | 定标项按重要性打权重，候选逐项打分乘权重求和 |
| Lock-in | 供应商锁定 | 用了就离不开的代价（云服务/私有协议的隐性成本） |
| Build vs Buy | 自建还是采购 | 自建可控但贵，采购快但受制于人——永远对比着算 |

## 3. 动手实操（演练）

### 3.1 演练一：完整模拟选型（场景：给项目五选"任务调度"）

```
背景：AI 客服要做日报定时任务+超时会话扫描，选调度方案。

第 1 步定标（先写场景标准，配权重）：
| 标准           | 权重 | 理由                          |
|----------------|------|-------------------------------|
| 团队熟悉度      | 30%  | 小团队，学习成本是硬成本        |
| 运维成本        | 25%  | 没有专职运维，要省心            |
| 精度（秒级/分级）| 20%  | 超时扫描分钟级够用             |
| 社区/维护活跃度 | 15%  | 别选到要绝迹的                 |
| 分布式支持      | 10%  | 当前单机，未来可能多实例        |

第 2 步候选三个：
  A Spring @Scheduled（自研栈自带）
  B XXL-Job（国内流行调度平台）
  C Quartz（老牌，Spring 内嵌）

第 3 步 POC 验证（每项 30 分钟小实验，不写大 demo）：
  精度实验：三个方案各跑一分钟级任务 1 小时，记延迟分布
  多实例实验：本地起两实例，看任务会不会重复执行
  运维实验：改一次 cron 表达式，各要几步/要不要重启

第 4 步加权评分+ADR：
  A 得 3.4 / B 得 3.8 / C 得 3.1 → 选 B？不——
  当前单实例+分钟级+两人团队，B 的平台运维是负债不是资产，
  选 A（@Scheduled + ShedLock 防重跑），ADR 写明
  "若任务数>20 或需多实例弹性，重评 B"。
  要点：分数高≠选它——定标权重才是主人，
  POC 数据服务于"你的场景"。
```

### 3.2 演练二：写一份正式 ADR

```
ADR-2026-09-19：调度方案选型
  背景：AI 客服需两类定时任务（日报生成/超时会话扫描），
    当前单实例部署，团队 2 人无专职运维。
  决策：Spring @Scheduled + ShedLock。
  理由：定标五项（熟悉度 30/运维 25/精度 20/社区 15/分布式 10）；
    POC 实测：分钟级延迟 <2s 满足需求；ShedLock 数据库锁
    解决未来两实例重跑问题；零新增组件=零新增运维。
  后果/代价：任务数增长后无控制台（要改代码重发布），
    预计任务>20 个时此代价不可接受——届时重评 XXL-Job
    （ADR 编号：本条，触发条件写死）。
  复盘日：2026-12（三个月后回看假设是否成立）。
  亮点：把"什么时候该推翻我"写进了文档——
    这是 ADR 比聊天记录值钱的地方。
```

### 3.3 演练三：AI 陪练"选型评审会"

```
让 AI 扮演"追新派架构师"挑战你的 ADR：
  AI："XXL-Job 分数更高你为什么不选？"
  你："分数是权重算出来的，我的权重里运维占 25%——
      我们没人管调度平台。你的场景权重可能和我不同。"
  AI："@Scheduled 没有可视化，出问题排查慢。"
  你："当前 4 个任务，日志+告警够用；这是 ADR 里写明的
      已知代价，触发条件（任务>20）到了我立刻重评。"
  录音复盘：被说服的点=ADR 论证不硬的点。
```

### 3.4 思考题

为什么 POC 要"用自己造的刁钻场景"而不是官方 demo？（提示：官方 demo 是厂商的推销场景——精心调优过、只展示优点；你的场景才有你的数据量、你的依赖、你的异常流。选型的风险从来不在"顺的时候"，在"不顺的时候"——POC 的价值就是把"不顺"提前演一遍。）

## 4. 面试连接

**Q：讲一次你的技术选型，怎么做的决策？**
> 调度方案那次。我的流程是定标先行：先和场景对齐什么重要——团队小没运维，所以"运维成本"权重 25%；然后三个候选、每项半小时的 POC（精度/多实例/改配置成本）；最后加权评分。有个细节：分数最高的不是最终选择——XXL-Job 分数高但它的平台运维对我们是负债，我选了 @Scheduled+ShedLock，并把"什么时候该推翻这个决定"写进了 ADR（任务超 20 个）。选型不是选最好的，是选最适合自己场景的，而且要让未来的自己知道当时为什么这么选。

**Q：怎么避免技术选型的主观性？**
> 三件事：定标先行（标准没定，讨论全是喜好之争）、POC 用自己的刁钻场景（别信官方 demo）、ADR 书面化（理由和数据存档，复盘有据可查）。另外我会把"决策的可推翻条件"写进 ADR——诚实的选型不是"永远正确"，是"错的时候知道怎么发现、怎么改"。
