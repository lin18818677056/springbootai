# Day 17 · 规范推广实战：让规范从"我遵守"到"团队真遵守"

> **今日目标**：兑现 M16 交接卡②——把"池子调大反而炸"这类坑沉淀的评审四连问，设计成团队真能落地的规范；掌握推广三部曲（工具卡点/试点话术/度量指标）；理解"没有卡点的规范等于没有规范"。
> **时长**：理论 1h / 演练 1.5h / 输出 0.5h
> **今日产出**：四连问落地三部曲方案（卡点设计+话术+度量）

## 1. 知识地图（先讲人话）

```
规范推广翻车的经典现场：
  你在群里发了个《性能优化规范》，@所有人，收获三个"收到"。
  一个月后压测，还是有人无脑调大池子。
  病根：发文档 ≠ 推广——规范落地有三道关：
    看见（多数人没点开）→ 理解（点开了没懂）→ 执行（懂了不做）。
  类比交通规则：贴墙上没人看，装摄像头（卡点）才有人守。

推广三部曲（对症三道关）：
  ① 工具卡点（治"不做"）：把规范变成工具强制执行——
    四连问做成 CI 检查项/PR 模板必填字段/上线检查单，
    不填过不去（规范长在流程里，不靠自觉）
  ② 试点话术（治"抵触"）：别一上来全团队推——
    先拉 1~2 个关系好的项目试点，用他们的数据说话：
    "A 组用了四连问，压测返工少了两次"——
    榜样比命令有力（day15 的试验收敛：用数据说服）
  ③ 度量指标（治"装样子"）：规范有没有用要用数字证明——
    指标：检查项填写率 / 被卡点拦下的次数 / 线上性能事故数环比
    没有度量的规范三个月后必然名存实亡

心法：规范的最高境界是"没人感觉到它的存在"——
  都长在工具里了，就像红绿灯，没人觉得它是负担。
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| CI Check | 持续集成检查 | 提交代码自动跑规范检查，不过不让合——规范的"摄像头" |
| PR Template | 提单模板 | 建议合入请求必须填的字段，把检查项长在流程里 |
| Champion | 拥护者 | 试点团队里帮你说话的人——推广要找"第一个吃螃蟹的" |
| Adoption Rate | 采用率 | 真在用规范的比例（填了但乱填不算） |
| Enforcement | 强制执行 | 卡点 vs 自觉的界线：底线用强制，最佳实践用倡导 |

## 3. 动手实操（演练）

### 3.1 演练一：给四连问设计工具卡点

```
M16 交接卡②的靶子：评审四连问
  （瓶颈在哪/数据证明/改了会怎样/副作用想过吗）

卡点设计（三个由轻到重的方案）：
  方案 A（最轻）：PR 模板必填——
    建 PR 时自动带出四连问模板，空着不让提交
    （成本半天；防"忘了"，防不了"乱填"）
  方案 B（中）：CI 关键词检查——
    脚本检查 PR 描述是否包含四段结构（瓶颈/数据/预期/副作用），
    缺段落打回并@填写人
    （成本 1 天；结构强制，内容靠人审）
  方案 C（最重）：检查单+机器人——
    高风险变更（涉及池子/缓存/连接数配置）自动触发
    "性能评审"标签，指定第二个评审人专看四连问
    （成本 2 天+人力；只对高风险变更启用，避免疲劳）

我的选择：A+B 组合起步，跑一个月看误报率再决定要不要 C。
  （推广也是迭代：先轻后重，别一步到"重"引起反弹）
```

### 3.2 演练二：试点话术（对组员和对老板各一版）

```
对试点组员（请求帮助，不是下命令）：
  "我在压测返工上吃了两次亏，总结了个'性能四连问'。
    想请你下次压测时帮我试用一下，哪里不顺直说——
    你是第一个用户，工具好不好用你说了算。
    试用成本就 5 分钟填一次模板。"
  要点：低门槛+示弱+给反馈权（不是"你给我执行"）

对老板（要授权，讲收益）：
  "压测返工平均每次烧 2 人天，上季度共 4 次 = 8 人天。
    我做了个四连问检查，试点一个月，目标是把返工降到 2 次以内。
    只动 PR 模板不动流程，风险低。一个月后我拿数据向您汇报，
    好就推广，不好就撤——您看行吗？"
  要点：数字+小步+可撤回（给老板零风险决策）

两版都录音演练。
```

### 3.3 演练三：度量与汇报闭环

```
设计度量面板（一个月后的汇报素材）：
| 指标              | 目标    | 实测   | 结论          |
|-------------------|---------|--------|---------------|
| PR 模板填写率      | ≥90%    | 94%    | 卡点生效      |
| 四连问拦下的变更   | >0      | 3 次   | 真拦住了（含一次池子调大）|
| 压测返工次数       | ≤2      | 1 次   | 收益 4 人天   |
| 试点组吐槽数       | 收集≥3 条 | 2 条 | 模板字段太长→精简 |
汇报话术（对老板，day02 金字塔）：
  "结论：四连问试点一个月，返工从 4 次降到 1 次，省约 4 人天，
   建议下月全组推广。成本：0 新增人力（卡点已自动化）。
   风险：模板填写质量依赖评审人，需一次 15 分钟宣贯。"
```

### 3.4 思考题

为什么规范推广要先"轻"后"重"（先模板后 CI 再机器人）？（提示：卡点越重，推广阻力越大、误报成本越高——一步到位的重卡点如果设计错，全团队每天为它买单，规范的信用直接破产；先轻后重让你用低成本验证规范本身对不对，对再加码。这和功能灰度发布是同一个思想。）

## 4. 面试连接

**Q：你怎么把技术规范在团队落地？**
> 我的核心做法是"规范长在工具里"：发文档只有三个"收到"，卡点才有执行力。四连问的落地我分三步：第一步 PR 模板必填（半天成本，防忘）；第二步 CI 结构检查（防乱填）；试点一个月看数据。推广策略上先拉一个试点组，话术是"帮我试用+你是第一个用户"，不搞强制；度量三个数——填写率、拦截次数、返工次数。试点结果返工从 4 次降到 1 次，省 4 人天，拿着这组数据去要全组推广的授权——用数据说话，比用行政命令体面且有效。

**Q：同事不遵守规范怎么办？**
> 先分清是"不知道"还是"不认同"还是"不方便"。不知道就宣贯；不认同的听他理由——规范可能是错的，辩论过就该改规范；不方便就是卡点设计问题，改工具而不是骂人。我的原则是：让遵守比违反更省力（工具自动化），规范才能长期活着；靠盯人守规范，人一忙就破功。
