# Day 03 · 技术方案写作：让别人照着干不出错

> **今日目标**：把 M9 学的方案写作升级成"团队可评审"的 RFC；核心训练是"决策点显式化"——把你脑子里的默认选项全部摆到纸面上。
> **时长**：理论 1h / 写作 1.5h / 输出 0.5h
> **今日产出**：项目六性能治理 RFC（可评审版）

## 1. 知识地图（先讲人话）

```
给自己看的方案 vs 给团队看的方案（本质区别）：
  给自己看：结论对就行（"用虚拟线程并行"一句话够了）
  给团队看：Why 也得写（"为什么不用线程池？为什么写操作不并行？"
    ——评审者要审的不是你的结论，是你的取舍逻辑）

RFC（Request For Comments，征求意见稿）七段骨架：
  ① 背景与目标：为什么做（业务钩子）+ 做到什么程度算成（数字）
  ② 现状与约束：现在的样子 + 动不了的约束（硬件/安全/历史包袱）
  ③ 方案总览：一张图 + 三句话（先看懂再谈细节）
  ④ 决策点清单：每个"我选了 A"都配"备选 B 为什么被否"★核心★
  ⑤ 风险与兜底：会坏在哪 + 坏了怎么办（回滚预案）
  ⑥ 里程碑与分工：谁、什么时候、交付什么
  ⑦ 开放问题：没想清楚的列出来——比装想清楚强一百倍

决策点显式化（今天的核心训练）：
  ❌ 隐式："工具调用改为并行执行。"
  ✅ 显式："工具调用改为并行执行。
     决策点：① 并行手段选虚拟线程（备选 CompletableFuture 全家桶：
       被否原因——回调链可读性差，虚拟线程直写风格更符合 M2 结论）
     ② 并行范围限只读工具（备选全部并行：被否——写操作并行有
       竞态风险，参考 M15 三道闸原则，安全优先于性能）"
  ——显式化的价值：评审者不用猜你的脑子；半年后你自己也看得懂；
    被推翻时知道"推翻的是哪条假设"
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| RFC | 征求意见稿 | 方案先晒出来挨打，别憋大招 |
| Decision Record | 决策记录 | 每个选择配理由和被否的备选（ADR 思想） |
| Trade-off Analysis | 取舍分析 | 没有完美方案，只有"为什么这个代价可接受" |
| Open Question | 开放问题 | 承认没想清楚——装懂才是评审杀手 |
| Consensus | 共识 | 不是所有人都同意，是没人强烈反对且愿意执行 |

## 3. 动手实操

### 3.1 把项目六重写成 RFC（逐段填）

```
【性能治理 RFC v1】
① 背景：AI 客服上线三月，P99 从 3s 涨到 8s（5 轮会话），
  trace 日增 30MB+。目标：P99 降 40%、存储降 70%（数字定死，
  不写"明显改善"这种没输出的词）
② 约束：本地单卡 Ollama（模型侧不可优化）；高危路径审计要求
  同步落库（安全约束）；无新增硬件预算
③ 方案总览：一张台账四行优化点（并行/异步/采样分层/G1 调参）
④ 决策点清单（至少写四个，参考 3.2）
⑤ 风险：异步可能丢 trace → 兜底：丢弃计数+错误全存；
  并行可能放大下游压力 → 兜底：汇合超时+安全阀
⑥ 里程碑：W1 测量 / W2 并发改造 / W3 存储改造 / W4 复测
⑦ 开放问题：压测环境不稳定怎么办？（遗留至今——如实写）
```

### 3.2 决策点清单写法（对拍练三次）

```
从项目六挑四个决策点，每个按"选择/备选/否决理由/推翻成本"写：
  ① 并行手段：虚拟线程 vs CF 编排 → 可读性赢；推翻成本=低（改写法）
  ② 并行范围：只读 vs 全部 → 安全赢；推翻成本=高（安全红线）
  ③ trace 采样率：10% vs 5%/20% → 留存 19% 够回放；推翻成本=中
    （调参即可，但要重测存储）
  ④ G1 停顿目标：50ms vs 200/20 → 三档实测甜点位；推翻成本=低
——写完自问：评审者最可能攻击哪条？把"攻击预演"写进开放问题
```

### 3.3 换位评审（用 AI 当恶意评审）

```powershell
# 把 RFC 喂给 AI，指令："你是严格的架构评审人，找出这份方案
# 三个最可能被挑战的决策点和两个没写清楚的隐含假设"
# 收集攻击点 → 逐条补进决策点清单或开放问题
# ——这就是 day24 模拟评审的靶子预演
```

### 3.4 思考题

为什么"开放问题"段落反而增加方案可信度？（提示：全打勾的方案只有两种： trivial 的或撒谎的。列出没想清楚的事 = 展示思考边界 = 让评审者把火力集中在真正需要拍板的地方——评审会的效率反而更高）

## 4. 面试连接

**Q：你的技术方案通常包含什么？**
> RFC 七段：背景目标（数字定死）、现状约束、方案总览（一图三句话）、决策点清单（核心——每个选择配被否的备选和理由）、风险兜底、里程碑分工、开放问题。我特别看重决策点显式化：性能治理方案里"为什么虚拟线程而不是 CF""为什么只读才并行"全写在纸上，评审效率高，半年后回看也不会懵。

**Q：方案评审被推翻了怎么办？**
> 先分清被推翻的是"结论"还是"假设"：决策点显式化的好处在这——如果推翻的是某条假设（比如"本地环境可复现"），我改假设不动结论；如果是结论，我认证据。我主张"评审对事、方案是消耗品"——被推翻不丢人，藏着掖着被上线后暴雷才丢人。
