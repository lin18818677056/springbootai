# Day 11 · 需求评审与砍需求：挑刺三问与砍留决策

> **今日目标**：学会在需求评审里提出"真问题"（不是抬杠）；掌握砍需求的三问决策法；理解"范围换时间/质量"是工程师最重要的谈判筹码。
> **时长**：理论 1h / 演练 1.5h / 输出 0.5h
> **今日产出**：需求挑刺清单（一个模拟需求挑出 3 个真问题）+ 砍留决策记录

## 1. 知识地图（先讲人话）

```
需求评审的本质：在写代码之前，用最便宜的方式消灭错误需求。
  需求阶段改一个字 = 1 分钟；开发后改 = 1 天；上线后改 = 1 周。
  （类比：装修前改图纸免费，贴完砖砸墙要加钱）

挑刺三问（评审时按顺序问，问到答案为止）：
  ① 为什么是现在？（价值与时机——不做行不行？晚做行不行？）
  ② 用户是谁？频次多高？（影响面——多少用户受益？
      每天 10 次的高频还是一年一次的低频？）
  ③ 怎么验证成功？（验收——上线后看什么数字？
      答不出数字的需求=没法判断白干没白干）

砍需求决策法（时间不够时的谈判筹码）：
  不是"做不完"三个字，而是给三档方案：
  A 全量 6 周 / B 核心链路 4 周（砍掉长尾场景）/
  C 最小可用 2 周（先上主流程，长尾下期）
  → 把"接不接"变成"选哪档"，决策权在业务，依据在你
  心法：范围、时间、质量三者只能保两个——
    这是工程师跟业务谈判的物理定律，不是态度问题。
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 大白话 |
|------|------|--------|
| PRD | 产品需求文档 | 业务的"图纸"：做什么、给谁用、怎么算成功 |
| MVP | 最小可行产品 | 能验证核心假设的最小版本（先卖煎饼别开满汉全席） |
| Priority | 优先级 | P0 必做 / P1 该做 / P2 可以不做（评审前先问清分级） |
| Acceptance Criteria | 验收标准 | "做到什么程度算完成"——写不清=上线必扯皮 |
| Trade-off | 权衡取舍 | 范围/时间/质量三选二，砍需求就是显式做选择 |

## 3. 动手实操（演练）

### 3.1 演练一：给模拟需求挑 3 个真问题

```
模拟需求（自己编一个真实感强的）：
  "给 AI 客服加'智能推荐'：在回答后顺便推荐 3 个相关商品，
   预计提升客单价。下月双 11 前上线。"

用挑刺三问拆解：
  ① 为什么是现在？→ "双 11 前上线"是时间不是理由。
     追问：错过双 11 损失多大？有数字吗？
  ② 用户是谁频次多高？→ 每次咨询都推？还是特定类目推？
     推 3 个的依据？用户烦不烦（体验风险）？
     追问：推荐点击率预期多少？有没有参考数据？
  ③ 怎么验证成功？→ "提升客单价"怎么归因？
     用户买了是推荐带来的还是本来就要买？
     追问：能做 A/B 吗？看组间对比才有因果。
  第 ③ 问的归因问题最致命——答不出验证方案的需求，
  上线后就是"数字涨了都说自己功劳，跌了都说别的因素"。

输出：挑刺清单 3 问+追问，每问配"如果答不上来怎么办"。
```

### 3.2 演练二：砍需求三档方案演练

```
场景：推荐功能评审后评估要 6 周，业务只给 4 周（双 11 硬时限）。

三档方案卡（现场演练着说）：
  A 方案（全量）：推荐引擎+个性化+AB 平台——6 周，赶不上
  B 方案（核心）：固定规则推荐（热销榜 top3）+ 埋点——4 周，
      能赶双 11，个性化下期做
  C 方案（最小）：只做纯展示位（不接推荐）——2 周
  我的建议：B。理由：赶得上时限+能收集点击数据为下期个性化
    提供依据+风险最低（规则版出问题概率小）
  演练话术："时间我保双 11，但全量 6 周做不完。三档方案在这，
    建议 B：双 11 前上热销榜规则版，数据回流后下期上个性化。"
```

### 3.3 演练三：AI 陪练"既要又要"的业务方

```
让 AI 扮演"全都要"的业务方：
  业务："4 周，全量，个性化也要。"
  你：（三档方案重申+物理定律："范围/时间/质量只能保两个"）
  业务："加两个人呢？"
  你：（布鲁克斯法则："往延期项目加人更延期"——
      新人熟悉代码 2 周，联调沟通成本翻倍；
      可以加人做独立模块如埋点，主链路不动）
  业务："那就 B，但个性化必须下期第一个做。"
  你：（书面确认：范围 B 档清单+下期排期承诺，邮件拉齐）
录音复盘：有没有被"全都要"绕晕？
```

### 3.4 思考题

为什么说"上线后看什么数字"是需求评审最值钱的一问？（提示：它同时完成三件事——倒逼业务想清楚价值（数字都说不出的需求多半是拍脑袋）、给你验收依据（避免"做完了但业务说没效果"的扯皮）、为下期砍留提供数据（这个功能数据差，下期砍它有依据）。）

## 4. 面试连接

**Q：需求评审你会关注什么？**
> 挑刺三问：为什么是现在、用户是谁频次多高、怎么验证成功。第三问最关键——上线后看什么数字，答不出的需求我会明确提出来先补验证方案。举例子：双 11 推荐需求，我用三问拆出归因问题，最后推动从"个性化全量"改为"规则版+埋点先行"，4 周按时上线，数据还给下期个性化提供了依据——砍需求不是对着干，是把范围换时间的选项摆到桌面上。

**Q：业务需求和你的技术判断冲突怎么办？**
> 先区分是"价值判断"还是"成本判断"。价值判断（该不该做）尊重业务，但要求说清验证标准；成本判断（值不值这个代价）我给三档方案+每档的代价和收益。我会守住底线项（资损/安全/稳定），其他的把决策权交给业务——带着选项谈判，而不是带着情绪对抗。
