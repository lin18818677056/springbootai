> **今日目标**：理解 Bounded Context——同一个词在不同上下文是不同模型；画出商城"商品的三个身份"边界图；打通"上下文即微服务边界"与 M6 拆分的呼应。

## 1. 知识地图

```
限界上下文（Bounded Context）：一个模型/一套通用语言成立的边界
  ——通用语言不是全公司统一的！出了上下文，同一个词就是另一个模型（这是 DDD 最反直觉的点）

"商品"的三个身份（今天的核心案例）：
  ┌─ 商品详情上下文：Product = 标题/图文/评价——为"转化率"服务，字段几十上百个
  ├─ 库存上下文：    Product = SKU/仓库/可用量/冻结量——为"扣减"服务，其他字段全是噪音
  └─ 营销上下文：    Product = 类目/价格带/标签——为"圈品"服务，只要能被规则命中的字段
  三个上下文里它都叫 Product，但字段/行为/不变量完全不同：
    库存的 Product 有"不能超卖"不变量；详情的 Product 有"图文必填"；营销的 Product 能被圈
  ——如果用一个"大而全" Product 类服务三个上下文：改详情字段触发库存服务发布（M6 day01 的耦合灾难）

上下文的三条性质：
  ① 边界内：一套模型+一套通用语言+一个团队（康威定律的落点）
  ② 边界间：只能通过"翻译"通信（API/MQ 事件——day11 上下文映射与防腐层）
  ③ 数据上：不共享库表！每个上下文私有存储（哪怕冗余一部分数据——一致性问题用事件解决）

上下文即微服务边界（与 M6 day01 拆分对话）：
  M6 拆分的依据是"业务职能"（订单/库存/营销三个服务）——它恰好≈限界上下文
  DDD 给了这个直觉一个理论根基：服务边界=模型边界=语言边界
  ——一个服务里两套语言（订单服务里又有"履约"词汇）= 拆分不够（拆单/履约该独立）
  ——两个服务说同一套语言（详情和库存字段高度重叠）= 可能拆过头了（合并评估）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Bounded Context | 限界上下文（模型适用边界） |
| Context Boundary | 上下文边界（语言/模型/团队三合一） |
| Model Consistency (within) | 上下文内模型自洽 |
| Translation (between) | 上下文间靠翻译通信 |
| Private Data | 上下文私有数据（不共享库表） |
| Conways' Alignment | 康威对齐（团队=上下文=服务） |
| Shared Kernel（反模式警示） | 共享内核（滥用=强耦合） |

## 4. 面试连接

**Q：什么是限界上下文？为什么 DDD 强调它？**
> 限界上下文是一套模型和通用语言成立的边界——出了边界，同一个词就是另一个模型。最典型的例子是我们的"商品"：详情上下文里它是图文评价（为转化率服务），库存上下文里它是 SKU 和可用量（为扣减服务），营销上下文里它是类目标签（为圈品服务）——三个 Product 字段、不变量、存储规模完全不同，只有名字相同。DDD 强调它是因为：没有边界，团队就会造一个"大而全"的 Product 类，改详情字段触发库存服务回归测试，模型和数据都被"通用"绑架。有了边界，每个模型只服务一种身份，简单且可独立演进。上下文之间靠翻译通信，这正是 day11 防腐层的入口。

**Q：限界上下文和微服务是什么关系？**
> 它们解决不同层的问题但高度对齐：上下文是"模型边界"（逻辑概念），微服务是"部署边界"（物理单元），DDD 提供了微服务拆分一直缺的理论根基——**服务边界应该对齐上下文边界**。我的经验法则：一个上下文一个服务起步；上下文内再大也不拆（保持事务与语言一致性），多个小上下文可合并部署降成本。判断拆错方向的两个信号：一个服务里出现两套业务词汇（拆分不够）；两个服务字段高度重叠且频繁同步数据（拆分过头）。我们商城 M6 拆的订单/库存/营销三个服务，复盘后对照上下文边界基本吻合，但"拆单与履约"词汇混在订单服务里——按今天的标准它应该独立，已列入演进计划。

**Q：上下文之间怎么共享数据？**
> 原则：不共享库表，只共享"翻译后的表示"。两种方式：同步走 API（返回对方上下文的 DTO，进来就转成自己的模型）；异步走事件（OrderPaid 事件广播，库存/积分各自订阅并转成自己的内部模型，本地冗余一份查询数据——最终一致，M6 事务消息保证可靠）。反模式是 Shared Kernel：把 ProductDO 放公共包让所有服务 import——短期省了翻译，长期所有人被同一张表 schema 绑架，改一个字段全公司回归。我们做过自查，common-entity 包在库存服务里有两处 import，已列入改造。
