## 1. 知识地图

```
热点问题 ≠ 延期，热点 = 高价值决策点——工作坊留白，会下用 ADR 收口（day01 模板接上）：

热点①拆单发生在创建后还是支付后？（day12 遗留）
  证据回顾：平台规则=超时未付全单关；商家发货按仓拆
  决策：支付后拆单（OrderSplit 挂在 OrderPaid 之后）——理由：未付订单拆了也要全关，白拆
  模型后果：子订单在支付后创建，各带独立履约状态 → 子单是独立聚合（day16 边界素材）
热点②部分退款怎么建模？
  决策：退款是独立聚合（Refund），不塞进订单——一个订单 N 笔退款（金额值对象累加≤支付额）
  事件：RefundCreated/RefundSucceeded 带 Money 金额；订单聚合只记"已退总额"投影
  ——"订单不管理退款，订单只知道退了多少"= 聚合尽量小的直觉（day16 正式规则化）
热点③OrderCompleted 的触发时机？
  决策：签收+7天自动完成，评价可提前但不可推迟——定时策略（紫贴）触发，不是用户命令
  ——策略触发的事件在代码里就是 Job/延迟消息（M5 延迟消息的领域化身）

从时间线推导边界（事件风暴→架构的惊险一跃）：
  聚类观察：哪些事件总是一起变？→ 订单生命周期 8 事件 = 订单上下文核心
           履约事件（Shipped/Delivered）只依赖"收货地址+商品清单"→ 履约上下文候选
  聚合候选：命令→聚合的映射表里，同一聚合受理的命令数=它的"负载"
           订单聚合 8 个命令 / 退款聚合 3 个 / 子单聚合 4 个 → 订单聚合最重，day16 重点审查

《订单域建模文档》结构（今天的收口产出）：
  ① 事件清单表（20+ 事件/触发者/受理聚合） ② 事件时间线图 ③ 状态机草图（CREATED→...→COMPLETED）
  ④ 聚合候选与边界说明 ⑤ 上下文划分与映射（day10/11 成果挂接）⑥ 热点 ADR 三则
```

```markdown
## ADR-007：订单拆单时机定为支付后
**背景**：day12 事件风暴热点——拆单在创建后还是支付后；涉及子单聚合设计。
**决策**：OrderSplit 仅由 OrderPaid 触发（支付后拆）。
**备选**：创建后拆——未付订单需逐子单关单，状态机复杂度翻倍；大促下无意义拆分占 40%。
**后果**：子订单为支付后新建的独立聚合；父订单只保留拆分投影；
         超时关单只作用于父单（简化 50% 定时任务量）。
**状态**：已采纳（2026-09，评审：产品+研发各 1）
```

## 4. 面试连接

**Q：事件风暴的产出怎么沉淀成工程资产？**
> 分四级落法：①事件清单直接变 MQ 消息契约与事件类（day18 的 OrderCreatedEvent 名字就来自橙贴）；②时间线翻转为状态机——时间线是"从左到右发生什么"，状态机是"订单此刻在哪"，day24 状态机代码的语义来源就是它；③命令→聚合的映射表推导事务边界与 Repository 设计（day16/17 的直接输入）；④热点问题转 ADR——我们三则热点 ADR 让"拆单时机"从口头争论变成有出处的决策。沉淀的纪律是 48 小时内成文，建模文档不归档等于没开工作坊。

**Q：怎么从事件时间线推导出上下文和聚合边界？**
> 两个聚类视角：上下文级看"事件共变性"——哪些事件总在同一次需求里一起变（履约事件只依赖地址和商品清单，跟订单状态机解耦，所以履约是独立上下文候选）；聚合级看"命令受理聚集"——统计每个候选聚合受理的命令数，订单聚合 8 个命令最重，就是 day16 要重点审查的对象（聚合越小越好）。补充第三视角：补偿流程独立分组——Refund/StockReleased 这类补偿事件自成时间线分支，它们属于售后上下文而不是订单主干。三个视角交汇出的边界，比拍脑袋画框图有据可依。

**Q：补偿流程在建模上怎么处理？**
> 补偿流程（退款/库存释放/关单）在事件风暴里单独成线，不混入主干——因为它们的触发者是"策略或逆向命令"，语义是"把世界改回某个状态"。工程化落法：补偿事件独立命名（StockReleased 而不是 UnLock）、补偿逻辑进独立的策略类/Job（M5 的延迟消息、M6 的对账都是它的技术底座）、补偿聚合独立（退款聚合）。最忌讳把补偿塞进主流程 if-else——那是 day26 要重构的"上帝方法"的典型原料。
