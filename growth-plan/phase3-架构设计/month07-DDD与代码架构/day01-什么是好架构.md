# Day 01 · 什么是好架构：从 M6 的拆分决策说起

> **今日目标**：回答"什么是架构、什么是好架构"——不背定义，用 M6 的拆分决策反向验证；理解康威定律并学会用它解释组织与系统的互相塑造。
> **时长**：概念 1.5h / 实战画图 2h / 复盘 0.5h
> **今日产出**：你司（或商城）架构图 + 问题标注清单 + "好架构"一句话定义

## 1. 知识地图

```
架构的定义（三层递进，别背第一层）：
  表层：架构 = 组件 + 连接方式（图上的框和线）
  本层：架构 = 重要决策的结构化表达（ Important decisions，难以更改的才叫重要）
    ——M6 day01 的"按业务域拆五服务、依赖方向单向无环"就是架构决策；
       "order 服务用 8081 还是 8082 端口"不是（改起来太容易）
  深层：架构 = 对变化的前置投资（你现在画的每一道边界，都是为了未来某类变化"只改一处"）

架构两大维度：
  逻辑架构：模块职责与依赖关系（六边形分层/领域模型/接口契约）
  物理架构：部署拓扑（几台机器/容器编排/网络分区）
  ——同一个"拆分"决策在两个维度的投影：逻辑上=限界上下文边界（M7 day10），
    物理上=独立部署单元（M6 的六模块/五服务）

康威定律（Conway's Law）：系统结构必然映射组织沟通结构
  四条推论：①沟通决定架构 ② replicated monolith（复制式单体=三团队各写一半同款系统）
  ③先通后拆（系统集成先于模块细分）④同构持续（组织变了系统慢慢跟着变）
  逆康威（Inverse Conway Maneuver）：想要目标架构 → 先调整团队结构
  ——面试用例："为什么我拆五服务不拆十服务？因为团队就 3 个人——康威定律摆在那，
   10 个服务的沟通成本会把 3 人团队压垮。技术决策背后是组织现实。"

好架构的一句话标准（本月的"北极星"）：
  合适（Fit for purpose）+ 演进友好（Evolutionary）
  合适：不炫技——3 人团队上 K8s 全家桶是自毁；日活 100 的系统引入分库分表是灾难
  演进友好：承认"今天的架构一定不对"，关键是改起来的成本曲线平缓
    ——M6 的模块边界就是拆服务的预演（演进友好证据）；M7 的六边形就是"领域不变、
      外围随便换"（演进友好加倍）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Architecture | 架构（重要决策的结构化表达） |
| Logical / Physical Architecture | 逻辑架构/物理架构 |
| Conway's Law | 康威定律（组织↔系统同构） |
| Inverse Conway Maneuver | 逆康威（先改组织再改架构） |
| Evolutionary Architecture | 演进式架构 |
| Architecture Decision Record (ADR) | 架构决策记录（决策要留档） |
| Trade-off | 权衡（架构=取舍的艺术） |

## 3. 动手实操：画图与标注

```powershell
# 实战一：画你司（或商城）的架构图，手绘或 draw.io 均可
#   必须包含：逻辑分层 + 物理拓扑 两个视角
# 然后做"问题标注"（每处标注写清：现象/根因/架构层面的改进方向）：
#   示例（商城版标注）：
#   ① marketing 服务直接读 order 库（跨服务读库）——根因：拆分时没定数据所有权
#      → 改进：数据所有权归 order，marketing 走 API 或事件冗余（M6 day18 思想）
#   ② 所有服务共用一个 Redis 实例——根因：没有资源隔离（M6 day13 舱壁思想）
#      → 改进：核心缓存与普通缓存分实例或至少分 DB+限流
#   ③ 网关里有业务逻辑（拼装商品详情）——根因：网关职责不清
#      → 改进：网关只做"路由/鉴权/限流/灰度"四件事（M6 day05 的定位）
# 实战二：给自己写第一条 ADR（架构决策记录）：
#   ADR-001：mall 拆分为五服务
#   - 背景：单体改造成本与团队规模（3 人）
#   - 决策：按业务域拆五服务，依赖单向无环
#   - 备选方案：不拆（演化成本）/拆十服务（康威定律不允许）
#   - 后果：跨服务一致性复杂度上升（用 M5/M6 方案兜住）；独立部署收益
#   ——ADR 模板五段：背景/决策/备选/后果/状态。写 3 条以上你就是"有档案的工程师"
```

## 4. 面试连接

**Q：什么是好架构？（架构师的送命题）**
> 不背"高内聚低耦合"，答"合适+演进友好"并给证据："合适——架构必须匹配团队规模与业务阶段，我拆五服务不拆十服务，因为康威定律下 3 人团队撑不起 10 服务的沟通成本；演进友好——承认今天的边界明天一定不够，所以我把模块边界做成未来拆服务的预演（M6 六模块就是证据），用 ADR 记录每个重要决策让后来者能理解'为什么这样'。架构的本质不是画出完美的图，是让下一轮变化到来时，改动被约束在少数模块内。"追问"那你怎么量化演进友好"：留到 day03 的适配度函数（Fitness Function）——"我手写过分层依赖检查器，把'依赖方向正确'变成 CI 里可跑的测试。"（预告 M7 主线）

**Q：康威定律是什么？怎么利用它而不是被它支配？**
> 系统结构必然映射组织沟通结构——团队怎么沟通，系统就长什么样。被支配的样子：三个团队合写一个系统，结果长出"复制式单体"（三套一半功能的同款）；利用它的样子：按目标架构倒排团队（逆康威）——想要业务域独立的服务，就按业务域分组团队（订单组/商品组），让沟通结构与目标架构对齐。我的实践："商城拆分时我把'服务 Owner 制'写进了分工文档：每个服务有唯一责任人，团队边界=服务边界——三个月后系统边界依然清晰，这就是顺水推舟。"
