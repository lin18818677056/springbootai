# Day 08 · 领域与子域分级：核心/支撑/通用

> **今日目标**：理解 DDD 的第一刀——把业务切分成子域并分级（Core/Supporting/Generic）；完成商城全域子域分级表；想清楚"投入产出"——核心自研、通用外采。
> **时长**：概念 1.5h / 商城分级实操 2.5h / 面试整理 1h
> **今日产出**：商城子域分级表（含投入策略）+ 微服务边界对照

## 1. 知识地图

```
领域（Domain）= 你要解决的业务问题范围；子域（Subdomain）= 领域的子问题切分
问题空间（Problem Space）：这个问题域由哪些子域构成？（战略设计的"看清"）
解空间（Solution Space）：每个子域用什么模型/上下文承载？（day10 的"落地"）
  ——一个子域 ≠ 一个限界上下文，但通常 1:1 或 1:N（day10 展开）

三级子域（判据：这是不是我们的差异化竞争力？）：
  核心域（Core Domain）：赚钱的看家本领，别人抄不走——投入最牛的人+最严的规范
  支撑域（Supporting）：核心域离不开，但本身不构成竞争力——够用就好，控制成本
  通用域（Generic）：所有公司都一样、有成熟方案的——外采/开源/SAAS，别自己造

商城子域分级表（今天的核心产出）：
  子域       | 级别 | 判据（为什么）                    | 投入策略
  订单交易   | 核心 | 交易转化率=营收命脉，规则高频变化  | 自研+充血模型+本月重构对象
  营销优惠   | 核心 | 大促玩法=差异化竞争力（秒杀/拼团）| 自研+可配置（day25 规则引擎）
  库存       | 支撑 | 核心依赖但同质化程度高（扣减逻辑）| 自研但从简，复用成熟方案
  用户/地址  | 支撑 | 标准能力，无差异化                | 简单实现/账号体系外采
  支付       | 通用 | 支付宝/微信 SDK 成熟，规则渠道定   | 接第三方，自己做适配层（day23）
  消息通知   | 通用 | 短信/推送全行业同质               | 三方 SAAS+自建开关
  ——面试金句："分级不是给模块贴标签，是给研发资源定分配——核心域养专家，通用域买服务。"
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Domain | 领域（业务问题范围） |
| Subdomain | 子域（领域的子问题） |
| Core Domain | 核心域（差异化竞争力所在） |
| Supporting Subdomain | 支撑域（必要但不构成竞争力） |
| Generic Subdomain | 通用域（行业同质，有成熟方案） |
| Problem / Solution Space | 问题空间 / 解空间 |
| Investment Strategy | 投入策略（分级的目的） |

## 3. 动手实操：给"支付为什么是通用子域"写论证

```text
论证模板（面试可直接用）：
① 竞争力判据：用户不会因为"你家支付流程更顺"选你——转化率差异来自商品与营销（核心域），
   支付渠道规则是支付宝/微信定义的，我们只是接入方。
② 成熟方案判据：渠道 SDK/聚合支付（如 Ping++）已是商品，自研网关的成本买不到差异化。
③ 但注意边界：支付"接入与适配"里的对账/风控策略可能上升为支撑甚至核心
   （M6 day19 的对账体系就是资损防线——同一模块不同子问题可以分属不同子域！）
   ——这正说明：子域是"问题"的分级，不是"代码模块"的分级。
实操：把商城 7 个子域按上表重盘一遍，每个写"如果砍掉这个团队会怎样"的判据。
```

```text
子域分级 → 微服务边界的对照（衔接 M6 day01 拆分）：
  核心域订单服务：独立微服务+领域四层+充血模型（本月重构）
  通用域支付：thin 服务只做适配层（day23 的 PayAdapter），领域逻辑让位给三方

  ——反模式警示：把所有服务按核心域规格建设 = 资源错配；把核心域按通用域简做 = 自废武功
```

## 4. 面试连接

**Q：什么是子域分级？为什么要分？**
> DDD 战略设计第一步：把业务切分成子域并分三级——核心域（差异化竞争力，如电商的交易与营销）、支撑域（核心离不开但不同质，如库存）、通用域（全行业同质有成熟方案，如支付通知）。分级的本质是研发资源分配：核心域投入最强的团队用最重的建模手段（充血模型/事件风暴），通用域直接外采做薄适配层，支撑域居中。反面教材是"均匀用力"——我见过把通知服务也建领域四层、而订单 Service 还是贫血巨石的团队，资源倒挂。我们商城实测：核心域 2 个、支撑域 2 个、通用域 3 个，人效分配 5:3:2。

**Q：支付为什么常被归为通用子域？它就不能是核心吗？**
> 三个判据：竞争力上用户不为支付流程买单（为商品与营销买单）；成熟度上渠道 SDK 已是商品；规则制定权在支付宝/微信不在我们。所以"支付接入"是通用域——做薄适配层即可（day23 的 PayAdapter 就是它的正确形态）。但有两个上升通道：①对账与资损防控（M6 day19）做深了是支撑域能力；②如果业务是聚合支付平台（如收钱吧），"支付"本身就是核心域——**同一业务在不同公司的子域级别不同，分级永远相对你的商业模式而言**。这句话是面试的加分点。

**Q：子域和微服务是什么关系？一个子域一个服务吗？**
> 子域是问题空间的切分，微服务是解空间的部署单元，二者相关但不强制 1:1。经验法则：核心域子域≈上下文≈服务（边界稳定值得独立）；支撑域可几个子域合一个服务（库存+仓储）；通用域常常"没有服务"——直接调三方 SAAS。真正的对齐物是限界上下文（day10），子域分级告诉我们"投多少"，上下文告诉我们"边界在哪"——顺序不能反：先分级后画边界，否则会为通用域过度建设。
