# Day 18 · 异地多活：单元化与数据同步

> **今日目标**：理解容灾三级（冷备/同城双活/异地多活）的成本与能力边界；掌握单元化架构（Set 化）与数据同步方案；设计商城双活方案——day04 单元化的纵深展开。
> **时长**：方案对比 1.5h / 单元化设计 2h / 同步方案 1.5h
> **今日产出**：《商城双活方案 v0》含路由/同步/切换三设计 + 容灾成本对比表

## 1. 知识地图

```
容灾三级演进（成本与能力对照——先算账再选级，day01 方法论的高可用版）：
① 冷备/温备：异地一套闲置环境，故障时切——RTO 小时级，数据可能丢小时级
   便宜，但"切换时才知道能不能用"（演练成本高，真实切换常翻车）
② 同城双活：同城两机房（RTT<2ms）——应用双活+存储同步复制
   可扛机房级故障（光缆/火灾），RTO 分钟级 RPO=0；扛不了城市级灾难
   用户无感知路由（LB 层完成），数据层半同步双写
③ 异地多活（单元化/Set 化）：多地机房各承 50% 流量，日常双活
   扛城市级灾难（汶川/疫情级别的区域不可用）；核心难题：数据一致性+流量路由
   成本最高（重复建设+同步链路+运维复杂度×N），大厂标配，中小公司同城双活封顶

单元化（Set 化）设计三要素（day04 的纵深）：
① 数据分片定单元归属：按 user_id 尾数分 Set——华东 ASet（尾 0-4）华北 BSet（尾 5-9）
   原则：一个用户的所有数据（订单/购物车/红包）都在同一单元——单元内闭环，
   跨单元调用降到最低（只有商品/库存这类"全局读"数据跨单元）
② 流量路由：接入层按 uid 尾数路由到归属单元（网关规则/颜色标染色）；
   错误单元的请求重定向（302/内部转发）——路由错了数据不在，等于白跑
③ 全局服务单点化处理：库存/支付这类强一致全局资源——
   库存：中心化扣减（单元只做缓存预扣，最终扣减走中心）或 分片预留（每单元固定额度）
   支付：全局单一支付中心（资金安全 > 就近原则）

数据同步两件套：
  全局读数据（商品/营销）：单向同步（中心→单元），单元只读，冲突不存在
  用户数据（订单/购物车）：双向同步 + 冲突检测（版本号/时间戳 LWW）+
    铁律"归属单元才可写"——从架构上消灭双写冲突（比同步算法更可靠）
  同步工具谱系：Canal（MySQL binlog）/ DTS / Redis shake——M4 的复制知识在此升级
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Cold/Warm Standby | 冷备/温备（异地闲置切换） |
| Same-city Dual-active | 同城双活 |
| Geo-distributed Multi-active | 异地多活 |
| Unit / Set 化 | 单元化（数据+流量闭环） |
| Data Routing | 数据路由（按 uid 归属） |
| Conflict Resolution | 冲突解决（版本/LWW） |
| RTO/RPO by Tier | 分级容灾目标 |

## 3. 动手实操：商城双活方案 v0

```markdown
<!-- docs/ha/mall-dual-active-v0.md —— 设计稿（本地 docker 模拟两"机房"） -->
## 商城双活方案 v0（单元化设计三件套落地）
### 单元划分
- ASet（华东）：uid 尾数 0-4；BSet（华北）：uid 尾数 5-9
- 每单元 = 网关+订单+商品+秒杀+Redis+MySQL 从库（全量组件，可独立服务 50% 用户）
### 流量路由（网关规则）
```
if uid % 10 < 5 → route ASet ; else → BSet    # 接入层染色+路由
# 错误路由纠正：订单服务收到非归属单元请求 → 返回 302 带 X-Unit-Reroute
```
### 数据同步设计
| 数据类   | 方向        | 工具            | 冲突策略            |
|---------|------------|-----------------|---------------------|
| 商品/营销 | 中心→单元   | Canal 单向      | 无（单元只读）       |
| 订单/购物车 | 归属单元内写 | Canal 双向+过滤 | 版本号+归属单元可写铁律|
| 库存     | 中心扣减    | 秒杀预扣走中心 Lua | 单元缓存可重建      |
### 切换剧本（ASet 机房失联）
① 网关探活 ASet 连续失败 30s → 全量路由切 BSet（尾 0-4 用户路由到 B）
② BSet 承接 100%：容量预案——订单服务自动扩容（HPA day04）+非核心降级（day17）
③ ASet 恢复：先只读回放（binlog 追平）→ 灰度切回 10% 流量 → 逐步恢复
④ 演练记录：RTO 目标 5min（探活 30s+切换 1min+预热 3min）
### 本地验证（docker 模拟）
- 两套 docker-compose（mall-aset / mall-bset）+ 网关路由规则
- 停掉 ASet 全部容器 → 模拟切流 → 观察尾 0-4 用户请求在 BSet 正常下单
```

## 4. 面试连接

**Q：异地多活怎么设计？最大难点是什么？**
> 先说选级逻辑：同城双活（同步复制 RPO=0，扛机房级故障）和异地多活（单元化，扛城市级灾难）成本差一个量级，中小规模先同城封顶——我们商城 v0 方案按同城双活起步、按异地多活的单元化标准设计（uid 尾数分 Set），未来平滑升级。异地多活三要素：数据按 uid 分片定归属（一个用户数据全在一个单元内闭环）、流量按归属路由（网关染色+错误路由重定向）、全局资源单点化处理（库存中心扣减/支付全局中心）。最大难点不是流量切换（分钟级可演练），是数据一致性——双向同步的冲突问题。我们的答案不是更聪明的冲突算法，而是架构上消灭冲突：归属单元才可写+全局数据单向只读，让冲突在规则下不存在；残余风险靠版本号检测+对账兜底（day13 资金铁律的延伸）。切换剧本必须月度演练，没演练过的多活是理论多活。

**Q：单元化后跨单元怎么办？比如用户 A（ASet）给用户 B（BSet）转账/发红包？**
> 三种策略按场景选：①代理转发——请求带去 B 单元执行（RTT 增加 30ms，红包这类低频资金操作可接受）；②异步消息——A 单元写本地+发 MQ，B 单元消费落库（ Feed 关注/消息通知类，秒级延迟可接受）；③全局服务——资金类强一致操作走全局中心（支付/清结算本来就是中心化设计）。原则：单元化不是把所有东西打散，是"用户数据单元内闭环+全局资源显式单点化"——最怕的是既想打散又想强一致，结果做出分布式事务灾难。跨单元调用的监控要单独打标（X-Unit-Reroute 头），占比超标说明分片键设计有偏（比如某 KOL 粉丝全在另一单元），那是产品形态问题要单独治理。

**Q：切流怎么保证不丢数据？**
> 切流的核心是"单向流动+追平再切"。正常切流（灰度调整）：目标单元数据本来就是实时的（归属路由下没写过分叉），直接调整路由比例即可，无数据问题。机房级切换（ASet 失联切 BSet）：①BSet 接管期间 ASet 的增量写全部进不来了——但 ASet 本来就失联，无所谓；②ASet 恢复后关键一步：不能立刻接流量——先以只读模式追 binlog（把失联期间 BSet 侧同步过来的数据和本地残留对齐，残留的"孤儿写"要人工/脚本清理），追平后才允许它重新作为归属单元接写；③灰度回切：先切 10% 流量观察对账（订单数/金额守恒，day13 对账铁律复用），再逐步放量。总结成一句：切流不丢数据的本质是"任何时刻一个 uid 只有一个可写点"，所有机制都围绕消灭双写。
