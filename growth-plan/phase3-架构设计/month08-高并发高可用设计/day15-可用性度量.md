# Day 15 · 可用性度量：SLA 与错误预算

> **今日目标**：掌握 SLI/SLO/SLA 三件套与 9 的换算；MTBF/MTTR 与错误预算（Error Budget）；给商城定义 SLO 并搭监控大盘——高可用的第一步是"可度量"。
> **时长**：概念 1.5h / SLO 定义 1.5h / 大盘搭建 2h
> **今日产出**：商城《SLO 定义表》+ 可用性监控大盘 + 错误预算看板

## 1. 知识地图

```
高可用不是口号，是可度量、可预算、可追责的工程指标——先会算再说可用：

9 的换算表（背下来，面试常考心算）：
  99%     = 3.65 天/年      （"基本能用"）
  99.9%   = 8.76 小时/年    （三个9：互联网标配底线）
  99.95%  = 4.38 小时/年
  99.99%  = 52.6 分钟/年    （四个9：核心交易系统）
  99.999% = 5.26 分钟/年    （五个9：金融级，成本指数上升）
  ——每多一个 9，成本翻数倍（冗余+多活+自动化），先问业务值不值

三件套（Google SRE 术语，中英对照记忆）：
  SLI（指标）：系统实际表现的量化——成功率/延迟 P99/吞吐
  SLO（目标）：SLI 的目标值——"下单成功率 ≥ 99.95%"
  SLA（协议）：对外承诺+违约赔偿——SLO 留缓冲后的对外版本
  关系：SLI 是温度计，SLO 是健康线，SLA 是体检报告上的承诺

错误预算（Error Budget）——SLO 的工程化用法：
  预算 = 1 - SLO：99.95% 的 SLO → 每月可容忍 0.05% 失败 = 10000 次请求里 5 次
  用法：预算烧完 → 冻结发布（只修不稳）→ 预算充足 → 放心迭代
  ——它把"稳定 vs 迭代"的撕逼变成数字决策（SRE 的精髓）

MTBF/MTTR（可用性的两个杠杆）：
  可用性 = MTBF / (MTBF + MTTR)
  MTBF（平均无故障时间）↑：靠冗余+预案（day16-19）
  MTTR（平均恢复时间）↓：靠发现快（监控告警 1min）+定位快（链路追踪）+恢复快（回滚/切主）
  ——新手只盯 MTBF（不宕机），高手同时压 MTTR（挂了快速起）——后者性价比更高
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| SLI / SLO / SLA | 指标 / 目标 / 对外协议 |
| Error Budget | 错误预算（稳定vs迭代的数字决策） |
| MTBF / MTTR | 平均无故障/平均恢复时间 |
| Golden Signals | 黄金四信号（延迟/流量/错误/饱和度） |
| Burn Rate | 预算燃烧速率（快烧告警） |
| Partial Availability | 部分可用（降级态怎么计） |

## 3. 动手实操：商城 SLO 定义与大盘

```markdown

## 商城 SLO 定义表（v1）
| 服务域   | SLI                 | SLO            | 错误预算/月   | 计数口径            |
|---------|---------------------|----------------|--------------|---------------------|
| 下单     | 成功率（5xx+超时）   | ≥ 99.95%       | 21.6 min     | 请求级，排除 4xx    |
| 商品读   | 成功率               | ≥ 99.99%       | 4.3 min      | 降级返回旧值=成功   |
| 支付回调 | 端到端延迟 P99       | ≤ 800ms        | -            | 从回调进到落库      |
| 秒杀     | 成功率               | ≥ 99.9%        | 43 min       | 拒绝（售罄）不算失败|
| 消息消费 | 堆积延迟 P99         | ≤ 30s          | -            | 消费位点滞后        |
关键口径决策（数字决定语义）：
  ① 降级成功算不算"可用"？→ 商品读算成功（用户拿到旧值无感知），下单不算（用户诉求未达成）
  ② 秒杀"手慢了"算失败吗？→ 不算（业务预期内的拒绝），但拒绝率>90% 且 Redis 健康要告警（配置事故）
## 错误预算看板规则
- 每日滚动计算当月预算消耗；burn rate > 14.4×（1h 烧完 2 天预算）→ P0 告警
- 预算剩余 <20%：冻结非核心发布，只允许稳定性变更
- 每月复盘：预算去哪了（发布事故/依赖故障/容量不足三类占比）
```

## 4. 面试连接

**Q：你们的系统可用性多少？怎么保证的？**
> 先说口径再说数字：我们商城对内 SLO 下单 99.95%、商品读 99.99%，月度错误预算分别是 21.6 分钟和 4.3 分钟——对外 SLA 在 SLO 基础上再留 20% 缓冲。保证手段分两个杠杆：压 MTBF 靠冗余与预案（无状态多实例、Redis 哨兵、MySQL 主从、大促预案 day19）；压 MTTR 靠"快发现快恢复"——黄金四信号大盘+症状优先告警（成功率跌破 SLO 1 分钟内 P0），配合 M6 的链路追踪定位、灰度发布与秒级回滚。特别说明错误预算的用法：当月预算烧到剩 20% 就冻结非核心发布——"稳定 vs 迭代"不再靠嗓门大，靠数字。这个回答的结构是：口径→两杠杆→错误预算治理，比说"我们有哨兵有主从"高一个层级。

**Q：99.99% 难在哪？为什么不说 100%？**
> 心算题：99.99% 全年 52.6 分钟。难在三件事叠加：①故障是复合的——网络抖动、依赖方抽风、变更引入，不是自己努力就够，跨团队依赖的可用性是乘法（四个 99.9% 依赖串起来只有 99.6%）；②成本指数上升——每个 9 意味着更多冗余副本、自动化故障转移、多活架构（day16-18），边际成本陡增；③变更与稳定的矛盾——不停迭代就要不停发布，每次发布都是风险敞口。不说 100% 是因为那是自欺欺人：没有错误预算的团队最终会被一次大故障反噬，承认会挂、量化会挂多少、挂了怎么办，才是工程态度。

**Q：什么是错误预算？实际怎么用？**
> 定义：预算 = 1 - SLO，99.95% 的月 SLO 意味着每月可以"合法失败" 21.6 分钟。三个实际用法：①发布决策——预算剩 20% 冻结非核心发布，团队从"能不能发"的撕逼变成看数字；②告警分级——burn rate 燃烧速率超 14.4 倍（1 小时烧完 2 天预算）触发 P0，比"成功率低于 X%"更早发现问题；③复盘量化——每月看预算消耗结构（发布事故/依赖故障/容量不足），决定下月改进投向。它解决的是组织问题：SRE 和业务开发对"稳定性要求"的分歧被翻译成同一种货币。我们商城落地在 Grafana 看板，预算耗尽的那周,发布流水线自动卡在审批节点。
