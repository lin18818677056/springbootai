# Day 20 · 故障复盘方法：从 blameless 到架构改进

> **今日目标**：掌握无指责复盘（Blameless Postmortem）方法论；时间线还原与五问根因分析；把复盘产出落成架构改进项——用本月演练过的三次"故障"写出三份合格复盘。
> **时长**：方法论 1.5h / 三份复盘编写 3h / 改进项整理 1h
> **今日产出**：《复盘模板》+ 三份复盘报告（Redis 切换/熔断误杀/限流漏配）+ 改进项看板

## 1. 知识地图

```
故障复盘的价值 = 防止同一坑掉进去第二次——写得好的复盘是团队最贵资产，写砸的是废纸

Blameless 三原则（Google SRE）：
① 对事不对人：写"配置未走 review"不写"张三配错了"——追责文化会让人隐瞒故障
② 复盘的是系统：人的失误是必然（都会犯），要问"系统为什么允许这个失误造成故障"
③ 产出是行动项：每份复盘必须出改进项（带 owner+deadline），否则等于没复

复盘报告五段结构（模板，直接套用）：
① 故障摘要：一句话影响面（"详情页 4 分钟不可用，影响 1.2 万请求"）
② 时间线：精确到分钟的事件序列（发现→响应→定位→恢复），用监控截图佐证
③ 影响分析：SLO 消耗（day15 错误预算口径）/资损/舆情
④ 根因分析：五问法（5 Whys）——问到"系统层面"才停
   反例：为什么挂？Redis 挂了。为什么没兜底？没配。——停在配置层是废复盘
   正例：为什么兜底没生效？→ 降级开关没彩排过 → 预案管理流程没有"开关必彩排"环节
     → 改进项：开关清单强制彩排准入（改的是流程与架构，不是骂人）
⑤ 行动项：改进项表格（问题/动作/owner/deadline/验证方式）

五问法的两个技巧：
  问"为什么"问到系统/流程层（第五问应该是"什么机制本可拦截"）
  区分近因（Redis 挂）与根因（切换窗口没有应用侧兜底设计）——修根因才防复发

改进项的三种落点（决定复盘是真改进还是纸面文章）：
  架构落点：加兜底/加冗余/改设计（最硬）
  流程落点：准入卡点/变更规范/彩排制度（防人祸）
  观测落点：补告警/补大盘（发现更快）——MTTR 的两杠杆再次呼应 day15
```

## 复盘① Redis 哨兵切换窗口下单失败（day16 演练转化）
- 时间线：14:00 stop 主 → 14:00:10 sdown → 14:00:35 switch-master → 14:01:20 业务全恢复
- 影响：预扣失败 47 笔（SLO 消耗 45s，预算内）；用户侧"抢购失败"提示
- 五问：为什么失败？→ Redis 30s 不可写。为什么没有兜底写路径？→ 预扣依赖 Redis 单路。
  为什么单路？→ 认为哨兵切换够快不用兜底。为什么这个假设没被验证？→ 切换演练没测业务侧。
  什么机制本可拦截？→ 演练验收标准缺"业务无感"维度。
- 行动项：①预扣失败走"DB 条件更新"降级路径（架构，本周）②演练验收加业务无感检查（流程）
  ③预扣失败率告警阈值 1%（观测，本周）
## 复盘② 熔断误杀正常流量（day17 演练转化）
- 时间线：压测中 RT 210ms（未超 800 预算）但熔断开启 → 详情页营销位 10s 兜底
- 五问：为什么熔断？→ 慢阈值 200ms 配置过紧。为什么过紧？→ 照抄了预算表告警线没有区分
  "熔断线"与"告警线"。→ 行动项：熔断线=P99×2.5 单独推导（架构配置）；配置变更双审（流程）
## 复盘③ 限流阈值漏配一个接口（假设性复盘——历史事故改编）
- 行动项：接口清单与限流配置自动比对 job（观测）+ 新接口上线 checklist 强制限流项（流程）

## 4. 面试连接

**Q：讲一个你经历过的线上故障和复盘。（高频——面试官在考你的复盘方法论）**
> 用五段结构讲，重点展示"问到系统层"。背景：压测演练中 Redis 主从切换，窗口内 47 笔秒杀预扣失败。时间线精确到秒（sdown 10s/switch-master 35s/业务恢复 80s），影响按错误预算口径算（45 秒，预算内但不达标在"无感"维度）。根因五问不停在"Redis 挂了"：为什么业务失败？切换 30 秒没有兜底写路径；为什么没有？假设哨兵够快；为什么假设没验证？演练验收只测组件不测业务。真正的根因是演练标准缺"业务无感"维度。行动项三条分三类落点：架构上预扣失败走 DB 条件更新降级、流程上演练验收加业务无感检查、观测上失败率告警。一句话总结我的复盘观：修复故障的是运维，防止复发的是架构师——复盘必须产出架构或流程改进，否则只是情绪宣泄。

**Q：什么是 blameless 文化？为什么重要？**
> 复盘对事不对人：写"配置未经 review"不写"某人配错"。重要性在于信息自由流动：如果复盘指向个人，当事人会隐瞒细节、旁观者会粉饰太平，复盘报告变成免责文档而非知识资产。blameless 不是不追责——责任转移为系统问题："人会犯错是常数，系统为什么允许这个错误引发故障才是变量"。我们落地三个细节：复盘纪要不出现人名只出现角色（操作者/审批者）；行动项的 owner 是"问题域负责人"而非"犯错的人"；跨团队故障先各自复盘再联合对齐，避免互相甩锅。一个验证标准：新人看我们三份历史复盘，能直接学到"哨兵切换要测业务侧""熔断线与告警线要分开推导"这类可复用结论——这才是复盘作为资产的证明。

**Q：怎么保证复盘的行动项真的落地？**
> 三个机制。第一，行动项必须有验证方式（"预扣降级路径压测通过"），没有验证方式的行动项在 review 时直接打回——它等于"以后注意"这种废话。第二，改进项进迭代排期而不是 backlog：架构类行动项占下个迭代 20% 容量是硬性预留，否则永远被业务需求挤掉。第三，月度复盘的复盘：检查上月行动项完成率，未完成的升级到负责人周会——流程本身也要被复盘。另外分享一个技巧：把行动项按"架构/流程/观测"三类强制分桶，三类都空着的复盘基本是废复盘——这个检查让我们早期几份"下次小心"式的复盘现了原形。
