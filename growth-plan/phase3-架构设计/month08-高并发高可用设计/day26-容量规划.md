> **今日产出**：《容量规划台账 v1》（全组件+成本）+ 巡检 job + 扩容触发规则表

## 1. 知识地图

```
容量规划 = 让"够不够用"永远有据可查——day01 是起点估算，今天是可持续运营的闭环：

容量规划闭环（五环）：
① 估算（day01）：业务量→峰值 QPS→组件需求（静态锚点）
② 验证（day23）：压测拐点×0.75 → 实测容量（动态校准）
③ 台账（今天）：每组件三行数字——当前水位/实测容量/触发阈值
④ 巡检（自动化）：定时 job 核对水位 vs 阈值，越界告警
⑤ 扩容（day04 路线图）：触发即执行预案（手动开关或 HPA 自动）

台账的核心三列（每组件必填，缺一列的台账是资产清单不是容量规划）：
  当前水位：生产实际用量（巡检采集）
  实测容量：压测得出的能力上限（不是配置上限！）
  触发阈值：水位到达实测容量×60% 时触发扩容评估（提前量原则）

成本估算（容量规划的另一面——技术方案要能算钱）：
  实例成本：月核时×单价——订单 3 实例 4C8G × 720h × 单价
  中间件成本：Redis 内存 GB 单价/MQ 集群/DB 实例规格
  常见优化杠杆：混部（非核心低峰缩容）/弹性（HPA 按时段）/降配（压测验证后的合理规格）
  ——"能算出钱的架构师"和"只会画图的架构师"是两个职级

扩容触发规则表（巡检的判据库）：
| 指标 | 触发条件 | 动作 |
|-----|---------|------|
| 服务 CPU | 日均峰值 >60% 持续 3 天 | 评估扩实例 |
| 连接池 | pending 峰值 >0 每日 >10 次 | 扩池或降 RT（day05） |
| Redis 内存 | >70% maxmemory | 扩容或淘汰策略复核 |
| MQ 滞后 | 峰值 >30s | 加消费实例（day23 结论） |
| DB 磁盘 | 剩余 <30% | 归档/扩容计划 |
| 容量水位 | 水位 >实测×60% | 扩容评估会（周会固定议题）|
```

// 容量巡检 job（台账的自动化——每天 9 点跑，越界发企微）：
@Component
public class CapacityPatrol {
    @Scheduled(cron = "0 0 9 * * ?")
    public void patrol() {
        // 服务 CPU 日峰值（Prometheus API）
        double cpu = prom.queryMax("max by (app)(rate(process_cpu_usage[1d]))*100");
        check("订单服务 CPU", cpu, 60, "评估扩实例");
        // 连接池 pending 次数
        long pending = prom.queryCount("hikaricp_connections_pending > 0");
        check("连接池 pending 次数", pending, 10, "扩池或降 RT");
        // Redis 内存水位
        double mem = prom.queryMax("redis_memory_used_bytes / redis_memory_max_bytes*100");
        check("Redis 内存", mem, 70, "扩容或策略复核");
        // 台账水位 vs 阈值（读 ledger-v1 的结构化版本 capacity.json）
        ledger.checkAll();
    }   // 输出：巡检日报（每项 当前值/阈值/结论），越界项 @运维群
}

## 4. 面试连接

**Q：你怎么做容量规划？（P8 必考——考的是闭环不是估算）**
> 五环闭环：估算（day01 七步链给静态锚点）→ 压测验证（day23 拐点×0.75 给实测容量）→ 台账（每组件三列：当前水位/实测容量/触发阈值——注意"实测容量"不是配置上限，压测出来的才算数）→ 巡检（每日 job 采集水位越界告警）→ 扩容执行（触发规则表+day04 路线图）。举例：MySQL 台账写着"实测 8000 TPS（16 库分片），阈值 4800"，巡检发现日峰值 TPS 涨到 4500 就进周会扩容评估，而不是等 8000 打满出事故。成本侧同步管理：台账带月成本估算，压测数据反过来支撑降配决策（读从库从 32G 降到 16G，压测验证过）——容量规划的价值一半是防事故，一半是省钱，这是它能进管理层汇报的原因。

**Q：怎么向老板解释"为什么要提前扩容花钱"？**
> 用三组数字讲，不讲技术细节。第一组：风险量化——当前水位距实测容量还有 X 天到达（按增长曲线），到达阈值那天大促或一次营销活动就可能触发雪崩，参考同类事故的行业资损数字；第二组：成本对比——提前扩容的月增量成本 vs 事故的一次性损失（赔偿+舆情+事故处理人力），前者通常是一个数量级小；第三组：弹性方案——不是永久扩容，HPA 低峰自动缩容后实际月成本只涨 Y%（台账里的优化空间列）。给管理层的容量汇报三句话模板："水位 75% 还剩 6 周、扩容月成本 +¥1200、不扩的事故期望损失 ¥8 万"——数字齐了，决策自然发生。这也是我理解的架构师向上管理：把技术风险翻译成财务语言。

**Q：容量规划和性能优化什么关系？先做哪个？**
> 先规划后优化，但互相喂。容量规划回答"现有系统能扛多少"——是防守，保证业务增长不踩坑；性能优化回答"能不能扛更多"——是进攻，提高单位资源容量。流程上：压测（day23）先给出拐点，这是两个学科共同的输入——拐点前的低垂果实（索引、缓存、池参数）先摘掉，性价比极高（day24 案例：加索引 P99 640→140ms，一行配置顶三台机器）；拐点后的深水区优化（重构、换存储）要按 ROI 排期，不如直接扩容。台账里两者统一：每次优化后回填"实测容量"列，容量白涨；每次扩容后回填成本列——"用 ¥1000 优化换出 ¥3000 扩容预算"就是性能优化的商业价值。一句话：优化是提升容量性价比的手段，规划是保证不翻车的底线，都服务同一个数字——单位成本的可持续吞吐。
