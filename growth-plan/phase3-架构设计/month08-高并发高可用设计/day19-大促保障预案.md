```java
// 开关化的工程落地（Nacos 配置中心——M6 day17 的 @RefreshScope 复用）
@RestController
public class PromoGuard {
    @Value("${promo.sw-reco-off:false}")          // 默认关，秒级可开
    private boolean recoOff;

    @GetMapping("/api/product/detail")
    public ProductDetailVO detail(Long id) {
        var cfs = List.of(
            detailCf(id),                          // 主路不可降
            promoCf(id),                           // 营销：失败兜底（day06 exceptionally）
            recoOff ? CompletableFuture.completedFuture(RecoDTO.staticHot())  // 开关短路
                    : recoCf(id));                 // 推荐：正常链路
        CompletableFuture.allOf(cfs.toArray(new CompletableFuture[0])).join();
        return assemble(cfs.stream().map(CompletableFuture::join).toList());
    }   // 开关不是异常处理——是"预案可执行"的物理形态，且必须在彩排中真触发过
}
```

## 4. 面试连接

**Q：大促保障你们怎么做的？（P8 必考题）**
> 五个阶段倒排讲。T-30 容量预估：大促档参数（转化×3、峰值因子×20）推出三张表——详情读 5 万/s、下单写 5000/s、秒杀预扣 10 万/s，并和依赖方对齐容量。T-21 扩容压测：资源按峰值×1.5 申请，阶梯压到目标值验证余量。T-14 预案开关化：这是我认为最有价值的动作——三张预案清单（降级/限流/数据）每条都做成配置中心开关，每个开关三要素：触发条件（监控指标）、执行动作（开关 ID）、回滚动作，缺一环的预案是摆设。T-7 全链路彩排：影子流量压测+故障注入，每条预案真触发一遍记录生效时间。T-0 作战：一页纸手册（容量表/开关表/值班表）+作战室值班。给面试官的钩子：彩排中我们发现"购物车合并"开关触发后数据合并 job 缺失——预案彩排抓的就是这种文档上完美、实战会翻车的缝隙。

**Q：为什么大促放行限额是容量×0.9 而不是 1.0？**
> 两个依据。一是 M6 day13 的拐点原则：系统在 75% 水位以上出现非线性劣化（排队论：到达率接近服务率时等待时间指数上升），留 10% 是让系统工作在拐点左侧的线性区。二是故障叠加概率：大促当天限流放满 100% 意味着任何一个依赖抖动都没有缓冲——限流值本身要吸收"瞬时超调"，放太满等于把最后一道闸焊死。实际执行中大促档=压测容量×0.9，秒杀场景更保守（×0.75），因为秒杀的请求分布更尖（毫秒级脉冲）且拒绝对业务影响可控（用户看到手慢了）。这本质是把"容量"从静态数字变成"可运行的水位"，和错误预算（day15）是同一个思想：给意外留预算。

**Q：大促的数据安全怎么保障？**
> 三层。事前：对账 job 加密到 5 分钟一次（day13 红包对账的战时版），退回/补偿脚本必须预演过；大促增量数据落影子表（t_order_b2026）——统计、营销返场都先在影子表上算，活动后合并，隔离了"大促数据污染生产逻辑"的风险。事中：数据链路全走异步（MQ 削峰），DB 压力有上界；Redis 预扣数据定时快照（预扣是热点数据，哨兵切换窗口 RPO 秒级，快照让重建有据）。事后：活动结束跑全量对账（Redis 各桶剩余+订单金额 vs 总库存），差异走补偿；复盘时数据类问题单独立项。资金红线一句话：宁可活动后补发，不可活动中超发——day13 的原则在大促下加倍执行。
