# Day 04 · 水平扩展：从 100 QPS 到 10 万 QPS 的路线图

> **今日目标**：掌握水平扩展的四要素（无状态化/LB 分层/弹性伸缩/单元化）；画出商城 100→10 万 QPS 的扩容路线图——每一步扩容点讲清"瓶颈在哪、动作是什么、代价是什么"。
> **时长**：四要素学习 1.5h / 路线图绘制 3h / 无状态化改造检查 0.5h
> **今日产出**：商城扩容路线图（5 个扩容点）+ 无状态化自查表

## 1. 知识地图

```
垂直扩展（换 bigger 机器）有物理天花板且贵；水平扩展（加 more 机器）是互联网的正解
  前提四要素：
  ① 无状态化（Stateless）：任何实例可以随时加入/退出——状态全部外置
     Session → Redis（spring-session）；本地缓存 → 可丢失设计（day02 两级缓存的短 TTL 就是无状态友好）；
     本地文件 → 对象存储；定时任务 → 分布式调度（XXL-Job/分片，防重复执行）
     自查法："kill 掉一个实例，用户无感知吗？"——无感知=无状态 ✓
  ② 负载均衡分层（LB）：请求怎么均匀打到 N 个实例
     DNS（地域级，TTL 缓存慢）→ LVS（四层，内核态，百万级）→ Nginx（七层，十万级）
     → Gateway（业务级，M6 全家桶，路由/鉴权/灰度）
     ——每层的容量天花板不同，层层接力，各干各的活
  ③ 弹性伸缩（Auto Scaling）：流量波峰自动加实例，波谷回收省钱
     K8s HPA：CPU>70% 或 QPS 指标触发扩容；扩容速度要跑赢流量爬坡（预热问题→day19）
  ④ 单元化（Set 化）：终极形态——按用户维度把"流量+数据+应用"切成独立单元
     user_id 尾号路由到单元 A/B/C，每单元自治（应用+DB 都在单元内）
     ——单元内闭环=跨单元无交互=爆炸半径可控+异地多活自然成立（day18 承接）

商城 100 → 10 万 QPS 扩容路线图（今天的核心产出，5 个扩容点）：
  100 QPS（单实例）→ 500（+LB+2 实例，瓶颈：单点）
  → 2000（+Redis 缓存，瓶颈：DB 读）→ 8000（+本地缓存+读写分离，瓶颈：热点读/DB 读写混合）
  → 3 万（+MQ 异步写+分库分表，瓶颈：DB 写）→ 10 万（+单元化+异地多活，瓶颈：单机房容量与容灾）
  ——每步记录：瓶颈现象/扩容动作/代价（成本或复杂度）——面试白板可以直接画
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Stateless | 无状态（实例可随意扩缩） |
| L4 / L7 LB | 四层 / 七层负载均衡 |
| HPA (Horizontal Pod Autoscaler) | 水平自动扩缩容 |
| Set-based / Unitized Architecture | 单元化架构（Set 化） |
| Scale-out vs Scale-up | 水平 vs 垂直扩展 |
| Session Externalization | Session 外置 |

  ——复盘一句话："每级只解决当前瓶颈，并为下一级预留接口——扩容是演进不是推倒重来"

## 4. 面试连接

**Q：系统从 100 QPS 涨到 10 万 QPS，你怎么演进？**
> 我按五个扩容点讲，每个点都是"瓶颈出现→动作→代价"：500 时加 LB+多实例解决单点；2000 时上 Redis 缓存把读 99% 挡掉（DB 读先于 DB 写成为瓶颈——电商读写比决定）；8000 时读写分离+本地缓存，代价是接受主从延迟并处理"读己之写"；3 万时写链路 MQ 削峰+分库分表 16/64，代价是跨片查询与事务复杂度——好在 M7 把聚合边界缩小过，单事务只碰订单聚合，分片后依然单分片闭环；10 万时单元化，按用户尾数切四个自治单元，顺带获得异地多活能力。核心心法是"每级只解决当前瓶颈，代价提前显性化"——跳级（没瓶颈硬上单元化）是把复杂度当装饰品。

**Q：无状态化具体指什么？有哪些常见的"隐藏状态"？**
> 无状态=任何请求可以被任何实例处理，实例随时可增减。显性的 Session 大家都知道外置 Redis 或改 JWT（我们 M6 网关透传 X-User-Id 已做）；容易漏的是四个隐藏状态：本地缓存（要设计成可丢失，短 TTL 是无状态友好的）、本地文件（对象存储替代）、@Scheduled 定时任务（多实例重复执行，要分布式调度或分片）、进程内计数器/限流器（M6 的单机 RateLimiter 在多实例下限流 N 倍失效——这正是 day17 要升级分布式限流的原因）。自查手法就一句：kill 一个实例，用户无感知、数据无丢失、任务不重复——三条都过才算无状态。

**Q：单元化（Set 化）是什么？什么规模才需要？**
> 单元化是按用户维度把流量、应用、数据整体切成 N 个自治单元：user 尾号路由决定"这个人属于单元 A"，他的请求、订单数据、服务实例全部在单元 A 内闭环——单元之间默认零交互。三个收益：容量线性扩展（加单元=加容量）；爆炸半径可控（单元 A 故障不影响 B）；异地多活自然成立（单元分布在不同城市，单城市故障切流即可，day18 承接）。成本也真实：跨单元的数据一致性、全局维度的查询（报表）、数据迁移工具都要建设。我的判断标准：单机房容量天花板或容灾等级要求先到，才上单元化——我们商城 Level5（10 万 QPS）才引入，前面的扩容层级里它是过度设计。
