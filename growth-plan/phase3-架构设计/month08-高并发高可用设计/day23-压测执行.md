# Day 23 · 压测执行：阶梯加压与拐点定位

> **今日目标**：掌握阶梯加压法（Step Load）与拐点识别；四维观测（RT/吞吐/资源/中间件）判读；跑通商城三条核心链路压测——兑现 M6 day13"拐点×0.75"伏笔的全链路版。
> **时长**：阶梯设计 1h / 三链路压测执行 3.5h / 拐点分析 1h
> **今日产出**：三条链路压测报告（阶梯数据表+拐点标注）+ 水位结论回填预算表

## 1. 知识地图

```
压测执行的核心不是"压多猛"，是"怎么读数"——阶梯加压把系统逼出真实容量拐点：

阶梯加压法（Step Load）：
  每级 5 分钟：50 → 200 → 500 → 1000 → 2000 → 5000 并发（按目标容量×1.5 设计最上级）
  每级观察四维指标，两级之间留 2 分钟恢复窗口（避免前级余热污染后级读数）
  为什么不用瞬时打满（Spike）：一步到顶只能知道"挂不挂"，阶梯能知道"挂在哪级、怎么挂"

四维观测判读表（每级四格，拐点=任一维非线性劣化）：
  ① RT 维：P50/P99——拐点特征：P99 先陡增（长尾先崩），P50 还稳
  ② 吞吐维：QPS——拐点特征：加压但 QPS 不再涨（平台期=系统饱和）
  ③ 资源维：CPU/内存/GC/IO——CPU<70% 但 RT 飙=等锁或等下游（瓶颈在别处）
  ④ 中间件维：连接池 pending/MQ 滞后/缓存命中率——命中率跌 10%=流量分布偏或 TTL 集中

拐点与水位的换算（M6 day13 ×0.75 原则的全链路版）：
  拐点并发 = 四维中最先劣化的那一级
  安全水位 = 拐点容量 × 0.75（留 25% 缓冲吸收瞬时超调+故障叠加）
  容量结论写法：'下单链路拐点 6200 TPS，安全水位 4650 TPS，大促预估 5000 → 需扩消费实例'

常见"假拐点"辨析（压测报告的纠错能力）：
  压测机瓶颈：wrk 单机 4 线程打满 → QPS 平台是压测机的不是系统的（换机/分布式加压验证）
  LB 均匀性：某实例 CPU 100% 其他 30% → 是负载均衡问题不是容量问题（看各实例分位数）
  数据规模失真：空表压测 B+ 树 3 层，生产 5 层——容量结论打折（数据工厂灌 80% 规模再压）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Step Load | 阶梯加压 |
| Knee Point | 拐点（非线性劣化起点） |
| Platform Phase | 平台期（加压吞吐不涨） |
| Safe Watermark | 安全水位（拐点×0.75） |

## 4. 面试连接

**Q：怎么做容量评估？怎么知道系统极限？**
> 两步走：静态估算打底（day01 七步链条给数量级），动态压测定拐点。压测执行用阶梯加压——每级 5 分钟逐步加并发，每级看四个维度：RT（P99 先陡增）、吞吐（QPS 平台期=饱和）、资源（CPU 不高但 RT 飙=等锁等下游）、中间件（连接池 pending/MQ 滞后起飞）。拐点=最先劣化的那一级，安全水位=拐点×0.75（M6 day13 的原则：留 25% 吸收瞬时超调和故障叠加）。举例我们的下单链路：拐点 800 并发 5800 TPS，安全水位 4350，大促预估 5000 不达标——结论不是"优化代码"而是扩消费实例到 5 个，复压验证。另外要会识别假拐点：压测机自身打满、LB 不均、空表数据规模失真，三类都会给出错误的容量结论——压测报告的可信度取决于对这些陷阱的排查记录。

**Q：压测中 P99 飙高但 CPU 不高，怎么排查？**
> 这是典型的"等"而不是"算"——CPU 不高说明瓶颈不在计算，在等待。四步排查：①看连接池 pending——HikariCP 等连接会直接拉长 RT 且不耗 CPU，pending>0 基本就是它（我们 800 并发级 pending 9，正是拐点特征）；②看下游 RT——SkyWalking trace 拉最慢的 10 条链路，定位是哪个下游跳变慢（营销服务 200ms 是 P99 飙升主因的案例我们遇到过）；③看锁竞争——MySQL 的 innodb_lock_waits、Java 侧 jstack 搜 BLOCKED（day03 写瓶颈三查的复用）；④看 GC——jstat/Grafana 的 gc pause，Full GC 停顿会周期性拉高 P99 而 P50 无感。定位后对症下药：池小扩池（day05 公式）、下游慢熔断降级（day17）、锁热点分桶（day08/09）、GC 调参或降分配率。这题的本质：性能问题先分类"算的瓶颈还是等的瓶颈"，排查路径完全不同。

**Q：为什么安全水位是拐点×0.75？不留 100% 用满不是浪费吗？**
> 三个理由。第一，拐点右侧是排队论支配区：到达率接近服务率时，等待时间按 1/(1-ρ) 发散——ρ=0.9 时等待已是 ρ=0.5 的 10 倍，"用满"的代价是 P99 指数恶化而非线性增长。第二，生产流量不是压测机流量：压测是匀速的，生产是脉冲的（秒级突发 2~3 倍），拐点水位运行时一次脉冲就冲过拐点进入劣化区。第三，故障叠加：任何一个实例重启/依赖抖动，剩余实例要吸收它的份额——25% 缓冲就是故障时的吸收垫（N+1 实例思想的容量版）。所以"浪费"的 25% 实际是三份保险：脉冲缓冲+故障缓冲+劣化区隔离。大厂实践普遍在 70%~80% 水位，我们取 0.75 与 day13 单接口结论保持一致——同一原则贯穿单接口与全链路，这才是方法论。
