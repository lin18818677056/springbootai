## 1. 知识地图

```
RFC（Request For Comments）vs ADR vs 概要设计——文档三兄弟：
  ADR（M7 day12）：一个决策一页纸（背景/决策/理由/后果）——记录"为什么这么选"
  RFC：完整方案（本文档）——回答"这个系统怎么设计、怎么上线、怎么演进"
  概要设计：RFC 的技术子集——给开发看；RFC 面向"开发+业务+评审方"三方
  关系：RFC 里每个关键决策点可链接到对应 ADR；ADR 是 RFC 的决策索引

RFC 标准结构（九节，前五节今天完成，后四节 day13 补对比/灰度/回滚/演进）：
  0. TL;DR（结论先行！）——3~5 句话说清：做什么/方案一句话/关键数字/当前状态
     ——评审人 30 秒决定"要不要细看"，结论先行是写给评审人的尊重
  1. 背景与问题：为什么做（业务驱动）、不做会怎样（痛点的量化）
  2. 目标与非目标：可量化的目标（P99<5ms/日千万链）+ 明确不做的清单（day03 scope）
     ——非目标章节是 scope 控制的文档化，评审扯皮的防火墙
  3. 方案总览：一张架构图+核心决策表（决策/备选/理由/影响面）
  4. 详细设计：按领域分节（ID 生成/跳转/统计），每节=图+数据模型+关键代码
  5. 容量与性能：day02 四维估算结论表+压测报告引用（day04 P99 数据）
  6. 方案对比（day13）：哈希 vs 发号器、301 vs 302 的完整论证表
  7. 灰度计划（day13）：按流量百分比 1%→10%→50%→100%，每步观测指标
  8. 回滚预案（day13）：触发条件/执行步骤/数据回补
  9. 演进路线（day13）：MVP→V1→V2 与触发条件（day26 专讲）

结论先行写作法（金字塔原理在技术文档的应用）：
  反面教材："我们考虑了 A 方案……然后考虑 B 方案……最后选了 C"——评审人看到 B 才知道你要干嘛
  正确姿势："选择 C（发号器+Base62）。理由：唯一无冲突+可逆定位分片。
           A/B 被否原因见附录 A。"——先给答案，论证放后，评审人可按需下钻
  数字密度：每节至少 1 个数字（QPS/延迟/容量/百分比）——没有数字的设计等于没设计

与 M7 ADR 五段的对齐（伏笔兑现）：
  ADR 的[背景→决策→理由→后果→备选]是"决策粒度"，RFC 的[1,2,3→4,5→6]是"系统粒度"
  ——写 RFC 时每个关键决策内部仍按 ADR 五段展开，文档就有了"索引+正文"两层结构
```

## 2. 核心概念（中英对照）

# RFC：短链接系统设计 v1.0
状态：草稿 → 待评审 | 作者：me | 评审人：待定 | 日期：2026-09

## 0. TL;DR
为商城运营活动提供短链服务：日增 1000 万链、峰值跳转 1.4 万 QPS、跳转 P99<5ms。
方案一句话：发号器发号 + Base62 编码短码 + 两级缓存跳转 + 异步统计闭环。
关键数字：62⁷ 空间 3.5 万亿（十年无忧）/ 读路径 Caffeine+Redis 双层命中 99.9% /
统计崩溃丢失上界 5s（0.006%）。**决策亮点：code=Base62(id) 可逆，免映射表、免哈希冲突、
分片键一次到位。**

## 1. 背景与问题
运营活动链接（含 utm 参数）平均 180 字符，短信通道按 70 字符计费——一条带参链接 3 条短信费。
推广位点击数据无法归因（链接被截断/丢失参数），运营每月人工统计 2 人日。
不做会怎样：短信成本年 XX 万 + 归因数据缺失导致投放优化瞎子摸象。

## 2. 目标与非目标
目标：①跳转 P99<5ms（活跃码）②日增 1000 万链写 QPS 500/s 平稳承接
③点击统计分钟级延迟、误差<0.5% ④可用性 99.95%（跳转是营销命脉）
非目标（明确不做）：自定义短码（V2 评估）/ 短链撤销与改指向（发新码替代）/
App 内深度链接路由 / 防钓鱼主动识别（只做黑名单拦截，举报驱动）

## 3. 方案总览
（架构图：Client → Gateway → ShortLinkSvc →[Caffeine→Redis→MySQL 分片]
                              ↘ 点击事件 → MQ → StatsConsumer → DB
                              ↘ 黑名单布隆前置）
核心决策表：
| # | 决策 | 备选 | 理由 | 详见 |
|---|------|------|------|------|
| D1 | 发号器+Base62 | 哈希截断/自增 | 无冲突+可逆定位分片 | §4.1 |
| D2 | 302+60s 短缓存 | 301 | 统计是核心资产，短缓存降 40% 回源 | §4.2 |
| D3 | 内存聚合异步统计 | 同步 UPDATE | 跳转 P99 生死线，丢失 0.006% 可承受 | §4.3 |
| D4 | 布隆黑名单前置 | 实时查库 | 90% 流量 O(1) 放行，1 亿条 0.12GB | §4.2 |

## 4. 详细设计
### 4.1 ID 生成与短码（对齐 ADR-2026-009）
SegmentIdGenerator 双 buffer 预取（M8 day08 秒杀崩溃点的修复），10 万/号段；
Base62 编解码纯函数，code↔id 双向 O(7)；分片 id%64，跳转=decode+主键单次命中。
### 4.2 跳转链路
布隆前置（黑名单拦截）→ Caffeine(10 万/W-TinyLFU/TTL 10min) → Redis(24h 续期) →
MySQL 主键 → 302+Cache-Control:60s。不可变数据：无缓存失效问题。
### 4.3 统计闭环
内存 LongAdder → 5s flush → MQ → 批量合并落库 → 小时对账（0.5% 阈值）。
UV：HLL 实时展示 + T+1 离线重算结算，展示数据不进结算。

## 5. 容量与性能
四维估算（day02 模板）：读 1.4 万 QPS / 写 500 TPS / 3 年 4TB 含索引 / 带宽 22Mbps。
压测（day04）：Caffeine 命中 P99<1ms；全程含 Redis P99<5ms 达标（报告见附件）。

## 4. 面试连接

**Q：你的方案文档一般包含哪些内容？怎么让评审高效？（P8 协作面必问）**
> 我的 RFC 是九节结构，核心是结论先行：开头 TL;DR 五句话——做什么、方案一句话、三个关键数字、决策亮点，让评审人 30 秒建立全局；然后背景与目标，目标必须可量化（P99<5ms），同时专门有一节"非目标"写清楚不做什么——这是评审扯皮的防火墙，我在短链 RFC 里明确写了"不做自定义短码、不做改指向"，评审时没有人再问"为什么不能改链接"，因为 scope 谈判前置到了文档。主体是方案总览+详细设计，每个关键决策配一张三列表：决策、被否的备选、理由，并链接到对应 ADR——决策粒度用 ADR、系统粒度用 RFC，两层结构让"为什么"和"怎么做"都能快速定位。最后容量与性能一节全部是数字：四维估算结论加压测报告引用，没有数字的设计等于没设计。这条写作习惯来自 M7 的 ADR 训练——先练会一页纸说清一个决策，才谈得上三十页说清一个系统。

**Q：怎么判断一份技术文档写得好不好？（追问：你们团队文档质量如何保障？）**
> 三个硬指标：①数字密度——每节至少一个可验证的数字，通篇形容词（"高性能""高可用"）的文档直接打回；②可反驳性——每个决策带被否的备选，评审人能对着论证表挑刺，挑不出刺的方案才是好方案，写"无备选"等于宣告没思考过；③30 秒可定性——TL;DR 让人快速决定"细看还是略读"，尊重评审人注意力。团队保障机制：文档进 git 管理（修订可追溯）、评审前 24h 发出（拒绝会上首读）、评审纪要必须落行动项（谁/做什么/何时）。我在 M9 写了四份 RFC 两轮评审，最深的体会是：写文档时的强迫症，就是上线后的安全感——文档里含糊的一句话，就是生产上的一次扯皮。
