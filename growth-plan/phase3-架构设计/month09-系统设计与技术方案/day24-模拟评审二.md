```
  第一轮（day23）评的是"老方案"（商城 M5-M8 积累），考的是用新清单照旧方案；

  评审人 E（成本视角）：长连接网关的机器账算了吗？——"1 亿 DAU 多少网关机器？"
  评审人 F（新晋评审）：故意问基础问题——检验方案"新人可读性"（文档交接完备性 6.5）

评审执行（六维巡检，本轮重点在①⑤⑥三维——第一轮的③④维支付方案已深度覆盖）：
  1.3 合规约束 FAIL：IM 消息内容合规（内容安全审核）完全没提——

  1.4 组织复杂度 WARN：MVP 说"3 人 1 月"，但 WebSocket 网关+注册中心+可靠投递
      三件基础设施，3 人 1 月交付存疑——排期乐观
  5.1 资源成本 FAIL：网关机器账没算——补算：1 亿 DAU、10% 同时在线=1000 万连接，
      单网关 10 万连接 → 100 台网关（4C8G）+注册中心+MQ，月成本 ~6 万——
      这一笔账直接把方案从"顺手做"变成"要立项"（成本数字改变方案命运的实例）
  6.2 监控覆盖 WARN：消息送达率有指标，但"投递延迟分布"没有——
      P99<200ms 是 SLO，但缺 30 分钟级延迟（堆积探测）的监控
  6.5 文档完备 PASS：新晋评审 F 的 5 个基础问题全部能从 RFC 直接找到答案——
      结论先行+决策表的写法经受住了"新人测试"

评审纪要择要（本轮 6 问）：
  Q1（D）WebSocket 握手怎么认证？被伪造连接怎么办？
    答：握手带 token（复用商城 JWT）+服务端验证后才注册连接；心跳带轻量签名防会话劫持
    ——RFC 原文只写了"接入网关"，认证细节缺失 → 补 §4.0 接入认证节
  Q2（D）用户 A 能否伪造 conv_id 拉取 B 的会话消息？
    答：拉取接口必须校验"uid ∈ conv 成员"——RFC 有了但埋在数据模型节，
    应提升为安全设计显式条款 → 补成员校验清单（发/拉/已读回执三个接口）
  Q3（E）1000 万连接的注册中心（Redis）扛得住吗？
    答：算过单连接映射 ~200B×1000 万=2GB，Redis 单机够；但 QPS：上下线事件峰值
    10 万/s 写——Redis 单节点 8 万/s 扛不住 → 方案修订：上下线事件走 MQ 异步批量写
  Q4（F）为什么消息先落库不先推送？（新人理解成本）
    答：RFC §4.3 有论证——存储必达、推送尽力；落库是事实，推送是加速
  Q5（E）灰度期间新旧网关并存，注册中心怎么兼容？
    答：好问题！原方案没考虑——注册中心节点 ID 加版本段，新旧网关各注册独立前缀，
    路由层按版本转发 → v1.1 补双版本共存方案
  Q6（D）离线消息有大小限制吗？恶意大消息攻击？
    答：消息体上限 10KB（超限走文件消息），频控：单 uid 30 条/s——
    原方案有频控没提大小限制 → 补

修订闭环：im-rfc v1.0 → FAIL 2（内容合规/机器账）+ WARN 3 → v1.1
  ——成本账（Q3/1000 万连接→100 台网关）是本轮最重发现：没有机器账的方案是"技术方案"，
    有机器账的方案才是"立项方案"
```

## 3. 动手实操：网关机器账

```java
// learning/month09-system-design/src/GatewayCapacity.java（IM 网关容量成本核算——评审 Q3/Q4 的数字来源）
public class GatewayCapacity {
    public static void main(String[] a) {
        long dau = 100_000_000;                    // 1 亿 DAU
        double onlineRatio = 0.10;                 // 10% 同时在线（IM 经验值 8~15%）
        long onlineUsers = (long) (dau * onlineRatio);          // 1000 万连接
        long connsPerGateway = 100_000;            // 单网关 4C8G netty 承载 ~10 万连接
        int gateways = (int) Math.ceil((double) onlineUsers / connsPerGateway);  // 100 台

        double regMemMB = onlineUsers * 200 / 1024.0;           // 注册中心内存：uid→node 200B/条
        long updownEventsPerSec = 100_000;          // 上下线事件峰值（早上集中上线）
        System.out.printf("在线连接 %d 万 → 网关 %d 台(4C8G)%n", onlineUsers / 10_000, gateways);
        System.out.printf("注册中心内存 %.0fMB（单机 Redis 够）%n", regMemMB);
        System.out.printf("上下线事件 %d 万/s > Redis 单机 8 万/s → 必须走 MQ 异步批量写%n",
                updownEventsPerSec / 10_000);
        // 成本：网关 4C8G ~¥400/月 ×100 + Redis 哨兵 ~¥600 + MQ 集群 ~¥2000 ≈ ¥4.3 万/月
        double monthCost = gateways * 400 + 600 + 2000;
        System.out.printf("月成本 ≈ ¥%.1f 万 → 这是立项数字，不是技术玩具%n", monthCost / 10_000);
        // 结论：成本核算改变了方案的定位——技术可行性 ✓ 只是入场券，成本可行性决定立项
    }
}
```

## 4. 面试连接

**Q：如果老板问你"做 IM 要多少钱"，你怎么回答？（成本视角题）**
> 用机器账回答，不用形容词。算给他看：1 亿 DAU 按 IM 行业 10% 同时在线是 1000 万条连接，单台 4C8G 网关 netty 承载约 10 万连接，100 台网关起步；注册中心内存账是每连接 200 字节映射共 2GB，单机 Redis 够，但上下线事件峰值每天早上集中上线时 10 万每秒，超过 Redis 单机 8 万的写入上限，所以要走 MQ 异步批量写——这是容量账倒逼架构决策的实例。成本合计：网关 100 台乘 400 元月租加 Redis 哨兵加 MQ 集群，约 4.3 万每月，加上开发 3 人月和内容审核 API 按量费用，首年总投入大致 XX 万。这笔账的意义超出数字本身：它把方案从"技术可行"翻译成"立项决策"——老板真正问的从来不是"能不能做"，是"值不值、分几期做"。所以我所有 RFC 的容量节现在都强制含机器账，这个习惯就是本轮评审被成本评审人教育出来的——没有成本的架构方案是技术自嗨。

**Q：两轮模拟评审下来，你对架构评审最大的认知变化是什么？（元认知题）**
> 三个变化。第一，评审清单的价值在"照出盲区"不在"确认正确"——第一轮照出优惠券对账盲区（我八个月没想过），第二轮照出内容合规缺失（准入级约束被我当成增强项），这些都不是"想不想得到"的问题，是单一视角结构性地看不到的问题，独立视角加清单才能照出来。第二，成本和合规是方案的一等公民不是附录——机器账直接改变方案定位（技术方案变立项方案），合规缺失直接判 FAIL（不是 WARN），这两条在我早期的方案里都是空白。第三，好的挑战是礼物——新晋评审问"为什么消息先落库"逼我把论证写得更显式，成本评审问注册中心 QPS 逼出了 MQ 异步写的架构改进——被问住的每一个问题都变成了 v1.1 的修订项。所以我现在会把评审人的画像设计得故意刁钻：安全、成本、新晋三个视角，专挑方法论的软肋打——模拟评审的强度应该高于真实评审，上考场前用最难的题练。
