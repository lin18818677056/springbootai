## 1. 知识地图：六天主线串讲

```
W2 一条主线：从"请求-响应"思维切换到"长连接+消息"思维——完全陌生的领域靠六步法破题：

day08 扫码登录：三方五步时序+状态机（WAITING→SCANNED→CONFIRMED→USED）+两段式一次性 code
  → 核心收获：状态机模式（M7 day24）第四次复用——扫码/订单/消息/活动，"多方协作防状态错乱"
     是可迁移的模式；轮询→长轮询→WebSocket 的演进触发条件思维
day09 长连接选型：四方案（轮询/长轮询/SSE/WebSocket）压测对比（内存 500/300/200MB 级差）
  → 核心收获：选型跟数字走；网关三件套（注册中心/心跳短于 LB 超时/平滑发布）
day10 IM 消息模型：读/写扩散按群规模分档（500 人阈值）+ per-会话 Sequence + 未读数 O(1)
  → 核心收获：Feed 推拉是同源问题但结论不同——量级分布决定模型，不能背结论；
     conv_id 分片=会话内查询本地化，数据模型为读路径服务
day11 IM 可靠投递：至少一次投递+两层幂等（服务端 client_id/端侧 seq）+游标同步
  → 核心收获："严格一次"不可达，工程答案是"不丢+幂等去重"的契约翻译；
     每一跳超时重试必须有预算（M8 day05 思想）；消息先落库，推送只是加速器
day12 万人群：读扩散存储+在线广播推送+风暴四招（限流/合并/抽样/熔断切拉）
  → 核心收获：节点聚合（跨节点投递=节点数不是成员数）；"降级≠丢失"——推送是优化，
     拉取是保底，任何时刻双轨；大群的价值/成本比分析决定传播语义降级
day13 RFC 下：决策矩阵（权重打分）+灰度四步（准入/回退触发器）+回滚三要素+演进路线
  → 核心收获：回滚成本是设计出来的；后四节回答"怎么安全落地"，前五节回答"系统是什么"

两份 RFC 互查纪要（day13 遗留，day14 收口）：
  差距1 短链 RFC 的灰度节最初写的是"直接全量"——短链不可变+无状态，全量合理，
       但必须写明"为什么可以全量"的论证（无灰度也是一种决策，要给依据）
  差距2 IM RFC 的容量节缺"降级后的容量"（纯拉模式下单网关支撑量）——降级方案也要算账
  差距3 两份 RFC 的演进节触发条件单位不统一（一个用人数一个用 QPS）——统一为
       "业务量+资源水位"双指标触发
```

## 2. 12 题自测（先答后翻答案）

```text
1. 扫码登录为什么用"一次性 code 换 token"两段式，不直接发 token？
2. 二维码状态机的五个状态和非法流转示例？
3. 长轮询 1 万连接为什么同步 Servlet 会崩？改造关键是什么？
4. SSE vs WebSocket 各自内存开销？选型三问是什么？
5. WebSocket 心跳为什么是 30s？（和什么数字比较？）
6. IM 读扩散 vs 写扩散的分档阈值？各自读写路径特点？
7. 为什么用 per-会话 Sequence 不用全局发号器？
8. 未读数怎么算的？为什么是 O(1)？
9. "至少一次投递"下怎么做到"不重"？两层幂等各管什么？
10. 消息断网 10 分钟怎么补全？多端游标同步的坑是什么？
11. 10 万人群跨节点推送的关键优化？优化后投递次数是多少？
12. 灰度四步的准入指标和回退触发器？回滚三要素？
```

<details>
<summary>参考答案（先自己答完再展开）</summary>

1. token 泄露窗口最小化：确认响应即使被中间人截获，一次性 code 60s 且用后即废，换 token 那一步攻击者拿不到。
2. WAITING→SCANNED→CONFIRMED→USED（+EXPIRED 兜底）；非法示例：USED→SCANNED（回退）、WAITING→CONFIRMED（跳级）——状态机直接拒绝。
3. 1 万挂起请求=1 万线程，Tomcat 线程池（默认 200）爆掉；改异步 Servlet/DeferredResult，线程归还池，挂起只占内存。
4. 1 万连接：SSE 300MB/ws 200MB；三问：方向（单向 SSE/双向 ws）、基础设施（代理支持 Upgrade 吗）、团队能力（运维过长连接吗）。
5. 30s < Nginx/云 LB 空闲超时 60s——心跳必须短于中间设备的静默超时，否则假死连接。
6. ≤500 人写扩散（读路径快/写放大可控）；>500 读扩散（写一次/读侧懒加载摊平）。
7. 排序只在会话内有意义，全局单调浪费且集中压力大；INCR 会话维度天然分片压力。
8. 未读数=last_msg_seq−last_read_seq；两游标都是 O(1) 读取，无需计数。
9. 服务端：msg_client_id 唯一约束管"落库不重"；端侧：seq 判重管"渲染不重"。
10. 上线带 max_seq 拉增量（游标即断点）；多端坑：未读数按最落后端、已读同步按最领先端，两套语义分开。
11. 注册中心按节点聚合分组；跨节点投递数=在线节点数（≈50），节点内本地遍历。
12. 狗粮(功能)→1%(送达率>99.9%)→10~50%(水位<60%)→全量；触发器：P0 bug/送达率<99.5%/水位>80%；三要素：触发条件/执行步骤（含时限）/数据回补。
</details>

## 3. 弱项清单与补强

```text
自测暴露的三个薄弱点（诚实记录）：
① SSE 的 HTTP/1.1 六连接上限记成了浏览器全局限制——实际是同域名 HTTP/1.1 限制，HTTP/2 多路复用解除
   补强：day09 补一行更正注释；面试表述时主动说明协议版本前提
② 灰度准入指标只会说"看监控"，说不出"看哪个指标、阈值多少"——指标和阈值是灰度方案的血肉
   补强：把 IM 灰度表的指标列背下来（送达率 99.9%/投递 P99 200ms/水位 60%），迁移到支付 RFC
③ 状态机能画但"为什么不用 if-else"的论证不够锐利——正确答案：状态机是"合法性由数据定义，
   if-else 是合法性由代码路径定义"，前者新增状态只改流转表
   补强：把这句论证写进 M7 状态机知识卡的"为什么"一栏

周记（150 字）：W2 最大的突破是"陌生领域不慌"——长连接和 IM 是我零实战的领域，
```

## 4. 面试连接

**Q：你接触一个全新领域（比如 IM），怎么快速形成设计能力？（元问题，W2 周记的面试版）**
> 三步：先用六步法的第一步"需求澄清"把问题问对——什么方向的推送、多大规模的群、丢消息的容忍度，问题问对了一半答案就浮现了；然后做"模式映射"——新领域的概念往已知模式上挂：IM 的读/写扩散就是 Feed 的推拉问题变体，扫码状态机就是订单状态机换皮，可靠投递的游标同步就是订单对账的序号共识思想，消息风暴治理就是 M8 限流熔断四件套迁移——90% 的"新问题"是旧模式在新约束下的重新组合；最后用量化逼出决策——写扩散在 500 人以下可控、万人群必须读扩散，这些阈值都是算出来的不是背的。我在两周内从 IM 零基础到产出过评审的 RFC，靠的就是这套"问对问题→模式映射→量化决策"的流程，它比"背 IM 八股"快得多，而且面试官追问任何一层我都能往下拆。
