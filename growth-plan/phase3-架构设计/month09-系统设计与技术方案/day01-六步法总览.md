## 1. 知识地图

```
系统设计六步法（每步有时间盒和必答问题——45 分钟标准分配）：
① 需求澄清（5min）：问出功能性+非功能性需求
  必答：核心用例是什么？QPS/数据量/RT/一致性要求？明确"不做什么"（scope 控制）
  新手误区：跳过直接画架构图——评审第一刀就砍在这里
② 容量估算（5min）：M8 day01 七步链 + 本月 day02 的存储/带宽/缓存三维
  必答：峰值 QPS/存储 3 年量/带宽/缓存内存——数字决定架构档位
③ 接口设计（5min）：核心 API 签名（REST/gRPC）
  必答：5~8 个核心接口，写清请求响应与错误码——接口即契约，暴露领域理解
④ 数据模型（10min）：表结构/索引/分片键/缓存 key 设计
  必答：核心实体关系图+分库分表策略（M8 day03 三判据复用）+热点数据缓存设计
  ——时间最长的一步：数据模型错了后面全错
⑤ 架构演进（15min）：MVP→V1→V2 三级，每级画图+触发条件
  必答：第一版怎么最简可用？量到什么阈值触发下一级？（day26 演进叙事的框架预演）
⑥ 权衡与风险（5min）：TOP3 风险+预案+被否的备选
  必答：每个决策的 trade-off（CAP/成本/复杂度）——"没有银弹"的显式表达

先兑现 M8 day30 思考题："秒杀方案拿去评审，第一个被挑战的会是什么？"
我的答案：不是技术点，是"复杂度与团队规模不匹配"（组织维度挑战）。
论证：五层漏斗+分桶+对账+预案，是小团队接不住的运维复杂度——技术最优≠组织最优。
应对（也是 M9 的答案预演）：六步法第⑤步演进叙事——MVP 版"答题+DB 乐观锁+限流"三人可维护，
触发条件（日订单>10 万或团队>8 人）再演进到 Redis 预扣版——把"复杂"变成"分期"。
启示：系统设计的完整答案=技术维度（六步法）×组织维度（演进分期/团队认知成本）——day25 TCO 呼应

六步法的底层逻辑：它是"工程版"的架构评审 Checklist（M8 day27 六维）——
  ①②对应需求契合（评审维①）、③④对应瓶颈与一致性（维②③）、⑤对应可演进（维⑤）、⑥对应可用性与成本（维④⑥）
  ——写方案时按六步走，评审时按六维查，同一套知识的两视图
```

```text
练手拆题（30 分钟限时）："设计一个分布式限流器"（故意选 M8 day17 做过的——检验方法论能否复述已有知识）：
① 需求：集群级精确限流（网关/服务通用），QPS 精度 ±5%，可用性 99.99%（限流器挂了宁可放行）
② 估算：100 个服务实例×平均 1000 规则=10 万规则；决策 QPS 50 万（每请求 1 次判定）
③ 接口：allow(ruleId, tokens) / batchAllow / updateRule
④ 数据模型：规则表（Redis hash：ruleId→{limit, window}）；计数 zset 滑窗（day17 方案）
⑤ 演进：MVP=Redis Lua 集中计数 → V1=Token Server 集群（精确+本地兜底）→ V2=多 TS 分片
⑥ 风险：Redis 挂（本地均分兜底放行）/TS 单点（2+ 部署）/时钟偏移（用服务端时间）
——结论：六步法把 M8 的散点知识组织成了"可表达的设计"，这就是方法论的价值
```

## 4. 面试连接

**Q：给你 45 分钟设计一个系统，你的流程？（系统设计面试开场必问）**
> 六步法走，时间盒 5/5/5/10/15/5。前 15 分钟定地基：需求澄清问清核心用例和非功能四项（QPS/RT/一致性/可用性），明确不做什么；容量估算用现成链条——QPS 七步链（DAU→峰值→读写比）加存储三维（行数×行宽×3 年增长、带宽=QPS×报文、缓存=二八×热数据集），数字决定架构档位；接口设计给 5~8 个核心 API，标注幂等性。中间 25 分钟是主体：数据模型 10 分钟（ER+分片键三判据+缓存 key），架构演进 15 分钟——MVP→V1→V2 三级，每级有量化触发条件，这一步最能区分候选人：背模板的人画一张终态大图，有工程经验的人会告诉你"第一版绝不上这个组件，因为团队接不住"。最后 5 分钟权衡与风险：TOP3 风险带预案、至少一个被否的备选。这套流程我在 M9 用四份 RFC 完整跑过——短链、IM、支付，评审过也返工过，不是纸上谈兵。

**Q：（M8 思考题兑现）你的秒杀方案拿去评审，会被挑战什么？**
> 第一个被挑战的一定不是技术，是"复杂度与团队规模不匹配"——五层漏斗加分桶加对账加预案，三个人的团队接不住这种运维复杂度，技术最优不等于组织最优。我的应对是把复杂度做成分期：MVP 版就是答题+DB 条件更新+网关限流，三个组件三个人能维护，日订单 10 万以内完全够用；触发条件到了（订单量或团队规模）再演进 Redis 预扣版，再往后才是分库分表。评审时主动把演进路线图画出来，把"复杂"翻译成"分期可控"，这个挑战就变成了加分项。这个思考也改变了我做设计的习惯：现在每个方案我都会先问"这个团队半年内接得住吗"，接不住的一律进演进路线而不是首版——工程是人的工程。
