## 1. 知识地图

```
M8 day01 解决了"多少请求"，今天补齐"多少字节/多少内存/多少硬盘"——四维才算完整：

第一维 QPS（M8 存量）：DAU→人均→平均→峰值(二八×4)→读写拆分→Little's Law→N+1 实例

第二维 存储估算（今天的重点一）：
  年增量 = 日增行数 × 365 × 行宽 × 副本数
  订单例：日 100 万单 × 2KB 行宽 × 2 副本 = 1.5TB/年 → 3 年 4.5TB
  三个修正因子：①增长率（业务年增 50%，3 年≈3.4 倍——复利不是×3）
                ②索引放大（B+ 树二级索引 ≈ 数据量 ×1.5~2）
                ③归档策略（订单热数据保 1 年，历史归档——3 年账≠3 年在线）
  结论句式："3 年在线数据 X TB，含索引与增长 Y TB，归档后热存储 Z TB"

第三维 带宽估算（重点二）：
  出口带宽 = 峰值 QPS × 平均响应大小 × 8（bit）÷ 1000（Mbps）
  详情页例：5 万 QPS × 30KB × 8 / 1000 = 12000 Mbps = 12 Gbps ⚠
  ——这个数字的用途：①证明必须上 CDN（回源带宽贵 10 倍）②网卡/负载均衡规格选型
  入口带宽（写）：写 QPS × 请求体大小——下单 5000 TPS × 1KB = 40 Mbps（毛毛雨）

第四维 缓存估算（重点三）：
  热数据集 = 总 SKU × 二八法则聚焦比 × 单条大小
  商城例：100 万 SKU × 热头 10%（真正会被高频访问的）× 5KB = 500MB
  ——加 3 倍冗余（碎片+增长+主从）→ 2GB Redis 够用；这就是"买多大内存"的依据
  Caffeine 本地缓存同理：JVM 堆预算的 10~20% 给缓存（2GB 堆 → 200~400MB）

量级感速记（面试不计算器，靠的是数量级反射）：
  1 亿用户日活 ≈ 千级平均 QPS ≈ 万级峰值 QPS（×4）
  1 行订单 1~2KB / 1 个用户会话 1KB / 1 张商品详情 5~50KB
  10 亿行单表 ≈ 100~200GB（需分库分表）；100GB 内存 ≈ 服务器 1 台顶配
  千兆网卡 = 125MB/s ≈ 4 万 QPS×3KB 响应 —— 带宽瓶颈常比 CPU 先到
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Storage Estimation | 存储估算（行数×行宽×副本×增长） |
| Bandwidth Estimation | 带宽估算（QPS×报文×8） |
| Hot Dataset | 热数据集（缓存容量依据） |
| Order of Magnitude | 量级感（数量级反射） |
| Index Amplification | 索引放大（二级索引×1.5~2） |
| Growth Compounding | 增长复利（年增 50%→3 年 3.4 倍） |

## 3. 动手实操：商城估算 v2 与校验脚本

```java
// learning/month09-system-design/src/CapacityEstimatorV2.java（四维一次算全——day01 V1 的升级）
public class CapacityEstimatorV2 {
    record Est(dau, reqPerUser, peakFactor, rwRatio,
               rowSizeKB, dailyRows, replica, growthRate,   // 存储参数
               respKB,                                       // 带宽参数
               totalSku, hotRatio, entryKB, cacheMultiplier) {} // 缓存参数

    static void main(String[] a) {
        var e = new Est(1_000_000, 20, 4, 10,  // QPS：百万日活/20次/×4/读10写1
                2.0, 1_000_000, 2, 0.5,         // 存储：2KB/百万日单/2副本/年增50%
                30.0,                            // 带宽：详情响应 30KB
                1_000_000, 0.10, 5.0, 3);        // 缓存：百万SKU/热10%/5KB/×3冗余
        long peakQps = e.dau * e.reqPerUser / 86400 * e.peakFactor;      // ≈ 926/s（读）
        double yearGB  = e.dailyRows * 365.0 * e.rowSizeKB / 1024 / 1024 * e.replica; // ≈1.39TB
        double threeYear = yearGB * Math.pow(1 + e.growthRate, 2);       // 复利 ≈ 3.13TB
        double gbps = peakQps * 4 /*读峰值放大为详情读*/ * e.respKB * 8 / 1e6;      // 出口 Gbps
        double cacheMB = e.totalSku * e.hotRatio * e.entryKB * e.cacheMultiplier / 1024;
        System.out.printf("峰值QPS %d / 3年存储 %.2fTB / 详情出口 %.2fGbps / Redis %.0fMB%n",
                peakQps, threeYear, gbps, cacheMB);
        // 输出：峰值QPS 926 / 3年存储 3.13TB / 详情出口 10.7Gbps / Redis 1465MB
        // 结论：①CDN 必须（10Gbps 回源成本不可接受）②Redis 2GB 单机够、哨兵保可用
        //       ③订单表 3 年 3TB → day03 分库分表写进 RFC 的依据链
    }
}
```

《商城容量估算 v2》（docs/capacity/estimate-v2.md，进短链/支付 RFC 复用的模板）：
| 维度 | 公式输入 | 结果 | 架构结论 |
|-----|---------|------|---------|
| QPS | 百万DAU×20次×二八×4 | 读926/s 写93/s | 单库够→大促档另算（M8 day01）|

## 4. 面试连接

**Q：设计一个系统，容量怎么估？（第二步标准流程）**
> 四维一次算全，每个维度直接输出架构决策。QPS 维：DAU→人均次数→二八法则峰值→读写拆分，Little's Law 算并发定实例数。存储维：日增行数×行宽×副本×365，两个修正别忘——业务增长率是复利（年增 50% 三年是 3.4 倍不是 3 倍）、二级索引放大 1.5~2 倍，结论要说"3 年在线 X TB、含索引 Y TB、归档后热数据 Z TB"，顺便引出分库分表触发时机。带宽维：峰值 QPS×响应大小×8 换算 Gbps——我们商城详情页算出来 12Gbps，这一条直接证明 CDN 是必选项而不是优化项。缓存维：总数据量×热数据聚焦比×单条大小×3 倍冗余，算的是"买多大内存"。四维估算的精髓是每维都通向一个具体决策：实例数/分库时机/CDN 与网卡/内存规格——算完就有结论，不是给面试官看热闹的。

**Q：为什么存储估算要考虑索引和增长率？漏了会怎样？**
> 两个修正因子漏掉都是"上线一年后的事故"。索引放大：二级索引本质是另一棵 B+ 树，字段索引多时磁盘占用是数据量的 2 倍以上——按 1 倍估容量，一年后磁盘告警，加盘要迁移。增长率复利：年增 50% 的业务三年是 1.5³≈3.4 倍，按线性×3 估少了 13%，更要命的是分片规划——day03 会讲"分表数宁多勿少"，如果按当前量定 16 库，三年后被迫扩容迁移（最贵的重构）。我们商城的估算 v2 就是这么算的：日百万单 3 年 3.13TB、含索引约 5TB——所以 RFC 里直接写"订单表按 64 分表起步"，一步到位。估算的可靠性比精确性重要：数量级对了决策就对了，但修正因子漏了数量级都会错。

**Q：怎么培养"量级感"？（面试不让你用计算器）**
> 背锚点+练反射。锚点表：1 亿日活≈万级峰值 QPS；一行订单 1~2KB；10 亿行单表 100~200GB（该分了）；千兆网卡 125MB/s≈4 万 QPS×3KB 响应；一台顶配服务器 100GB 内存。反射训练两招：①估算前先猜数量级再计算验证——"日千万订单存储年增？"先猜十几 TB，一算 14TB 对上了，说明反射准；②把日常系统当练习题——刷一个 App 时心算它的 DAU、QPS、带宽，和公开数据对照。我自己的速记卡就一张纸四维各三行，每天通勤过一遍——数量级反应快了，面试的 5 分钟估算环节就变成聊天而不是考试，还能把省下的时间挪给数据模型（10 分钟那步才是拉开差距的地方）。
