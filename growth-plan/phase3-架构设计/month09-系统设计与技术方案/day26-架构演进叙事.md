# Day 26 · 架构演进叙事：MVP→V1→V2 / YAGNI

> **今日目标**：架构演进叙事方法论——每级量化触发条件、YAGNI 的正确用法与滥用、演进路线图写作法；四份 RFC 补演进章节的正式论证。
> **时长**：演进方法论 1.5h / 四 RFC 演进章节补强 2h / YAGNI 辨析 0.5h
> **今日产出**：《演进路线图写作法》+ 四 RFC v1.2（演进节定稿）

## 1. 知识地图

```
演进叙事的三要素（day01 六步法第⑤步的方法论深化）：
  ① 分级：MVP（最小可用）→ V1（生产级）→ V2（规模级）——每级一个交付边界
  ② 触发：每级的"进入条件"必须量化（业务量+资源水位双指标——day14 互查纪要的修订落地）
  ③ 退出：每级要有"为什么现在够用"的论证（防过度设计）+"什么时候不够"的预判（防欠设计）

MVP→V1→V2 的通用模式（四份 RFC 的演进节提炼）：
  | 级 | 特征 | 组件纪律 | 论证焦点 |
  |----|------|---------|---------|
  | MVP | 验证业务成立 | 组件最少化（能用单库不用中间件）| "最简为什么够" |
  | V1 | 扛住生产流量 | 上必要基础设施（缓存/队列/主从）| "触发条件到没到" |
  | V2 | 扛住规模增长 | 上规模组件（分库分表/多活/治理全套）| "演进不推倒重来" |
  演进的核心纪律：V2 的架构在 V1 写代码时就要"留缝"——分片键从第一天就想好、
  接口预留分页游标、配置外置——演进是"换零件"不是"推倒重来"

量化触发条件实例（四 RFC 的演进节定稿摘录）：
  短链：MVP→V1 触发（日链量>10 万 或 跳转 P99>5ms）
        V1→V2 触发（3 年存储预估>2TB 或 峰值跳转>5 万 QPS）→ 分库分表
  IM：MVP→V1（群成员>500 或 在线连接>1 万）→ 读扩散大群+注册中心
      V1→V2（单群>5 万 或 消息峰值>1 万条/s）→ 广播流+风暴治理全套
  支付：MVP→V1（支付成功率<99.9% 或 单渠道占比>80%）→ 渠道双活+三方对账
       V1→V2（商家数>1 万）→ 分账平台化
  商城：订单量>10 万/日 或 团队>8 人 → 秒杀从"答题+DB 乐观锁"演进 Redis 预扣版
       （M8 day30 思考题的正式回答在四份 RFC 中全面应用）

YAGNI 的正确用法与滥用（day23 评审争议的方法论收口）：
  正确用法：YAGNI="You Aren't Gonna Need It **Yet**"的工程化执行——
    不做，但要"留缝"：不抽象"可对账资产"接口（第三类资产出现再抽象），
    但每类资产的对账实现都按统一三要素写（快照/流水/核对规则）——抽象延后，规约先行
  滥用 1："现在不需要就不设计"——分片键都不想，V2 扩容时全表迁移（最贵的重构）
  滥用 2："永远做最简"——MVP 上线后触发条件到了还不动（欠设计债比技术债更难还）
  辨析口诀：YAGNI 管"现在不建楼"，不管"不画地基"——触发条件到了能 48h 内
  拿出 V1 方案，说明地基画了；触发条件到了才"从零开始想"，说明 YAGNI 用成了借口

演进叙事的写作法（评审/答辩的表达框架）：
  反面："我们的架构支持亿级流量"（终态大图冒充演进——背模板者的写法）
  正面："当前 MVP 架构（图）支撑日 X 量级，因为 Y 够用；当 Z 指标达到阈值（数字），
       演进到 V1（图），改动范围限于 A 模块，预估成本 B 人日；进一步到 V2（图）……"
  ——每级：图+为什么够+什么时候不够+到下一级的改动范围与成本
  这个叙事的本质：把"架构能力"翻译成"投资节奏"——P8 汇报的语言
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Evolutionary Architecture | 演进式架构（分级+触发+留缝）|
| Trigger Condition | 触发条件（业务量+水位双指标）|
| YAGNI | 你不会需要它（延迟实现，不延迟设计）|
| Over/Under-design | 过度/欠设计（演进要双向防）|
| Investment Narrative | 投资叙事（架构=分期投资）|
| Migration Path | 迁移路径（换零件不推倒重来）|

## 3. 动手实操：演进触发条件检查器

```java
// learning/month09-system-design/src/EvolutionTrigger.java（演进触发条件：量化检查器）
import java.util.*;

public class EvolutionTrigger {
    record Trigger(String name, double current, double threshold, String action) {
        boolean fired() { return current >= threshold; }
    }
    public static void main(String[] a) {
        // 商城秒杀演进检查（M8 day30 思考题的落地工具）
        var checks = List.of(
            new Trigger("日订单量（万）", 6.5, 10, "→ 演进 Redis 预扣版"),
            new Trigger("团队人数", 5, 8, "→ 复杂度治理可启动"),
            new Trigger("秒杀峰值 QPS（万）", 1.2, 5, "→ 分桶+集群限流全套"));
        System.out.println("══ 商城秒杀演进触发检查 ══");
        checks.forEach(t -> System.out.printf("%-18s 当前 %.1f / 阈值 %.1f %s%n%s%n",
                t.name(), t.current(), t.threshold(),
                t.fired() ? "🔴 已触发" : "🟢 未触发",
                t.fired() ? "  └→ " + t.action() : "  └→ 维持现状（YAGNI 合规）"));
        // 演进留缝检查（V1 写码时问自己四个问题）：
        System.out.println("""
            ══ "留缝"自检四问（每级交付时过一遍）══
            1. 分片键/分片规则想好了吗？（V2 扩容不迁移的前提）
            2. 接口预留游标/分页了吗？（大数据量下的兼容）
            3. 配置外置了吗？（换组件不改代码）
            4. 新组件有开关吗？（可回滚的演进）""");
        // 输出：日订单 6.5 万未触发 → 维持现状（有数字的"不做"才是 YAGNI，没数字的"不做"是懒惰）
    }
}
```

## 4. 面试连接

**Q：怎么避免过度设计？（YAGNI 题，但要答出深度）**
> 先把 YAGNI 用对：它的完整语义是"你不会需要它**直到需要**"——管的是"现在不建楼"，不管"不画地基"。我的执行纪律是"抽象延后，规约先行"：评审时被建议抽象"可对账资产"接口，当时只有订单和优惠券两类资产，抽象是 YAGNI，我延期了；但每类资产的对账实现都按统一三要素写（快照、流水、核对规则），所以第三类资产出现时抽象只是归并现有实现，48 小时能交付——这就是"留缝"。反向的过度设计信号我防三条：组件数超过当前规模的必要集（日 10 万链的短链上了分库分表）、为"可能的未来"写配置项和扩展点（没人用的灵活度是维护负债）、评审时说不出"最简为什么够"（论证缺失）。还有一条容易被忽略的：欠设计比过度设计更危险——MVP 上线后触发条件到了还不动，欠下的架构债是复利的，过度的成本是一次性的。所以我的演进节每级都带量化触发条件加 EvolutionTrigger 检查器，"做不做"不看感觉看数字——有数字的"不做"才是 YAGNI，没数字的"不做"是懒惰。

**Q：讲一个你主导的架构演进过程？（演进叙事实战）**
> 用秒杀的演进讲，正好是四份 RFC 里最完整的演进链。起点是 M8 的认知：五层漏斗的完整方案对三人小团队是接不住的运维复杂度——技术最优不等于组织最优。所以 MVP 版刻意做减法：网关答题加 DB 条件更新加单机限流，三个组件，日 10 万订单内完全够用，写代码时就留了缝——库存 key 设计成分桶格式、状态机独立模块、限流配置外置。触发条件写死：日订单 10 万或峰值 QPS 5 万。现在跑到 6.5 万日订单，EvolutionTrigger 检查未触发，维持现状——每一次"维持现状"的决策都有数字支撑。当触发条件到了，演进到 V1 的动作清单已经预演过：Redis Lua 预扣替换 DB 条件更新（改动只在库存模块）、集群限流替换单机（只改网关配置）、MQ 削峰接入（订单模块加消费者）——预估 10 人日，因为分片键和状态机第一天就定了，不需要动数据模型。这个案例我想表达的演进观：演进式架构的核心资产不是代码是"预演过的路线图"——每一级的图、触发条件、改动范围和成本都提前写好，演进时刻就变成执行而不是设计，业务无感，团队从容。
