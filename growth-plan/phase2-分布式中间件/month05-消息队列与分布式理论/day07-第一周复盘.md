## 1. 知识地图：第一周主线串讲

```
day01 选型：价值（解耦/异步/削峰）与代价（一致性/复杂度/延迟）
day02 架构：NameServer 无状态路由（AP 的工程体现）+ Broker 存储 + 集群/广播
day03 存储：CommitLog 混写保顺序写 → ConsumeQueue 索引两跳读 → IndexFile 运营查
day04 可靠闸门：发送 ACK → 刷盘（SYNC/ASYNC）→ 复制（SYNC/ASYNC Master）+ mmap/sendfile
day05 消费分配：Rebalance 三触发 → 必然产生重复窗口 → 长轮询=拉的简单+推的实时
day06 消费兜底：RetryTopic 16 级退避 → DLQ 人工修复 → 幂等三板斧（Redis/唯一索引/状态机）

一条主线：MQ 的一切设计都在"不丢 & 不重 & 快"三角里找平衡——
  不丢：三道闸门 + 至少一次投递
  不重：做不到 Exactly-Once 就让消费幂等
  快：  顺序写 + PageCache + 零拷贝 + 长轮询
```

## 2. 主菜：《MQ 可靠性保障清单》（正式版，直接存 learning/docs/）

```markdown
# MQ 可靠性保障清单（以 RocketMQ 为例，规则可迁移）

## 发送段（丢不丢的第一关）
- [ ] 核心链路用同步发送或异步发送（禁止 OneWay 传业务消息）
- [ ] 发送失败有重试（retryTimesWhenSendFailed≥2），重试自动换 Broker
- [ ] 强一致场景用事务消息（半消息+回查）替代"先落库再发消息"
- [ ] 发送侧记录发送日志（msgKey+状态），异常可人工补发
- [ ] 超时预算明确（sendMsgTimeout 默认 3s，链路压测验证过）

## 存储段（Broker 端不丢）
- [ ] 刷盘策略与业务匹配：金融 SYNC_FLUSH / 一般交易 ASYNC+主从
- [ ] 主从复制：至少 ASYNC_MASTER（多副本），关键数据 SYNC_MASTER 或 DLedger
- [ ] 磁盘容量监控（CommitLog 80% 告警），过期删除时间确认（fileReservedTime）
- [ ] 消息保留期 > 最大故障恢复时间（保证重放能力）

## 消费段（不丢+不重的最后一关）
- [ ] 消费逻辑幂等：Redis 预判 + DB 唯一索引 + 业务状态机三层
- [ ] 先处理后提交位移；异常返回 RECONSUME_LATER 进重试队列
- [ ] maxReconsumeTimes 按业务设定，避免无意义 16 次重试
- [ ] DLQ 告警 + 人工修复 SOP（定位→修复→重投→复盘）
- [ ] 消费者组订阅关系全局一致（防 Rebalance 互踢）
- [ ] 消费耗时监控：单条 P99 < 心跳周期，避免被误踢反复 Rebalance

## 兜底段（一切失效之后）
- [ ] 关键业务有对账 Job（如库存/订单一致性核对，day26 落地）
- [ ] 有消息轨迹（day24 开启），出问题 5 分钟内定位到消息
- [ ] 有应急预案：积压追平方案（day13）、Broker 宕机切换演练（day26）
```

## 3. 六题自测（每题 2 分钟，录音或写要点）

```text
1 NameServer 无状态意味着什么？为什么不用 ZooKeeper？30s 路由不一致影响什么？
2 画 CommitLog→ConsumeQueue 读取路径。为什么 20 字节定长？tagHash 为什么可能误判？
3 ASYNC_FLUSH 下"进程崩溃"和"机器断电"丢的数据一样多吗？（不一样，PageCache 兜底进程级崩溃）
4 Rebalance 必然产生重复的原因？三个触发条件里哪个是人为大忌？
5 幂等三板斧各自的失效场景？（Redis 宕机→唯一索引兜；唯一索引为什么永远不失效？）
6 一条消息重试 16 次进 DLQ，它的 delayLevel 间隔是怎样的？为什么退避越来越久？
```
