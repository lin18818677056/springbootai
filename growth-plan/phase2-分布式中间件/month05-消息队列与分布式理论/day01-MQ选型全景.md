# Day 01 · MQ 选型全景：价值、代价与四选一

> **今日目标**：用秒杀项目的真实场景反推 MQ 的三大价值（解耦/异步/削峰）与三大代价，输出《MQ 选型决策表》——本月所有深入都从"为什么需要它"开始。
> **时长**：概念 1.5h / 决策表 2h / 面试表达 1h
> **今日产出**：《MQ 选型决策表》+ 三大价值在秒杀中的实证笔记

## 1. 知识地图

```
没有 MQ 的世界（同步调用链）：
  下单 → 扣库存 → 发短信 → 加积分 → 发优惠券
  RT = 50+30+200+40+60 = 380ms，短信服务一挂全链路挂

有 MQ 的世界（异步解耦）：
  下单 → 扣库存(30ms) → 发一条消息 → 返回 80ms
                          ↓
        短信/积分/优惠券 各自消费，谁挂了不影响主链路

三大价值（背下来，面试开场就用秒杀举例）：
  ① 解耦 Decoupling：生产者不知道消费者是谁，加订阅方零改动
  ② 异步 Asynchronization：主链路只做必须同步的事，RT 从 380→80ms
  ③ 削峰 Peak Clipping：5000 并发秒杀 → 队列排队 → 消费端按能力 500/s 处理

三大代价（说得出代价才显得专业）：
  ① 一致性变弱：同步变异步 = 强一致变最终一致，要补幂等与对账
  ② 复杂度上升：多了一个要运维/监控/排障的系统
  ③ 延迟不确定：高峰期消息排队，实时性敏感场景要评估
```

## 2. 核心概念：四大 MQ 对比（中英对照）

| 维度 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| 定位 | 日志流平台 | 业务消息中间件 | 传统企业消息 | 云原生消息流 |
| 吞吐 | 百万级/s | 十万级/s | 万级/s | 百万级/s |
| 延迟 | ms 级（批量换的） | ms 级 | μs~ms 级（最低） | ms 级 |
| 事务消息 | 有（偏流处理） | 有（业务友好，半消息+回查） | 无 | 有 |
| 延迟消息 | 无（需改造） | 有（18 级+时间轮） | 有（插件） | 有 |
| 消息回溯 | 按 offset 强 | 按时间/offset | 弱 | 按 offset |
| 存储 | 每个 Partition 独立日志 | 所有队列共用 CommitLog | 内存+磁盘混合 | 分层存储（BookKeeper） |
| 典型场景 | 日志/数仓/流计算 | 电商交易/订单/金融 | IoT/低延迟任务路由 | 大数据+消息一体 |

```text
一句话选型（面试标准答案）：
  日志采集/大数据管道 → Kafka（吞吐王，生态贴合 Flink/Spark）
  电商交易/订单链路 → RocketMQ（事务+延迟+轨迹，业务特性全）
  老系统对接/超低延迟 → RabbitMQ
  云上多租户存算分离 → Pulsar
我们秒杀项目选 RocketMQ：要事务消息（扣库存）+ 延迟消息（关单）+ 轨迹（排查）
```

## 3. 动手实操：用秒杀场景填《MQ 选型决策表》

```text
《MQ 选型决策表》模板（你的版本要填满 6 行）：
| 决策点 | 候选 | 我们的场景 | 结论 | 一句话理由 |
|--------|------|-----------|------|-----------|
| 订单异步化 | Kafka vs RocketMQ | 要事务消息保障扣库存 | RocketMQ | 半消息+回查业务语义清晰 |
| 订单超时关单 | 轮询 DB vs 延迟消息 | 15 分钟延迟 | RocketMQ 延迟消息 | 免轮询，时间轮精准触发 |
```

## 4. 面试连接

**Q：你们为什么选 RocketMQ 不选 Kafka？**
> 不背参数表，用"三需求一对比"答：我们的交易链路需要①事务消息保障扣库存与落单一致（Kafka 事务偏流处理语义，半消息+回查更贴合业务）、②延迟消息做关单（Kafka 原生没有）、③消息轨迹排查（Kafka 要自己搭）。吞吐上万 QPS 的订单链路 RocketMQ 完全够用；Kafka 我们用在日志采集，各得其所。——给出"按场景分工"的结论，比"谁好谁坏"高一个层级。

**Q：MQ 的引入一定让系统更快吗？**
> 不是。异步缩短的是"用户感知 RT"，不是总工作量。排队期间消息在堆积，如果消费能力 < 生产速率持续增长，积压会放大故障（消费者内存/重试风暴）。所以引入 MQ 的同时必须回答"消费端吞吐多少、积压阈值多少告警"——这就是 day13 的伏笔。
