# Day 25 · 秒杀二阶段②：积压演练与消费端监控告警

> **今日目标**：把 day13 的积压方法在秒杀工程上真实演练一遍（订单事件积压→追平→复盘），补齐消费端监控六格与告警规则，定稿秒杀版《积压应急预案》。
> **时长**：演练 2.5h / 监控告警 2h / 预案定稿 30min
> **今日产出**：秒杀积压演练记录 + 监控告警清单 + 秒杀版应急预案

## 1. 知识地图

```
秒杀场景的积压特殊性（对比 day13 通用版）：
  ① 积压对象是订单事件——每条背后是真金白银的单，绝不能跳过（非核心才能跳）
  ② 积压的业务后果：用户看到"排队中"（前端已在 M4 做了排队页）→ 体验可容忍 X 分钟
     ——所以先算"积压消化时长"再决定动作，不是无脑扩容
  ③ 峰值特征：秒杀开始的 5 分钟积压是设计内的（削峰本来就是故意的！）
     ——监控要区分"设计内削峰"与"事故性积压"：DIFF 曲线在活动开始后爬升后回落=正常

消费端监控六格（秒杀版，接 M4 step05 的监控体系）：
  ① DIFF（堆积量）：阈值 10 万告警（按消化速率换算成分钟数更直观：积压>可容忍时长告警）
  ② 消费 TPS：跌破基线 50% 告警（可能消费者挂了/变慢）
  ③ 单条消费耗时 P99：>500ms 告警（防心跳超时被踢→Rebalance 风暴）
  ④ 重试量（%RETRY% 主题 TPS）：突增告警（下游故障前兆）
  ⑤ DLQ 数量：>0 就 P2 告警（有单子处理不了了）
  ⑥ 消费者在线数：跌破预期实例数告警（先于堆积发现）

告警分级（值班响应视角）：
  P3 邮件：DIFF 缓慢上涨 / 重试率上升 ——工作时间处理
  P2 电话/IM：DIFF 超消化时长 / DLQ>0 / 消费者掉线 ——30 分钟内响应
  P1 大盘：交易成功率下跌（秒杀下单接口）——全链路应急，MQ 只是嫌疑之一

消费端限流（防御性编程，防消费打挂下游）：
  场景：积压追平时一口气拉出大量消息 → 消费端瞬间打爆 DB
  手段：①消费线程池上限（天然限流）②pullBatchSize 控制批量 ③消费前查下游健康（熔断半开）
  ——限流的本质：保护的不是 MQ，是下游 DB/服务（Sentinel 在消费端同样适用，M4 的知识迁移）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Designed Peak Clipping | 设计内削峰（活动开始的预期积压） |
| Incident Backlog | 事故性积压（异常导致） |
| Consume Baseline | 消费基线（平时 TPS 的统计值） |
| Alert Threshold | 告警阈值（DIFF/TPS/P99/DLQ 六格） |
| Consumer Rate Limit | 消费端限流（线程池+批量+熔断） |
| Time-to-Drain | 消化时长（积压量/消费 TPS，决策的核心数字） |

## 4. 面试连接

**Q：大促时 MQ 积压了 20 万订单消息，用户在投诉，怎么办？**
> 按决策顺序答：①先算 Time-to-Drain：积压 20 万 / 消费 TPS 500 = 400 秒——6 分钟内能消化且业务有排队页兜底 → 优先提速能力而不是慌；②提速三板斧按序上：消费线程池→消费者实例（受限于队列数）→批量写库；③全程盯六个指标（DIFF/TPS/P99/重试/DLQ/在线数），防"追积压打爆 DB"的次生灾害（消费端限流意识）；④事后复盘：为什么积压超预期？队列数规划/消费逻辑慢查询/下游抖动？进预案迭代。加分点："我实际演练过这个场景——20 万积压用三板斧 X 分钟追平，幂等与顺序消费保证追平期间 0 重复 0 乱序。"（演练过=底气）

**Q：怎么区分"设计内削峰"和"事故积压"？**
> 看三个特征：曲线形态——设计内削峰是"活动开始爬升→消费能力持续消化→回落"，事故积压是"持续上涨不回头"；根因关联——削峰与活动开始时间强相关，事故伴随下游故障/消费者掉线信号；二次指标——削峰时单条耗时正常，事故时 P99 拉高或 TPS 断崖。监控上我把 DIFF 换算成"消化分钟数"告警，而不是裸告警堆积量——业务能容忍 10 分钟排队，告警就该在"预计消化超 10 分钟"时触发。这个"换算"是运营思维进入技术设计的细节。
