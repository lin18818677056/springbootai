# Day 13 · 消息积压治理：100 万积压追平演练

> **今日目标**：模拟 100 万条积压并演练追平（扩容+转发新 Topic 两套方案），输出《积压应急预案》——大促值班时照着做，这就是"稳定性能力"的实锤证据。
> **时长**：造数 1h / 演练 2.5h / 预案文档 1.5h
> **今日产出**：积压演练记录 + 《积压应急预案》

## 1. 知识地图

```
积压的本质：生产速率 > 消费速率 持续累积
  消费速率上限 = 队列数 × 单队列串行吞吐（或 消费者数×线程数，取小）
  ——所以队列数是并行度天花板！建 Topic 时就该按峰值消费能力规划队列数

积压排查三板斧（先定位再动手）：
  ① 看 Dashboard：DIFF 值（堆积量）、消费 TPS 是掉到 0 还是有但慢
     掉到 0 → 消费者挂了/被踢（Rebalance 风暴/订阅不一致/心跳超时）
     有但慢 → 消费逻辑变慢（慢 SQL/下游故障/GC）
  ② 看消费线程：jstack 看消费线程池在等什么（DB 连接池耗尽是常客）
  ③ 看生产端：是不是流量突刺（大促/爬虫/上游重试风暴）

治理方案三层（面试按这个层次答）：
  ① 预防层：队列数规划（消费峰值 × 冗余）、消费幂等（敢扩敢跳）、监控告警（DIFF 阈值）
  ② 应急层（正在积压）：
     a 扩消费者实例（受限于队列数：8 队列最多 8 个有效消费者——超出只是闲着）
     b 提升消费并行度：消费线程池调大 + 批量拉取（pullBatchSize）/批量处理
     c 紧急扩队列 + 灰度重建消费组（新组=新 offset 从头消费，有幂等才敢干）
  ③ 兜底层（积压 100 万+，常规手段追不上）：
     转发新 Topic：写一个"搬运工"消费者（只拉不处理）→ 10 倍队列数的新 Topic
                  → 起临时消费者集群并行消费 → 追平后下线临时资源
     跳过策略：非核心消息直接 ACK 丢弃（日志类），核心消息绝不跳（靠对账补偿）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Backlog / Diff | 积压量（Dashboard 的 DIFF 总和） |
| Consume TPS | 消费 TPS（消费速率） |
| pullBatchSize | 单次拉取条数（调大提升批量处理效率） |
| Consumer Thread Pool | 消费线程池（consumeThreadMin/Max） |
| Forwarding Topic | 转发新 Topic（积压兜底的"拆流"方案） |
| Skip Strategy | 跳过策略（重置 offset 到最新，非核心消息应急用） |
| Reset Offset | 位移重置（重放/跳过都靠它，mqadmin resetOffsetByTime） |

## 3. 动手实操：100 万积压追平演练

```powershell
# ① 造积压：写 ProducerBurst.java 用 20 线程快速发 100 万条（每条 sleep 模拟小消息）
#    消费端故意把 consumeThreadMin=1 且处理 sleep(50ms) → 消费跟不上 → 积压形成
#    观察 Dashboard DIFF 一路涨到 1,000,000（截图，这就是"事故现场"）

# ② 演练方案 A：扩消费者
#    起第 2/3/4 个消费者实例 → 观察 DIFF 下降速率变化
#    起第 9 个消费者（队列只有 8 个）→ 观察它的日志：分不到队列，纯闲置！
#    结论亲手验证："扩容受限于队列数"

# ③ 演练方案 B：调并行度
#    消费线程池 1→32 + pullBatchSize 32→1000 → 观察 TPS 提升（记录前后数据）
#    若瓶颈在 DB（处理要写库）：加批量 INSERT + 连接池调大 → TPS 再上台阶
#    （记录每次调整的 TPS 数据，做成阶梯表——这就是面试的"调优有量化记录"）

# ④ 演练方案 C：转发新 Topic（100 万+兜底）
#    Forwarder 消费者：拉到消息原样发到 BACKLOG_TOPIC_16（16 队列）
#    起 16 个临时消费者（或 4 个×4 线程）并行消费新 Topic
#    记录：搬运速率、追平总耗时、追平后下线临时资源
#    ⚠ 演练用 IdempotentConsumer 兜底（方案 C 可能与在途消费产生少量重复）

# ⑤ （可选）跳过演练：mqadmin resetOffsetByTime -s now 重置到最新
#    观察 DIFF 归零——理解"跳过=放弃这批消息"的代价，非核心才可用
```

## 4. 面试连接

**Q：线上 100 万消息积压，怎么处理？（高频场景题）**
> 四步走，先定位后动手：①定位积压原因（消费者挂了？消费变慢？流量突刺？）——不同原因解法完全不同；②紧急扩容：加消费者实例到队列数上限（说清"受限于队列数"），同时把消费逻辑变快（线程池/批量/慢 SQL 优化）；③追不上就拆流：写搬运工把消息转发到 16 倍队列数的新 Topic，临时集群并行消费，追平后回收；④事后复盘：队列数规划、消费幂等（敢扩敢重放）、DIFF 告警阈值、核心/非核心消息分级预案。最后亮数据："我在自己环境演练过 100 万积压，方案 C 追平耗时 X 分钟。"（演练过的场景题=降维打击）

**Q：积压会不会把 Broker 压垮？**
> 不会立刻——RocketMQ 消息在磁盘（CommitLog），积压只是占磁盘，不占内存。真正的风险链：①磁盘写满 → Broker 保护性拒绝写入；②消费者重启/重平衡后从旧 offset 重拉 → 拉取风暴冲击 Broker 网络；③积压的旧消息集中到期（延迟消息场景）→ 突发投递。所以预案里必须有磁盘容量告警与"重放限速"意识。（把"积压"从恐慌话题变成容量规划话题）
