> **今日目标**：纠正"CAP 三选二"的主流误读，用 Nacos AP/CP 切换 + 两周以来积累的中间件案例验证理论，写《CAP 纠错笔记》——从今天起每个理论都要落到具体中间件。
> **时长**：理论 2h / 实例映射 2h / 笔记定稿 1h
> **今日产出**：《CAP 纠错笔记》+ 理论→中间件映射表 v1

## 1. 知识地图

```
CAP 正确打开方式（先破后立）：
  破——三大误读：
    误读① "三选二，CAP 各拿一个"→ 错。P（分区容错）不是可选项！
    误读② "平时也必须在 C 和 A 里选"→ 错。C/A 的取舍只在【分区发生时】才矛盾
    误读③ "CA 系统存在"→ 单机系统谈不上 CAP（CAP 讨论的是分布式）。

  立——正确表述：
    P 是前提：网络分区（Partition）在分布式系统里一定会发生（交换机抖动/机房切割）
              拒绝 P = 拒绝分布式。所以真实选择是：
              分区发生时：C（返回一致但可能不可用）还是 A（返回可用但可能不一致）？
    平时呢？  CA 都能给（无分区时一致+可用兼得）——CAP 是"分区时的取舍"，不是"常态取舍"

  一个精确判例（背熟，面试秒杀级回答）：
    RocketMQ NameServer：Broker 心跳断了，NameServer 仍返回旧路由 → 选 A（可用）
    Kafka unclean=false：ISR 空，分区拒绝服务 → 选 C（一致）
    两者都是合法选择，取决于业务：路由旧 30s 无妨（AP），交易消息不能错（C 倾向）

BASE（CAP 中 A 选择的工程化方法论）：
  Basically Available 基本可用：降级也可以（限流/熔断/兜底数据）
  Soft State 软状态：允许中间态（"支付处理中"）
  Eventually Consistent 最终一致：给时间就一致（对账/补偿/重试收敛）
  与 MQ 的关系：整个异步消息体系就是 BASE 的化身——
    半消息=软状态，重试+对账=最终收敛，限流降级=基本可用（M4/M5 做的一切都在这套框架里）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Consistency | 一致性（线性一致：读到最新写入） |
| Availability | 可用性（每个请求都能得到非错误的响应） |
| Partition Tolerance | 分区容错（网络分区时系统仍能运行） |
| Network Partition | 网络分区（节点间通信断裂，集群分裂成孤岛） |
| BASE | 基本可用/软状态/最终一致 |
| Eventual Consistency | 最终一致 |
| AP / CP | 分区时选可用 / 分区时选一致 |

## 4. 面试连接

**Q：讲讲 CAP？系统设计时怎么用？**
> 三层递进：①破误读——P 不是可选项，CAP 是"分区发生时 C 与 A 的取舍"，平时 C/A 兼得；②给判例——NameServer 返回旧路由是 AP，Kafka unclean=false 是 CP 倾向，都是合法选择；③给方法论——选 A 的代价用 BASE 兜（软状态+最终一致+补偿），并说明"我们的秒杀就是 BASE 化设计：可用性优先+对账收敛"。能从定理讲到工程方法论，这道题就答穿了。

**Q：BASE 和最终一致听起来很虚，具体是什么？**
> 拿自己项目讲：秒杀下单是软状态（订单"处理中"），库存异步扣（事务消息半消息=软状态），一致性靠三层收敛（消费重试→死信人工→对账 Job）。"最终"不是无限期：我们对账周期 5 分钟、告警兜底，一致性收敛时间是有 SLA 的。虚词落实为机制+时限+兜底，就不虚了。
