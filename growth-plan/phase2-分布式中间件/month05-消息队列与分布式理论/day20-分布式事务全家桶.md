# Day 20 · 分布式事务全家桶：从 2PC 到最大努力通知

> **今日目标**：一次性讲透 6 种分布式事务方案（2PC/3PC/TCC/SAGA/消息最终一致/最大努力通知）的原理、代价与适用场景，输出《分布式事务选型决策树》初版——W4 的实战将在真实代码里兑现其中两种。
> **时长**：原理 3h / 决策树 2h
> **今日产出**：《分布式事务选型决策树》v1 + 六方案对比表

## 1. 知识地图：六方案一图流

```
强一致系（能不用就不用，性能与可用性代价大）：
  2PC（Two-Phase Commit 两阶段提交）
    协调者问全员"能提交吗"(Prepare，锁资源) → 全员 YES 才 Commit，一人 NO 全体回滚
    三宗罪：同步阻塞（Prepare 后资源锁死）、协调者单点（挂了全员卡死）、
           第二阶段部分失败数据不一致（Commit 消息没送到部分节点）
    落地：XA（数据库层）、Atomikos/Seata AT 模式（应用层改良：一阶段本地提交+undo log）
  3PC：加 CanCommit 预询 + 超时自动提交 → 缓解阻塞，引入新不一致风险，几乎没人用（知道即可）

最终一致系（互联网标配）：
  TCC（Try-Confirm-Cancel）
    业务层两阶段：Try 预留资源（冻结库存）→ Confirm 确认（扣冻结）→ Cancel 释放
    三个坑（面试必答）：空回滚（Try 没到 Cancel 先到→Cancel 要能识别）、
      悬挂（Cancel 后迟到的 Try→Try 要检查是否已回滚）、幂等（三个接口都可能重试）
    适用：金融强业务语义（转账），改造成本高（每接口写三个方法）
  SAGA：长事务拆成一串本地事务 Ti + 补偿 Ci，正向执行，失败逆向补偿
    编排 Orchestration（中央协调器，如 Seata Saga/Temporal）vs 协同 Choreography（事件驱动互相订阅）
    适用：流程长/跨系统/无法改造为 Try-Confirm 的场景（如调外部支付）
    风险：补偿逻辑复杂、无隔离性（中间态可见，要业务容忍）
  消息最终一致（可靠消息）：本地消息表 或 事务消息（day10/day22 对比落地）
    本地事务+发消息的原子性 → 消费端幂等 → 最终一致。BASE 化身，吞吐高，最常用
  最大努力通知：重试 N 次通知+查询对账兜底（支付回调就是这个：支付宝通知商户）
    可靠性最低，靠对方提供查询接口兜底

对比锚点（一张表压全部）：
  方案        | 一致性 | 性能 | 改造成本 | 隔离性 | 典型场景
  2PC/XA      | 强     | 差   | 低(框架) | 好     | 传统数据库跨库、低并发
  TCC         | 最终   | 中   | 高       | 好(预留)| 资金/库存等核心资源
  SAGA        | 最终   | 高   | 中       | 差     | 长流程跨系统
  消息最终一致 | 最终   | 高   | 中       | 差     | 订单-库存-通知类异步链路
  最大努力通知 | 弱     | 高   | 低       | 无     | 第三方回调
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| 2PC (Two-Phase Commit) | 两阶段提交（Prepare/Commit） |
| XA Protocol | XA 规范（数据库两阶段提交标准） |
| TCC (Try-Confirm-Cancel) | 补偿型事务（资源预留/确认/取消） |
| SAGA | 长事务分步补偿模式 |
| Orchestration / Choreography | 编排（中心协调）/ 协同（事件驱动） |
| Compensation | 补偿（逆向操作，如"扣款"的补偿是"退款"） |
| Empty Rollback | 空回滚（Try 未执行就 Cancel） |
| Suspension | 悬挂（Cancel 执行后 Try 才到达） |
| Local Message Table | 本地消息表 |
| Best Effort Notification | 最大努力通知 |

## 3. 动手实操：决策树绘制

```text
《分布式事务选型决策树》绘制规则（存 learning/docs/tx-decision-tree.md）：
  从"业务能不能容忍中间态"开始分支：

  能强一致且并发低？ → 2PC/Seata AT（说清代价：锁+性能）
  ↓ 不能
  核心资源需要预留语义（钱/库存）且能改造三接口？ → TCC（防空回滚/悬挂/不幂等）
  ↓ 不能改造
  长流程跨系统（有外部调用）？ → SAGA（编排 or 协同二选一）
  ↓ 不是长流程
  异步可解耦（A 成功后 B 必须发生）？ → 消息最终一致（本地消息表 or 事务消息）
  ↓ 都不是（通知第三方）
  最大努力通知 + 查询对账兜底

  决策树每个叶子节点必须带：①代价提示 ②我们项目的实例
  （消息最终一致→秒杀扣库存链路；最大努力通知→模拟支付回调场景）
自检：拿三个虚构需求走一遍决策树，路径必须唯一且说得通
```

## 4. 面试连接

**Q：分布式事务你们怎么做的？为什么不用 XA？**
> 先定性：我们场景是跨服务异步链路（下单-库存-通知），追求可用性与吞吐，选择 BASE 路线——消息最终一致（事务消息+消费幂等+对账兜底）。不用 XA 的原因：2PC 同步阻塞+协调者单点，高并发下性能不可接受；AT 模式虽改良但仍强耦合锁窗口。然后分层展开 TCC（若核心资金场景，讲三坑）、SAGA（若长流程）。收尾观点："没有最好的方案，只有匹配一致性预算的方案——交易核心走 TCC/事务消息，边缘通知走最大努力，强一致留给单库事务。"

**Q：TCC 的空回滚、悬挂、幂等分别怎么解决？**
> 三问三答带实现：空回滚——Cancel 前查 Try 事务记录，不存在则记一条"已空回滚"标记直接返回成功；悬挂——Try 执行前检查"是否已被 Cancel"（有标记则拒绝执行）；幂等——事务记录表唯一键+状态机（Try/Confirm/Cancel 都可能重试，各状态只允许一次流转）。本质都是"一张事务控制表 + 唯一约束 + 状态机"——和你已有的幂等三板斧是同一套思想换了个马甲（面试时点破这个"万法归一"是加分项）。
