# Day 26 · 秒杀二阶段③：故障注入与对账修复

> **今日目标**：对秒杀 MQ 链路做三场故障演练（kill Broker / 网络分区 / 毒消息），每场都用"对账发现→轨迹定位→修复→复盘"闭环处理，产出《故障演练报告》——这是本月含金量最高的项目产出。
> **时长**：演练 3h / 对账与修复 2h / 报告 1h
> **今日产出**：故障演练报告（三场）+ 对账工具 + 修复记录

## 1. 知识地图

```
故障演练（Chaos Engineering）三要素：
  ① 稳态假设：系统在正常状态下的可度量行为（秒杀版：下单成功率/库存账平/订单-库存一致）
  ② 故障注入：主动制造异常（kill 进程/断网/数据污染）
  ③ 验证与改进：观察系统表现是否符合预期，暴露弱点并修复
  ——你的秒杀项目已经历 M4 压测（性能）+ 今天故障演练（韧性），作品完整度上一台阶

三场演练设计（每场都走完整闭环）：
  演练① kill Broker：
    注入：docker compose stop broker（下单进行中）
    预期：发送失败重试换 Broker（单 Broker 环境则失败进本地缓存/报错）→ 客户端收到限流降级响应
    验证点：Redis 预扣成功但 MQ 发送失败的单 → 事务消息半消息/本地缓存如何兜底？
           Broker 恢复后消息是否补发？→ 用户侧最终是否 0 丢单？
  演练② 网络分区（模拟 Broker 与消费者隔离）：
    注入：docker network disconnect 隔离 broker 与 consumer
    预期：消费者心跳超时被踢 → Rebalance → 恢复网络后自动重连重平衡
    验证点：隔离期间的重复消费窗口（day05 学的）幂等是否兜住；恢复后 DIFF 是否自动追平
  演练③ 毒消息（数据污染）：
    注入：手工发一条格式非法的订单事件（字段缺失）
    预期：消费异常 → 重试 16 次 → DLQ → 告警
    验证点：毒消息是否堵塞其他消息（Concurrently 不堵/Orderly 堵队列——顺序消费的代价实测）；
           DLQ 修复重投流程走一遍

对账体系（宏观账，与轨迹微观镜配合）：
  库存对账：Redis 剩余 + 已售(DB 订单数) + 关单回补 = 初始库存（恒等式）
  订单对账：订单表状态 vs 支付回调记录 vs 消息轨迹（三方核）
  工具：ReconcileJob 定时跑 + 演练后手动全量跑，差异明细落表
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Chaos Engineering | 混沌工程/故障演练 |
| Steady State | 稳态假设（正常行为的可度量定义） |

| Blameless Retro | 无指责复盘（演练报告的写法原则） |

# 简化版：docker pause <consumer容器> 15s（模拟进程假死）→ unpause
# 观察：心跳超时→被踢→Rebalance 日志→恢复后重平衡+可能的消息重投 → 幂等日志验证兜底

# 三场演练各跑一次全量对账，结果写进报告

## 4. 面试连接

**Q：你们系统做过故障演练吗？讲一个印象最深的。**
> STAR 完整叙事：S-背景（秒杀 MQ 链路上线二阶段，验证韧性）；T-任务（验证 Broker 宕机、网络分区、毒消息三场景的数据一致性与恢复能力）；A-行动（docker 注入故障→稳态监控→对账 Job 核库存恒等式→轨迹定位异常消息）；R-结果（发现两个真问题：①毒消息会堵死顺序消费队列——加了 suspend 时间与最大重试修复；②Broker 恢复后部分单据靠重试收敛耗时 40s 超预期——加了发送端本地缓存补发）。亮点收尾："演练不是证明系统没问题，而是把问题暴露在演练日而不是大促日——这场演练发现的两个问题在大促里就是事故。"（这段话本身就值一个 P7 评价）

**Q：对账系统怎么设计？**
> 三层：①恒等式设计——库存对账用"初始=已售+剩余+锁定"这类业务恒等式，差异即异常；②粒度分级——全量对账（每日低峰）+增量对账（每 5 分钟，只核变动区间）+演练专项（即时全量）；③差异处理——差异落表不自动修（防止对账本身出错放大故障），分级告警人工确认后修，修完复盘根因。配合轨迹：宏观对账发现"哪一批"不一致，微观轨迹定位"哪一条"出问题——宏观+微观双镜组合。
