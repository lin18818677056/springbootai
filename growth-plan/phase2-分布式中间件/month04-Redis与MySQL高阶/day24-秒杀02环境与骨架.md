## 1. 知识地图

```
本项目技术栈全景（对照 step01 §4-5，每个选型的理由）：
  Spring Boot 3.x        Web 骨架（JDK17+，虚拟线程可选）
  MyBatis-Plus           ORM（简单 CRUD 快，扣减 SQL 手写才可控）
  Redis 7                预扣库存/一人一单/令牌（--requirepass 生产习惯）
  RocketMQ 5.3.1         削峰+事务消息+延迟消息关单（三合一，选它不选 Kafka
                         的理由：事务消息与延迟消息是秒杀刚需）
  Sentinel 1.8.8         网关/接口限流 + 预热模式（秒杀陡增流量的标配）

docker compose 拓扑（infra/ 目录）：
  ┌mysql:8.0────┐ ┌redis:7-alpine┐ ┌rmqnamesrv:9876┐
  │ 3306 seckill│ │ 6379 密码保护 │ └──────┬────────┘
  │ init.sql 自动建表│ │ maxmemory 512mb│ ┌─────▼─────────┐
  └─────────────┘ │ allkeys-lru  │ │rmqbroker:10911 │
                  └──────────────┘ │ -n namesrv:9876│
                                   │ brokerIP1=127.0.0.1│
                                   └────────────────┘

两张表的两个唯一索引（★今天最重要的理解题）：
  seckill_order.order_no  UNIQUE  → 消费幂等的 DB 底线（重复消息插入必抛异常）
  seckill_order.(user_id,goods_id) UNIQUE → 一人一单的 DB 底线
    （Redis 层 SISMEMBER 预判只是快筛——DB 唯一索引才是法律）
  思想：Redis 层挡量，DB 层保真——和两级扣减同一哲学

init.sql 的 version 字段（乐观锁伏笔）：
  UPDATE ... WHERE goods_id=? AND stock_count>0 就是"无版本号乐观锁"
  （用业务条件当版本判断，比 version 字段更贴合扣减场景）
```

### 3.3 建表设计解读卡（抄进笔记，面试被问"表怎么设计的"就用）

```text
seckill_goods（库存表）逐字段意图：
  stock_count   DB 兜底库存（UPDATE WHERE stock_count>0 的主角）
  version       预留乐观锁（本方案用业务条件扣减，字段备用）
  start/end_time 活动时间窗（Lua 里 EXISTS init key 的数据来源）
seckill_order（订单表）逐字段意图：
  order_no UNIQUE   幂等底线：MQ 重复投递插入报 DuplicateKey → 捕获即忽略
  (user_id,goods_id) UNIQUE  一人一单底线：并发双请求最多一条插得进去
  status 0待支付/1已支付/2已关闭  关单状态机（step04 延迟消息的判断依据）
★设计哲学一句话：所有"不许发生"都在 DB 用约束兜底，
  Redis/MQ 层的校验都是为了性能，不是为了正确性。
```

## 4. 面试连接

**Q：你们的表结构怎么设计的？为什么这么设计？**
> 从约束讲起："订单表两个唯一索引是整个防超卖/防重的 DB 底线——order_no 唯一索引保证 MQ 重复投递不产生重复订单，(user_id,goods_id) 唯一索引保证一人一单在并发下也绝对成立。库存表用 stock_count>0 条件更新做无版本乐观锁，Redis 预扣与 DB 实扣偏差靠对账 Job 兜底。"收尾升华："我的原则是 Redis/MQ 层的校验为性能服务，正确性全部由 DB 约束兜底——分层信任，各司其职。"

**Q：为什么选 RocketMQ 不选 Kafka/RabbitMQ？**
> 秒杀有三个刚需逐个对号：① 事务消息（半消息+回查）解决"Redis 预扣成功但消息必达"——Kafka 无事务消息（只有本地事务表方案）；② 延迟消息做超时关单——RocketMQ 5.x 支持任意秒级延迟，RabbitMQ 要装插件、Kafka 要自己做时间轮；③ 消息可靠性（同步刷盘+主从）金融级可配。Kafka 优势在大吞吐日志流场景，秒杀这种业务交易消息 RocketMQ 更对口。

**Q：bootRun 启动报连不上 RocketMQ，怎么排查？**
> 给排查路径而不是背答案：① docker compose ps 看容器健康；② mqadmin clusterList 看 broker 注册的 IP——Windows Docker 常见坑是 broker 注册了容器内网 IP，客户端无法回连，broker.conf 配 brokerIP1=127.0.0.1 解决；③ 再看应用日志的具体连接地址与配置是否一致。这套"从基础设施到应用配置"的排查顺序本身就是工程素养的展示。
