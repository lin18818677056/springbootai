## 2. 主菜：《分库分表决策树》正式版（存 learning 仓库 docs/ 目录）

```text
《分库分表决策树》—— 拿到"表扛不住了"诉求后的判断流

【Q0】单表多大？增速如何？
  ├─ <500 万行且增速平缓 → 不拆。给索引优化方案（month03 全套）
  └─ ≥2000 万行 / 增速 >500 万每月 / 磁盘水位 >70% → Q1

【Q1】慢 SQL 治理过了吗？
  ├─ 没有 → 先跑 month03 治理五步（可能白拆）
  └─ 治理完仍顶不住 → Q2

【Q2】读多还是写多？
  ├─ 读占 70%+ → 先读写分离 + 缓存（day22/day12），重新评估
  └─ 写也顶不住 / 单表还是巨大 → Q3

【Q3】能归档吗？
  ├─ 有明显冷热（如 6 个月前订单）→ 归档库瘦身 60%+，重新评估
  └─ 数据都热（如 IM 消息近期全热）→ 决定拆 → Q4

【Q4】垂直还是水平？
  ├─ 表内有超大字段/业务混杂 → 垂直分表/分库（先做，成本最低）
  └─ 行数/写入是主要矛盾 → 水平分片 → Q5

【Q5】分片键怎么选？
  ├─ 80% 查询带某维度（如 user_id）→ 它当分片键
  ├─ 有第二查询维度 → 基因法埋 ID（day16）
  └─ 时序数据 → range 按时间
  → 分片数：预留 2-4 年增长，取 2 的幂（翻倍扩容友好）

【Q6】全局 ID？→ 雪花（主）/ 号段（时钟不可信场景）（day17）

【Q7】迁移怎么做？→ 双写六步法 + 对账三层 + 灰度切读（day20）

【Q8】拆后查询治理清单（上线前过一遍）：
  □ 游标分页替代深分页  □ 跨片聚合归并策略  □ ES 承接复杂查询
  □ 跨库 JOIN 改业务组装/冗余  □ 分布式事务边界标注（month05）
```

## 4. 面试连接（周复盘的"串珠讲法"训练）

**Q：讲一个你做过的分库分表设计（完整项目叙述，15 分钟版）**
> 按"决策→设计→落地→验证"四段讲，全程引用本周代码资产：
> ① 决策：500 万行膨胀实验数据（day15）+ 漏斗排除法；
> ② 设计：user_id 分片 + 基因法双维路由（10 万对拍不一致=0，day16）+ 雪花 ID 含回拨防护（day17）；
> ③ 落地：手写五步管线 Demo（day18），生产用 ShardingSphere 对照；
> ④ 验证：双写+对账程序捕捉人为差异（day20），灰度切读方案。
> ★叙事纪律：每个结论跟一个数字/实验（"迁移率 75% 是我实测的"），这是 P7+ 与背书者的分水岭。

**Q：如果重新设计，你会改哪个决定？**
> 满分陷阱题，考反思能力。模板："我会更早引入游标分页规范——上线初期没管住前端翻页，深分页问题后置爆发；以及全局 ID 如果重来会直接用带时间戳的雪花而非自增+映射表，省掉一轮迁移。"（展示：真实项目里没有完美设计，敢说改进点=真的做过）
