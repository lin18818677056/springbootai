## 1. 知识地图

```
同步 vs 异步链路（step04 §1，改造动机一句话：DB 是瓶颈）：
  【改造前】下单 → Redis 预扣 → DB 扣库存 → 插订单 → 返回
            RT ≈ 200ms+（5000 并发下 DB 行锁排队爆炸）
  【改造后】下单 → Redis 预扣 → 发事务消息 → 返回"排队中"  RT < 50ms
            消费端按 DB 能力匀速：扣库存+落单
            前端轮询 /seckill/result 拿最终结果

事务消息半消息机制（step04 §2，解决"预扣成功 ↔ 消息必达"）：
  ① 发半消息（Half，消费者不可见）
  ② 执行本地动作（Redis 标记预扣凭证）
  ③ 成功 → COMMIT 消息可见 / 失败 → ROLLBACK（并回滚 Redis 预扣）
  ④ Broker 收不到确认 → 定时回查（Check Back）本地状态
  ★回查要轻量：只查凭证存在性，不做业务

三层消费幂等（step04 §3，层层递进的防重墙）：
  第一层 Redis 预判：tryLock(orderNo, 60s) → 挡 99% 重复（快）
  第二层 唯一索引：orderNo UNIQUE → 重复插入抛 DuplicateKey 捕获忽略（准）
  第三层 条件更新：UPDATE ... WHERE status=0 → 状态机兜底（稳）
  为什么不只要第一层？Redis 锁过期瞬间/主从切换都可能漏 → 层层冗余

超时关单（step04 §4，延迟消息 + 状态机）：
  下单成功 → 发 15 分钟延迟消息 → 到点检查：仍待支付？
    → 关单（WHERE status=0 改 2）+ 回补 DB 库存 + 回补 Redis 预扣
  并发冲突自解：用户恰好同时支付 → 双方都用条件更新抢状态
    → 只有一个成功 → 天然幂等（不用分布式锁！）

可靠性全景表（step04 §5，面试就背这张）：
  生产端丢消息 → 事务消息+回查
  Broker 宕机  → 同步刷盘 + 主从
  重复投递     → 三层幂等
  消费失败     → 重试 16 次递增 → 死信队列 → 人工补偿
  消息积压     → 监控 Lag → 扩消费者/批量转发
```

## 2. 核心概念（中英对照）

| 英文 | 中文 | 要点 |
|------|------|------|
| Half Message | 半消息 | 事务消息第一阶段 |
| Check Back | 回查 | Broker 反查本地状态 |
| Consumer Idempotency | 消费幂等 | 三层防重 |
| Delay Message | 延迟消息 | 超时关单引擎 |
| Dead Letter Queue | 死信队列 | 重试耗尽的归宿 |
| State Machine | 状态机 | 条件更新防并发 |

## 4. 面试连接

**Q：下单改异步后，怎么保证订单不丢不重？**
> 不丢：事务消息三段保障——半消息→本地凭证→回查，发送失败回滚 Redis 预扣；Broker 同步刷盘+主从防宕机丢失；消费失败重试 16 次+死信兜底。不重：三层幂等递进——Redis 锁挡 99% 重复（快）、orderNo 唯一索引绝对兜底（准）、状态条件更新防并发回退（稳）。收尾："我做过故障演练：kill 消费者重启后消息继续消费无丢失，手工重发消息 10 次订单仍只有 1 条。"（day27 验收项即面试证据）

**Q：压测中发现的最大的瓶颈是什么，怎么解决的？**
> 用真实数据讲（以 step05 §4 常见瓶颈为骨架，填你的实测）："第一轮压测 TPS 只有 X，六格看板发现 MySQL TPS 先到顶+消费 Lag 堆积——定位到消费线程数（20）超过热点行锁吞吐，锁等待排队。把消费线程降到 N+批量提交后 TPS 提升到 X'。"强调方法论："每次只改一个变量，前后数据说话——瓶颈修复不是玄学是实验。"（这条回答的含金量=你是不是真压测过）

**Q：流量再涨 10 倍，你的架构怎么演进？**
> 分层演进路线：① 库存分桶——1 行热点拆 10 桶并行扣（Redis 侧），合并统计；② 热点单元化——秒杀商品按用户路由到独立单元，故障隔离；③ 多级缓存下沉——本地缓存命中率再提升，Redis 集群水平扩；④ MQ 扩容+消费者弹性伸缩；⑤ 前置层再收紧——验证码难度动态调整。收尾："架构演进不是推倒重来，是把漏斗每一层按新水位重新校准。"（这句是 P8 视角）
