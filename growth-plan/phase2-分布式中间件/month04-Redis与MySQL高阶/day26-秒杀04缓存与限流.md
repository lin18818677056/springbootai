# Day 26 · 秒杀 04：多级缓存与限流（day12 知识的项目落地）

> **今日目标**：day12 学的缓存三大问题今天在真实项目落地：Caffeine+Redis 两级缓存把详情接口做到 3000+ QPS 且 DB 零压力；Sentinel 预热限流接住秒杀陡增流量。理论和实践之间的那座桥，今天走通。
> **时长**：实现 2.5h / 压测验证 1.5h
> **今日产出**：两级缓存详情接口 + 3000 QPS 压测数据 + 三问题防护实测 + Sentinel 限流曲线

## 1. 知识地图

```
两级缓存读取链路（step02 §1，为什么是"本地→Redis→DB"这个顺序）：
  请求 → Caffeine(本地, TTL 10s)   命中≈微秒、零网络 → 直接返回
       → Redis(TTL 30min+随机)     命中≈1ms、一次网络往返 → 回填本地
       → MySQL                     兜底 → 回填两级
  本地缓存收益：把 Redis 的网络往返也省掉 → 单机 3000+ QPS 的来源
  为什么本地 TTL 短（10s）：多实例各自一份本地副本，长 TTL=实例间不一致窗口放大

三大问题在本项目的对策（day12 理论 → step02 实现，逐一对号）：
  穿透 → 空值哨兵：DB 查不到 set key="" 60s
         （读代码注意：空值与正常值是同一个 key 两种值，逻辑里 ""equals 判断）
  击穿 → 互斥重建：setIfAbsent(lockKey,3s) 抢锁，抢到的查 DB 回填，
         没抢到的 sleep(50) 递归重查（重试上限 3 次！step02 常见坑第 3 条）
  雪崩 → TTL 加随机 0~600s + 本地缓存兜底 + Sentinel 限流最终防线
  ★对比 day12 的手写版：生产版多了"空值哨兵细化/重试上限/Caffeine 池化"

库存的特殊性（step02 §5 的关键架构决策）：
  详情数据（名称/图片/时间）→ 可缓存，最终一致无妨
  库存数字                  → 绝不走详情缓存！走 step03 实时预扣
  "展示数据与交易数据分离"——面试一句话讲透为什么详情页显示还有库存
  但下单却失败（展示是缓存快照，交易是实时扣减）

缓存预热（Warm-up）：
  活动开始前 5 分钟把全部秒杀商品灌进两级缓存
  → 避免开抢瞬间"集体 miss → 击穿式回源"（= 防雪崩的事前手段）
  实现：ApplicationRunner / 调度任务触发

Sentinel 限流（step03 §3，与限流的正确姿势对齐）：
  Warm Up 预热模式：阈值从 低→满 用 10s 爬坡——秒杀流量陡增最配
  （冷启动 JVM 未预热/JIT 未编译，一上来放满阈值=全部超时）
  限流响应 ≠ 500：返回 429"排队人数过多"（限流是保护，不是故障）
```

### 3.2 三大问题防护实测（step02 验收第 3 条，手工触发）

```powershell
# ① 穿透防护：查不存在的 id（连续 10 次）
1..10 | ForEach-Object { curl.exe http://localhost:8080/seckill/goods/999999 }
#   观察：全部快速返回"商品不存在"；Redis 里 seckill:goods:999999 = ""(TTL 60s)
#   DB 查询日志：只在第一次出现（空值哨兵生效）
# ② 击穿防护：删 key 后立即 20 并发查
docker exec -it <redis容器名> redis-cli -a redis123 del seckill:goods:1
1..20 | ForEach-Object -ThrottleLimit 20 { curl.exe http://localhost:8080/seckill/goods/1 }
#   观察：DB 查询日志只出现 1 次（互斥锁生效，其余 19 个等回填）
# ③ 雪崩抽查：看 5 个商品的 Redis TTL 是否各不相同
1..5 | ForEach-Object {
  docker exec <redis容器名> redis-cli -a redis123 ttl seckill:goods:$_
}
#   期望：5 个 TTL 值分布在 1800~2400s（随机抖动生效）
```

## 4. 面试连接

**Q：详情接口怎么做到高 QPS 且 DB 零压力？**
> 两级缓存+三防护+预热：Caffeine（10s，微秒命中）→ Redis（30min+随机，毫秒命中）→ DB 兜底；穿透用空值哨兵 60s，击穿用互斥锁重建（抢锁失败递归重查但有上限），雪崩用 TTL 抖动+活动前预热。数据背书："100 并发压测，两级缓存 QPS 3000+，DB QPS 0，Caffeine 命中率 95%+——三档对比数据都在压测表里。"加分细节："缓存对象用 record 不可变类，防调用方修改污染缓存（step02 常见坑第 1 条）。"

**Q：缓存和数据库的一致性怎么处理的？**
> 分数据类型回答（展示 day13 知识的项目化）：详情类——Cache Aside 写路径（更新 DB 后删缓存）+ 短 TTL 自然过期兜底；库存类——干脆不缓存，Redis 预扣就是交易事实，展示数字容忍短暂不准（"展示与交易分离"是显式架构决策）；订单结果——走轮询查询不做缓存（时效敏感）。收尾："我不用一套方案打天下，按数据用途分配一致性预算。"

**Q：限流阈值怎么定的？为什么用预热模式？**
> 阈值=压测校准的单机极限×0.8 安全系数（不是拍脑袋）。Warm Up 用于下单链路：秒杀流量从 0 瞬间到峰，JVM/JIT/连接池都没热透，直接放满阈值=第一批请求全部超时；预热 10s 让系统爬坡进入状态。轮询接口用快速失败：读请求拒绝成本为零，排队反而占线程。这套"按链路特性选限流效果"的思路就是答案核心。
