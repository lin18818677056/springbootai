## 1. 知识地图

```
秒杀为什么难（四个难点定架构，面试开场白）：
  ① 瞬时洪峰：平时 100 QPS 的系统瞬间 50 万 QPS（5000 倍！）
     → 任何"用 DB 硬扛"的方案都先出局 → 必须漏斗化拦截
  ② 热点行：1000 件库存 = 1 行数据被百万请求抢 UPDATE
     → DB 行锁串行化 → 必须把扣减挪到 Redis（内存单线程 10 万 QPS+）
  ③ 黄牛脚本：机器手速 10ms/次 vs 人类 200ms
     → 必须防刷（令牌/验证码/风控），否则真实用户永远抢不到
  ④ 不许超卖也不许少卖：超卖=资损事故，少卖=库存浪费
     → 原子扣减（Lua）+ DB 兜底 + 对账 三重保险

应对的总体架构（五层漏斗，step01 的灵魂）：
  ┌─────────────────────────────────────────────┐
  │ ① 前端层：按钮置灰/验证码/静态页 CDN          │  50万 → 10万
  │ ② 网关层：Sentinel 限流 + 令牌校验            │  10万 → 5000
  │ ③ 应用层：Redis Lua 原子预扣（防超卖核心）     │  5000 → ~1000
  │ ④ 异步层：RocketMQ 事务消息削峰               │  按 DB 能力匀速
  │ ⑤ 落库层：MySQL 乐观锁扣减 + 订单落库         │  ~1000 单
  └─────────────────────────────────────────────┘
  核心思想一句话：数据库只承受 1/500 的入口流量

异步化的产品代价（架构师要懂的取舍）：
  同步下单：用户等到"成功/失败"（RT 200ms+，DB 扛不住）
  异步下单：立即返回"排队中"→ 前端轮询结果（RT<50ms，体验换吞吐）
  ★能接受"排队"是整个方案成立的前提 → 所以需求澄清第一件事问这个

为什么用事务消息而不是"先扣 Redis 再发普通消息"：
  普通消息：Redis 扣成功 → 发消息失败 → 库存没了订单也没有（资损！）
  事务消息：半消息 → 本地动作 → 提交/回滚 → Broker 回查兜底
  （RocketMQ 的分布式事务解法，month05 分布式理论的最佳先导案例）
```

## 4. 面试连接

**Q：设计一个秒杀系统，你怎么入手？**
> 三段式：① 需求先行——库存量/瞬时 QPS/是否允许排队/限购规则/超时关单，"是否允许排队"决定异步化架构是否成立；② 漏斗设计——前端拦截→网关限流→Redis 预扣→MQ 削峰→DB 落库，核心指标"DB 只承受 1/500 入口流量"；③ 三个硬保障——防超卖（Lua 原子+DB 乐观锁+对账）、防刷（一次性令牌+限购+风控）、高一致（事务消息+三层消费幂等+超时关单状态机）。加分句："这套架构我完整实现过，5000 并发压测 0 超卖，复盘报告里有逐项瓶颈优化数据。"（day27 完成后这话就成立）

**Q：为什么下单要异步？用户等不及怎么办？**
> 本质是"用户体验换系统吞吐"的交易：DB 单行扣减能力 ~1000 TPS，同步等 50 万请求=用户 RT 爆炸+系统雪崩。方案：立即返回"排队中"（RT<50ms），前端轮询 result 接口——绝大多数用户在 1-2 秒内拿到结果（1000 单 × 匀速消费），体感接近同步。产品兜底：等待动画+排队序号，把技术等待包装成"挤爆了"的营销氛围（双十一都在这么干）。

**Q：库存放在 Redis 还是 DB？为什么？**
> 都放，职责不同：Redis 是"预扣层"——单线程+Lua 保证原子，扛住瞬时扣减洪峰；DB 是"事实源"——异步消费时用 `WHERE stock_count>0` 乐观锁扣减兜底，Redis 与 DB 偏差由对账 Job 发现。只放 DB=行锁热点打挂 DB；只放 Redis=宕机丢账。两级扣减互为保险，这是"不超卖"的工程本质：不信任任何单一组件。
