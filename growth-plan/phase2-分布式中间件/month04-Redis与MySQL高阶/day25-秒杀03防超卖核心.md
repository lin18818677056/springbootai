## 1. 知识地图

```
超卖的教科书复现（三步分离的必然结局）：
  T1: GET stock → 1
  T2: GET stock → 1        ← T1 还没写回，T2 也读到了 1
  T1: SET stock 0          扣 1
  T2: SET stock 0          再"扣"1 → 但实际只卖了 1 件，库存记录少了 2 → 超卖！

为什么是 Lua 而不是分布式锁（day14 的知识在这里做取舍，面试加分）：
  分布式锁：把并发变串行 → 正确但吞吐低（每次加锁 1-2ms RTT）
  Lua：Redis 单线程内一次性执行 → 天然原子、零额外 RTT、吞吐 10 万 QPS+
  取舍结论："能靠原子操作解决的，绝不引入锁"——锁是最后的手段

seckill.lua 的三条防线（对照 step03 §1 脚本逐行）：
  ① EXISTS init key     活动未初始化 → 拒（-3）：防"活动没开始就扣"
  ② SISMEMBER bought    一人一单预判 → 拒（-2）：同一用户重复请求
  ③ GET+tonumber+DECR   库存检查与扣减原子完成 → 拒（-1）或扣（1）
  ★三步在同一原子脚本里，任何并发交错都不可能超卖
  （SADD 记录已购在扣减成功之后——顺序不能反，否则失败也会占名额）

DB 兜底扣减（第二道保险，消费端执行）：
  UPDATE seckill_goods SET stock_count = stock_count - 1
  WHERE goods_id = ? AND stock_count > 0
  → 影响行数=0 理论不可达（Redis 已挡），真发生了=两层有偏差 → 告警对账
  双保险哲学：Redis 挡量（性能），DB 保真（正确性）

防刷令牌（step03 §4，防的是"绕过前端"）：
  GET /seckill/token → UUID 存 Redis TTL 30s（一次性）
  POST /seckill/order → Lua 里原子"校验+删除" token（拆开就有重放漏洞）
  频控：同用户每秒 1 次取令牌（INCR+EXPIRE）

降级预案（Redis 挂了怎么办，step03 §5）：
  超时率>10% → 切 DB 直扣模式（限流阈值降到 500，慢但正确）
  完全不可用 → 活动熔断（"系统繁忙"，保 DB 要紧）
  恢复后     → 对账 Job：Redis 预扣 vs DB 实扣，偏差告警
```

## 3. 动手实操

### 3.1 主菜：Lua 脚本逐行标注（在 step03 基础上加深理解）

```lua
-- seckill.lua（step03 §1 原脚本 + 并发意义标注）
-- KEYS[1]=库存 KEYS[2]=已购set KEYS[3]=初始化标记 ARGV[1]=userId
if redis.call('EXISTS', KEYS[3]) == 0 then
    return -3                          -- 防线0：没初始化=活动未开始/未预热
end
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                          -- 防线1：一人一单（set 判重 O(1)）
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then
    return -1                          -- 防线2：库存不足（tonumber 防字符串比较 bug）
end
redis.call('DECR', KEYS[1])            -- 原子扣减：单线程内不可能交错
redis.call('SADD', KEYS[2], ARGV[1])   -- 先扣后记：失败路径不占名额
return 1
-- ★思考：为什么不用 WATCH/MULTI 事务？
--   WATCH 乐观锁在高并发下重试率高（冲突→重试→更冲突），Lua 一次成功
```

## 4. 面试连接

**Q：你的秒杀怎么做到不超卖？**
> 双保险+三防线：Redis 层 Lua 原子扣减——活动初始化校验、一人一单 set 判重、库存检查与 DECR 在同一原子脚本内，单线程执行不可能交错；DB 层消费端 `UPDATE ... WHERE stock_count > 0` 乐观锁兜底，影响行数为 0 触发告警对账。最后补数据："5000 并发抢 1000 库存实测：精确成交 1000、0 重复用户、Redis 与 DB 两边库存都归 0。"（实测数据 day25 结束后你就有了）

**Q：为什么用 Lua 而不是分布式锁？**
> 锁把并发请求串行化，正确但吞吐低（每次加锁 1-2ms 往返）；Lua 利用 Redis 单线程特性在服务端一次执行完成，无额外往返、吞吐 10 万 QPS 级。取舍原则："原子操作能解决的绝不引入锁——锁引入了新问题（超时续期/死锁/误删，我 day14 手写过三代锁深知其复杂度）。"加分认知："WATCH 乐观锁也能对，但高冲突场景重试风暴，Lua 一次成功——这是选 Lua 而非事务的真正原因。"

**Q：Redis 扣了库存但订单没生成，怎么办？**
> 三个环节各有兜底：① 发送侧用 RocketMQ 事务消息——半消息+本地事务+Broker 回查，保证"预扣成功 ↔ 消息必达"；② 消费侧三层幂等——Redis 幂等锁预判、orderNo 唯一索引兜底、状态条件更新；③ 对账 Job 定期比对 Redis 预扣 vs DB 实扣，偏差告警人工介入。一句话："不可能做到绝对无窗口，但每个窗口都有检测和修复手段——这就是最终一致的工程化。"
