# Day 16 · AT 深入与压测：全局锁代价与适用边界

> **今日目标**：压测 AT 的性能损耗（对比本地事务）；搞清 AT 隔离级别的"读未提交"本质；把 M5 TCC 三坑（空回滚/悬挂/幂等）映射到 AT 场景；输出"AT 适用边界"结论。
> **时长**：隔离级别 1.5h / 压测实验 2.5h / 边界总结 1h
> **今日产出**：AT 压测报告（数据）+ 隔离级别笔记 + 适用边界清单

## 1. 知识地图

```
AT 隔离级别的真相（面试送分题也是送命题）：
  写隔离：全局锁保证（day15）——两个全局事务不会同时持有同一行
  读隔离：AT 默认"读未提交"！
    场景：全局事务 A 改了库存=99（一阶段本地已提交）但全局事务还没提交
         此时 B 直接 select → 读到 99（A 可能还要回滚！）
    ——因为一阶段就提交本地了，普通 select 当然能读到
  补救：@GlobalLock + select for update —— 读之前拿全局锁，实现"读已提交"
    （select for update 被 Seata 代理：先查 TC 全局锁，被占则等待）
  面试金句："AT 用读未提交换了性能，需要强读一致的场景要么 for update 拿全局锁，
            要么这个场景根本不该用 AT"

AT 的性能账单（压测实验）：
  成本项：①前后镜像各一次查询 ②undo_log 插入+删除 ③TC 两次 RPC（注册+上报）
         ④全局锁竞争（热点行串行化！）
  实验设计：
    A 组：本地事务下单+扣库存（单库，基准）
    B 组：AT 双服务链路（非热点：每个用户不同商品）
    C 组：AT 热点行（所有请求扣同一个商品 1001 的库存）
  预期结论：B 组损耗 30%~50%（RPC+镜像开销）；C 组 TPS 崩（全局锁串行）——
    "AT 的性能瓶颈不在框架开销在全局锁，热点行是 AT 天敌"

M5 TCC 三坑在 AT 里的对应（框架帮你防了哪些）：
  空回滚：AT 二阶段回滚基于 undo_log，没有镜像就回不了滚——框架天然不会"空回滚"
  悬挂：AT 不存在"先执行了回滚再执行业务"——因为分支注册在业务执行前（一阶段）
  幂等：二阶段重试场景少（回滚重试由 TC 控制），但 TC 超时重发仍可能——
        undo_log 的 log_status 状态位兜底
  ——结论：AT 框架封装掉了 TCC 的三坑，但代价是锁与镜像；TCC 换来的是自己控制粒度

AT 适用边界（结论卡片）：
  ✅ 短事务 / 中低并发 / 非热点行 / 想要快速落地（零侵入）
  ❌ 热点行扣减（秒杀库存→M4 已用 Redis+Lua） / 长事务（全局锁持有久） /
     高并发核心链路（损耗不可接受） / 中间件不落库的资源（MQ 消息没法生成镜像）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Read Uncommitted (AT default) | 读未提交（AT 默认隔离级别） |
| @GlobalLock + select for update | 读已提交的补救方案 |
| Dirty Write | 脏写（绕过全局锁的修改） |
| Hot Row Contention | 热点行竞争（全局锁串行化） |
| Mirror Overhead | 镜像开销（前后镜像查询） |
| Benchmark Baseline | 压测基准（本地事务对照） |
| Applicability Boundary | 适用边界 |

## 3. 动手实操：三组压测

```powershell
# 压测工具：JMeter 线程组（阶梯 50/100/200 并发，每档 2 分钟）
# A 组基准：/order/local-create（单库本地事务版）
# B 组：/order/create（AT 双服务，商品随机 1001~1010）
# C 组：/order/create?productId=1001（AT 双服务，全部打 1001）

# 记录表（示例格式，以实测为准）：
#   并发 | A组 TPS/RT  | B组 TPS/RT  | C组 TPS/RT
#   50   | 1800/28ms   | 950/52ms    | 90/550ms
#   100  | 2400/41ms   | 1200/83ms   | 95/1050ms（锁等待线性涨）
#   200  | 2600/77ms   | 1350/148ms  | 96/2100ms（TPS 不涨纯排队）
# 分析要点：
# ① B/A ≈ 50% 损耗：TC RPC + 镜像 + undo_log 写放大
# ② C 组 TPS≈1/锁持有时间：全局锁把并发压成串行（10ms/笔 → 上限 100 TPS）
# ③ C 组 seata-server 日志出现 "global lock acquire failed, will retry"

# 佐证实验：看 TC 的 lock_table（全局锁表）——C 组永远是同一行锁记录
# 结论写入笔记：下单扣库存的"库存行"就是热点行 → 该链路 AT 只适合原型阶段，
# 生产方案=day17 TCC 或 M4 的 Redis 预扣（库存本质是计数器问题，不是事务问题）
```

## 4. 面试连接

**Q：AT 模式的隔离级别是什么？怎么实现读已提交？**
> AT 默认读未提交：因为一阶段就提交本地事务，全局未提交的数据对普通 select 可见。要读已提交需 @GlobalLock + select for update——Seata 代理该查询，先向 TC 申请全局锁，持有期间读到的一定是全局已提交数据。追问"为什么 AT 不默认给读已提交"：每次读都查全局锁开销太大，AT 的设计哲学是"快"——绝大多数读不需要跨事务强一致，需要时显式加锁（权限交给业务）。收尾："所以选 AT 之前先问业务两个问题：读要不要看到未提交数据？写有没有热点行？——两个都不能忍，别用 AT。"

**Q：你们压测过 AT 吗？什么结论？**
> 压过三组对照：本地事务基准、AT 非热点、AT 热点行。结论：非热点损耗约一半（TC 两次 RPC+前后镜像+undo_log 写放大）；热点行是 AT 天敌——全局锁把并发压成串行，TPS≈1/锁持有时间，200 并发压一个商品库存 TPS 卡在 95 且 RT 线性上涨。落地决策："订单创建→扣库存这条链我们最终没用 AT 走生产：库存行天然热点，改用 Redis 预扣+异步落库（M4 秒杀方案）；AT 保留在'订单创建+营销券核销'这种低冲突链路。"——技术选型讲"哪里用了哪里没用+为什么"，比"我们用了 Seata"高一档。
