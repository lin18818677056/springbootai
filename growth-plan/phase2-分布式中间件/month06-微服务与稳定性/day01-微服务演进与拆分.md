# Day 01 · 微服务演进与拆分：从草图到方案

> **今日目标**：验证 M5 day30 埋的"秒杀拆分第一刀"草图，掌握服务拆分原则与分布式单体反模式，输出商城五服务拆分方案——先想清楚再动手，这是架构师第一步。
> **时长**：演进史 1h / 拆分设计 2.5h / 草图验证 1.5h
> **今日产出**：商城拆分方案（含"为什么这么拆"答辩稿）

## 1. 知识地图

```
架构演进四代（每代解决上一代的什么痛）：
  单体 Monolith：一个 WAR 打天下
    痛：发布互相影响/故障全局爆炸/团队协作冲突（代码冲突）/无法按需扩容
  SOA（面向服务架构）：ESB 企业服务总线做集成，服务粗粒度
    痛：ESB 是单点+瓶颈，XML 慢，"重"总线"轻"服务
  微服务 Microservices：服务围绕业务能力构建，去中心化治理，独立部署
    痛（新代价）：分布式复杂性（网络不可靠/数据一致性/链路排查）——M5 学的全是给这个还债
  云原生 Cloud Native：K8s 编排/声明式 API/不可变基础设施/服务网格下沉治理

拆分三原则（按优先级背）：
  ① 按业务能力 Business Capability：订单/商品/库存/营销/用户——业务语言就是服务边界
  ② 按团队康威律 Conway's Law：系统结构=组织结构（2 人的团队拆 10 个服务=自找苦吃）
  ③ 按数据自治：一个服务一个库（Database per Service）——共享库是分布式单体的根源

反模式：分布式单体 Distributed Monolith（拆了比不拆更惨）：
  特征自查：服务间同步调用链超长（A→B→C→D）/ 共享一个库 / 一次需求改 5 个服务 /
           必须整体发布 / 服务间 DTO 强耦合
  本质：把单体的耦合搬到网络上，还附赠分布式所有代价——拆分粒度的最大坑

拆分粒度判断（面试高频）：
  "多小算小服务？"——不看代码行数，看三问：
  ① 能独立部署吗？（不拖别的服务）② 能独立理解吗？（一个脑子装得下）③ 团队能独立拥有吗？
  起步建议：粗粒度起步，按痛感逐步拆（"先分模块后拆服务"的演进式拆分）
```

## 2. 核心概念（中英对照）

| 概念 | 说明 |
|------|------|
| Monolith | 单体架构 |
| SOA (Service-Oriented Architecture) | 面向服务架构（ESB 总线时代） |
| Microservices | 微服务架构 |
| Cloud Native | 云原生（容器/编排/声明式） |
| Distributed Monolith | 分布式单体（拆了但没拆好的反模式） |
| Conway's Law | 康威定律（组织结构决定系统结构） |
| Database per Service | 每服务独立数据库 |
| Business Capability | 业务能力（拆分的第一坐标） |
| Strangler Fig | 绞杀者模式（渐进式替换遗留系统） |

## 3. 动手实操：商城拆分方案设计

```text
第一步：验证 M5 day30 的秒杀拆分草图（带着批判眼光）：
  草图方案：网关 / 订单 / 库存 / 用户 四服务
  用今天的标准重审：
  □ 订单与库存拆开对吗？——对：库存是独立业务能力+独立伸缩需求（大促库存写压力大）
  □ 用户服务独立对吗？——存疑：秒杀场景用户只是鉴权，拆出去增加一次 RPC——
    若只有鉴权职责，先用网关 JWT 挡住即可，用户服务等有"用户中心"业务再拆
    ——结论：M5 草图要修正（拆分时机也是拆分决策的一部分）
  这一步的价值：学会"批判自己的旧决策"=架构成长最快的动作

第二步：商城五服务拆分设计（step01 的业务）：
  mall-gateway  网关：路由/鉴权/灰度/限流入口（无业务逻辑！）
  mall-user     用户：注册/登录/地址（领域：账号与身份）
  mall-product  商品：商品/库存（领域：商品与库存聚合——step01 把库存放这里）
  mall-order    订单：订单聚合/订单状态机（领域：交易主流程）
  mall-marketing 营销：优惠券/积分（领域：营销资产，扣减可异步）
  每个服务回答三个问题（写进方案）：
  ① 为什么它是独立服务？（业务能力+伸缩/发布节奏差异）
  ② 它拥有哪些数据表？（Database per Service 清单）
  ③ 它依赖谁？（依赖方向必须无环！order→product/user/marketing，反向不得出现）

第三步：拆分方案答辩稿（2 分钟版，写下来）：
  "按业务能力拆五个服务+一个网关；依赖方向单向无环：订单调用商品/用户/营销，
  营销扣减走消息异步（M5 事务消息经验复用）；每个服务独立库；
  起步粒度偏粗（五服务），保留演进空间——比如商品与库存未来按读写分离再拆。"
```

## 4. 面试连接

**Q：你们服务是怎么拆的？为什么这么拆？**
> 三层答：①拆分坐标——按业务能力（报服务清单+各自拥有的表）；②依赖治理——依赖方向单向无环，跨服务数据不共享库，同步调用只允许"订单→基础域"，异步事件用于营销类旁路；③粒度论证——引用康威律（团队规模决定服务数量），承认"分布式单体"风险并给出演进式策略（粗起步按痛感拆）。加分句："拆分最大的成本不是技术是认知——每个新服务都要配齐治理配置（超时/重试/熔断/监控），所以我们有服务初始化模板。"（引 day07 清单伏笔）

**Q：什么时候不该拆微服务？**
> 反向思考题，答三点：①团队小（<10 人）业务复杂度低——单体+模块化足够，拆服务是给自己上枷锁；②流量小到单库单机都没压力——分布式一致性代价纯亏；③领域边界没想清楚就拆——边界错了来回改，比单体重构还贵（绞杀者模式都比乱拆强）。收尾观点："微服务解决的是组织扩展问题，不是技术炫技——先问'我要解决什么痛'再拆。"（能答"不该拆"的候选人，才是真懂微服务）
