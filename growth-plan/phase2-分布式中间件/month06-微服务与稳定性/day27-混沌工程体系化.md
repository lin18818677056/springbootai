# Day 27 · 混沌工程体系化：稳态假设、故障注入与爆炸半径

> **今日目标**：建立混沌工程方法论（稳态假设/最小爆炸半径/持续验证）；用 ChaosBlade 对商城做 3 场标准化演练（CPU 满/网络延迟/杀实例），逐一验证 RUNBOOK 预案；完成"发现→修复"闭环。
> **时长**：方法论 1.5h / 三场演练 3h / 闭环归档 0.5h
> **今日产出**：3 场演练报告（预案验证结果）+ 混沌实验清单 + 修复项跟踪表

## 1. 知识地图

```
混沌工程（Chaos Engineering）的定义（Netflix OSS 起源）：
  对系统主动注入故障，验证"韧性设计是否真的有效"的科学实验
  ——day13 说过"预案没演练过=没有预案"，混沌工程就是系统化的演练
  核心思想：与其等生产随机故障打脸，不如主动按剧本打——受控的故障是最好的老师

方法论五步（每个实验都要走，缺一步就是瞎搞）：
  ① 稳态假设（Steady State Hypothesis）：定义"正常"的量化指标
     （下单错误率<0.1%、P99<500ms、对账零差异——先有基线才能判断"坏了"）
  ② 假设实验（Hypothesis）：注入故障后系统会怎样？（熔断应该 10s 内生效……）
  ③ 执行注入（Injection）：ChaosBlade/Chaos Mesh 注入 CPU/网络/进程级故障
  ④ 观察验证（Verification）：大盘+告警+trace 是否按预期表现？
  ⑤ 最小爆炸半径（Blast Radius）+ 中止开关（Abort）：出问题立刻停实验
  ⚠ 铁律：生产混沌=先从测试环境开始+非高峰时段+有回滚预案+汇报过

最小爆炸半径的控制维度：
  范围：先单实例 → 再单服务 → 最后跨服务（永远不要一上来就炸整个集群）
  时间：定时中止（chaosblade 的 --timeout 参数）
  强度：CPU 拉到 60% 而不是 100%——"先让系统跛脚，看它是否跛而不倒"

三场标准演练（对应 RUNBOOK 三行，day13 的表今天逐行验证）：
  实验① CPU 满（60%/90% 两档）→ 验证：系统保护（day11）介入+P99 告警（day24）
  实验② 网络延迟注入（product 加 800ms 延迟）→ 验证：慢调用熔断（day10）+fallback 秒回
  实验③ 杀掉 product 实例 → 验证：注册中心剔除（day03）+Feign 熔断+流量切健康实例
  ——每场记录：预期/实际/差异/修复项（预案失效的地方就是本月最有价值的产出）
```

## 3. 动手实操：三场标准化演练

```powershell
# ChaosBlade（Windows 学习环境用 docker 容器内注入，模拟生产 Linux 场景）：
# docker run -d --name chaos-target mall-product:latest   # 或直接注入运行中的容器
# docker exec chaos-target sh -c "blade version"          # blade 二进制放入容器

# 实验①：CPU 满（60% 强度，120s 自动中止）
# docker exec chaos-target sh -c `
#   "blade create cpu load --cpu-percent 60 --timeout 120"
# 观察（预期 vs 实际）：
#   ✅ Grafana CPU 面板爬升；P1 CPU 告警 5min 内触发（day24 的 for:5m 在起作用）
#   ✅ 系统保护规则触发（day11 配的 CPU=80% 档位）→ 入口流量被拦截
#   ⚠ 发现问题：告警文案没写 RUNBOOK 链接 → 修复项①（回填 annotations）

# 实验②：网络延迟 800ms（product 出口）
# blade create docker network delay --time 800 --interface eth0 --destination-port 3306 --timeout 180
# 观察：
#   ✅ order→product 慢调用比例飙高 → day10 熔断规则触发（maxRT=1s）
#   ✅ SkyWalking trace 显示 product 边变红（day26 三支柱联动）
#   ⚠ 发现问题：熔断时长 10s 但故障持续 180s → 反复"熔断-半开-再熔断"空转
#     → 修复项②：熔断时长评估（应接近故障恢复预期，或用持续探测）

# 实验③：杀 product 实例（docker stop）
# 观察：
#   ✅ Nacos 15s 标记不健康 30s 剔除（day03 实验复现）
#   ✅ 剔除前 Feign 熔断兜住失败请求（响应 3s→0ms 断崖，day10 数据复现）
#   ✅ 双实例场景：流量自动切到健康实例，用户无感——多实例的意义在这一刻具象化
#   ⚠ 发现问题：单实例的 marketing 服务没有副本 → 修复项③：核心服务至少 2 副本

# 收尾：三场演练的修复项进《混沌实验清单》跟踪表（实验/预期/实际/发现/修复项/状态）
```

## 4. 面试连接

**Q：什么是混沌工程？怎么做一次规范的混沌实验？**
> 混沌工程是"主动注入受控故障，验证韧性设计有效性"的实验学科——把等生产事故打脸变成按剧本演练。规范流程五步：先定义稳态假设（量化基线：错误率<0.1%、P99<500ms），提出实验假设（杀一个实例流量应自动切换、用户无感），控制最小爆炸半径执行注入（单实例→单服务渐进，带 timeout 中止开关），全程观察大盘/告警/trace 验证预期，最后归档差异形成修复项。强调纪律："我们只在测试环境做全量混沌，生产只做'跛脚级'注入（CPU 60%）且非高峰+有 abort——混沌的目的是建立信心，不是制造事故。"（知道边界的人才是能用的）

**Q：演练发现预案失效怎么办？举一个真实发现。**
> 三场演练抓到三个真问题：告警缺 runbook 链接（值班收到不知道下一步）；熔断时长 10s 配 180s 网络故障导致反复空转（熔断-半开-再熔断循环）；marketing 核心服务单副本（实例一杀服务全断）。处理方式：修复项进跟踪表（问题/负责人/期限），修复后回归演练验证——"混沌实验的价值不在'系统扛住了'的演练，而在'系统没扛住'的发现：这三个修复项比三场成功演练值钱十倍。"（MTTR 缩短的故事：演练前故障恢复靠人肉发现约 15 分钟，演练+告警闭环后 5 分钟内——数字化的稳定性成果）
