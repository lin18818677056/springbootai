# Day 13 · 服务韧性设计：超时、隔离、容量与预案

> **今日目标**：把本周 Sentinel 的零散技术收拢成"韧性设计方法论"——超时预算怎么定、舱壁隔离怎么做、容量怎么压、预案怎么写；做出商城的《稳定性预案表》。
> **时长**：方法论 2h / 压测定容 2.5h / 预案表 0.5h
> **今日产出**：韧性设计清单 + 容量压测报告 + 稳定性预案表（走进简历的项目资产）

## 1. 知识地图

```
韧性（Resilience）设计四板斧——把 week2 的工具装进方法论框架：

① 超时预算（Timeout Budget）——"钱"的类比：
   每层调用花的时间像花钱：预算要逐层递减且总额封顶
   网关 5s > order→product 3s > product→db 1s（每层 ≤ 上层一半，给重试留余地）
   反例：所有层都配 30s——一个慢依赖把整条链拖死（超时形同虚设）
   设定方法：P99 实测耗时 × 2~3（不是拍脑袋！day23 的 RED 监控会给出 P99）

② 舱壁隔离（Bulkhead）——船的密封舱：
   一舱进水不沉全船。应用内隔离维度：
   a. 线程池隔离：核心依赖独占线程池（调支付、调第三方）
   b. 信号量隔离：轻量并发数限制（Sentinel 并发线程数流控）
   c. 连接池隔离：DB 连接池/Redis 连接池各自上限（不能让报表查干连接池）
   d. 缓存/队列隔离：核心缓存与普通缓存分开，慢任务队列单独建（day04 动态线程池用上）

③ 容量规划（Capacity Planning）——先知道自己的极限：
   压测找拐点：QPS 从低往高压，看 RT 突增/错误率出现的点 = 容量上限
   线上限流阈值 = 上限 × 安全系数 0.7~0.8（day09 的 QPS=100 不是拍的，是压出来的 130×0.75）
   经典曲线：并发上升 → 吞吐先升后降（资源耗尽），RT 单调上升——"最佳并发"在拐点前

④ 故障预案（Runbook）——"坏的时候谁做什么"：
   三级预案：降级预案（功能可用性换资源）/ 扩容预案（加机器/加实例）/ 回滚预案（改坏了怎么办）
   预案三要素：触发条件（指标阈值）/ 执行步骤（谁点哪里）/ 恢复验证（怎么确认好了）
   ——预案没演练过 = 没有预案（day27 混沌工程专门验证预案）
```

## 3. 动手实操：给商城做一次容量压测

```powershell
# JMeter/wrk 压测 /api/order/probe/ping（无外部依赖，测"纯框架容量"）：
# 阶梯加压：10 并发 → 50 → 100 → 200 → 500，每档跑 1 分钟记录 QPS/RT P99/错误率
# 预期曲线（笔记本参考值，以实测为准）：
#   10并发  QPS≈2000  RT≈5ms
#   100并发 QPS≈8000  RT≈12ms   ← 吞吐拐点附近
#   200并发 QPS≈9000  RT≈22ms   ← 吞吐不涨了，RT 还在涨（过了最佳并发）
#   500并发 QPS≈8500  RT≈60ms   ← 排队消化，错误率开始出现
# 压测 /api/order/detail（走 Feign+product+Redis 全链路）：
#   容量明显下降（跨 3 跳）→ 记录"链路成本"：每多一跳 RT+几 ms、容量打几折
# 输出《容量压测报告》：拐点 QPS / 建议限流阈值（拐点×0.75）/ 扩容触发线

# 给核心接口配上线流规则（基于压测数据，不再是拍脑袋）：
#   /order/detail: QPS=拐点×0.75（例：压出 2000 → 限 1500）
#   /order/create: 并发线程数=30（写接口用并发数阈值，防止排队把 DB 连接池占满）
```

## 4. 面试连接

**Q：限流阈值怎么定的？拍脑袋吗？**
> 绝不拍脑袋，三步：①压测找拐点——阶梯加压看吞吐不再上升而 RT 持续上涨的临界点；②乘安全系数——线上阈值=拐点×0.7~0.8，留出突发余量和 GC 停顿容忍；③上线后观察修正——限流触发率长期为 0 说明太松，频繁触发且业务受损说明太紧。加分句："我们预案表里每个接口的阈值旁边都标着压测日期和版本——代码变了容量会变，阈值是活数据不是配置完就忘的静态数字。"

**Q：核心服务的依赖治理你们怎么做？**
> 四个动作：①依赖分级——核心依赖（支付）与可降级依赖（推荐）区别对待；②超时预算——逐层递减（网关 5s>服务 3s>DB 1s），保证上游失败时下游不白干；③隔离——支付这类高风险依赖独立线程池/信号量，报表查询单独连接池，一个舱进水不沉全船；④熔断预案——每个依赖标明"挂了走什么降级"（fallbackFactory 的文案都按业务语义写）。收尾："依赖治理的本质是承认'任何依赖都会挂'，设计时把'挂了怎么办'想在前头，而不是故障时现场发明方案。"
