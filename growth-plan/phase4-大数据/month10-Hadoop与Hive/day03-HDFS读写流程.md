# Day 03 · HDFS 读写流程与三副本放置

> **今日目标**：把两个高频白板题画到肌肉记忆——①客户端写一个文件的完整流程（协商位置→管道传输→逐级确认）；②读流程为什么强调"就近读取"；③三副本放置策略（本机架→跨机架→同机架第二台）的完整逻辑。今天不装任何新东西，纯把 day02 的架构"跑"起来。
> **时长**：写流程 1.5h / 读流程与机架感知 1.5h
> **今日产出**：读写流程两张手绘时序图（白板标准）+ 副本放置实验

## 1. 知识地图

```
写流程（假设写一个 300MB 文件，3 副本）——先说人话：
"你把包裹交给总台，总台指定三个货架，第一货架收货后转给第二货架、
 第二货架转给第三货架，一条传送带串起来，逐级签字确认。"

① 客户端找 NameNode："我要写 /logs/app.log，300MB"
   NameNode 检查：权限过不过？文件已存在吗？父目录在吗？
   通过后返回"可以写"（此时不分配 DataNode——块还没切出来）
② 客户端切块：300MB 切成 3 块（128+128+44）
③ 客户端再次问 NameNode："第一个块放哪三个 DataNode？"
   NameNode 按副本放置策略返回一个 DataNode 列表（如 DN1→DN2→DN3，有顺序！）
④ 客户端把块写入 DN1（只写给最近的一个），DN1 收一点就转给 DN2，
   DN2 再转给 DN3——三个节点连成一条"流水线（Pipeline）"，数据像接力棒流动
⑤ 每个节点收到数据都存盘并向上一级回 ACK，客户端收到 DN3 的 ACK 才算这包写成功
⑥ 第一块完成 → 重复 ③~⑤ 写第二块…… 全部完成后向 NameNode 提交"写完了"
⑦ NameNode 落 EditLog：文件与块的映射正式入账

关键细节（面试官爱抠的地方）：
- 客户端不经过 NameNode 传数据！NameNode 只发"地址"，数据走客户端→DataNode 直连
  ——总台账只管登记，不搬货（否则 NameNode 带宽被数据冲爆）
- 流水线是"边收边转"，不是"DN1 全收完再给 DN2"——降低端到端延迟
- 某个 DN 中途挂了怎么办？流水线剔除它，剩余节点继续写，
  完事后 NameNode 发现副本数不足，异步补齐到 3（写不阻塞，恢复异步做——和 M8 思想一致）

读流程——人话："报书名给总台，总台给你一张'离你最近的取书单'，
你分头去各个货架取，哪个货架近先取哪个。"
① 客户端问 NameNode："读 /logs/app.log"
② NameNode 返回块列表 + 每块副本所在的 DataNode（按"离你近的排前面"排序）
③ 客户端对每个块就近挑一个 DataNode 直接读（并行读多个块！）
④ 拼装返回
关键点：读的并行度天然来自"块撒在多台机器"——这就是分块的第二重意义：
写的时候是故障单元，读的时候是并行单元。

三副本放置策略（Rack Awareness 机架感知）——人话版：
"第 1 份放客户端所在机架的一台机器（就近写）；
 第 2 份放另一个机架（防整个机架断电/交换机挂）；
 第 3 份放第 2 份同机架的另一台机器（读的时候跨机架只走一次网络）。"
权衡点明：如果 3 份全放不同机架——最安全，但每次写要跨机架 3 次，写慢；
如果全放同机架——写得快，但机架整体故障丢数据。
现在的策略是"2 个机架 3 份副本"的平衡解——又是权衡题的答法（不是背策略，是讲 why）。
```

## 2. 核心概念（中英对照+大白话）

| 概念 | 大白话解释 |
|------|------|
| Pipeline | 流水线写（客户端→DN1→DN2→DN3 边收边转） |
| ACK | 确认信号（每级收好数据都向上一级回话，最后回给客户端） |
| Rack Awareness | 机架感知（放副本时知道谁和谁在同一个机架） |
| Locality | 就近读取（优先从网络距离最近的副本读） |
| Replication Monitor | 副本补齐器（NameNode 发现副本不足，异步安排补拷贝） |

## 3. 动手实操：观察读写在真实发生

```powershell
# 实验①：上传时观察流水线（伪分布式只有 1 个 DN，但日志仍能看到 pipeline 建立）
docker exec hadoop-single hdfs dfs -put /tmp/big.bin /big2.bin
docker exec hadoop-single bash -c "grep -i 'pipeline' /opt/hadoop/logs/*datanode*.log | tail -5"

# 实验②：验证"写副本数不足不阻塞"——把副本数临时改为 1 再上传
docker exec hadoop-single hdfs dfs -setrep -w 1 /big2.bin
docker exec hadoop-single hdfs fsck /big2.bin    # 应显示 1 replica

# 实验③：手动改回 3，观察 NameNode 异步补副本的指令（补齐动作在后台发生）
docker exec hadoop-single hdfs dfs -setrep 3 /big2.bin
docker exec hadoop-single hdfs fsck /big2.bin    # 隔几秒再看，replica 回到 3
# ——这就是"副本自愈"：写路径不管修复，后台异步补（对照 M8 秒杀"写不阻塞"思想）

# 实验④：读的就近验证（伪分布式看不出来，但可以看读的块统计）
docker exec hadoop-single hdfs dfs -cat /big2.bin > $null
docker exec hadoop-single bash -c "grep -i 'Serving block' /opt/hadoop/logs/*datanode*.log | tail -3"
# Web UI http://localhost:9870 里点开 big2.bin 能看到每个块的副本位置列表
```

## 4. 面试连接

**Q：白板画一下 HDFS 写文件的完整流程？（高频白板题，画图 3 分钟）**
> 七步：客户端先向 NameNode 发起 RPC 申请写，NameNode 做权限和存在性检查后允许；客户端按 128MB 切块，对每个块向 NameNode 要一份 DataNode 列表——这个列表按机架感知策略排好序；然后客户端把数据写给列表第一个 DataNode，DataNode 之间连成流水线边收边转，每一级落盘后向上一级回 ACK，客户端收到最后一级的确认这一包才算成功；所有块写完，客户端向 NameNode 提交完成，映射关系进 EditLog。两个加分点：一是强调数据不过 NameNode，它只发地址不搬数据，否则元数据节点带宽被打爆；二是故障处理——流水线中某个 DataNode 挂了，客户端会把它从流水线剔除继续写，副本不足由 NameNode 后台异步补齐，写路径永远不为修复阻塞——这个"主流程不管修复"的思想和业务系统的对账补偿是同一套。

**Q：三副本为什么要跨机架放？全放同一机架不行吗？**
> 这题考权衡思维。全放同机架：写最快（数据不出机架，机架内网络通常带宽更高），但机架是真实的故障域——机架交换机挂了或机架断电，三份副本一起没，数据真丢。全放不同机架：最安全，但每次写要跨机架走 3 遍网络，吞吐被跨机架带宽卡住。默认策略是折中：第一份在客户端同机架（写快），第二份在另一个机架（防机架级故障），第三份跟第二份同机架不同节点（读跨机架只走一次，另外同机架第二台挂了也不用跨机架补）。一句话：副本策略的本质是在"故障域隔离"和"网络开销"之间找平衡——不是背下来就行，要能说出每一份的 why。
