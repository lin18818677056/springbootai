# Day 18 · 数据质量与血缘：大数据的对账

> **今日目标**：把 M8 学的"对账思维"平移到数据域——搞懂数据质量六性、DQC 规则两档（强规则阻断/弱规则告警）、数据血缘与影响分析；设计 10 条覆盖核心表的 DQC 规则。一句话：**业务系统对账"每一分钱"，数仓对账"每一行数据"。**
> **时长**：质量六性与 DQC 1.5h / 血缘 1h / 规则设计实操 2h
> **今日产出**：《DQC 规则清单》（10 条，含强弱档位）+ 血缘图 + 质量监控思路

## 1. 知识地图

```
问题引入：数仓的数据是"读时模式"进来的（day10：宽进），脏数据不可避免——
那谁来看住质量？答案不是"小心点"，是"制度化对账"。
（M8 day13 支付对账的逻辑：差错是常态，系统要能自己发现差错。）

数据质量六性（给"干净"下定义，六把尺子）：
① 完整性：该有的行有没有——今天订单数比昨天少 90%？（掉数了）
② 准确性：值对不对——金额出现负数/城市字段是乱码？
③ 一致性：同一事实各处口径一致——订单表的 GMV 和支付表的 GMV 对不上？
④ 及时性：到点了吗——每天 3 点该出的表 5 点还没出？（下游全堵）
⑤ 唯一性：不该重复的重复了吗——订单号出现两行？
⑥ 有效性：格式合规吗——手机号 11 位吗？日期合法吗？

DQC（Data Quality Control）规则两档（分级处置，就像告警分级）：
强规则（阻断）：不达标就不让数据往下流——表分区行数骤降 50%、主键重复
  → 处置：任务失败告警+下游任务挂起（宁可晚，不可错——和支付"宁可拒不可损"同源）
弱规则（告警）：超标了先记着继续跑——空值率超 5%、值域外比例超 1%
  → 处置：记质量分+通知 Owner，人工决定是否修复重跑
分档原则：影响下游正确性的用强，影响分析体验的用弱——全强会天天狼来了。

10 条规则怎么设计（按表分主键/完整性/值域/波动四类，覆盖核心表）：
主键类：①dwd_order_detail 的 oid 分区内唯一（强）
完整性：②ods_order_di 当日行数 > 0（强）③dwd uid 空值率 < 0.1%（强）
值域类：④amount ∈ [0, 100000]（弱）⑤dt 格式合法（强）
波动类：⑥当日行数 / 前 7 天均值 ∈ [0.5, 2.0]（强——掉数/灌重的第一哨兵）
一致性：⑦DWD 当日 GMV 与 ODS 粗算 GMV 差异 < 0.5%（强——分层对账）
跨表类：⑧支付表当日金额 ≈ 订单表已支付金额（弱——两库口径对账）
及时性：⑨核心表分区 03:30 前就绪（强——否则下游挂起）
唯一性：⑩ads 指标与昨日快照对比环比波动告警（弱）
—— 波动检测（第 6/10 条）是精髓：固定阈值挡不住业务自然增长，
  "和自己的过去比"才是可持续的质量基线（自适应阈值的朴素版）

数据血缘 Blood Lineage——"数据的族谱"：
  定义：字段级/表级的数据来源与去向链路（A 表的 x 列来自 B 表 y 列经过什么加工）
  获取：分层规范好（表名前缀+任务命名规范）血源自動可解析；或用 Atlas/DataHub 采集
  两大用途：
  ① 影响分析：上游表结构要改 → 沿血缘下游全列出 → 精准通知受影响方
    （没有血缘=出事故才知道谁在用这张表）
  ② 排障定位：ADS 数字不对 → 沿血缘回溯每一层 → 定位到 ODS 某天的分区
  （血缘的本质：把"拍脑袋知道"变成"系统可查"——M6 微服务链路追踪的数据版）
```

## 2. 核心概念（中英对照+大白话）

| 概念 | 大白话解释 |
|------|------|
| Data Quality 六性 | 完整/准确/一致/及时/唯一/有效（六把干净的尺子） |
| DQC Rule | 质量规则（强=阻断，弱=告警） |
| 波动检测 | 和历史均值比（自适应的质量基线） |
| Blood Lineage | 数据血缘（表和字段的族谱） |
| Impact Analysis | 影响分析（改上游前先查下游谁在用） |
| Quality Score | 质量分（表的健康度量化） |

## 3. 动手实操：DQC 规则落地验证

```sql
-- 用已有 shop 库验证核心规则（真跑一遍才算数）
-- 规则⑥：波动检测（订单表当日 vs 前 7 天均值）——模拟"掉数"场景
-- 造一个"掉数日"：0923 分区只放 1 行（正常应有 3 行）
INSERT OVERWRITE TABLE shop.dwd_order_di PARTITION (dt='20260923')
  SELECT 3, 101, 1001, 199.0;
-- 执行检查 SQL（这就是最朴素的 DQC 任务）：
SELECT '20260923' AS dt,
  (SELECT COUNT(*) FROM shop.dwd_order_di WHERE dt='20260923') AS today_cnt,
  (SELECT ROUND(AVG(c),1) FROM (
     SELECT COUNT(*) AS c FROM shop.dwd_order_di
     WHERE dt BETWEEN '20260916' AND '20260922' GROUP BY dt) t) AS avg7
-- 结果：1 vs 约 2.4 → 比例 0.41 < 0.5 → 强规则触发：任务应失败并告警

-- 规则⑤：主键唯一性检查
SELECT oid, COUNT(*) FROM shop.dwd_order_di WHERE dt='20260924'
  GROUP BY oid HAVING COUNT(*) > 1;
-- 有返回行 = 主键重复 = 强规则阻断信号

-- 规则③：空值率检查
SELECT ROUND(SUM(CASE WHEN uid IS NULL THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS null_pct
  FROM shop.dwd_order_di WHERE dt='20260924';

-- 生产形态：规则 SQL 模板化 + 每任务收尾自动执行 + 结果写 dqc_result 表
-- （day27 调度编排时，把 DQC 任务插在 DWD 与 DWS 之间——检查不过，下游不跑）
```

## 4. 面试连接

**Q：数仓的数据质量怎么保障？（开放题，考体系）**
> 我的框架是"六性定标准、两档定处置、波动定基线、血缘定追责"。首先用质量六性把"干净"变成可度量的六把尺子：完整、准确、一致、及时、唯一、有效——不能只说"数据要准"，要说"准确到什么指标"。然后把规则分两档执行：强规则阻断——主键重复、分区行数骤降这类影响下游正确性的，检查不过任务直接失败、下游挂起，宁可晚出数不可出错数；弱规则告警——空值率略高、值域偶发超界这类影响体验的，记质量分通知 Owner。第三是基线用波动检测而不是固定阈值——业务天然在涨，"行数 > 1 万"这种阈值半年就失效，"当日行数在前 7 天均值的 0.5~2 倍之间"才能长期跑，这是质量规则的自我适应。最后靠血缘闭环：数字不对沿血缘逐层回溯定位，上游要变更沿血缘下游全通知。落地形态是把规则 SQL 模板化插进调度链（DWD 出来先过 DQC 再放行 DWS）。这套东西的思想源头就是业务系统的对账：差错是常态，系统要能自己发现差错——我做过支付对账，这套是同一方法论在数据域的平移。

**Q：上游业务库要改表结构，你怎么保证数仓不被打爆？（协作场景题）**
> 三道工序。第一道靠血缘做影响分析：变更申请单进来，先沿血缘把下游所有表、任务、报表列全——这是分层数仓的天然红利，表名前缀和任务命名规范让血缘可以自动解析，改一张 ods 表，能五分钟内列出"3 个 DWD 任务、2 张 DWS、5 个 ADS 报表"受影响。第二道靠分层做缓冲：业务库改字段，ODS 原样跟着变（它本来就是镜像），但 DWD 层做适配层——优先让业务方提供兼容视图或双写期，DWD 的清洗 SQL 只在适配点改一处，下游 DWS/ADS 完全不动——这就是当初坚持"下游只读 DWD"的回报。第三道靠灰度做验证：变更日先在测试分区跑全链路 DQC 对账（当日 GMV 与旧口径差异、行数波动），对上了才放开生产分区。我们真实踩过的坑是上游字段类型从 int 改 string 没通知，DWD 隐式转换把非数字静默成 NULL，三天后运营发现报表 GMV 少了一截——从那以后变更审批必附血缘影响清单，这是血的教训换的制度。
