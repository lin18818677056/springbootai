# Day 17 · 事实表三种类型与选型

> **今日目标**：分清事实表的四种类型（事务/周期快照/累积快照/无事实）——一句话：**事务表记"每次发生"（一单一行），周期快照记"每天盘点"（一天一店一行），累积快照记"一个流程的里程碑"（一单从下单到收货全周期一行）**。今天为电商设计三类事实表各一张。
> **时长**：四类型辨析 1.5h / 设计实操 2h
> **今日产出**：三类事实表设计（含判别依据）+ 选型决策卡

## 1. 知识地图

```
问题引入：day16 说"事实表=一行一次事件"——但有些业务事实不是"事件"：
"今天店里还剩多少库存"不是一次事件，是"某个时点的状态"；
"这个订单从下单到签收用了几天"不是一次事件，是"一段流程的总结"。
不同性质的业务事实，要用不同形态的事实表装——四种类型：

① 事务事实表 Transaction Fact（最常见）——"日记本"
  一行 = 一次业务事件，事件一发生就写一行，写完不改
  例：dwd_order_di（一行一单）、dwd_payment_di（一行一笔支付）
  特点：只增不改（追加型），粒度最细，数据量最大
  判别口诀：问"每次发生记一行？"——是，就是事务表

② 周期快照事实表 Periodic Snapshot——"每日盘点表"
  一行 = 一个周期（天/小时）× 一个对象（门店/用户/商品）的状态或累计
  例：dws_inventory_daily（一行=某商品某天的库存快照）、
     dws_user_balance_daily（一行=某用户某天的余额）
  特点：哪怕当天没有事件发生也要写行（状态本身就是事实）；
       由事务表聚合或直接拍快照生成
  判别口诀：问"要回答'某天某时点是多少'？"——是，就是周期快照
  （类比：体重秤——不是"每次进食记一行"，而是"每天早上称一次记一行"）

③ 累积快照事实表 Accumulating Snapshot——"流程里程碑表"
  一行 = 一个有生命周期的流程实例，列是各里程碑的时间
  例：dwd_order_lifecycle（一行一单：下单时间/支付时间/发货时间/
     签收时间/取消时间，加上各阶段耗时）
  特点：会更新（每完成一个里程碑 UPDATE 对应列）——数仓里少有的"会改的表"；
       一行的业务含义是"这个单子从头到尾经历了什么"
  判别口诀：问"要回答'一个流程各阶段用了多久'？"——是，就是累积快照
  （类比：快递跟踪单——一张单子上"揽收/转运/派送/签收"的时间全在）

④ 无事实事实表 Factless Fact——"只记关系发生过"
  没有度量数字，只有维度外键，记"某事发生过"
  例：学生选课表（一行=某学生某天上了某节课，没有分数度量——出勤本身是事实）
  电商例：ads_campaign_exposure（用户×活动×日期——参加了没，没有金额）
  判别口诀：问"事件本身就有分析价值但没有数字？"——是，就是无事实事实表

选型决策卡（一张表记住怎么选）：
| 业务问题 | 表类型 | 电商例子 |
|---------|--------|---------|
| 卖了多少单、多少钱 | 事务 | dwd_order_di |
| 今天各商品库存多少 | 周期快照 | dws_inventory_daily |
| 订单平均多久签收 | 累积快照 | dwd_order_lifecycle |
| 哪些用户参加了大促活动 | 无事实 | ads_campaign_user |

三种类型的关系（生产视角）：事务表是源头（DWD），周期/累积快照是加工产物
（DWS/ADS）——"先记流水账，再拍快照，最后串流程"。
```

## 2. 核心概念（中英对照+大白话）

| 概念 | 大白话解释 |
|------|------|
| Transaction Fact | 事务事实表（一行一次事件，只增不改） |
| Periodic Snapshot | 周期快照（固定周期拍状态照，无事件也记） |
| Accumulating Snapshot | 累积快照（一行记一个流程全里程碑，会更新） |
| Factless Fact | 无事实事实表（只记"发生过"，没数字度量） |
| Grain（粒度） | 一行代表什么（建模第一步先定粒度！） |
| Milestone | 里程碑（流程中的关键时点） |

## 3. 动手实操：三类事实表设计与落地

```sql
-- ① 事务事实表（day16 已建 dwd_order_di——粒度：一行一笔订单明细）

-- ② 周期快照：商品库存日快照（无事件也记行）
CREATE TABLE shop.dws_inventory_daily (dt STRING, sku_id BIGINT, stock INT)
  PARTITIONED BY (dt STRING)
  ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE;
-- 造数：注意 sku 200 在 0923 无销售事件，但库存快照仍要记行（这就是与事务表的区别）
INSERT OVERWRITE TABLE shop.dws_inventory_daily PARTITION (dt='20260923')
  SELECT 1001, 50 UNION ALL SELECT 200, 8;
INSERT OVERWRITE TABLE shop.dws_inventory_daily PARTITION (dt='20260924')
  SELECT 1001, 43 UNION ALL SELECT 200, 3;
-- 分析价值：SELECT dt,stock FROM ... WHERE sku_id=200 ORDER BY dt → 库存趋势线

-- ③ 累积快照：订单生命周期（一行一单，里程碑列+耗时）
CREATE TABLE shop.dwd_order_lifecycle (oid BIGINT, uid BIGINT,
  create_time STRING, pay_time STRING, ship_time STRING, finish_time STRING,
  pay_lag_min DOUBLE, ship_lag_hr DOUBLE, finish_lag_hr DOUBLE)
  ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE;
INSERT INTO shop.dwd_order_lifecycle VALUES
 (9001,101,'2026-09-20 10:00:00','2026-09-20 10:05:00','2026-09-21 09:00:00','2026-09-23 14:00:00', 5, 23.0, 53.0),
 (9002,102,'2026-09-22 20:00:00','2026-09-22 20:01:00','2026-09-23 08:00:00','2026-09-24 12:00:00', 1, 12.0, 28.0);
-- 一句话产出业务答案：平均支付等待 3 分钟 / 平均签收 40 小时
SELECT ROUND(AVG(pay_lag_min),1) AS avg_pay_min, ROUND(AVG(finish_lag_hr),1) AS avg_finish_hr
  FROM shop.dwd_order_lifecycle;

-- ④ 选型对账（自问自答四连）：
-- "昨天卖了多少钱"→事务表；"今天还剩多少货"→周期快照；
-- "发货一般拖几天"→累积快照；"谁领了券没花钱"→无事实+事务组合
```

## 4. 面试连接

**Q：事实表有哪几种类型？分别什么场景用？（建模进阶必考）**
> 四种，用四个电商问题串着记。事务事实表：一行一次业务事件，订单表一行一单，只增不改，是最常见的主力表，回答"卖了多少钱"。周期快照事实表：固定周期给状态拍照，一行是"某天某对象的状态"，哪怕当天什么都没发生也要记行——典型是库存日快照，回答"今天还剩多少货"；它和事务表的本质区别是"状态本身就是事实"，不依赖事件发生。累积快照事实表：一行记录一个流程实例的全部里程碑时间列，订单从创建到支付到发货到签收一行装完，而且会随流程推进更新——它是数仓里少有的"会改的表"，回答"流程各环节耗时长不长"。无事实事实表：没有度量只有维度外键，记录"关系发生过"——用户参加了哪个活动，本身没有数字但出勤就是分析价值。选型口诀：问金额找事务、问时点找周期、问耗时找累积、问有无找无事实。落地关系是：事务表在 DWD 当源头，周期和累积快照是下游加工产物——先记流水账再拍快照最后串流程。

**Q：设计事实表，粒度（Grain）怎么定？定错了会怎样？（考建模功底）**
> 粒度是事实表的"一行代表什么"——建模第一步先声明它，后面所有度量都依赖这个承诺。我的定法是三问：业务最细要分析到哪一步？（订单行级还是订单级）、源头数据支持多细？（日志里有 sku 级，账单只有单级）、存储与查询的平衡？（越细越通用也越大）。定错的两种后果都见过：粒度定粗了——比如订单表一行一单，后来运营要分析"同一单里哪个品类卖得好"，发现拆不了，只能回炉重做模型从历史重算，代价极大；粒度定细了——把页面每一次曝光都记进事实表，数据量翻十倍，90% 的查询其实用不到这个粒度，白白拖慢所有人。实践准则是"细而不冗"：粒度取业务分析的最细有意义层级（订单明细到 sku 行级），但不高过它（不存 pv 埋点到订单事实表，行为数据另立事务表）。补一句纪律：粒度必须写进建表文档的第一行，任何度量列都要能回答"在这个粒度下它怎么加"——可加性对不上粒度的度量定义就是错的。
