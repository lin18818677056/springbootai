# Day 15 · 数仓分层：厨房进货到上桌

> **今日目标**：搞懂数仓为什么要分层、四层（ODS/DWD/DWS/ADS）各自干什么——一句话：**原始数据进来先"囤在冷库"（ODS），洗净切配（DWD），做成半成品（DWS），装盘上桌给老板看（ADS）**。这是本月主线项目的"总设计图"。
> **时长**：分层原理 1.5h / 电商数仓分层设计 2h
> **今日产出**：电商数仓分层图（含每层表清单）+ "为什么要分层"的三个硬理由

## 1. 知识地图

```
问题引入：不分层行不行？——业务库 20 张表直接连进来出报表？
想象三个常见惨案：
  ① 五个人算 GMV，五种口径（含不含退款？含不含运费？）——每人的 SQL 从原始表
    一路算到出数，口径全靠自觉；
  ② 上游日志格式变了，二十个直接读原始数据的报表全炸——没有"中间防波堤"；
  ③ 运营要看"近 90 天复购率"，每次都全表扫亿级明细——算十分钟还占着队列。
分层的本质：把"一次加工到位"拆成"层层加工、每层负责一件事"——
像厨房：进货区（生冷不忌）→ 洗配区（洗菜切配讲卫生）→ 备餐区（半成品标准化）
→ 出餐口（装盘上桌即食）。

四层职责（每层一句话+一张典型表）：
ODS（Operational Data Store 原始层）——"进货区，原样囤货"
  职责：业务库/日志的原样落点，不做任何清洗（保真，为了能重放重算）
  表形态：ods_order_di（di=日增量）、ods_user_df（df=日全量）、外部表+TEXTFILE
DWD（Data Warehouse Detail 明细层）——"洗配区，洗净切好"
  职责：清洗（去重/补默认值/类型归一/拆异常行）+ 维度退化（把常用维度字段
  冗余进行里，比如订单明细带上品类名，避免每次查询都 Join）
  表形态：dwd_order_detail_di，按天分区，ORC 格式——下游唯一的数据入口
DWS（Data Warehouse Summary 汇总层）——"备餐区，半成品"
  职责：按主题轻度聚合（用户日活跃宽表、商品日销售宽表）
  表形态：dws_user_action_1d（每用户每天的指标集合）——一行=一人一天
  价值：跨主题复用（复购率、留存、GMV 全从这层算，口径统一）
ADS（Application Data Service 应用层）——"出餐口，即取即用"
  职责：面向具体报表/大屏的最终结果（GMV 大屏、漏斗、排行榜）
  表形态：ads_gmv_overview，行数极小（一天几行~几千行），直接对接 BI/接口

"为什么要分层"三个硬理由（面试标准答案，每个都能举本周实验背书）：
① 解耦与防波堤：上游格式变化被 ODS/DWD 挡住，下游报表不动（day11 外部表
  +读时模式债在 DWD 还掉——两层配合就是防波堤）
② 口径统一：中间层算一次"什么是有效订单"，全公司复用同一定义——
  DWD 是"数据宪法"，口径争论在 DWD 解决一次，下游不再吵
③ 性能与成本：ADS 大屏查的是几行的汇总表而不是亿级明细（day12 分区裁剪
  的上级答案：分区让你少扫 1095 倍，分层让你少扫 10 的 6 次方倍）
副产品：每层是上一层的"逻辑备份"（day05 误删三道安全网的第三道：从上游重算）
```

## 2. 核心概念（中英对照+大白话）

| 概念 | 大白话解释 |
|------|------|
| ODS | 原始层（原样囤货，不做清洗，外部表+TEXTFILE） |
| DWD | 明细层（清洗+维度退化，一行一笔业务事实） |
| DWS | 汇总层（轻度聚合宽表，一行=一人/一物一天） |
| ADS | 应用层（报表大屏专用结果表，行数极少） |
| di / df | 日增量（increment，每天新增）/ 日全量（full，每天全份快照） |
| 维度退化 | 把维度表的常用字段冗余进事实表（省 Join） |
| 数据血缘 | 数据从哪来加工到哪去的链路图（分层的天然产物） |

## 4. 面试连接

**Q：数仓为什么要分层？每一层干什么？（数仓面试第一题）**
> 先讲"不分层的三个惨案"再讲答案：口径打架（五个人五种 GMV）、上游变动全线炸（没有防波堤）、每次分析都全表扫（性能灾难）。分层就是把加工拆成四步流水线：ODS 原样囤货——外部表加 TEXTFILE 保真，为了随时能重放重算；DWD 清洗加维度退化——去重补默认值、把品类名这类常用维度冗余进行里，它是全仓唯一的"干净数据入口"，口径的"宪法"在这层定；DWS 按主题轻度聚合——一行一人一天或一行一物一天，让复购留存这类跨主题指标从同一张表算，天然口径统一；ADS 出成品——直接对接大屏报表，行数极少所以快。三个收益对应三个惨案：防波堤对应解耦、DWD 对应口径统一、ADS 对应性能——外加一个副产品：每层都是上一层的逻辑备份，误删能逐层重算，这是我们数据安全的最终底牌。我在单机 Docker 上把这套四层完整建过：从埋点日志到 GMV 大屏，ADS 表一天只有几行，查询毫秒级——分层前后就是"扫亿行"和"扫几行"的区别。

**Q：维度退化是什么？为什么 DWD 要做？（细节题，考真做过）**
> 维度退化就是把维度表的常用字段直接冗余进事实表明细里——订单明细表不只存 category_id，连 category_name、渠道名、省市都一并写进去。为什么：下游高频查询如果每次都要 Join 维度表，Join 是分布式计算最贵的操作之一（会触发 Shuffle，day22 讲倾斜时细说）；而这些维度字段变化极少（品类名一年改几次），冗余的代价几乎为零。什么时候做：DWD 生成时一次性 Join 全（当天日志刚进来就退化好），下游 DWS/ADS 全程无 Join。边界也要说：退化有度——只退化"稳定的、高频使用的"字段，会频繁变化的维度（比如用户实时等级）不能退化进 DWD，要么放 DWS 更新，要么查询时现 Join。一句话：用少量存储冗余换大量计算开销，这是数仓里最划算的一笔交易——本质和 MySQL 里"适当反范式化"是同一个权衡。
