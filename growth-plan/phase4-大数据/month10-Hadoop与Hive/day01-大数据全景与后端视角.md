## 1. 知识地图

```
先说人话：大数据 = "一台机器存不下的数据"和"一台机器算不完的活"怎么办。
答案朴素得惊人——很多台机器一起存、一起算，再配个"总指挥"。
所以大数据技术栈的五层，每层都在回答一个很具体的问题：

① 存到哪里？—— 存储层
  HDFS：把一个大文件切成块，撒到几十台机器上，各存 3 份防盗防丢
  （类比：图书馆一本书太厚放不进一个格子？撕成 100 本小册子，分散到 3 个馆区各放一套）
② 怎么算？—— 计算层
  MapReduce：把大活拆成小活，分给几十台机器同时干，最后汇总
  Spark / Flink：同样的思路，但更快（后面月份细讲）
  （类比：全班 50 人数作业本，一人数一摞，班长汇总——比班长一个人数快 50 倍）
③ 谁来分配机器？—— 资源层
  YARN：集群的"包工头"，哪台机器有空闲内存和 CPU，就把任务派给谁
  （类比：线程池的集群版——corePoolSize 换成了"整个机房"）
④ 怎么写查询？—— 分析层
  Hive：给"拆活算数"套上 SQL 外壳——你写 SQL，它翻译成 MapReduce 去跑
  Presto / ClickHouse：更快的交互式查询引擎（后面接触）
  （类比：不会开手动挡没关系，Hive 是自动挡——SQL 进去，分布式任务出来）
⑤ 数据怎么进来？—— 同步层
  DataX / Sqoop：批量搬（每天凌晨把 MySQL 昨天的单子搬进数仓）
  Flink CDC / Canal：实时搬（MySQL 一有变动就同步）
  （类比：每天定时进货 + 有新货随时上架）

五层串起来一句话：DataX 把数据搬进 HDFS，YARN 派机器，MapReduce/Spark 干活，
Hive 让你用 SQL 指挥这一切——本月就吃透这条链。
```

**今日重头戏：兑现 M9 day30 思考题——"MySQL 已经能跑分析 SQL，为什么还需要 Hive？"**

```text
我的正式回答（三层论证，面试可直接用）：

① 量级关：单机索引撑不住百亿行
  MySQL 的 B+ 树是为"单机内存装得下热数据"设计的（M4 day02 学过）。
  10 亿行的订单表，一个全表 GROUP BY = 磁盘全扫分钟级起步，
  而且大数据分析往往要"全量历史"，不是"最近一年"——3 年 30 亿行，单机存储都悬。
  HDFS 的答案是：数据撒在几十台机器上，算的时候几十台机器一起扫——
  单机 30 分钟的活，30 台机器 1 分钟干完（粗算，实际有协调开销）。

② 隔离关：分析和交易抢资源本身就是事故
  就算 MySQL 勉强跑得动，分析 SQL 一跑就是全表扫描，
  会把 buffer pool（内存缓冲池）里热的交易数据全部挤出去——
  线上下单接口 RT 瞬间从 5ms 飙到 500ms。这就是 M8 day01 读写分离的极致版：
  交易库和分析库物理隔离，分析的事再重也不碰交易机器。
  数仓的第一价值就是"把分析搬走"。

③ 生态关：SQL 之外还需要一整套加工流水线
  分析不只是"跑个查询"：要清洗脏数据、要按天分区归档、要一环扣一环加工
  （原始层→明细层→汇总层）。Hive 的表模型（分区/分桶/存储格式）
  和它背后 HDFS 的文件系统天然支持这套"批处理流水线"——MySQL 的行式存储做这些很别扭。

一句话总结：MySQL 管"今天这一单"（毫秒级、在线事务），
Hive 管"过去三年每一单"（分钟级、离线分析）——不是谁替代谁，是分工不同。

反身对账（诚实记录）：这题我在 M9 day30 只答出了"量级不同"一层，
今天补齐"隔离"和"生态"两层后答案才完整——跨月伏笔兑现时往往能再长出一层。
```

## 2. 核心概念（中英对照+大白话）

| 概念 | 大白话解释 |
|------|------|
| HDFS (Hadoop Distributed File System) | 分布式文件系统——把大文件切块撒到多台机器存的"软件版磁盘阵列" |
| MapReduce | 分而治之的计算模型——拆活（Map）+ 汇总（Reduce） |
| YARN (Yet Another Resource Negotiator) | 集群资源调度器——决定哪台机器干哪个活的"包工头" |
| Hive | SQL on Hadoop——写 SQL 就能分析 HDFS 上的数据 |
| Data Warehouse（数仓） | 数据仓库——把各处业务数据集中起来做分析的"专用图书馆" |
| OLTP / OLAP | 联机事务处理（扛交易，行级增删改查）/ 联机分析处理（扛分析，大批量扫描聚合） |
| Data Skew（数据倾斜） | 数据倾斜——活分得不均匀，一台机器累死其他机器闲着（day22 主角） |

## 3. 动手实操：环境搭建

```powershell
# 第一步：确认 Docker 正常
docker version
# 第二步：拉起单机 Hadoop（伪分布式：一台容器里模拟全套角色）
# 镜像选型：自有配置的 docker-compose 更贴近真实（big-data/01 有完整版），先用轻量镜像验证链路
docker run -d --name hadoop-single -h hadoop `
  -p 9870:9870 -p 8088:8088 -p 9864:9864 `
  apache/hadoop:3.3.6 bash -c "hdfs namenode && hdfs datanode"
# 第三步：验证 HDFS 活着（浏览器打开 http://localhost:9870 应能看到 Web UI）
docker exec hadoop-single hdfs dfsadmin -report
# 第四步：上传第一个文件试试（把本月目录说明放进 HDFS）
echo "hello bigdata" > hello.txt
docker exec hadoop-single hdfs dfs -mkdir -p /user/root
docker cp hello.txt hadoop-single:/tmp/hello.txt
docker exec hadoop-single hdfs dfs -put /tmp/hello.txt /user/root/
docker exec hadoop-single hdfs dfs -cat /user/root/hello.txt
# 看到 hello bigdata 输出 = 存储链路通。端口语义：9870=NameNode UI，8088=YARN UI
```

## 4. 面试连接

**Q：MySQL 已经能跑分析 SQL，为什么还需要 Hive/数仓？（M9 day30 思考题正式版）**
> 三层原因。第一是量级：MySQL 的 B+ 树索引和缓冲池都是为单机设计的，百亿行全表聚合分钟级起步，而分布式方案把数据和计算摊到几十台机器并行，时间能压两个数量级。第二是隔离：分析 SQL 是全表扫描大户，会挤掉交易热数据导致线上接口抖动，所以分析的活必须物理搬走——数仓本质是读写分离的极致形态。第三是生态：离线分析需要的是一整套加工流水线——清洗、分区归档、逐层加工，Hive 的分区表和 HDFS 的文件组织天然为批处理设计，行式存储的 MySQL 做这些很别扭。所以结论是分工：OLTP 交给 MySQL，OLAP 交给 Hive，各自在自己擅长的负载里工作。我自己在项目里就见过反面案例：有人在主库直接跑运营报表，全表扫描把下单接口 P99 从 40ms 顶到 900ms——那次之后我们所有的分析需求一律走数仓。

**Q：你是 Java 后端，为什么要转大数据方向/学大数据？（定位题，必准备）**
> 不是转行，是补全。后端做到高阶必然碰到"数据大了怎么办"：大表归档、报表查询变慢、运营要全量行为分析——这些的终点都是数仓。我学大数据的目标是能和数仓团队对话：懂分区设计才能建好同步任务，懂数据倾斜才能帮他们定位我这边数据的问题（比如某商家订单量占一半导致倾斜），懂数仓分层才能明确"哪些指标该数仓算、哪些该业务库实时出"。本月我自己从零搭了一套电商数仓——四层加工、倾斜治理、调度编排都亲手做过，不是为了转岗，是为了在"业务系统"和"数据系统"的交界处把工作接住。
