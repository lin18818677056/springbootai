## 4. 面试连接

**Q：你是 Java 后端，为什么要学大数据？学了之后给你带来什么？（定位大题）**
> 三层递进。第一层是被迫的：业务数据过亿后，MySQL 里跑一条全表分析的 SQL 就能把交易主库拖垮——buffer pool 热数据被冲掉，下单 RT 从 5ms 飙到 500ms。隔离是刚需，数仓本质就是读写分离的极致版。第二层是主动的：把分析负载搬到独立的技术栈（HDFS+Hive），靠的是水平扩展——30 台便宜的机器并行扫，单机 B+ 树撑不住的量级就撑住了；而且 Hive 分区表+HDFS 目录组织天然支持"清洗→汇总→出报表"的流水线。第三层是回馈：这套系统的设计思想反过来升级了我的后端功力——NameNode 的 FsImage+EditLog 就是 RDB+AOF，JournalNode 多数派就是哨兵选主的近亲，数仓对账就是支付对账的平移，INSERT OVERWRITE 就是接口幂等。学习结果可以量化：我从零搭了单机集群，跑通了"业务库→ODS→DWD→DWS→ADS→大屏"全链路，产出了小文件治理方案、建表规范、倾斜治理手册、调度脚本四份制度文档——不是背概念，是有动手证据的。

**Q：（模拟面试压轴）讲一下你们的数据是怎么从 MySQL 到大屏上的？**
> 按"数据的一生"讲，每一站带一个决策点。同步层：业务库通过同步工具把 binlog/表数据原样落到 HDFS，按天一个目录。存储层：HDFS 三副本两机架，NameNode 高可用由 JournalNode 多数派+ZKFC 保证——这里我踩过小文件的坑：每 5 分钟滚动一个文件，一天 288 个小文件，NameNode 内存和寻址都遭罪，后来源头改成小时级合并+分层规范收口。计算层：YARN 划了 prod/offline/dev 三个队列，报表任务走 prod 保底资源，探索查询挤不垮它。加工层：四层数仓——ODS 外部表原样挂载（保险柜），DWD 清洗去重+维度退化（口径宪法），DWS 预聚合宽表（贵计算只算一次），ADS 大屏专用表。质量层：DQC 强规则主键唯一+波动检测，脏数据进隔离区不销毁；上线前做了全链路对账 14→12→12→12 四段对平。调度层：DolphinScheduler 编排依赖链，失败重试 3 次，全败即整线 STOP+告警；补数靠幂等写+参数化日期从上游按拓扑重跑。整条链讲完 5 分钟，每一站都有"为什么这样设计"和"出了什么事"——这就是体系化表达，比单点知识值钱得多。
