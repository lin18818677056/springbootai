## 3. 动手实操：《HDFS 小文件治理方案》v1

```markdown
<!-- docs/hadoop/small-files-plan-v1.md —— 本周落地成品（面试可直接讲的项目材料） -->
# HDFS 小文件治理方案 v1（电商埋点日志场景）
## 1. 现状与问题
- 埋点采集端每 5 分钟滚动一个日志文件，单机 288 文件/天，集群 30 台 → 日增 8600 小文件
- 实测（day04 实验）：1 万小文件使 NameNode 堆内存上涨约 1.5MB 元数据+调度开销爆炸
- 风险：按此增速，3 年 900 万文件/节点 → NameNode OOM，fsck 超时
## 2. 治理方案（三层）
| 层 | 动作 | 责任方 | 验收 |
|----|------|--------|------|
| 源头 | 采集端改 1 小时滚动；上传前本地 merge | 业务团队 | 单机日增 ≤24 文件 |
| 存量 | 每日凌晨合并任务：按天 getmerge 重写 ODS 原始目录 | 数据团队 | 每天每目录 ≤24 文件 |
| 规范 | 数仓规范写死：DWD 每分区文件 128M~1G；ODS 开快照 | 委员会 | 落进建表 Checklist |
## 3. 回滚与验证
- 合并任务幂等（重写目录可重跑）；合并前后 checksum 对账（M8 day13 思想）
- 监控：NameNode heap 与 files-with-missing-blocks 双指标告警（M8 黄金四信号复用）
```

## 4. 面试连接

**Q：面试官让你"讲讲 Hadoop"，3 分钟怎么讲？（串讲题，考知识组织）**
> 按问题链讲，不按组件罗列。第一句定调：Hadoop 解决"一台机器存不下也算不动"——核心是分布式存储 HDFS 和分布式计算 MapReduce，中间 YARN 管资源。存储层三句话：切块撒开存三份，128MB 是元数据量和并行度的折中；NameNode 管元数据是单点，靠 HA 双主加 JournalNode 多数派保命，它的内存是集群天花板，所以小文件是灾难——我们治理过，源头合并加存量重写加分层规范三板斧。计算层两句话：Map 拆活局部算，Reduce 按 key 汇总，中间 Shuffle 落盘是性能大头，所以 Combiner 预聚合是标配；MR 慢在三轮磁盘 IO，这也是 Spark 出现的原因。收尾一句展示视野：这套东西和后端知识同构——NameNode 像注册中心，多数派像哨兵选主，局部聚合像内存计数，我是带着后端工程视角进大数据的，上手快、能跨域排查。3 分钟讲完有数字有故事有视野——比背 20 个名词的候选人强一档。

**Q：这一周学的东西，和你的 Java 后端工作有什么关系？（动机考察）**
> 三个直接关系。一是排查能力：线上数据同步任务失败，我知道去看 YARN 日志、HDFS fsck、DataNode 心跳——很多后端到这就两眼一抹黑只能等数仓团队上班。二是设计对话：埋点采集方案的文件滚动频率、同步任务的分片策略，这些是我们后端定的，不懂小文件问题就会把数仓下游坑惨——我这一周亲手算过 150 字节元数据账，方案评审时能说数字。三是思想复用：局部聚合再全局汇总、主流程不管修复、多数派防脑裂——大数据的这些"发明"全是后端老知识的放大版，学大数据反过来加深了我对后端的理解，比如重新理解了为什么对账要异步。一句话：不是为了转岗学大数据，是为了在系统边界上不犯糊涂。
