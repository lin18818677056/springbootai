## 1. 知识地图：一周六线串讲

```
本周主线一句话："Kafka 是把'随机世界'改造成'顺序流水线'的高吞吐传送带"——

① 它是谁？（day01）——三身份
  消息队列（M5 同岗位）/数据管道（大数据总入口）/可回放存储（进度条能拨回去）
  对照 RocketMQ：业务消息看 RocketMQ，数据洪流看 Kafka

② 长什么样？（day02）——四词模型
  Broker 仓库 / Topic 货架 / Partition 格口 / Offset 进度条
  顺序只保证格口内；key 路由是保序钥匙；消费组组内独占、组间广播

③ 为什么快？（day03）——四原因一哲学
  顺序写（百倍）/ 页缓存+零拷贝（4→2 次拷贝）/ 批量压缩（2~5 倍）/ 分区并行
  哲学：资源有价，架构即交换（M8 主线的 Kafka 版）

④ 分区怎么定？（day04）——吞吐倒推三步+三道闸
  目标吞吐÷单分区实测→留余量；过闸：只能加不能减/broker 上限/下游消费力

⑤ 怎么换人？（day05）——Rebalance 治理
  三类触发（99% 是成员意外下线）/两条被踢线（心跳+干活）
  四策略演进（代价递减）；三板斧：静态成员+超时按最坏耗时定+CooperativeSticky

⑥ 数据安不安全？（day06）——副本与可靠性
  Leader 干活 Follower 抄作业 / ISR 考勤表（落后时间而非条数）
  acks 三档+min.insync.replicas 防假高可用；unclean 选举的 C/A 取舍
```

## 4. 面试连接

**Q：完整讲一下 Kafka 的架构和你对它的理解？（开场综合题）**
> 三层递进：先一句话定位，再核心机制，再工程取舍。定位：Kafka 是分布式追加日志系统，在外卖单里它同时是消息队列（削峰解耦）、数据管道（各系统数据总线）和可回放存储（offset 可拨回）。机制四件套：物理上 Broker 集群存数据；逻辑上 Topic 划分业务，每个 Topic 切 N 个 Partition——分区是并行与顺序的最小单位（格口内 append-only 有序，靠 key 路由保业务序）；消费上 Consumer Group 组内独占分区、组间广播，进度（offset）提交回 broker 内部的 __consumer_offsets 主题，状态外置所以消费者可死可换；可靠性上每个分区一主多备，ISR 动态考勤，acks=min.insync.replicas 组合保证"成功即安全"。取舍层面最能体现理解：它为吞吐砍掉了随机写（全顺序）、自建缓存（用 OS 页缓存）、精细延迟消息（RocketMQ 强项）——所以选型上数据洪流选 Kafka、强事务业务消息选 RocketMQ，我两个都用过，各守各的岗位。这样 2 分钟讲完，有定位有机制有取舍，比背 20 个名词有效。

**Q：这周学的所有机制里，你认为哪个设计最精妙？（检验内化）**
> 我选 __consumer_offsets 的"用 Kafka 存 Kafka"。第一层是工程优雅：消费进度本身就是一条条普通消息，放进一个内部 Topic，天然继承分区副本持久化全套能力，零额外组件。第二层是思想价值：状态外置——消费者实例可以随时死、随时换，进度在集群里不丢，这是把"无状态计算+有状态存储"分离的经典示范；我在 M7 做工作流引擎时把流程状态从内存挪到数据库，踩的就是同一个道理。第三层是延伸：正因为 offset 是消息、消费历史是流，Kafka Streams 才能做"把消费组本身当作流来管理"，log compaction（Compact 压实保每个 group 的最新进度）才有了用武之地——一个设计决策支撑了后续一堆能力。能把"精妙"说成机制因果链而不是一句感慨，才是真消化了。
