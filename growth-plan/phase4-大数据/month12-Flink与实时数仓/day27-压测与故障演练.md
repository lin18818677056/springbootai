# Day 27 · 压测与故障演练：上线前的"撞车测试"

> **今日目标**：对 day26 的整车做上线前验收——压测（把流量拉到目标峰值看会不会散架）+ 故障演练（把《故障预案速查表》六条真演一遍）。没撞过的车不敢上路，没演练过的预案等于没有。
> **时长**：压测 2.5h / 演练 2.5h / 输出 0.5h
> **今日产出**：压测报告（容量上限数字）+ 演练记录表（6/6）+ 上线验收结论

## 1. 知识地图（先讲人话）

```
压测回答的问题：这辆车最多能开多快？开到多快开始散架？
  方法还是老三样（M11 day27 的控制变量法平移到流世界）：
  ① 定档位：datagen rows-per-second 从 1000 → 5000 → 20000 逐级拉
  ② 看仪表：UI 四仪表盘——Records In / busy% / 反压状态 / Lag
  ③ 找拐点：busy 持续 100%、输出开始滞后输入 = 这就是容量上限
  撞车点分析（散架的姿势通常是这三种之一）：
    算不动（busy 100%，加并行——day23 倒推卡）
    搬不动（网络/序列化瓶颈，看 Network 相关指标）
    存不动（状态/CKPT 跟不上，day22 决策树）

故障演练回答的问题：真撞了，你会不会按预案走？
  演练纪律（消防演习原则）：
    ① 一次只断一样（控制变量，别一次炸三个）
    ② 演练前记下当前 CKPT 位置（等会验证恢复到哪）
    ③ 每次演练记录：时间线 + 恢复时长 + 数据损失检查
  演练清单对照 day26 的速查表六条：
    TM 挂（day08 做过，快速复跑）/ JM 挂 / 断流 / CKPT 连挂 / 结果不对 / 升级回滚

诚实边界（演示环境的演习规则）：
  datagen 内置造数没法"中途停"——断流演练用"停掉源容器"替代或文档推演；
  JM 挂演练会连 UI 一起带走（观察手段：docker ps + jobs Rest API 恢复后核对）
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Load Test | 压测 | 把流量拉到目标峰值，看系统撑不撑得住 |
| Capacity Limit | 容量上限 | 系统开始"散架"的流量拐点（压测要拿到的核心数字） |
| Chaos Engineering | 混沌工程 | 主动制造故障来验证预案（演练的学名） |
| Recovery Time | 恢复时长 | 从"挂"到"完全恢复出数"的分钟数（演练要量化的指标） |
| Blast Radius | 爆炸半径 | 一个故障波及的范围（演练评估隔离性） |
| Acceptance Test | 验收测试 | 上线前的最终关卡（今天的产出就是验收结论） |

## 3. 动手实操

### 3.1 压测：三档拉流量找拐点

```sql
-- 用 day16 的 dwd 清洗链路作业（或最简 GROUP BY 作业）作为被测对象
-- 档位① rps=1000：基线。UI 记录 busy%、输出速率
SET 'parallelism.default' = '1';
-- 档位② rps=5000：忙碌档。busy% 预期 60~80%
-- 档位③ rps=20000：过载档。预期 busy 100% + 反压指示灯亮 + 输出滞后
-- 每档跑 3 分钟，记录进《压测报告》：
--   | 档位 rps | 并行度 | busy% | 反压? | 输出滞后 |
--   | 1000     | 1      | 30%   | 否    | 0        |
--   | 5000     | 1      | 85%   | 边缘  | 秒级     |
--   | 20000    | 1      | 100%  | 是    | 持续拉大 |
-- 扩容验证：20000 档切并行度 8（day23 倒推卡：单并行 3000×8=24000>20000）
--   预期 busy 回落 70% 左右——容量结论：该作业单链路安全容量约 2000 条/s/并行
```

### 3.2 故障演练：六条预案逐条演（记录表）

```powershell
# 演练①：TM 挂（复跑 day08，验证整链路恢复）
docker kill flink-tm
# 记录：作业进入 RESTARTING → TM 自动重启（docker restart 策略或手动 docker start flink-tm）
# 恢复后检查：UI 无异常；从最近 CKPT 继续；输出无时间空洞（窗口没断档）
docker start flink-tm

# 演练②：JM 挂（最狠的一条：UI 和作业一起停）
docker kill flink-jm; docker start flink-jm
# 观察：作业自动重新部署恢复（standalone 模式重启 JM 后作业重跑自 CKPT）
# 记录恢复时长：___ 秒（生产上 JM 高可用就是把这个恢复自动化+秒级化）
```

```
演练③ 断流：datagen 无法中途停 → 演练替代方案：把 rps 改成极小或停掉源作业 INSERT，
        观察"无新数据但作业健康"（Lag 概念的反面教材：没数据≠挂了）
演练④ CKPT 连挂：把 CKPT interval 改 1s + 大状态（day22 素材）→ 制造失败 → 按决策树处置
演练⑤ 结果不对：故意把 day19 对拍差异放大（漏掉 action='pay' 条件）→ 走嫌疑人清单归因
演练⑥ 升级回滚：day24 的 savepoint 流程反着走一遍（新版不兼容 → 旧版读档回滚成功）
每条记录：开始时间 / 操作 / 现象 / 恢复动作 / 恢复时长 / 数据损失检查（√）
```

## 4. 面试连接

**Q：你的实时作业上线前做了哪些验收？（工程成熟度信号题）**
> 两类验收加一份结论。压测验收：用控制变量法三档拉流量找容量拐点——单并行压到 busy 100% 得到单工人吞吐约 3000 条/s，按目标峰值倒推并行数再加 50% 余量；最终配置下峰值流量 busy 稳定 70% 左右，留有余量。故障验收：预案六条真演一遍——kill TaskManager 验证 Checkpoint 自动恢复无时间空洞、kill JobManager 验证集群恢复、断流场景验证"没数据不等于挂了"的判断力、故意放大对拍差异验证归因流程、savepoint 回滚验证升级退路。每条演练都有恢复时长记录。最后产出一份上线验收结论：容量数字、演练覆盖、监控告警三线齐备才放行。这套流程让我在面试里敢说"我的项目不只是能跑，是经过撞车测试的"。

**Q：线上出了数据不对，你的排查顺序？（预案的实战问法）**
> 三层往上查，每层有判定标准：先查"作业层"——UI 看作业是否 RUNNING、有没有重启记录、CKPT 是否连续失败（大多数问题在这一层就现形）；再查"链路层"——上游 Kafka 有没有断流、Records In 是否归零（没数据不等于挂了，别瞎重启作业把状态搞乱）；最后查"数据层"——动用实离对拍的嫌疑人清单归因：口径漂移、窗口边界、迟到丢弃、数据源不同步，用差异率三档判定严重程度。纪律是"先定位再动手"——没定位就重启，轻则丢恢复点，重则把小事故变连环事故。
