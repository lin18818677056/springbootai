# Day 19 · 实离对拍：实时账和离线账，数字必须对上

> **今日目标**：项目周第 5 天，也是本月灵魂——把 day17 的实时 GMV 和 M11 的离线 GMV 做对拍（三本账方法论第四次上场）；搞清实时链路的固有误差源；产出《实离对拍 SOP》（生产每天的例行核对怎么做）。
> **时长**：对拍设计 1h / 对拍执行 2h / 差异分析与 SOP 2h
> **今日产出**：对拍报告（含差异率）+ 误差源清单 + 《实离对拍 SOP》

## 1. 项目设计（先讲人话：为什么要拍）

```
两条链路算同一个指标（今日成交额）：
  实时账：Flink 窗口聚合（day17 产出）——新鲜，但可能有误差
  离线账：Spark T+1 全量重算（M11 产出）——慢一天，但是"最终真相"
  —— 对拍 = 每天用"真相"给"新鲜"校准一次
  —— 对不上不可怕，可怕的是不知道差多少、为什么差

三本账方法论的第四次上场（跨月主线）：
  M8（分布式对账）：重复请求不重复记账——对账思想的诞生
  M10（数仓对拍）：ODS→DWD→DWS→ADS 层层对账
  M11（双引擎对拍）：Hive 算的=Spark 算的（引擎可以换口径不能换）
  M12（实离对拍）：实时账≈离线账（新鲜是近似，精确靠兜底）
  —— 一句话：数字会骗人，交叉验证不会

实时链路的固有误差源（对拍差异的"嫌疑人清单"）：
  ① 乱序丢弃：水位线外到达的迟到数据被丢（or 侧输出）→ 实时账偏小
  ② 窗口边界：跨窗口边界的单子归属差异（事件时间 vs 落地时间）
  ③ 口径漂移：实时过滤条件（action='pay'）和离线不完全一致
  ④ 重复：append 场景恢复重放（day17 用 upsert 已规避）
  ⑤ 数据源不同步：实时读 Kafka 流，离线读 HDFS 落地文件——
     落地作业挂了一小时，离线账就少一小时（这是离线的误差！）
  —— 对拍差异不是"实时错了"的判决书，是"找茬游戏"的起点

对拍口径（先对口径再对数字——M11 day26 的纪律）：
  指标：当日成功订单的金额合计+订单数
  时间：同为自然日（事件时间口径）
  实时源：day17 print 输出的当日窗口合计（演示环境聚合）
  离线源：shop.dwd_order_detail_di 当日 amount 合计
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| RT-Offline Reconciliation | 实离对拍 | 每天拿离线真相给实时校准 |
| Inherent Drift | 固有误差 | 实时链路天生会有的小偏差（量级可控） |
| Caliber Alignment | 口径对齐 | 先对"算什么"再对"算出来多少" |
| Threshold Alert | 阈值告警 | 差异率超线（如 1%）才告警，别当惊弓之鸟 |
| T+1 Correction | T+1 修正 | 离线账出来后覆盖/修正实时结果 |
| Single Source of Truth | 唯一真相源 | 结算以谁为准（离线账）——写进口径文档 |

## 3. 动手实操：执行一次完整对拍

```sql
-- ===== 第 1 步：离线账（真相源）=====
-- spark-shell 或 hive：当日成交合计
-- SELECT sum(amount), count(*) FROM shop.dwd_order_detail_di
--   WHERE dt='2026-09-27' AND amount > 0;
-- （M11 环境：记录 离线GMV=____，离线单量=____）

-- ===== 第 2 步：实时账（新鲜源）=====
-- day17 的窗口输出逐行累加（演示环境的 print 结果手工汇总；生产=
--   SELECT sum(gmv), sum(order_cnt) FROM ads_gmv_realtime
--   WHERE window_start >= 当日零点）
-- 记录 实时GMV=____，实时单量=____

-- ===== 第 3 步：算差异率 =====
-- 差异率 = |实时GMV − 离线GMV| / 离线GMV × 100%
-- 判定：≤1%  通过（固有误差范围内）
--      1%~5% 预警（查嫌疑人清单）
--      >5%  告警（大概率口径或链路故障）
-- 演示环境预期：datagen 是假流，无法真对拍 M11 真数据——
--   本次对拍留"流程证据"（SQL/步骤/判定表），
--   数据一致性由 M11 的三本账实验背书（诚实记录，不伪造数字）
```

```
第 4 步：差异归因演练（假设差异率 3%，走一遍排查）
  □ 口径核对：实时 WHERE action='pay' vs 离线 amount>0——等价吗？
    （退款单：实时没排除退款 → 差异来源！）
  □ 边界核对：跨零点订单，实时按事件时间归昨天，离线呢？
  □ 丢失核对：水位线乱序度 5s，迟到 >5s 的单被丢了几笔？
    （埋点上报 P99 若是 3s，5s 够；若上游抖动到 10s——丢）
  □ 数据源核对：离线的落地作业当天有没有断流？（查落地日志）
  → 结论模板："差异 3%，其中退款口径差异 2.5%，迟到丢弃 0.5%，
    修口径后预期差异 <0.5%"——每 0.1% 都有出处
```

```
《实离对拍 SOP》（生产每日例行，直接抄）：
  1. 时间：每日 T+1 上午 10 点（等离线跑完）
  2. 口径：对拍前先核对两侧口径文档版本（改过口径要对齐）
  3. 执行：差异率 SQL 跑三本账（实时表/离线表/明细直算）
  4. 判定：≤1% 归档 / 1~5% 预警走嫌疑人清单 / >5% 告警拉群
  5. 修正：按"唯一真相源"原则用离线账修正历史窗口数据
  6. 留痕：差异率曲线日报（连续抬升=链路在劣化，比单日超阈值更早报警）
```

## 4. 面试连接

**Q：实时数仓怎么保证数据准确性？实时和离线对不上怎么办？（本月压轴题）**
> 分两层回答。第一层"事前防"：实时链路的正确性靠三段拼图（Source 可重放/Checkpoint 状态一致/幂等 Sink）+ 事件时间分窗守边界，把可控误差压到最小；第二层"事后校"：实离对拍——每天离线跑完后，拿离线账（最终真相）和实时账核对差异率，阈值分三档（≤1% 归档、1~5% 预警、>5% 告警）。对不上时按嫌疑人清单归因：口径漂移（最常见，比如退款单一侧没排除）、窗口边界差异（跨零点归属）、乱序丢弃（水位线外的迟到数据）、数据源不同步（离线落地断流）——注意离线自己也可能有误差。每笔差异都要归因到具体原因并留痕，我们要求"差异率的每 0.1% 都说得出出处"。另外两条工程纪律：对拍前先对口径文档版本（口径改了没同步是对不上的一大根源）；看差异率趋势而不只看单日——连续抬升说明链路在劣化，比超阈值更早报警。这套方法我在 M8 到 M12 演进了四次：从分布式对账、数仓分层对账、双引擎对拍到实离对拍——方法论是同一个：不信任单点，信任交叉验证。

**Q：实时账和离线账以谁为准？（产品/架构判断题）**
> 按用途分：大屏展示、实时监控、运营看趋势——实时账为准（够新鲜，误差可容忍）；财务结算、业绩考核、对外披露——离线账为准（唯一真相源写进口径文档）。然后做 T+1 修正：离线跑完后把实时表中已关闭窗口的数据用离线值覆盖修正，这样"白天看实时，隔天看修正后的准数"。这个"唯一真相源+修正机制"的设计点很关键：不是二选一，而是各司其职+最终收敛。
