# Day 04 · 时间语义与水位线：迟到的水该算进哪一班

> **今日目标**：本月最重要的概念课——事件时间 vs 处理时间，以及 Watermark（水位线）怎么解决乱序问题。正式兑现 M11 思考题②（"10:59 的订单 11:01 才到，算哪天的数"），并用 datagen+受控乱序实验亲眼看到窗口触发时机。
> **时长**：两种时间+水位线原理 2h / 乱序实验 2h / 输出 1h
> **今日产出**：水位线触发时机实验记录 + 《水位线调参卡》（乱序度权衡）+ M11 思考题②正式答案

## 1. 知识地图（先讲人话：M11 思考题②的答案）

```
先复盘 M11 留的悬念（M11 day30 交接卡思考题②）：
  "10:59 的订单 11:01 才到，算哪一天的数？"
  离线世界的回答很简单：按订单时间字段算（10:59 那天），T+1 全量重算，无所谓
  实时世界的回答很麻烦：数据流过来就处理，"到齐了吗"永远不知道——
    等太久结果慢，不等结果错（漏掉迟到的单子）
  —— 这就是今天的主题：时间语义和水位线

两种时间（必须分清）：
  Event Time 事件时间：数据【发生】的时刻（订单下单时间，业务字段）
  Processing Time 处理时间：数据【到达机器】的时刻（机器时钟）
  —— 大屏要的是"每分钟成交额"，必然按事件时间分桶；
     但数据可能迟到（网络抖动/上游积压），事件时间乱序到达

水位线 Watermark（点名的艺术）：
  类比：老师每过一会儿问一句"10:00 之前到的同学都齐了吗？"
    —— 问的就是水位线；"都齐了"就封窗口出结果
  机制：水位线 = 迄今见到的最大事件时间 − 允许乱序度(如 10 秒)
    语义："事件时间 ≤ 水位线的数据，我认为基本到齐了"
    触发：水位线越过窗口终点 → 触发窗口计算并出结果
  —— 水位线是【正确性与延迟的权衡旋钮】，不是消灭乱序：
     乱序度设大：数据全、结果准，出数慢
     乱序度设小：出数快，迟到数据多
  迟到数据怎么办（两个补救）：
    · allowedLateness：窗口出结果后再多等一会儿，来了就更新（更新结果）
    · 侧输出 Side Output：彻底迟到的收进"小黑屋"主题，人工/离线补偿

M11 思考题②正式答案（背下来）：
  按【事件时间】算，归 10:59 那一天（那一分钟的窗口）；
  水位线负责在"合理等待"后关闭该窗口；
  真正迟到的由 allowedLateness 补算或侧输出兜底——
  实时数仓通常再配一条离线核对链路（day19 实离对拍）做最终修正。
```

## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| Event Time | 事件时间 | 事情发生的时刻（业务字段，如 pay_time） |
| Processing Time | 处理时间 | 机器看到的时刻（时钟） |
| Watermark | 水位线 | "前面的基本到齐了"的进度宣告 |
| Out-of-orderness | 乱序度 | 允许迟到多少秒（权衡旋钮） |
| allowedLateness | 允许迟到 | 窗口关闭后再多等的宽限期 |
| Side Output | 侧输出 | 彻底迟到数据的"小黑屋"通道 |
| Idle Source | 空闲源 | 不出数据也不出水位线的源（会卡住全局水位线，坑） |

## 3. 动手实操：亲眼看到水位线关窗口

```sql
-- 实验：受控乱序流（datagen 做不了乱序，用 SQL 的滞后列模拟"事件时间迟到"）
-- 思路：源表处理时间 proc_t，人为造 event_time = proc_t - 随机 0~5 秒
--      再观察 10 秒滚动窗口的触发节奏
CREATE TABLE src (
  id INT,
  amt DOUBLE,
  proc_t TIMESTAMP_LTZ(3),
  WATERMARK FOR proc_t AS proc_t - INTERVAL '5' SECOND   -- 声明水位线：乱序度 5 秒
) WITH (
  'connector' = 'datagen',
  'rows-per-second' = '2',
  'fields.id.kind' = 'random', 'fields.id.min' = '1', 'fields.id.max' = '3',
  'fields.amt.min' = '10', 'fields.amt.max' = '100'
);
-- 注：datagen 的 proc_t 就是处理时间本身（不乱序）——这是"理想流"基线，
--     先看懂水位线怎么随数据推进；乱序实验在下方实验②用受控延迟造

-- 实验①：10 秒滚动窗口（观察：结果何时出现）
SELECT window_start, window_end, SUM(amt) AS gmv, COUNT(*) AS cnt
FROM TABLE(TUMBLE(TABLE src, DESCRIPTOR(proc_t), INTERVAL '10' SECOND))
GROUP BY window_start, window_end;
-- 观察 SQL 客户端结果刷新：窗口结束【+5 秒】后才出该窗口结果
-- —— 那 5 秒就是水位线在等"可能迟到的人"（截图①记下时间差）

-- 实验②：把乱序度调大重跑对照
-- （新建 src2，WATERMARK ... INTERVAL '15' SECOND，其他相同）
-- 观察：窗口结果出现更晚（等 15 秒）——乱序度的体感（截图②）
-- 结论记录：乱序度 5s vs 15s，出数延迟差 ____ 秒，这就是调参的代价

-- 实验③：观察水位线推进（调试视角）
SET 'execution.checkpointing.interval' = '3s';
-- UI → 作业 → Watermark 列：看每个算子的当前水位线随时间爬升（截图③）
```

```
调参卡速记（《水位线调参卡》主体）：
  · 乱序度初值：观测 P99 事件时间延迟（埋点上报延迟监控），取其上限
  · 兜底组合：乱序度(等大多数) + allowedLateness(补尾巴) + 侧输出(收极端)
  · 坑：多并行度下水位线取【所有源通道的最小值】——
    一个空闲的 Kafka 分区会让全局水位线卡住不动！
    解法：table.exec.source.idle-timeout 设空闲超时（闲源标记 idle 不参评）
```

## 4. 面试连接

**Q：讲讲 Watermark？它解决什么问题，怎么权衡？（本月头号必考题）**
> Watermark 解决的是"事件时间语义下，无界数据流中窗口何时关闭"的确定性问题是我的标准开头：流计算按事件时间分窗口，但网络延迟导致数据乱序到达，引擎永远不知道"该不该再等等"。水位线的机制是一行公式：迄今最大事件时间减去允许乱序度，语义是"事件时间小于等于水位线的数据，我认为基本到齐"，水位线越过窗口终点就触发计算。它是正确性与延迟的可调权衡，不是消灭乱序：乱序度设大结果准但出数慢，设小出数快但迟到多。迟到数据的两级补救：allowedLateness 让窗口关闭后继续收尾巴并更新结果，彻底迟到的走侧输出进补偿主题。我做过实验：10 秒窗口配 5 秒乱序度，窗口结束后 5 秒才出结果；把乱序度调到 15 秒，出数明显变慢——参数的代价直接可见。生产再加一条纪律：多并行度下水位线取所有通道最小值，要配 idle-timeout 防止空闲分区卡死全局水位线。最后接业务：水位线关了窗口、迟到的靠补偿，最终一致性由"实时+离线对拍"保证——这是实时数仓的正确性哲学（day19 展开）。

**Q：事件时间和处理时间怎么选？（追问）**
> 结论先行：只要业务关心"事情发生的时刻"（订单/成交/登录几乎都是），必须事件时间。处理时间只适用于"到达即事实"的场景（监控指标、限流计数）。用处理时间算"每分钟成交额"会出两类事故：上游积压时到达顺序错乱，分钟 GMV 忽高忽低；重放历史数据时全算到"现在"，结果不可复现。事件时间的代价是要配水位线和处理迟到，复杂度换正确性——这笔账在数仓场景永远划算。我的经验：源表建表时把 WATERMARK 声明写进 DDL 当成固定动作，和 NOT NULL 约束同级对待。
