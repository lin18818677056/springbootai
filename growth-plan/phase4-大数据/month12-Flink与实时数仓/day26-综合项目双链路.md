## 2. 核心概念（中英对照+大白话）

| 英文 | 中文 | 大白话解释 |
|------|------|-----------|
| JDBC Connector | JDBC 连接器 | Flink 直写 MySQL 的"插座"（upsert 幂等写） |
| Data Platform | 数据平台 | 实时+离线合起来的完整地盘（不再是两条孤立链路） |
| Runbook | 故障预案 | "报警响了先干啥"的操作手册（慌乱时刻的救命卡） |
| SLA | 服务等级承诺 | 链路延迟/可用率的对外承诺（如分钟级出数、99.9%） |
| Data Freshness | 数据新鲜度 | 大屏数字滞后多少（实时链路的核心卖点） |
| Grayscale | 灰度 | 新逻辑先切 10% 流量验证，再全量（升级 SOP 的项目版） |

### 3.1 胶水①：ADS 落 MySQL（结果终于能被大屏读了）

```sql

--   window_start DATETIME PRIMARY KEY, gmv DECIMAL(18,2), order_cnt INT);
CREATE TABLE mysql_gmv_sink (
  window_start TIMESTAMP(3),
  gmv DOUBLE,
  order_cnt BIGINT,
  PRIMARY KEY (window_start) NOT ENFORCED   -- 主键=upsert 幂等的锚点

  'connector' = 'jdbc',
  'url' = 'jdbc:mysql://hive-mysql:3306/shop',

  'username' = 'root', 'password' = 'root123'

-- 把 day17 的 GMV 输出 INSERT INTO mysql_gmv_sink
-- 验证：MySQL 里 SELECT 反复查同一窗口，值被 UPDATE 不是重复 INSERT（幂等实锤）
```

## 4. 面试连接

**Q：完整介绍一下你的实时数仓项目？（简历核心项目的 3 分钟版）**
> 背景一句话：业务要分钟级经营决策，T+1 离线不够用。架构两张图：实时链路 Kafka 原始主题作 ODS，Flink 清洗去重成 DWD 明细流回写 Kafka 总线，下游两个消费者——GMV 窗口聚合（事件时间+水位线守正确性，JDBC upsert 落 MySQL 幂等喂大屏）和 TopN 先聚再排（状态三因子控膨胀）；离线链路复用已有 Hive/Spark 数仓做 T+1 全量。两条链路用实离对拍粘住：每天差异率三档判定，离线账做唯一真相源 T+1 修正实时表。质量保障三件：事件时间语义、Checkpoint+幂等 Sink 的端到端一致性、四指标监控加告警。结果：出数延迟 T+1→分钟级；kill 掉 TaskManager 恢复无时间空洞；对拍差异率 1% 以内。每个数字背后都有我这一个月的实验记录，欢迎随便挑一层追问。

**Q：这个项目里你踩过最深的坑是什么？（诚实+深度信号题）**
> 讲一个真的：项目初期 GMV 大屏数字偶尔"倒跳"——已经出的值过了一会儿变小。排查发现是 Update 语义的窗口结果直接写无主键表，迟到数据触发窗口 retract 重发，大屏读到中间状态。修复三步：窗口结果表加主键走 upsert（终态覆盖）；水位线乱序度从 3 秒调到 5 秒压住 P99 迟到；大屏查询侧加"只读已关闭窗口"过滤。这个坑让我真正理解了 day18 的 Append vs Update 不是概念题，是生产事故题——面试讲坑就要这种"现象→定位→修复→沉淀"四段式。
