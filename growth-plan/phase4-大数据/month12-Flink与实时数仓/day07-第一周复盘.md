## 1. 四大件串讲（一条故事线）

```
一个流作业的一生（W1 视角）：

第 1 站【day01 定位】：Flink 凭什么是真流——常驻+纯流式数据结构，
  数据不攒批直接流过算子（对照微批"攒一桶倒一桶"）
第 2 站【day02 架构】：JobManager 工头切图排班 / TaskManager 工人干活
  / Slot 工位；算子链把窄算子串一串省网络
第 3 站【day03 首作业】：Source→Transformation→Sink 三段式；
  Kafka offset 存算子状态（day09 的地基）
第 4 站【day04 时间语义】：事件时间(发生时刻) vs 处理时间(到达时刻)；
  水位线=最大事件时间−乱序度，宣告"前面的基本到齐"→关窗口出结果；
  迟到的靠 allowedLateness+侧输出兜底
第 5 站【day05 窗口】：窗口管分桶、水位线管封桶；
  滚动(定班车)/滑动(区间车,注意状态放大)/会话(包车)；
  增量聚合=小账本，内存 O(key) 不是 O(数据量)
第 6 站【day06 状态】：Keyed State 按 key 一本账 / Operator State 实例自己的账；
  HashMap 快 vs RocksDB 大而稳；一切状态都要问"什么时候可以忘"(TTL)

串联：真流处理的四大件——
  ① 常驻模型（作业不退出，数据流过）
  ② 事件时间+水位线（乱序世界的"到齐"裁定）
  ③ 窗口（无限流的有限切片）
  ④ 状态（常驻作业的记忆+快照）
  缺一件都撑不起"实时数仓"：没有②结果错，没有③没法出数，
  没有④做不了累计，没有①就不叫流处理。
```

## 3. 《水位线+窗口调参卡 v1》（项目周直接抄）


## 4. 面试连接

**Q：刚接触流计算，你的学习路径和踩过的坑？（软性问题，考真实性）**
> 我的路径是先建立"四大件"框架再填细节：先搞懂流批模型差异（为什么要有专门的流引擎），再学时间语义和水位线（流计算的正确性根基），然后是窗口和状态（出数节奏和记忆）。最大的三个坑：一是水位线取多通道最小值——空闲 Kafka 分区把全局水位线卡住，窗口集体不出结果，排查了半天才发现要配 idle-timeout；二是滑动窗口拍脑袋设步长，1 分钟窗 1 秒步长把状态放大 60 倍，Checkpoint 越跑越重；三是 GROUP BY 忘设 TTL，状态无界增长。这三个坑的共同教训：流计算的正确性参数是"业务约束"不是"技术默认值"——乱序度、步长、TTL 都要从业务里反推。现在我上线任何流作业都过一遍《调参卡 v1》。
