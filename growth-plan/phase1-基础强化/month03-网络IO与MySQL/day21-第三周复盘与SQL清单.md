## 3. 动手实操

### 3.1 《SQL 优化检查清单》正式版（今天的主产出）

```text
# SQL 优化检查清单 v1.0（发布到笔记/博客/团队 wiki）
【A 上线前 30 秒静态检查】
□1 SELECT 列最小化（覆盖机会/网络量）
□2 WHERE 列"裸奔"：无函数、无运算、类型对齐（防隐式转换）
□3 LIKE 不用前导 %
□4 命中行数量级可控：低区分度列不单独作为条件
□5 深分页用游标或延迟关联
□6 ORDER BY/GROUP BY 有索引前缀接住（防 filesort/temporary）
□7 join：被驱动表列有索引；驱动表先过滤；不用 SELECT *
□8 新索引过"三问"：最左前缀设计合理？能覆盖高频查询？单表 ≤5 个？

【B 上线时 30 秒动态检查】
□9 EXPLAIN：type ≥ ref；key 非空；key_len 符合预期列数
□10 rows 与业务预期同数量级；Extra 无 filesort/temporary/BNL
□11 压测 P95 耗时达标；耗时与 EXPLAIN 截图存档

【C 事故复盘时追加】
□12 统计信息是否过期（ANALYZE TABLE 验证）
□13 是否数据量增长越过"计划翻转"临界点
□14 长事务/锁等待（week4 后补全）

使用方式：贴在代码评审模板里 / 提交 SQL 变更时的自查项
```

### 3.2 周十题自测（合上笔记，答完对答案）

```text
 1. 页多大？页内怎么查找？          → 16KB；页目录二分+组内顺序
 2. 三层 B+ 树≈多少行的推导？      → 1170×1170×16≈2190 万（14B 路标/16 行每叶）
 3. 二级索引叶子和聚簇叶子差在哪？   → 索引列+主键 vs 整行；回表由此而来
 4. (a,b,c) 索引哪些查询能用？      → a / ab / abc / a+c(部分) / a order by b
 5. EXPLAIN 四要素？               → type 天梯 / key / rows / Extra 暗号
 6. 索引失效记三条最狠的？          → 隐式转换 / 函数包裹 / 前导模糊
 7. Hash Join 什么场景登场？       → 8.0.18+ 被驱动表无索引（BNL 替代者）
 8. 深分页两方案与约束？            → 延迟关联(通用) / 游标(最快但只连翻)
 9. 计划为什么突然翻转？            → 统计信息过期 rows 误判；ANALYZE TABLE
10. 你的优化检查清单有哪几类？       → 静态 8 项 / 动态 3 项 / 复盘 3 项
评分 ≥8=Week3 达标；<8 把错题对应 day 标记"回炉"排进下周一
```

## 4. 面试连接

**Q：你怎么保证团队产出的 SQL 质量？（管理视角，为 P8 铺垫）**
> 三道闸：① 制度——把检查清单嵌进 MR 模板和评审流程（静态 8 项自查）；② 工具——慢日志平台日报 + EXPLAIN 规则扫描（动态拦截 type=ALL/大 rows）；③ 文化——每次事故复盘沉淀回清单（v1→v2 演进）。加分句："我自己的清单就是从 5 条慢 SQL 病例复盘里长出来的，第 12~14 条全是踩坑后加的——清单的生命力在于持续更新。"

**Q：一周学完索引优化，你怎么验证自己真会了？**
> 三层验证法：① 能复现——每个失效场景我都有 EXPLAIN 证据（不是背口诀）；② 能教学——清单和博客是"讲给别人"的产物（费曼技巧）；③ 能实战——5 个病例走全流程并留前后耗时。这个回答本身就是元认知展示，面试官听到的是学习方法论。
