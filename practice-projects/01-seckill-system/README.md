# 项目一：高并发秒杀系统（Seckill System）

> **项目目标**：设计并实现一个能扛 5000+ 并发、零超卖的秒杀系统。这是面试含金量最高的后端项目，没有之一。
> **预计周期**：6-8 周（配合学习阶段二）
> **最终成果**：可演示系统 + 5000 并发压测报告 + 1 篇架构博客

## 业务场景

某电商平台"整点秒杀"活动：1000 件商品，预计瞬时流量 50 万请求，要求：
- **不超卖**（Oversell Prevention，防超卖）：库存扣减绝对准确
- **不少卖**：库存要卖完，不能因为系统问题浪费
- **体验**：下单响应 < 200ms（P99），失败快速返回友好提示
- **防刷**：黄牛脚本、重复下单要拦截

## 技术架构总览

```
用户 → Nginx/网关(Sentinel限流) → 秒杀服务
                                    ├─ Redis(Lua原子预扣库存 + 限购)
                                    ├─ RocketMQ(事务消息削峰)
                                    ├─ MySQL(最终库存扣减+订单落库)
                                    └─ 本地缓存Caffeine(商品详情热点)
```

**核心设计思想（流量漏斗，Traffic Funnel）**：每一层只放行"有资格"的请求，层层削减：
1. 前端：按钮置灰 + 答题/验证码（削掉机器人与手速差）
2. 网关：Sentinel 限流（放行 5000，其余直接拒绝）
3. Redis：Lua 原子扣减 + 一人一单（放行 1100，含重试）
4. MQ：事务消息异步落库（削峰填谷）
5. MySQL：最终一致性扣减（兜底防超卖）

## 项目结构（多模块）

```
seckill/
├── build.gradle                 # 根构建文件
├── settings.gradle
```

## 面试价值点（做完必须能讲清的问题）

1. 为什么用 Redis 预扣还要数据库兜底？（两级扣减的一致性与兜底逻辑）
2. Lua 脚本挂了怎么办？Redis 挂了怎么办？（降级链路设计）
3. MQ 丢了消息/重复消费怎么办？（事务消息 + 幂等）
4. 为什么不用数据库行锁直接扣？（热点行锁的吞吐上限推算）
5. 流量再涨 10 倍怎么办？（库存分桶/单元化/多级缓存延伸）
