# Step 5：压测、监控与项目复盘

> **本步目标**：用 JMeter 完成 5000 并发压测达标，接入监控指标看板，定位并修复 ≥ 3 个瓶颈，最后产出完整复盘报告与博客。这是项目从"能跑"到"能讲"的临门一脚。

## 1. 压测计划设计（JMeter）

| 要素 | 配置 | 说明 |
|------|------|------|
| 线程组 | 5000 线程，Ramp-up 60s | 阶梯加压，模拟真实涌入 |
| 采样器 | token → order → result 轮询链 | 用前置处理器串起完整链路 |
| 断言 | JSON code=0 或明确业务码 | 防止"HTTP 200 但业务失败"造假数据 |
| 监听器 | 聚合报告 + 后端监听器（InfluxDB/Grafana） | 实时观察 |
| 数据 | 10000 个测试用户（CSV 驱动） | 模拟真实用户分布 |

**达标标准（提前定义，避免事后找补）**：
- 下单链路 TPS ≥ 3000（单机按硬件打折）
- 下单 P99 RT < 200ms；轮询 P99 < 100ms
- 错误率 < 0.1%（不含被限流的业务拒绝）
- **库存精确：卖出 = min(库存, 有效请求)，0 超卖 0 重复**

## 2. 监控接入（压测时眼睛要看哪里）

| 层 | 工具 | 关键指标 |
|----|------|---------|
| 应用 | Micrometer + Prometheus + Grafana | QPS、RT 分位、线程池活跃/队列、拒绝数 |
| JVM | 同上（jvm 指标族） | GC 次数/停顿、堆使用 |
| Redis | redis_exporter | QPS、连接数、慢查询、内存 |
| MySQL | mysqld_exporter / slowlog | TPS、慢 SQL、锁等待 |
| MQ | Dashboard | 积压 Lag、消费 TPS |

一条核心看板建议：**下单 QPS、P99、错误率、Redis CPU、MySQL TPS、消费 Lag 六格同屏**——出问题 10 秒内锁定哪一层。

## 3. 瓶颈定位三板斧（按套路排查，不瞎猜）

```
第 1 板斧 现象层：Grafana 六格看板 → 哪层指标先恶化？
第 2 板斧 链路层：SkyWalking/Arthas trace → 慢在哪个方法/哪次外部调用？
第 3 板斧 深挖层：分情况
   ├─ CPU 高 → Arthas thread -n 3 / 火焰图（是业务计算还是 GC？）
   ├─ RT 高  → 慢 SQL 日志 / Redis 慢查询 / 网络抓包
   └─ 错误率高 → 日志聚合按 traceId 串链路
```

## 4. 常见瓶颈与修复（动手验证至少 3 个）

| # | 典型瓶颈 | 现象 | 修复手段 | 修复后预期 |
|---|---------|------|---------|-----------|
| 1 | Tomcat 线程不足 | RT 随并发直线上升，线程池打满 | `server.tomcat.threads.max=800` + accept-count 校准 | RT 平台期出现 |
| 2 | Redis 连接池不足 | Lettuce/连接等待超时 | Lettuce pool max-active=200（压测定） | Redis 侧 RT 稳定 |
| 3 | JSON 序列化开销 | CPU 被序列化吃掉 30%+ | Fastjson2 或替换 Jackson afterburner；VO 瘦身 | CPU 下降，QPS 提升 |
| 4 | 消费线程与 DB 锁冲突 | 消费 TPS 上不去，锁等待高 | 减消费线程 + 批量提交 + 热点行拆分（分桶库存） | 消费 TPS 提升 |
| 5 | GC 频繁 | GC 停顿吃掉 P99 | `-Xms=-Xmx` 固定堆 + G1 `MaxGCPauseMillis=100` | P99 抖动收敛 |

> 每次只改一个变量，记录**改动前/改动后**两组数据——这就是你博客与面试的"证据链"。
