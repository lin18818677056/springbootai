# 项目二：DDD 微服务商城（Microservice Mall）

> **项目目标**：把秒杀的单块应用思想升级为完整的微服务架构：领域驱动设计建模、服务治理、分布式事务、全链路可观测与稳定性保障。
> **预计周期**：8-10 周（配合学习阶段三）
> **最终成果**：可演示微服务系统 + DDD 建模文档 + 分布式事务方案 + 稳定性保障方案

## 业务范围（刻意收窄，聚焦架构学习）

商城只做四条核心链路，避免陷入无尽 CRUD：
1. **商品浏览**：列表/详情（缓存体系复用项目一经验）
2. **下单交易**：下单 → 扣库存 → 扣账户余额（分布式事务主战场）
3. **支付回调**：回调幂等 + 状态机（模拟支付）
4. **营销联动**：下单成功 → 发积分/发券（消息最终一致）

## 服务拆分（按限界上下文）

```
mall-gateway(9000)          # 网关：鉴权/路由/灰度头
mall-user(9001)             # 用户上下文：登录/账户余额
mall-product(9002)          # 商品上下文：商品/库存
mall-order(9003)            # 订单上下文：订单/状态机（核心域）
mall-marketing(9004)        # 营销上下文：积分/优惠券
nacos(8848) sentinel(8858)  # 基础设施
```

**拆分依据**（面试必问）：按 DDD 限界上下文而非技术分层；订单是核心域独立部署；营销是非核心链路，允许最终一致。

## DDD 分层（每个服务统一）

```
com.trained.project.mall.order
├── interfaces      # 接口层：REST / MQ Listener / Feign Provider
├── application     # 应用层：用例编排（OrderAppService.createOrder）
├── domain          # 领域层：聚合(Order)/值对象(Money)/领域服务/领域事件/Repository 接口
└── infrastructure  # 基础设施：Repository 实现/MyBatis/MQ 发送/Feign 调用
```

**铁律**：依赖只能从外向内（interfaces→application→domain），domain 不依赖任何框架注解（贫血检验：把 Spring 注解从 domain 删掉仍可编译）。
