# 04 · Kafka：分布式消息系统与流数据动脉

> **本篇目标**：吃透 Kafka 的分区模型、副本机制（ISR）、消息语义（至多/至少/精确一次）与高性能原理。Kafka 是实时链路的"大动脉"，实时数仓、CDC、日志收集全走它——**这是大数据面试与微服务面试的双料高频区**。

## 术语表

| 英文 | 中文 |
|------|------|
| Broker | 代理节点（Kafka 集群的一台服务器） |
| Topic / Partition | 主题 / 分区（主题的并行单元，分区=有序日志文件） |
| Offset | 偏移量（消息在分区内的唯一序号） |
| Producer / Consumer / Consumer Group | 生产者 / 消费者 / 消费者组（组内每分区只被一个消费者消费） |
| Replica / Leader / Follower | 副本 / 主副本（读写都在 Leader）/ 从副本 |
| ISR (In-Sync Replicas) | 同步副本集合（跟得上 Leader 的副本名单） |
| ACK / Acks | 确认 / 应答级别（0=不管；1=Leader 收到；all=ISR 全收到） |
| HW / LEO | 高水位 / 日志末端偏移（消费者只能读到 HW 之前的消息） |
| Rebalance | 再均衡（消费者组成员变化时的分区重新分配，会短暂停消费） |
| Log Compaction | 日志压实（同 key 只留最新值，适合状态类主题） |
| Idempotent Producer / Transaction | 幂等生产者 / 事务（精确一次语义的两块拼图） |

## 1. 核心模型：分区 = 并行与顺序的平衡点

```
Topic: order-events
├── Partition 0: [0][1][2][3]...  ← 只追加(append-only)的日志
├── Partition 1: [0][1][2]...      ← 分区内严格有序
└── Partition 2: [0][1][2][3][4]...
```

**三大铁律**：
1. **分区是有序性的最小单位**：Kafka 只保证分区内有序。要"同一订单的事件有序" → 以 `orderId` 为 key，hash 到固定分区。
2. **分区数 = 并行度上限**：消费者组内消费者数 > 分区数 → 多余的消费者空转。分区数规划：`目标吞吐 ÷ 单分区吞吐(约 10MB/s) × 2` 余量。
3. **分区只能加不能减**：减分区会让已有数据归属混乱，Kafka 干脆禁止。

## 2. 高性能四件套（面试必问"Kafka 为什么快"）

| 手段 | 说明 |
|------|------|
| 顺序写 | 消息只追加到文件尾，磁盘顺序写速度 ≈ 内存随机写 |
| Page Cache | 依赖操作系统页缓存，写入进缓存即返回，异步刷盘 |
| 零拷贝（Zero-Copy） | `sendfile()` 系统调用：数据从页缓存直达网卡，绕过用户态（少两次拷贝 + 两次上下文切换） |
| 批量 + 压缩 | 生产者攒批（linger.ms/batch.size）+ snappy/lz4 压缩，吞吐翻倍 |

## 3. 可靠性：副本与 ISR（Kafka 的灵魂）

```
Partition 每个分区有多副本，分布在不同 Broker：
  Leader(0)  ← 生产者/消费者都只跟它交互
  Follower-1(1) ┐ 不断拉取 Leader 数据
  Follower-2(2) ┘ 落后太多 → 被踢出 ISR
ISR = 跟得上 Leader 的副本集合（replica.lag.time.max.ms 默认 30s）
Acks=all：消息被 ISR 全部确认才算写入成功 → Leader 挂了也不丢
```

**HW（High Watermark，高水位）机制**：消费者只能读到"所有 ISR 都已复制"的位置 → 保证你读到的消息一定不会因 Leader 切换而"消失"（读到又没了 = 数据回退，比丢失更可怕）。

**选主**：Leader 挂了，Controller（控制器，集群中的一个 Broker）从 ISR 里选新 Leader → 这就是"unclean.leader.election=false"的意义：宁可分区短暂不可用，也不让落后的副本上位（CAP 里选 CP 的味道）。

## 4. 消息语义：Exactly-Once 怎么拼出来

| 语义 | 配置拼图 |
|------|---------|
| 至多一次（可能丢不重） | acks=0/1，消费先提交 offset 再处理 |
| 至少一次（不丢可能重） | acks=all + 重试；消费先处理后提交 offset |
| 精确一次（不丢不重） | 生产端幂等（`enable.idempotence=true`：broker 按 PID+序号去重）+ 事务（跨分区原子写）+ 消费端 read_committed + 业务幂等 |

**面试金句**："端到端精确一次 = Kafka 内部的幂等与事务 + 消费侧'处理成功才算提交'的位移管理 + 落库侧幂等（唯一键/upsert），三段各守一段，没有银弹。"

## 5. 消费者组与 Rebalance（生产事故重灾区）

- 消费者组：同组消费者分摊分区；**一个分区同一时刻只归组内一个消费者**。
- 触发再均衡：成员增减（扩容/宕机/处理超时被踢）或订阅变化 → 全组停手重新分配 → 期间**消费暂停**，大组可能停几十秒。
- 治理：
  1. 用 **Cooperative Sticky**（协作粘性）分配策略：增量搬迁而非全量重分。
  2. 调大 `max.poll.interval.ms`（两次拉取的最大间隔）防"处理慢被误踢"。
  3. 心跳与处理解耦认知：`poll()` 间隔超时 → broker 认为你死了 → 你其实还活着 → 分区被别人拿走 → 你还在提交旧分区 offset → 报错风暴。

## 6. 生产经验清单（后端工程师最用得上的部分）

| 问题 | 判断与处置 |
|------|-----------|
| 消息丢失 | 检查三处：生产者 acks 配置 / `min.insync.replicas` 是否 ≥2 / 消费端是否"先提交后处理" |
| 消息重复 | 消费端必须幂等（唯一键/upsert），生产端开幂等；不要幻想 Kafka 帮你端到端去重 |
| 消息积压 | 看 lag（滞后量）：单分区消费慢 → 提并行（分区数内加消费者）；分区不够 → 扩分区 + 重启组；下游真慢 → 批量消费 + 异步批量写库 |
| 乱序 | 换 key 策略（别用随机 key）+ 业务侧按事件时间排序兜底 |
| 大消息 | Kafka 不适合传大文件（默认 1MB 上限）→ 传引用（OSS 地址），数据走对象存储 |
| 数据保留 | `retention.ms` 按重算窗口定（如 7 天）；日志压实主题存"最新状态" |

## 7. 与微服务 MQ 的对比（你有 RocketMQ 背景，直接对齐）

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 定位 | 流数据管道、日志、实时数仓主力 | 业务消息（事务消息/延时消息/顺序消息） |
| 延迟 | 毫秒级（批量化优化） | 毫秒级 |
| 特色 | 极高吞吐、生态（Flink/Connect 原生集成） | 业务特性丰富（事务回查、死信、延时层级） |
| 选用 | 数据链路选 Kafka，业务交易链路选 RocketMQ——两者在数仓/微服务各守一摊 |
