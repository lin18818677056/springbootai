# 07 · 大数据面试题与生产实战要点

> **本篇目标**：把 01-06 的知识组织成"面试语言"和"生产判断力"。按"基础 → 原理 → 场景设计 → 排障"四层整理，每题给出**回答框架**而不是死答案——架构师面试考的是思考框架。

## 1. 基础层：概念必须秒答

**Q1：HDFS 读写流程？**
> 框架：NameNode 要位置 → 数据流绕过 NameNode → 流水线副本。补充亮点："读时就近（机架感知），写时先复制再确认，NameNode 只做元数据信令所以抗高并发。"

**Q2：Kafka 为什么快？**
> 框架：顺序写 + Page Cache + 零拷贝 + 批量压缩。补充亮点："单条其实不快，Kafka 的设计哲学是用批量换吞吐，天生不是低延迟产品。"

**Q3：Spark 和 Flink 怎么选？**
> 框架：世界观差异（微批 vs 真流）→ 延迟需求 → 生态成熟度。结论："离线选 Spark，秒级以下实时选 Flink；两者都在学是架构师标配。"

**Q4：数仓为什么要分层？**
> 框架：复用（省算力）+ 解耦（抗上游变更）+ 溯源（快速定位）三层价值，附 ODS/DWD/DWS/ADS 各自职责。

## 2. 原理层：体现深度的三道题

**Q5：Flink 怎么实现 Exactly-Once？（被问概率 90%）**
> 答题骨架：
> 1. 内部：Checkpoint 基于 Chandy-Lamport 思想，Barrier 对齐做分布式快照；
> 2. Source 端：offset 存快照，故障回退重放；
> 3. Sink 端：幂等写（upsert）或两阶段提交；
> 4. 代价：Barrier 对齐憋流、Checkpoint 间隔决定 Sink 可见延迟；
> 5. 升级话术："非对齐 Checkpoint 缓解反压下的超时，但要权衡恢复时需要拉取更多在途数据。"

**Q6：Watermark 原理与迟到数据？**
> 答题骨架：定义（最大事件时间 − 乱序度）→ 作用（给窗口关闭一个确定性判据）→ 迟到三级处理（allowedLateness 允许迟到 / Side Output 侧输出补偿 / 离线层修正）→ 权衡（正确性 vs 延迟）。

**Q7：Kafka ISR 机制与 HW/LEO？**
> 答题骨架：副本分 Leader/Follower → ISR 是跟上进度的副本集合 → acks=all + min.insync.replicas=2 才算可靠 → HW 是 ISR 共同进度，消费者只能读 HW 前（防 Leader 切换后消息"消失"）→ unclean 选举关闭，宁可短暂不可用不丢数据。

## 3. 场景设计层：P7 架构师的主考场

**Q8：设计一个"双 11 实时 GMV 大屏"，你怎么做？**
> 答题路径（背熟，直接对应项目三）：
> ```
> 采集：binlog(CDC) + 埋点 → Kafka（key 设计：订单号保序）
> 计算：Flink 分钟窗口聚合（事件时间 + Watermark 10s）
>       UV 用 HLL 近似（精度权衡：大屏 1% 误差无感）
>       TopN 先聚后排（防无界状态）
> 存储：Redis 热指标（大屏直连）+ ClickHouse 明细（下钻分析）
> 正确性：Checkpoint 10s + upsert 幂等 → kill 演练验证不丢不重
> 兜底：离线层重算 + 每日实离核对 + GMV 跌零告警
> 容量：单分区 ~10MB/s → 反推 Kafka 分区数与 Flink 并行度
> ```
> 加分项：主动说"我会先问 QPS 和精度要求再定方案，1 万 QPS 和 1000 万 QPS 是两个设计"。

**Q9：实时数仓和离线数仓怎么保证数据一致？**
> 答题路径：承认必然有差（实时丢迟到/离线全量重算）→ 核对机制（每日 ADS 层逐指标对比，差异率告警）→ 补偿机制（离线修正后回写/实时回溯重放）→ 根治思路（同一套口径的 SQL 双跑，逻辑代码化避免人工对不齐）。

**Q10：数据积压了怎么办？（考察排障体系化）**
> 答题路径：先定位（Kafka lag / Flink busy% / Sink RT 三处看）→ 再分类（源突增 / 算子瓶颈 / Sink 慢）→ 处置（提并行、扩分区、批量写、热点加盐）→ 预防（容量规划公式 + 积压告警前置到 lag>10 万）。

## 4. 排障层：生产 SRE（站点可靠性工程）味道的题

| 症状 | 排查链 |
|------|--------|
| Flink 作业频繁重启 | UI 看失败原因：Checkpoint 超时？（Barrier 卡在哪个算子）/ OOM？（状态无界？）/ 数据异常脏数据？（脏数据侧输出 + 告警而非重试风暴） |
| Hive/Spark 任务突然变慢 | 数据量突增？（分区行数对比）/ 倾斜？（task 长尾）/ 资源被抢？（队列水位）/ 小文件恶化？（文件数趋势） |
| ClickHouse 拒绝写入 | too many parts？（写入频次）→ 攒批；Merge（合并）积压？（后台线程数/磁盘 IO） |
| Kafka 消费组反复 Rebalance | max.poll.interval 超时？（处理太慢）/ 频繁发布重启？（用静态成员 membership） |

**排障通用方法论（面试官最想听到的框架）**：
> "先看监控定位层级（采集/传输/计算/存储哪一层）→ 用指标缩小范围（lag、busy%、RT、长尾）→ 复现最小案例 → 修复后补告警与文档 → 复盘进 Runbook（运维手册）。"
