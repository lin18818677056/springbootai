# 01 · 大数据全景与数仓理论

> **本篇目标**：建立全景认知——大数据生态里每个组件"住在几楼、干什么活"；理解数仓分层（ODS/DWD/DWS/ADS）与两种主流架构（Lambda/Kappa）。学完本篇，看到任何大数据组件你都能说出"它在架构里的位置"。

## 术语表

| 英文 | 中文 |
|------|------|
| OLTP / OLAP | 联机事务处理（业务交易）/ 联机分析处理（数据分析） |
| Batch Processing / Stream Processing | 批处理（攒一批算）/ 流处理（来一条算一条） |
| Data Warehouse | 数据仓库（面向分析的主题化数据集合） |
| Data Lake / Lakehouse | 数据湖 / 湖仓一体 |
| ODS (Operational Data Store) | 操作数据层（原始数据，业务库 1:1 搬进来） |
| DWD (Data Warehouse Detail) | 明细数据层（清洗、标准化后的明细事实） |
| DWS (Data Warehouse Summary) | 汇总数据层（按主题轻度聚合，如用户天粒度汇总） |
| ADS (Application Data Store) | 应用数据层（直接供报表/大屏/接口用） |
| Dimension / Fact | 维度（看数据的角度：时间/地区/商品）/ 事实（发生的事：订单/点击） |
| Star Schema | 星型模型（事实表在中心，维度表环绕——数仓建模主流） |
| Lambda / Kappa Architecture | Lambda 架构（批流两条链路）/ Kappa 架构（一切皆流） |

## 1. 一张图看懂大数据技术栈（先背楼层图）

```
┌─────────────── 应用层：报表/大屏/AB实验/推荐特征 ───────────────┐
├─────────────── 分析查询层：ClickHouse / Doris / Presto(Trino) ──┤  ← 交互式查询
├─────────────── 计算引擎层 ────────────────────────────────────┤
│   批处理: Hive(SQL on MR) → Spark   流处理: Flink              │
├─────────────── 资源调度层：YARN / K8s ─────────────────────────┤  ← 谁来分配 CPU/内存
├─────────────── 存储层：HDFS / 对象存储(S3/OSS) ────────────────┤  ← 海量文件底座
├─────────────── 传输层：Kafka（流）/ Sqoop/DataX（批同步）────────┤  ← 数据进出通道
└─────────────── 数据源：业务 MySQL / 日志 / 埋点 / 三方数据 ───────┘
```

**记忆口诀**："传输层进出、存储层存底、调度层分粮、计算层干活、查询层面对面"。

## 2. 后端思维 → 数据思维（四个转变）

| 后端习惯 | 数据世界 |
|---------|---------|
| 写操作频繁，读锁/写锁纠结 | 几乎**只读不改**：数据写一次，被算一万次 |
| 追求单请求毫秒级 RT | 追求吞吐（GB/秒），单条延迟无所谓 |
| 事务保证一致 | Checkpoint + 幂等写 + 对账保一致 |
| schema（表结构）从严 | 允许先存后定义（数据湖）或分层治理 |

## 3. 数仓分层：为什么数据要"层层加工"？

```
业务库 MySQL ──同步──→ ODS 原始层 ──清洗/规范──→ DWD 明细层
                                                    │
报表/大屏/接口 ←── ADS 应用层 ←──轻度聚合── DWS 汇总层
```

| 层 | 回答的问题 | 举例 |
|----|-----------|------|
| ODS | 数据长什么样（原样） | `ods_order`（业务订单表原样镜像） |
| DWD | 每一笔到底发生了什么 | 订单明细（去掉测试单、统一金额单位、补齐维度外键） |
| DWS | 每个主体每天怎么样 | 用户粒度：近 1 天下单数/GMV；商品粒度：日销量 |
| ADS | 业务要看的最终结果 | "GMV 周报"、"热销 Top10"、"复购率月报" |

**分层的三重价值**：
1. **复用**：DWS 算一次，十个报表共用，不重复扫明细（省算力 = 省钱）。
2. **解耦**：业务库改表只影响 ODS→DWD 一小段，下游稳如老狗。
3. **溯源**：报表数字对不上时，逐层回查，10 分钟定位哪层算错。

## 4. 维度建模入门（Kimball 派，国内数仓主流）

- **事实表（Fact Table）**：记录"发生了什么"，行数巨大。如订单事实表：`order_id, user_id(外键), goods_id(外键), date_key(外键), amount, count`。
- **维度表（Dimension Table）**：回答"从什么角度看得更细"，行数小。如商品维度表：`goods_id, 品类, 品牌, 供应商`。
- **星型模型**：事实表居中、维度表环绕如星星 → join 路径短，BI 工具友好。
- **建模三步骤**：选业务过程（下单/支付）→ 声明粒度（一行 = 一个订单商品项，粒度必须先定！）→ 确定维度与事实。

新手最常见的翻车：**粒度没先定**，同一订单 3 行明细被 SUM 成 3 倍 GMV——"先声明粒度"是数仓铁律。

## 5. Lambda vs Kappa：批流架构之争

| | Lambda 架构 | Kappa 架构 |
|--|------------|-----------|
| 思路 | 同一份逻辑写两遍：流层（快而近似）+ 批层（慢而精确），查询层合并 | 一切皆流，要重算就回放 Kafka 历史 |
| 优点 | 精确性兜底（批层重算可纠正） | 一套代码，维护成本低 |
| 缺点 | 两套代码两套 bug，逻辑对不齐 | 依赖 Kafka 保留期与流计算 Exactly-Once 足够强 |
| 适用 | 金融/计费等强精确场景 | 绝大多数互联网场景（现状主流） |

面试表达："Flink 支持 Exactly-Once + 事件时间语义后，Kappa 的两个前提基本成立，所以新业务我优先 Kappa，只在强精确场景保留批层兜底，并用'实离核对'任务验证两条链路一致。"

## 6. 一条数据的完整旅程（把组件串起来）

```
用户下单 → MySQL binlog → (Flink CDC) → Kafka(dwd_orders)
    → Flink 流计算（分钟窗口聚合）→ Redis(实时大屏) + ClickHouse(明细分析)
    → 每日离线：Hive/Spark 批处理重算昨日全量 → 报表与实时数字核对（实离一致）
```
