# 06 · 模型部署与推理优化：私有化与降本

> **本篇目标**：掌握"自己跑模型"的全套知识：Ollama（本地实验）→ vLLM（生产推理）、显存估算、量化（Quantization）压缩、推理加速技术全景。企业"数据不出域"场景下，这是架构师必备的私有化部署能力。

## 术语表

| 英文 | 中文 |
|------|------|
| Local Inference / Cloud API | 本地推理（自部署）/ 云端 API（调厂商） |
| Ollama | 本地模型运行工具（开发体验好，适合实验/个人） |
| vLLM | 高吞吐推理引擎（生产主流，PagedAttention 显存管理） |
| PagedAttention | 分页注意力（类操作系统分页管理 KV Cache，显存利用率大幅提升） |
| KV Cache | 键值缓存（生成时缓存的中间注意力结果，显存大头） |
| Quantization | 量化（FP16 → INT8/INT4，模型瘦身，精度微损） |
| GGUF / AWQ / GPTQ | 常见量化格式/算法（GGUF 通用、AWQ/GPTQ 主流 4bit） |
| Continuous Batching | 连续批处理（请求动态进出批次，吞吐数倍提升） |
| TTFT / TPOT | 首 Token 延迟 / 每 Token 生成时间（两大延迟指标） |
| Prefill / Decode | 预填充（处理输入）/ 解码（逐字生成）两阶段 |
| Tensor Parallelism | 张量并行（单层切到多卡，大模型单机装不下时用） |
| GPU 显存 | 显存（部署的第一约束资源） |

## 1. 部署选型：什么时候自部署，什么时候调 API

| 维度 | 云 API | 自部署（vLLM） |
|------|--------|---------------|
| 数据合规 | 数据出境风险 | 数据不出域（政企/金融刚需） |
| 成本模型 | 按 Token 付费（低频友好） | GPU 固定成本（高频/大规模摊薄更划算） |
| 运维 | 零运维 | 显卡采购、驱动、扩缩容、监控全套 |
| 定制 | 受限（厂商决定型号） | 任意开源模型 + 微调自由 |

**经验法则**：日调用量 < 百万次 → 先 API 起步验证业务；数据强合规或调用量巨大 → 自部署。**成本临界点自己算**：GPU 月成本 ÷ 月 Token 消耗 vs API 单价。

## 2. 显存估算：部署前必做的算术

```
模型权重显存 ≈ 参数量 × 精度字节数
  7B 模型 FP16：7×10⁹ × 2B ≈ 14GB
  7B 模型 INT4 量化：≈ 3.5~4GB
KV Cache 显存 ≈ 2 × 层数 × 上下文长度 × KV头维度 × 精度 × 并发数（随并发线性涨！）
经验：预留 = 权重 × 1.2 + KV Cache 峰值 + 激活值余量
```

**速查直觉**：单张 24GB（如 4090）→ 7B FP16 也可以 / 14B 量化可以 / 72B 不行（需量化 + 多卡）。

## 3. 三级跳：Ollama → vLLM → 集群

```bash
# Level 1：Ollama（开发/演示，一行起服务，自动暴露 OpenAI 兼容接口）
ollama pull qwen2.5:7b-instruct
ollama serve                      # http://localhost:11434/v1 ← Spring AI 直接对接

# Level 2：vLLM（生产单实例）
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --quantization awq \                    # AWQ 4bit 量化
  --max-model-len 8192 \                  # 上下文长度（影响 KV Cache 上限）
  --gpu-memory-utilization 0.9 \          # 显存水位
  --enable-prefix-caching                 # 前缀缓存（系统提示相同可复用，省一半预填充）

# Level 3：生产集群要点
# 多实例 + 负载均衡（K8s HPA 按队列长度扩缩容）
# 监控：TTFT/TPOT/队列长度/显存水位/每秒Token吞吐
# 大模型（>70B）：Tensor Parallelism 张量并行 或 量化后单机部署
```

## 4. 推理优化技术全景（知道原理与收益即可）

| 技术 | 原理 | 收益/代价 |
|------|------|----------|
| 量化 Quantization | 降低权重数值精度（FP16→INT4） | 显存降 4 倍、速度升；精度微损（评测集验证） |
| Continuous Batching | 请求动态进出批次 | 吞吐 ×3~10；单请求延迟略增 |
| Prefix Caching | 相同前缀（系统提示）复用 KV Cache | 多轮对话/批量任务省 50%+ 预填充 |
| Speculative Decoding | 小模型草稿 + 大模型验证并行生成 | 延迟降 2~3 倍；实现复杂 |
| KV Cache 优化（PagedAttention） | 分页管理缓存碎片 | 同显存承载更多并发 |
| 蒸馏 Distillation | 大模型教小模型 | 小模型成本低速度快；效果折损 |

**架构师话术**："推理优化的三板斧是量化（省显存）、连续批处理（提吞吐）、前缀缓存（省重复计算），选型顺序：先开 vLLM 默认优化，再量化，最后才考虑复杂技术。"

## 5. 应用侧对接要点（Java 视角收尾）

```yaml
# Spring AI 对接本地 vLLM/Ollama（都是 OpenAI 兼容协议）
spring:
  ai:
    openai:
      base-url: http://vllm-gateway:8000    # 指向自建推理服务
      api-key: not-needed
      chat.options.model: Qwen2.5-7B-Instruct
```

- **网关层**：自建推理服务前面加统一 AI 网关（鉴权/限流/模型路由/降级到云 API——本地满载时溢出云端，注意合规边界）。
- **容量规划**：以 TTFT（首 Token 延迟）SLA 反推并发：`并发 = GPU 数 × 单卡并发 × 目标利用率`，压测校准。
- **灰度策略**：量化模型先跑影子流量对比质量指标（评测集），达标再切流。
